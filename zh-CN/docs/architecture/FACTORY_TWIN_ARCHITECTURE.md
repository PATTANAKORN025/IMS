# 工厂数字孪生 — 运行时架构 (Factory Twin — Runtime Architecture)

运行中服务的形态：各组件之间的通信关系、各个模块所拥有的决策权，以及数字孪生其余文档所依赖的边界在何处被真正强制执行。

配套文档：**[重建方法论 (Reconstruction Methodology)](FACTORY_TWIN_RECONSTRUCTION.md)**（几何模型如何生成）、**[安全模型 (Security Model)](FACTORY_TWIN_SECURITY_MODEL.md)**（防御对象与防御机制）以及 **[操作员指南 (Operator Guide)](FACTORY_TWIN_OPERATOR_GUIDE.md)**（如何解读呈现结果）。

> [!NOTE]
> 本文档不包含任何几何图形、尺寸或空间坐标。它描述的是系统管线（plumbing），而非载荷数据（payload）。

---

## 1. 请求路径 (Request path)

```text
browser
  └─ proxy  (nginx)
       ├─ location = /auth-check      internal; 针对 Grafana /api/user 验证会话
       └─ location /factory-twin-3d/  auth_request /auth-check
            └─ factory-twin-3d  (express, :4100, 无 host 端口)
                 ├─ static  public/ + 内置 (vendored) three.js
                 ├─ /api/*  格式化 JSON (shaped JSON)
                 ├─ pg pool  ->  pgbouncer  ->  TimescaleDB   (只读角色 read-only role)
                 └─ private/  仅服务端读取，绝不挂载为静态资源
```

该路径具有三个承重级（load-bearing）的核心特性：

- **数字孪生不暴露任何宿主机端口。** 它仅存在于 docker-compose 内部网络中。唯一的入口路径就是反向代理的 `/factory-twin-3d/` location。
- **该 location 受 `auth_request` 门禁保护**，直接校验 Grafana 自身的会话 Cookie。无需维护第二个身份验证系统：登录仪表板的操作员即可直接访问数字孪生，未登录者将在抵达孪生服务之前直接收到 401。
- **Three.js 是内置集成的，而非从 CDN 获取。** 位于认证网关之后的容器在渲染时绝不能依赖第三方源。

## 2. 模块映射 (Module map)

| 文件 | 职责与归属 |
|---|---|
| `server.js` | 路由、pg 连接池、设备刷新、私有文件加载器以及服务白名单 (serving allowlists)。 |
| `lib/contracts.js` | 机器状态词汇表及其主题。单一权威定义，供 API 和渲染器共享。 |
| `lib/diagnostics.js` | 诊断信息序列化，结构性白名单设计 (allowlist-by-construction)。 |
| `lib/wire.js` | 私有几何图形的线上投影 (wire projection)：逐字段重建对外服务的每个槽位、立柱、区域和包络。 |
| `lib/mapping.js` | 物理位置到设备的映射契约，包括其拒绝规则。 |
| `lib/mes-import.js` | 外部制造数据 (MES) 的导入边界。 |
| `lib/evidence.js` | 证据来源注册表与提升契约。 |
| `public/app.js` | 场景构建、图层/视图系统、拾取 (picking)、检查器 (inspector)。 |
| `public/index.html` | HUD 抬头显示、控制面板、证据图例、样式。 |

`lib/evidence.js` 是一个 **契约 (contract)，而非清单 (inventory)**。它不持有任何设备记录，也不重复数据库中的任何内容；它的职责是判定未来来源允许声明什么。其规则记录于 [证据要求 (Evidence Requirements)](FACTORY_TWIN_EVIDENCE_REQUIREMENTS.md)。

## 3. HTTP 接口表面 (HTTP surface)

| 路由 (Route) | 返回内容 | 说明 |
|---|---|---|
| `GET /api/state` | 每个受监控设备的实时运行状态 | 唯一访问数据库的路由。使用只读角色。 |
| `GET /api/build` | 当前构建的指纹及单文件哈希 | 启动时根据运行镜像中源文件的字节计算。无法被环境变量覆盖，也无法由未运行的构建脚本伪造。 |
| `GET /api/floors` | 已部署楼层目录：id、序号、计算标签、区域是否存在 | 仅提供 id 和序号。绝不从私有文档中读取标签、顺序或描述。 |
| `GET /api/floor-geometry` | 外包络 (envelope)、轮廓外框 (footprint)、网格、立柱、墙体、**未配对墙面**、洞口开口、**CAD 设备**、已验证功能区 | 支持 `?floor=`；省略该参数表示默认楼层并返回逐字节相同的几何数据。当不存在私有几何数据时返回空但有效的结构（这是全新 clone 的默认状态，并非错误）。`slots` **绝不** 对外提供。 |
| `GET /api/floor-raw-cad` | 图纸自身的原始线条，按固定图层 **角色 (roles)** 分组 | 参考信息，并非关于楼层的断言证据。以 **CAD 自身坐标系** 提供 — 毫米、+y 向上、无镜像 — 使得客户端自行应用规范变换，若存在坐标系偏差会直接在叠加层显现而非被固化在数据中。每个角色仅携带 `id`、`segment_count` 和 `segments`；图纸的真实图层名称绝不离开服务端。明确报告其排除的内容。仅在开启叠加层时获取。 |
| `GET /api/floor-schematic` | 光栅示意图的转录数据 | 保留并受控，但 **没有任何页面会绘制它**：规范数字孪生仅以 CAD 楼层为准。 |
| `GET /api/diagnostics` | 仅限计数、布尔值和固定枚举 | 绝不包含任何坐标、标识符、路径、工艺或厂商名称。 |
| `GET /healthz` | 存活探针，包含数据库往返检测 | |

### 楼层按 id 寻址，而非硬编码编译

`lib/floors.js` 拥有楼层 id 空间，并且是唯一被允许构建进入 `private/` 路径的模块。1 层是第一个经过验证的数据集；添加第二个已测绘楼层只需放入文件即可，无需修改任何代码。

楼层 id 来自查询字符串，属于外部不可信输入并用于构建文件系统路径。系统按顺序应用两道门禁：

1. 必须完全匹配 `^floor[1-5]$` 正则 — 封闭模式，拒绝任何点、斜杠或分隔符。
2. 必须已存在于服务端通过扫描自身目录所构建的目录清单中。

第二道门禁实现了结构性白名单 (allowlist-by-construction)：**路径是根据目录清单中的 id 副本构建的，绝不使用调用方传入的字符串**，因此即便请求格式完全合规，服务端未找到的楼层也绝对无法被寻址。未部署的命名楼层将返回固定响应体的 `404` — 绝不返回空几何结构，因为空几何结构等同于断言该楼层存在且为空。

`?floor=` 是可选参数。省略它意味着默认楼层，回归测试断言这两种请求返回逐字节完全相同的响应，因此所有先于多楼层功能存在的旧 URL 依然保持原有语义。

### 数据对外服务采用白名单投影，绝不直接展开 (spread)

私有文档属于敏感资产。若通过对象展开操作对外发布，意味着 **私有文件中新增的任何字段在写入的瞬间就会被直接暴露**，包括源文件路径、真实名称或内部备注。

因此，白名单在 **两个层级** 同时生效：路由显式声明顶层字段，而 `lib/wire.js` 则逐字段重建每个槽位、立柱、区域边界框、外包络、功能区和冲突记录。只有有限数值、模式验证的 token 以及固定枚举才能输出，自由文本没有任何外泄通道 — 任何注释、路径或工艺名称都会直接被 token 检查拦截，而非被净化后回显。新字段必须显式添加到投影定义中才能输出到传输线路上。

任何无法被投影的内容将 **直接扣留而非强行转换**：没有可用位置的资产不会以备用坐标输出，因为凭空捏造位置比不展示更具破坏性。同样的规则适用于 *外延范围 (extent)*：`footprint_status` 为 `UNRESOLVED` 的设备记录以 `footprint: null` 传输，即便私有文档为其添加了尺寸，投影器也拒绝为其生成占用面积。旧版投影器曾使用 1 米的方块替代缺失尺寸，这导致捏造的尺寸以与测量尺寸相同的形态输出 — 在 CAD 楼层上，肉眼完全无法分辨这种捏造。

`projectSlot` 及其服务的 `slots[]` 图层已被 **彻底删除而非废弃闲置**，因此在路由中重新加入 `slots: wire.projectAll(...)` 绝不可能静默生效。

路由在代码中严格执行而非仅在文档中约定的两条规则：

- **未经验证的几何体不可渲染。** API 会重新计算可渲染过滤器，而非信任私有文件自身的标志；渲染器会再次应用相同的防御检查。
- **绝不推断任何映射关系。** 槽位始终为 `UNMAPPED`，除非权威记录另有明确声明。位置相近、编号连续或数量吻合绝不能作为建立映射的依据。

## 4. 渲染模型 (Rendering model)

### 图层与子图层 (Layers and sub-layers)

对象按其断言的主张类型进行分组。四个顶层图层（`structural`、`functional`、`operational`、`telemetry`）各自包含嵌套的子图层组，操作员控件既可以切换整个主张大类，也可以控制其中的单个成员：

| 顶层图层 | 子图层 |
|---|---|
| `structural` | `shell`（地板平板、方位网格、实测包络轮廓）、`columns` |
| `operational` | `machines`、`slots`、`presentation`（默认关闭） |
| `functional` | 无；单一大类 |
| `telemetry` | 无；单一大类 |

可见性解析支持任一层级，因此六个操作员开关直接映射到同一棵树上，无需平行的查找表。

### 视图模式 (Modes)

单应用支持五种模式。其中三种改变屏幕上呈现哪类断言主张；另两种改变围绕同一主张的外围工具控件密度。

| 模式 | 3D | 绘制图纸 (Drawing) | 前置需求 |
|---|---|---|---|
| `executive` | ✓ | | 实测楼层；最宽视野，控件全部隐藏 |
| `physical` | ✓ | | 实测楼层 |
| `schematic` | | ✓ | 转录图纸 |
| `split` | ✓ | ✓ | 两者皆备 |
| `inspection` | ✓ | | 实测楼层；所有控件展开 |

模式本质上是 body 样式类加上相机预设。**没有任何模式会改变物体的空间坐标**，回归测试通过在每次模式切换时对比逐字节的坐标快照来证明这一点。当缺少对应图纸时，依赖图纸的模式会被 **明确附带原因禁用**，而非隐藏 — “系统支持并排对比视图，但当前部署缺少所需数据”是一条极具价值的明确信息。

`split` 模式使用硬分隔线将两个视口紧贴排列，而非相互叠加：因为相互叠加等于宣称两个缺乏共享参考坐标系的系统之间存在空间配准。其横幅明确显示 `PHYSICAL + SCHEMATIC — UNREGISTERED`，而非贴上任何单一主张的标签。

场景布局中的每一项测量 — 渲染器尺寸、相机适配、图纸适配 — 均针对 **视口窗格 (pane)** 测量，绝不针对浏览器窗口。在并排视图中，窗格仅占窗口宽度的一半且起始于 HUD 右侧，因此基于窗口的测量会把面板预留在不属于该窗格的区域。

### 相机与视图语义 (Camera and view semantics)

三种预设（operator、building、overview）**仅控制取景构图**。切换视图仅改变相机位置、观察目标点及深度范围，绝不触碰任何物体的变换矩阵。回归测试套件全面证明了这一点：在首次切换前对所有渲染坐标进行固定精度快照，并在遍历三种视图并重置后进行逐字节比对。

修改取景适配代码前必须注意的两项细节：

- **适配取景是通过实测测得的，而非代数公式计算。** 斜向俯视相机看到的是物体的轮廓剪影，而非轴对齐包络盒；过去使用的闭式三角函数公式低估了观察距离并切掉了楼层角落 — 在最利于看清楼层的浅角度下这种裁剪最为严重。现在的适配将外包络的八个角点投影到测试相机中，并进行缩放调整直到它们落在叠加层预留的安全区域内。该算法对任何视角、宽高比和面板宽度均保持绝对精确。
- **Overview 取景涵盖的是包络的并集，而非配准对应。** 实测建筑边界与合成机器边界是两套独立的坐标系；并集取景将两者同时置于视野内，但不代表两者存在空间对应关系。参见 [操作员指南 (Operator Guide)](FACTORY_TWIN_OPERATOR_GUIDE.md) 中的警示。

构图计算在加载、几何数据抵达以及窗口调整尺寸时统一经由单一路径重新计算，因此视口变化绝不会导致两个视图基于不同输入进行适配。输入尚未抵达的预设将保持禁用，绝不静默回退到其他构图。

### 资源复用与按需渲染 (Resource reuse and render on demand)

几何体与材质在网格对象之间进行缓存与共享，而非逐对象重复构建；窗口缩放操作在每帧内合并为单次调用。

**画面帧完全按需绘制 (on demand)。** 该界面的瓶颈在于像素填充率 (fill-rate bound)，而非几何多边形数量：从 1366×768 到 3840×2160，帧时间中位数几乎完全跟随像素数量线性变化，而三角形面数恒定不变。在交互间隙场景处于完全静止状态 — 它没有任何动画，每 5 秒轮询一次遥测仅会改变极少数颜色。以每秒 60 帧盲目绘制是在将全部帧预算浪费在生成完全相同的画面上，在 4K 分辨率下每帧耗费超过 200 ms 却毫无画面变化。

现在仅在发生真实变化时才会绘制画面：相机移动、图层开关、模式/视图切换、窗口缩放、鼠标悬停、遥测更新。每次触发会绘制一小段连续帧序列而非仅绘制单帧，因为“发生变化”并不总能在同一 tick 内完成感知 — 例如纹理刚刚解码完成、精灵图刚完成布局排版、材质刚刚上传完毕。

实测性能：在 1080p 与 4K 下 **静止 2 秒内绘制 0 帧**；**在 0.8 秒的视角旋转拖拽期间绘制 102 帧**。交互流畅度丝毫不受影响，而静止待机时零开销。基于相同的填充率瓶颈考虑，设备像素比 (DPR) 上限被限制为 2。

**presentation** 图层采用实例化渲染 — 每个 (form, part) 对应一个 `InstancedMesh`，整层楼仅有 21 个对象和 21 次 Draw Call。当前测得的组件构成记录于 **[视觉质检 (Visual QA)](FACTORY_TWIN_VISUAL_QA.md)**。

## 5. 部署架构 (Deployment shape)

- 镜像通过 **白名单 `COPY`** 构建（`server.js`、`lib`、`public`）。`private/` 绝不会被复制进任何镜像层中。
- `private/` 在运行时以 **只读 (read-only)** 模式 bind-mount 挂载。生产主机只需将真实文件放入该路径即可生效，无需修改代码，也无需重新构建镜像。
- **应用程序代码已固化在镜像内。** 修改 `public/` 或 `lib/` 下的内容必须重新构建并重新创建该服务容器才能生效；只有 `private/` 能够实时挂载更新。这一点常常出乎维护人员的意料。
- nginx 在启动时解析上游主机名，因此在重新创建该容器后反向代理需要执行一次 reload。

具体命令与故障诊断详见 **[运维手册 (Operations Runbook)](../operations-runbook.md)**。

## 6. 规范正式路径以及过旧构建曾如何隐蔽其中

### 用户可见的工厂数字孪生有且仅有一个

```text
browser
  -> http://localhost:3000/factory-twin-3d/
  -> ims-proxy (nginx:1.31-alpine, 唯一发布主机端口的容器)
       location /factory-twin-3d/  { auth_request /auth-check;
                                     proxy_pass http://factory-twin-3d:4100/; }
       location = /auth-check      { internal; proxy_pass http://grafana:3000/api/user; }
  -> ims-factory-twin-3d (无主机端口，仅限 ims-internal 内部网络)
  -> /app/server.js  +  /app/private (只读 bind mount)
```

`127.0.0.1:4199` **仅用于验证与临时测试**。它是由 `scripts/twin-direct-container.ps1` 启动的一次性容器，绑定到本地回环地址，**没有任何认证网关**。它绝不是正式产品，也绝不允许出现验证端口已有新结果而正式路径依然处于陈旧构建状态的情况。

### 本章节旨在防止的故障

重新构建镜像并不等于重新部署服务。`docker compose build` 会更新镜像标签，但 **正在运行的容器将始终保持创建时所用的旧镜像**，直到它被显式重新创建 (recreate)。正是因为这一点，该部署曾连续落后代码仓库 6 个提交，而仓库代码、测试用例和镜像标签却早已更新 — 导致人们误以为重新构建的验证端口就是重新构建后的生产环境。

页面上的任何内容都无法直接暴露出这一问题：前端是静态文件，且不包含版本号。

### 现在的透明化保障机制

`GET /api/build` 返回在 **运行时根据当前运行镜像中的磁盘字节实时计算的** 指纹（fingerprint）— 包含 `server.js`、`lib/` 和 `public/`。它无法通过环境变量伪造，也无法声称运行着与其不同的代码版本。页面顶部将其显示为一个 `build …` 标签。

因此，验证部署只需一次简单的比对：

```sh
# 生产环境实际运行的指纹
docker exec ims-proxy wget -qO- http://factory-twin-3d:4100/api/build

# 验证容器运行的指纹
curl -s http://127.0.0.1:4199/api/build
```

**指纹相同意味着代码完全一致。** 指纹不同则意味着其中一方已经陈旧，无论镜像标签上写着什么。

### 重新部署命令

```sh
docker compose build factory-twin-3d
docker compose up -d --force-recreate --no-deps factory-twin-3d
```

`--force-recreate` 是必须携带的关键参数。缺少该参数，compose 可能会让健康的容器继续运行在旧镜像上。

### 访问控制及其对验证工作的含义

`/factory-twin-3d/` 受 `auth_request` 保护并对接 Grafana 自身会话，机制与 `/alarm-api/` 完全相同。未认证请求将收到 **来自网关的 401**，而非来自服务自身 — 若出现 404 或 502 则意味着路由配置故障。

因此场景与证据行为是通过回环验证容器进行验证的，该容器运行 **完全相同的镜像** 并通过指纹证明一致性。而访问控制本身则在回归测试套件中通过针对规范路径的未认证边界测试单独进行验证。
