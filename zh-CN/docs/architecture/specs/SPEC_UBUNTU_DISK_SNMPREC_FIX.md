# 规范: Ubuntu SNMP 磁盘真实性修复 (P0.2)

**状态：已于 2026-08-15 修复并部署。**

## 根本原因（已在 `READ_ONLY_AUDIT_2026-08-15.md` §3c 查明）

`monitoring/snmpsim/ubuntu.snmprec` 的磁盘条目 (`hrStorageSize`, OID `.5.2`) 是 `52428800`，而它的 `hrStorageUsed` 随机游走范围 (`.6.2`) 却是 `min=65536000,max=125000000` -- 从 `windows.snmprec` 复制粘贴了相同的 OID，却没有重新计算一个能保持在它之上的总量。已用量永远不可能小于总量的约 125%，所以 `parser.js` 的 `Math.min(diskUsedGb, diskTotalGb)` 强制将其夹紧，把每一个样本的磁盘使用率都死死卡在了 100%。

## 增长之谜纠正（按要求，在最终确定此修复之前）

在本次会话早前的一条笔记中曾声称，随着时间的推移 `disk_total_gb` “从 9,375 增长到 12,500 GB”，暗示有第二个漏洞。通过原始（非分桶）查询重新调查：`disk_total_gb` 在其整个历史中严格只有 2 个截然不同的值 -- `0` (9 行，来自解析器离线/空数据时的归零) 和 `12500` (3,484 行)。不存在中间值。这种“增长”是由于在 10 分钟的时间桶内，把真实的 `12500` 的行同偶尔出现的 `0` 的行放在一起求平均造成的假象。已在 `READ_ONLY_AUDIT_2026-08-15.md` 原地做了纠正。没有第二种机制 -- 仅仅这单一的已用量范围配置错误，就足以解释所有观察到的行为。

## 修复

只更改了 `hrStorageSize` (`.5.2`): `52428800` → `180000000`。`au` (分配单元, `.4.2` = `256000`) 以及已用量范围 (`.6.2`) 均保持不动 -- 是最小幅度的修改，而且已用量范围本身的形态 (它的变化规律) 被原封不动地保留了，没有被覆盖。

尺寸规划逻辑，从第一原则出发计算，而不是复制 `windows.snmprec` 的数字：选择 `180000000` 使得 `total_bytes = 180000000 × 256000 = 46,080,000,000,000` 字节 ≈ 42,915 GB，轻松超过已用范围的最大值 (`125000000 × 256000 / 1073741824` ≈ 29,802 GB)。由此产生的利用率区间：**36.4% (最小值) – 69.4% (最大值)** -- 一个健康、真实的范围，其形状与 `windows.snmprec` 自己的 32.8%-62.5% 区间大致相似（仅用作合理性参考，未复制），但其实际数值又区别于它，因为根据文件自带的头部注释，Ubuntu 有“更低资源占用”的特征，理应使用属于它自己的值，而不是 Windows 的值。

在调查期间，还顺便检查了同一文件中 RAM 的条目：`size=8388608, au=1024` 给出了 8192 MB 的总量，已用范围 `4194304-7864320` 给出了 4096-7680 MB (50%-93.75%) -- 已经是健康状态，不属于此漏洞的一部分，不予改动。

## 发布部署

`docker compose restart snmpsim` -- **重启范围最小化，遵从了在此情况下优先于重启 Node-RED 的指示**。`snmpsim` 会在进程启动时加载一次 `.snmprec` 文件 (`--force-index-rebuild`)；而 Node-RED 在每个周期都会重新通过网络向它拉取数据，没有客户端缓存，因此不需要重启 Node-RED。通过 `docker logs ims-snmpsim` 确认：纯净的重启，所有 3 种设备配置文件 (`Netk@`, `windows`, `ubuntu`) 均已重新打开并响应。

新的数值 (37.2%) 几乎完全落在了设计区间的理论下限 (36.4%) 上，这对于随机游走初期的样本来说符合预期。
