## 1. 执行摘要

**IMS** 代表了 PCB 生产线上的 YSPhotec / LDI 机器从**手动监控**系统向**采用 AIOps 的持续自动监控**的转变。

该系统采用**开源堆栈**架构，该架构以 **1,000 个虚拟用户 (VUs)** 通过了负载测试，同时维持了定义的故障预算（在极端混沌负载下，管道成功率 >95%）。

---

## 2. 问题 → 解决方案矩阵

### 之前（遗留问题）

| 问题 | 影响 | 每日成本 |
| ----------------------------- | ------------------------------------------------ | ------------------------------ |
| **延迟的可见性（手动）** | 需要巡视检查物理仪表 | 2 名员工 × 4 轮 = 8 小时/天 |
| **停机检测缓慢** | 2-4 小时才能检测到故障 | 累积的产量缺陷 |
| **手动数据录入** | 人为错误 ~15% | 无法跟踪趋势 |
| **反应式维护** | 等待出现缺陷再修复 | 计划外停机 |

### <img src="../../../docs/assets/icons/check-circle.svg" width="14" align="center"/> **状态：** 健康 之后（解决方案）

| 解决方案 | 结果 | 影响 |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| **连续 SNMP 轮询** | 每 30 秒进行一次自动化遥测采集 | 消除了手动抽样扫描 |
| **Z-Score 统计警报** | 在机器发生故障前检测 3σ 异常 | 主动维护 |
| **15 个仪表板** | 5 个基础设施（NOC、工程下钻、容量、元监控、摄取延迟） + 10 个制造（简易概览、警报控制台、警报字典、警报响应 (MTTA/MTTR)、工程分析、机器快照、制造指挥中心、操作员 Andon、数据就绪性、工厂数字孪生） | 在整个基础设施和制造线本身上实现全面可见性 |
| **LINE/Teams Webhook** | 警报格式和传递尝试逻辑是完整和正确的；真实交付需要未在此仓库中传送的操作员配置凭据（`LINE_CHANNEL_ACCESS_TOKEN`、`TEAMS_WEBHOOK_URL`） | 配置后响应更快 |
| **预测分析** | 线性回归预测 | 防止故障 |

## 3. 投资回报率 (ROI) 指标

### 之前与之后的对比

| 指标 | 之前（手动） | 之后（IMS） | 改进 |
| ----------------------- | -------------------------- | ----------------------------- | ------------------------------------------------ |
| **检测时间 (Time to Detect)** | 1-4 小时 | **< 10 秒** | 快 99.97% |
| **平均修复时间 (MTTR)** | > 2 小时 | **~15 分钟** | 减少 87.5% |
| **体力劳动** | 8 小时/天（2 名员工） | **消除了日常检查** | 每年节省 2,920 小时 |
| **数据准确性** | ~85%（人为错误） | **99.9%** | 准确性提高 17.5% |
| **数据粒度** | 每天 6 次读数 | **每天 2,880 次读数** | 数据量增加 480 倍 |
| **维护模式** | 反应式（坏了再修） | **预测式（预防）** | 主动维护大幅度减少停机时间 |

### 每年成本节约

| 类别 | 之前 | 之后 | 每年节省 |
| ------------------------ | --------------------------------- | ------------------- | ----------------- |
| **许可费用** | THB 3,000,000-10,000,000 | THB 0 (开源) | **THB 3-10M** |
| **体力劳动** | THB 730,000（2,920 小时 × THB 250） | THB 0 | **THB 730K** |
| **停机成本** | THB 500,000/事故 × N | 接近零 | **THB 2-5M** |
| **每年总节省额** | | | **THB 5.7-15.7M** |

### 投资回收期

```text
初始投资: ~THB 200,000 (实习生人工 + 计算资源)
年度节省: ~THB 5,700,000 (保守估计)
投资回收期: < 1 个月
投资回报率 (ROI): 2,750% (第一年)
```

## 4. 技术成就

| 组件 | 交付内容 |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Docker 堆栈** | 12 个容器，完全编排 |
| **遥测模式** | 两个独立的管道 — 基础设施（`sys_metrics`/`net_metrics`/`ldi_metrics`）和 LDI 制造（`ldi_data`，34 列：PE1-6、JE1-4、厚度、扫描速度、抗蚀剂剂量等） — 参见 `docs/architecture/DATABASE_SCHEMA.md` |
| **警报规则** | 30 条规则：6 条 LDI 特定规则 + 11 条基础设施规则（Grafana 原生），13 条管道/平台元监控规则（Prometheus/Alertmanager） |
| **仪表板** | 15 个仪表板（5 个基础设施 + 10 个制造） |
| **负载测试** | 最高 1,000 个虚拟用户（`chaos-stress.js`，故意的 5% 故障注入，>90% 的成功阈值）；`pipeline-stress.js` 目标是 >95% 的成功率 — 这不是 0% 故障保证，而是定义的、可接受的故障预算 |
| **CI/CD** | 带有安全扫描（Gitleaks）的 GitHub Actions |
| **文档** | 涵盖架构、运营、用户/管理员手册和企业指南的 40 多份文档 |
