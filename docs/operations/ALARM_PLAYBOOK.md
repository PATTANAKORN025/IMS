# IMS Alarm & Alert Playbook

> **Objective:** first-responder resolution steps mapped to the alerts and alarm codes this system actually generates. Every code and rule name below was checked directly against the live database and the provisioned alert rule files on 2026-08-10 — this replaces an earlier version that used fictional codes (`SYS-001`, `NET-002`, `LDI-001`) that never existed in this system.
>
> IMS has **three distinct alerting layers**, and they use different vocabularies — don't conflate them:
> 1. **LDI machine alarm codes** — numeric codes from the physical/simulated equipment itself, stored in `public.ldi_alarm_log`, catalogued in `public.ldi_alarm_ms_code`. See `ALARM_SEVERITY_GUIDE.md` for the full taxonomy.
> 2. **Grafana native alert rules** — threshold/anomaly rules Grafana itself evaluates against the database, split into LDI-specific (`monitoring/grafana/provisioning/alerting/ldi-rules.yml`) and infrastructure (`rules.yml`).
> 3. **Prometheus/Alertmanager rules** — meta-monitoring of the platform itself (`monitoring/prometheus/rules/ims-alerts.yml`) — is IMS's own pipeline healthy, not "is a machine out of spec."

All three route through the same delivery path: Grafana's native alerts fire directly; Prometheus alerts go through Alertmanager → Node-RED's `/alert-webhook` (`nodered_data/flows/alerting.json`), which formats a LINE Messaging API and MS Teams payload. **Real delivery to LINE/Teams requires `LINE_CHANNEL_ACCESS_TOKEN` and `TEAMS_WEBHOOK_URL`, which are absent from `.env` by design** — the formatting and delivery-attempt logic is provably correct and loud-on-failure (`node.error()` + a persistent red status in Node-RED), but nothing reaches a human until an operator configures real credentials per `docs/admin/ADMIN_MANUAL.md`.

## 1. LDI Machine Alarm Codes

The 19 codes below are the ones actually generated by `ldi_alarm_simulator.json` today (confirmed live against `ldi_alarm_log`); the full catalog in `ldi_alarm_ms_code` has far more (imported from a real historical export) but most aren't simulator-active. See `LDI_RCA_GUIDE.md` for how these correlate to process parameters.

| Code | Severity | Message | First response |
|---|---|---|---|
| `01060009` | Major | Wrong camera serial number | Camera/vision subsystem fault — check physical camera connection and serial config on the machine controller. |
| `0106000C` | Major | Failed to stop camera | Vision subsystem fault — power-cycle the camera module if it doesn't clear on retry. |
| `01060013` | Major | Found the same IP | Network address conflict on the machine's local network — check for a duplicate device. |
| `010E0064` | Major | Motor type undefined | Motion controller configuration fault — verify motor type is set in the machine's recipe/config. |
| `01100001` | Major | Failed to connect to PLC | PLC communication down — check the PLC's power and network link before anything else. |
| `01130002` | Major | Communication abnormality | General comms fault on the machine controller — check cabling and controller logs. |
| `10006` | Major | Failed to set imaging device to protection mode | Imaging device fault during a safety-mode transition — do not resume exposure until cleared. |
| `0106001C` | Minor | Stop trigger wait signal timeout | Timing/signal issue on a stop trigger — usually transient, watch for repeat occurrences. |
| `70004` | Warning | Position-synchronised output overspeed | Scan-speed excursion — see `LDI_RCA_GUIDE.md`'s MOTION category; correlates with `scan_speed` in `ldi_data`. |
| `80001` | Warning | Waiting for subdrawing preparation data timeout | Upstream data-prep delay, not a machine fault per se — check the MES/data feed for that job. |
| `90001` | Warning | Inner layer alignment to grip point failed | Alignment/registration issue — see `LDI_RCA_GUIDE.md`'s ALIGNMENT/PE-JE category. |
| `90004` | Warning | Outer layer alignment to grip point failed | Same category as `90001`, outer layer. |
| `90005` | Warning | Registration error (PE/JE) out of tolerance | Direct PE/JE tolerance breach — check `LDI Engineering Analytics`'s SPC panels for the specific machine. |
| `90012` | Warning | Alignment failed and operator cancelled exposure | Operator-cancelled — confirm with the operator this was intentional, not a repeated silent failure. |
| `91008` | Warning | Ambient temperature or humidity abnormal | Environmental excursion — see `LDI_RCA_GUIDE.md`'s THERMAL/HUMIDITY categories; correlates with `temperature`/`humidity` in `ldi_data`. |
| `91009` | Warning | Vacuum pressure out of control range | See `LDI_RCA_GUIDE.md`'s VACUUM category; correlates with `air_vacuum`. |
| `92013` | Warning | Network connection timeout | Machine-to-plant network issue — check the same network path SNMP/HTTP telemetry uses. |
| `93004` | Warning | Calibration cycle exception | Scheduled calibration didn't complete — check the machine's calibration log. |
| `97005` | Warning | Database connection exception | The machine's own local buffer/DB, not IMS's TimescaleDB — check the machine controller's local storage. |

**Where to see these live:** the `IMS LDI - Operator Andon Board`'s Action Queue panel (read-only, 5s refresh) shows Critical/Major alarms not yet resolved; the SQL equivalent is `SELECT * FROM public.ldi_alarm_log ORDER BY logdate DESC LIMIT 50;`. **To acknowledge or resolve an alarm**, use `IMS LDI - Alarm Console` — the Andon board is a deliberately non-interactive TV-wall kiosk; Alarm Console is the separate dashboard where those actions actually write to `public.ldi_alarm_lifecycle`.

## 2. Grafana Native Alert Rules — LDI (`ldi-rules.yml`)

| Rule | What it means | Investigate |
|---|---|---|
| **LDI Quality Drift — Max PE exceeds tolerance** | A machine's worst PE (position error) sample breached its `pe_setting` tolerance. | `LDI Engineering Analytics` → SPC panels for the affected machine. |
| **LDI Process Capability — Cpk below 1.33** | PE-based Cpk dropped below the 1.33 industry-standard capability floor. | Same dashboard; check whether it's a single excursion or sustained drift — see `LDI_SPC_GUIDE.md`. |
| **LDI Quality Drift — Max JE exceeds tolerance** | Same as PE drift, for JE (judgment error). | Same dashboard, JE panels. |
| **LDI JE Process Capability — Cpk below 1.33** | JE-based Cpk below 1.33. | Same dashboard. |
| **LDI Machine Alarm — new alarm in database** | A new row landed in `ldi_alarm_log`. This is the catch-all "something happened" rule — check §1 above for the specific code. | Operator Andon Board. |
| **LDI Temperature High — above 24°C spec limit** | Fixed-threshold rule, not a Z-Score anomaly — see `LDI_RCA_GUIDE.md`'s note that there is no statistical-anomaly panel on the LDI side, only this fixed threshold. | `LDI Engineering Analytics` temperature panel. |

## 3. Grafana Native Alert Rules — Infrastructure (`rules.yml`)

| Rule | Scope |
|---|---|
| High CPU / RAM / Disk Usage | Server/workstation resource thresholds. |
| High Temperature | Server chassis temperature. |
| High Network Error Rate / Network Packet Drops / Interface Down | Network interface health. |
| Bandwidth Saturation Forecast | Predictive — capacity trending toward saturation, not yet breached. |
| CPU Z-Score Anomaly (>3σ) / Temperature Z-Score Anomaly (>3σ) | Statistical anomaly detection — infrastructure only. There is **no equivalent Z-Score panel on the LDI side** (see `LDI Temperature High` above, which is a fixed threshold instead). |
| LDI Vibration Critical | **Paused.** `ldi_metrics.vibration` is confirmed always `0` for every LDI device (a known gap in the legacy `ldi_metrics` pipeline, not `ldi_data` — see `ARCHITECTURE.md`'s Known Gaps). This rule cannot fire meaningfully until that's fixed; it's paused rather than left silently unable to trigger. |

Investigate infrastructure alerts starting at `NOC Overview` or `Engineering Drill-Down`.

## 4. Prometheus / Alertmanager Rules (`ims-alerts.yml`)

These monitor **IMS's own pipeline health**, not machine or server state — "is the monitoring system itself working."

| Rule | Meaning | First response |
|---|---|---|
| `PrometheusDown` / `AlertmanagerDown` / `TargetDown` / `HighScrapeErrors` | The monitoring stack's own components are unhealthy. | Check `docker ps` for the affected container; see `INCIDENT_RESPONSE.md`. |
| `ServiceDown` / `ServiceHighLatency` / `SLABreachWarning` | Blackbox-exporter probe failures against a monitored endpoint (e.g. Grafana's own `/api/health`). | Check the target service directly; note this can be a transient artifact of a deliberate container recreate — see `DR_TEST_PLAN.md`'s Drill 2 evidence for a real example. |
| `SSLCertExpiring` | A monitored endpoint's TLS cert is nearing expiry. | Renew before expiry. |
| `Watchdog` | Always-firing heartbeat confirming Alertmanager routing itself works — **not** a real incident. Exclude it when scanning for actual firing alerts. |
| `PipelineDataStalled` / `PipelineDataDegraded` / `PipelineHighErrorRate` | Node-RED ingestion pipeline health — stalled/degraded/high-error-rate telemetry flow. | `Meta-Monitoring` dashboard; check `ims-node-red` logs for the specific failure signature (see `INCIDENT_RESPONSE.md`'s worked examples). |
| `CircuitBreakerOpen` | A device's SNMP circuit breaker tripped (CLOSED→OPEN after repeated failures). | Check the specific device's connectivity; the breaker self-resets to HALF_OPEN after a cooldown. |
