# การรับมือกับเหตุการณ์ (Incident Response)

> **กลุ่มเป้าหมาย:** SRE/ฝ่ายปฏิบัติการ, วิศวกรที่เข้าเวรรับแจ้งเหตุ (On-call Engineers)
> **วัตถุประสงค์:** จัดเตรียมกรอบการทำงานสำหรับระดับความรุนแรง (severity) และตัวอย่างสถานการณ์จริงที่ระบุวิธีการกู้คืนระบบจากเหตุการณ์ขัดข้อง
> **ที่มา:** ตัวอย่างสถานการณ์ด้านล่างล้วนเป็นเหตุการณ์ที่เกิดขึ้นจริงในประวัติการทำงานของระบบนี้ (มีการหาสาเหตุที่แท้จริงและได้รับการแก้ไขแล้วตามที่ระบุไว้) — ไม่ใช่สถานการณ์สมมติ

---

## กรอบระดับความรุนแรง (Severity framework)

| ระดับความรุนแรง | คำจำกัดความ                                                                     | ตัวอย่าง                                                                                    | เป้าหมายการตอบสนอง                                 |
| --------------- | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| **SEV-1**       | ข้อมูลบนโปรดักชันสูญหาย หรือการนำเข้าข้อมูลหยุดชะงักอย่างสมบูรณ์ทั้งสองไปป์ไลน์ | ทั้ง `ldi_data` และ `sys_metrics` หยุดรับข้อมูล                                             | ทันที — ทุกคนต้องช่วยเหลือ (Immediate — all hands) |
| **SEV-2**       | ไปป์ไลน์หนึ่งล่ม หรือคอนเทนเนอร์ไม่สามารถกู้คืนได้                              | การนำเข้าข้อมูล LDI ค้าง แต่ไปป์ไลน์ของโครงสร้างพื้นฐานไม่ได้รับผลกระทบ                     | ภายในกะการทำงาน                                    |
| **SEV-3**       | ประสิทธิภาพลดลงแต่ยังทำงานได้                                                   | ความหน่วงในการสืบค้น (query latency) สูงขึ้น, ข้อมูลจากเครื่องใดเครื่องหนึ่งไม่เป็นปัจจุบัน | วันทำการถัดไป                                      |
| **SEV-4**       | ปัญหาด้านความสวยงาม / ไม่มีผลต่อการทำงาน                                        | แผงแดชบอร์ดแสดงสีที่ไม่ตรงกับความเป็นจริง                                                   | เก็บไว้ใน Backlog                                  |

## การตอบสนองเบื้องต้น ไม่ว่าระดับความรุนแรงใดก็ตาม

1. **ตรวจสอบแดชบอร์ด Meta-Monitoring** — ดูความสมบูรณ์ของไปป์ไลน์, อัตราการนำเข้าข้อมูล, และอัตราการเกิดข้อผิดพลาด
2. **รันคำสั่ง `docker ps`** — ดูว่าทุกคอนเทนเนอร์อยู่ในสถานะ `Up` และ `healthy` หรือไม่?
3. **ตรวจสอบผ่านคำสั่ง `SELECT max(time) FROM public.ldi_data;`** (รวมถึงตาราง `sys_metrics`) — ดูว่าข้อมูลล่าช้าไปแค่ไหน?
4. **ตรวจสอบ Alertmanager/Grafana สำหรับการแจ้งเตือนที่ถูกทริกเกอร์** — ดู `docs/architecture/ALARM_PLAYBOOK.md` เพื่อทำความเข้าใจความหมายของแต่ละการแจ้งเตือน โปรดจำไว้ว่า `Watchdog` จะส่งการแจ้งเตือนเสมอและไม่ใช่เหตุการณ์ผิดปกติจริง

---

## ตัวอย่างที่แก้ไขจริง 1: การรีสตาร์ท TimescaleDB ไม่ทำให้การนำเข้าข้อมูลกลับมาทำงานได้

**สิ่งที่เกิดขึ้น (2026-08-10, ค้นพบระหว่างการทดสอบ DR):** หลังจากที่คอนเทนเนอร์ TimescaleDB ถูกสั่งหยุดและรีสตาร์ท (ไม่ว่าจะด้วยวิธีแมนนวลหรือโดยออร์เคสเตรเตอร์) การนำเข้าข้อมูล LDI อาจหยุดชะงักเป็นเวลาหลายนาที แม้ว่าตัวฐานข้อมูลจะกลับมาทำงานตามปกติแล้วก็ตาม — คำสั่ง `docker exec ims-timescaledb psql ... SELECT max(time) FROM ldi_data` ยังคงหยุดนิ่งอยู่ที่เวลาที่เกิดปัญหา

**สาเหตุที่แท้จริง (Root cause):** เกิดจากพฤติกรรมการแคชข้อผิดพลาด `server_login_retry` ของ PgBouncer หลังจากระบบหลังบ้าน (backend) ล่ม PgBouncer จะแคชการเชื่อมต่อที่ล้มเหลวไว้และจะไม่พยายามเชื่อมต่อใหม่ทันทีแม้ว่าระบบหลังบ้านจะกลับมาทำงานแล้ว — รวมไปถึง `pg.Pool` ของ Node-RED อาจติดอยู่ในสถานะล้มเหลวและไม่เคลียร์ตัวเอง (`server login has been failing, cached error: connect failed` ในบันทึกของ Node-RED คือสิ่งที่บ่งชี้ปัญหา)

**พารามิเตอร์คอนฟิกของ Watchdog:** `ldi_auth_check` ในไฟล์ `ldi_ingestion.json` จะนับจำนวนความล้มเหลวในการเชื่อมต่อติดต่อกัน (`ldiDbConnFailureStreak`) และเมื่อถึง 5 ครั้ง จะเรียกฟังก์ชัน `process.exit(1)` เพื่อให้ Docker ทำการรีสตาร์ท Node-RED ขึ้นมาใหม่พร้อมกับ pool ใหม่ (ผ่านนโยบาย `restart: unless-stopped` ของ Docker) **จากการสังเกตระหว่างการทดสอบ DR พบว่าความหน่วงของทริกเกอร์ (trigger latency) อยู่ที่ประมาณ 6 นาที** สำหรับเหตุการณ์ลูกโซ่นี้โดยเฉพาะ — การปรับเกณฑ์ขั้นต่ำของตัวนับจะถูกนำไปปรับปรุงในอนาคต (ดูในส่วน System Constraints & Technical Boundaries ของ `ARCHITECTURE.md`)

**การกู้คืนด้วยตนเอง (ได้ผลทันที):**

```bash
docker restart ims-node-red
```

ยืนยันการกู้คืนระบบ: คำสั่ง `SELECT max(time) FROM public.ldi_data;` ควรจะแสดงเวลาปัจจุบันภายในไม่กี่วินาที

## ตัวอย่างที่แก้ไขจริง 2: ข้อมูล telemetry ของเครื่องหนึ่งหยุดส่งเข้ามาอย่างเงียบๆ

**สิ่งที่เกิดขึ้น:** เครื่องจักรของจริงสองเครื่อง (เครื่องที่มีอักขระเว้นวรรคอยู่ใน Device ID เช่น `"EXPOSURE LDI-2"`) หยุดส่งข้อมูลรายงานโดยสมบูรณ์ โดยที่ไม่มีข้อผิดพลาดใด ๆ แสดงขึ้นในการแจ้งเตือนแบบปกติ

**สาเหตุที่แท้จริง (Root cause):** ตัวแปล flow-context ของ Node-RED (`flow.get()`/`global.get()`) ทำการแยกวิเคราะห์ string key ให้เป็นนิพจน์ property — ซึ่งหากพบช่องว่างใน key จะเกิดข้อผิดพลาด `Invalid property expression` รหัสของเครื่องถูกใช้โดยตรงเป็น context key ในสองจุด (inline parser ใน `ingestion.json` และใน `circuit-breaker.js`) จึงทำให้ในรอบการโพลข้ามเครื่องที่ Device ID มีเว้นวรรคหรือเครื่องหมายวรรคตอนไปอย่างเงียบๆ

**วิธีการแก้ไข (ทำไปแล้ว):** ปัจจุบันจุดที่มีการเรียกใช้ทั้งสองที่ จะทำการปรับ (sanitize) Device ID ให้อยู่ในรูปแบบของ context key ที่ปลอดภัย (`safeKey()` ใน `nodered_data/lib/parser.js`) ก่อนที่จะใช้เก็บลงใน `flow`/`global` ในขณะที่ยังคงรักษารหัสเครื่องดั้งเดิมไว้สำหรับการแสดงผลและการ join ตารางในระบบ การทดสอบรีเกรชัน (Regression coverage) อยู่ที่: `tests/unit/circuit-breaker.test.js`

**สิ่งที่บ่งชี้ปัญหาที่ต้องเฝ้าระวัง:** พบข้อความ `Invalid property expression` ในบันทึกของ Node-RED, หรือแถวของอุปกรณ์เครื่องใดเครื่องหนึ่งไม่ขยับเลยในตาราง `ldi_data`/`sys_metrics` ในขณะที่เครื่องอื่นยังคงทำงานปกติ

## ตัวอย่างที่แก้ไขจริง 3: คอนเทนเนอร์ไม่ทำการกู้คืนอัตโนมัติหลังจากถูกสั่งหยุด

**สิ่งที่เกิดขึ้น (จากการทดสอบ DR, 2026-08-10):** คำสั่ง `docker kill ims-timescaledb` ไม่กระตุ้นให้นโยบาย `restart: unless-stopped` ของ Docker ทำงาน — ยืนยันสองครั้งผ่านการสตรีม `docker events` สด (พบเพียงเหตุการณ์ `kill`/`die` โดยไม่มีการทำงาน `start` อัตโนมัติ) แม้ว่าจะตั้งค่านโยบายไว้ถูกต้องที่คอนเทนเนอร์แล้วก็ตาม

**สถานะ:** อยู่ระหว่างการวิเคราะห์ — กำลังประเมินปัจจัยทางสภาพแวดล้อม (อาจเกี่ยวกับ Docker Desktop/WSL2 โดยเฉพาะ; ยังไม่ได้รับการยืนยันบนโฮสต์ Linux ในสภาพแวดล้อมโปรดักชัน)

**การกู้คืนด้วยตนเอง:**

```bash
docker start ims-timescaledb # หากคอนเทนเนอร์ยังมีอยู่แต่ไม่ได้ทำงาน
# หรือ, หากวิธีแรกไม่ได้ผล:
docker compose up -d timescaledb
```

จากนั้นทำตามขั้นตอนของตัวอย่างที่ 1 — การรีสตาร์ท TimescaleDB จะส่งผลลูกโซ่ให้เกิดรูปแบบปัญหาการนำเข้าข้อมูลค้างเช่นเดิม

## การยกระดับเหตุการณ์ (Escalation)

สำหรับปัญหาที่ไม่อยู่ในตัวอย่างที่ระบุไว้ข้างต้น หรือระดับ SEV-1/SEV-2 ที่ไม่ได้รับการแก้ไข:

1. ตรวจสอบหัวข้อ System Constraints & Technical Boundaries ใน `docs/architecture/ARCHITECTURE.md` — อาจมีการบันทึกข้อมูลเกี่ยวกับพารามิเตอร์ของระบบไว้แล้ว
2. ตรวจสอบ `docs/operations/TROUBLESHOOTING.md` สำหรับคำสั่งดีบัก SRE ในระดับที่กว้างขึ้น
3. หากเป็นปัญหาที่ไม่เคยเกิดขึ้น ให้หาสาเหตุที่แท้จริงแบบเดียวกับ 3 ตัวอย่างด้านบน: จำลองปัญหาหากสามารถทำได้อย่างปลอดภัย (ดูที่รูปแบบแผนการซ้อมรองรับความล้มเหลวแบบควบคุมและการเก็บหลักฐานใน `docs/operations/DR_TEST_PLAN.md`) จดบันทึกสิ่งที่ค้นพบ — รวมถึงบันทึกในหัวข้อ System Constraints & Technical Boundaries ของ `ARCHITECTURE.md` ด้วย

## เอกสารที่เกี่ยวข้อง

- `docs/architecture/ARCHITECTURE.md` — ส่วน System Constraints & Technical Boundaries จะเป็นรายการข้อจำกัดอย่างเป็นทางการของระบบ
- `docs/operations/ALARM_PLAYBOOK.md` — ความหมายของการแจ้งเตือนแต่ละแบบ
- `docs/operations/DR_TEST_PLAN.md` — แผนการซ้อมความล้มเหลวแบบควบคุมและหลักฐานจริง
- `docs/operations/BACKUP_RESTORE.md` — ข้อมูลสำหรับการจัดการเมื่อเกิดเหตุการณ์ที่เกี่ยวข้องกับการสูญหายของข้อมูล
- `docs/operations/TROUBLESHOOTING.md` — คำสั่งดีบัก SRE แบบทั่วไป
