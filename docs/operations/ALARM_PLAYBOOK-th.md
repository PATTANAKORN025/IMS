# คู่มือการจัดการสัญญาณเตือนและการแจ้งเตือน IMS

> **กลุ่มเป้าหมาย:** SRE/ฝ่ายปฏิบัติการ, พนักงานควบคุมสายการผลิต
> **วัตถุประสงค์:** ขั้นตอนการแก้ไขปัญหาเบื้องต้นที่เชื่อมโยงกับการแจ้งเตือนเฉพาะและรหัสสัญญาณเตือนที่สร้างโดยระบบ
> **แหล่งที่มา:** ทุกรหัสและชื่อกฎด้านล่างได้รับการตรวจสอบโดยตรงกับฐานข้อมูลจริงและไฟล์กฎการแจ้งเตือนที่จัดเตรียมไว้เมื่อวันที่ 2026-08-10
>
> IMS มี **ชั้นการแจ้งเตือนที่แตกต่างกัน 3 ชั้น** และใช้คำศัพท์ที่แตกต่างกัน — อย่าสับสนเข้าด้วยกัน:
>
> 1. **รหัสสัญญาณเตือนเครื่องจักร LDI** — รหัสตัวเลขจากตัวอุปกรณ์จริง/จำลอง ซึ่งจัดเก็บใน `public.ldi_alarm_log` และจัดหมวดหมู่ใน `public.ldi_alarm_ms_code` ดู `ALARM_SEVERITY_GUIDE.md` สำหรับการจัดหมวดหมู่ฉบับเต็ม
> 2. **กฎการแจ้งเตือนดั้งเดิมของ Grafana** — กฎเกณฑ์/ความผิดปกติที่ Grafanaประเมินกับฐานข้อมูล แบ่งเป็นเฉพาะ LDI (`monitoring/grafana/provisioning/alerting/ldi-rules.yml`) และโครงสร้างพื้นฐาน (`rules.yml`)
> 3. **กฎ Prometheus/Alertmanager** — การตรวจสอบระดับอภิมานของตัวแพลตฟอร์มเอง (`monitoring/prometheus/rules/ims-alerts.yml`) — ตรวจสอบความสมบูรณ์ของไปป์ไลน์ของ IMS เอง ไม่ใช่ "เครื่องจักรทำงานผิดปกติหรือไม่"

ทั้งสามจะถูกส่งผ่านเส้นทางเดียวกัน: การแจ้งเตือนดั้งเดิมของ Grafana จะทำงานโดยตรง; การแจ้งเตือนของ Prometheus จะผ่าน Alertmanager → `/alert-webhook` ของ Node-RED (`nodered_data/flows/alerting.json`) ซึ่งจะจัดรูปแบบเพย์โหลดสำหรับ LINE Messaging API และ MS Teams **การส่งข้อมูลจริงไปยัง LINE/Teams จำเป็นต้องใช้ `LINE_CHANNEL_ACCESS_TOKEN` และ `TEAMS_WEBHOOK_URL` ซึ่งเป็นพารามิเตอร์การกำหนดค่าภายนอก** ตรรกะการจัดรูปแบบและการส่งข้อมูลได้รับการตรวจสอบและมีความเสถียร พร้อมทั้งบันทึกสถานะเมื่อเกิดความล้มเหลว ข้อความจะถูกส่งเมื่อมีการกำหนดค่าข้อมูลรับรองตาม `docs/admin/ADMIN_MANUAL.md`

## 2. ขอบเขตการอนุญาต & กระบวนการแก้ไข

**ใครสามารถล้างสัญญาณเตือนได้?**

- **ผู้ปฏิบัติงาน (L1):** ได้รับอนุญาตให้ล้างสัญญาณเตือน `Warning` และ `Minor` _หาก_ สาเหตุที่แท้จริงทางกายภาพได้รับการแก้ไขแล้ว (เช่น การนำแผงที่ติดออก)
- **วิศวกรรม (L2/L3):** ต้องล้างสัญญาณเตือน `Major` และ `Critical` ทั้งหมด ผู้ปฏิบัติงานห้ามลบล้างสัญญาณเตือนเหล่านี้

**การตรวจสอบการแก้ไข:**
สัญญาณเตือนไม่ได้ "แก้ไข" เพียงเพราะเสียงสัญญาณเตือนหยุดดัง

1. **ล้างข้อผิดพลาดทางกายภาพ** บนเครื่องจักร
2. **รับทราบใน UI:** ใช้ `IMS LDI - Alarm Console` เพื่อทำเครื่องหมายสัญญาณเตือนว่า "รับทราบ" (Acknowledged) จากนั้น "แก้ไขแล้ว" (Resolved)
3. **ตรวจสอบ Telemetry:** เปิด `Operator Andon Board` ยืนยันว่าเครื่องจักรกลับสู่สถานะสีเขียวเป็นเวลาอย่างน้อย 3 รอบการโพลล์ติดต่อกัน (15 วินาที)

**สถานที่ดูสัญญาณเตือนแบบเรียลไทม์:** แผงคิวการดำเนินการ (Action Queue panel) ของ `IMS LDI - Operator Andon Board` (อ่านได้อย่างเดียว รีเฟรช 5 วินาที) จะแสดงสัญญาณเตือน Critical/Major ที่ยังไม่ได้รับการแก้ไข

| High Network Error Rate / Network Packet Drops / Interface Down | ความสมบูรณ์ของอินเทอร์เฟซเครือข่าย                                                                                                                                                                                                                                          |
| Bandwidth Saturation Forecast                                   | การคาดการณ์ — ความจุกำลังมีแนวโน้มเข้าสู่สภาวะอิ่มตัว แต่ยังไม่เกินขีดจำกัด                                                                                                                                                                                                |
| CPU Z-Score Anomaly (>3σ) / Temperature Z-Score Anomaly (>3σ)   | การตรวจจับความผิดปกติทางสถิติ — เฉพาะโครงสร้างพื้นฐานเท่านั้น **ไม่มีแผง Z-Score ที่เทียบเท่าในฝั่ง LDI** (ดู `LDI Temperature High` ด้านบน ซึ่งเป็นขีดจำกัดคงที่แทน)                                                                              |
| LDI Vibration Critical                                          | **หยุดชั่วคราว** การสตรีม `ldi_metrics.vibration` มีค่าเป็น `0` สำหรับอุปกรณ์ LDI (ข้อจำกัดของระบบในไปป์ไลน์ `ldi_metrics` รุ่นเก่า ไม่ใช่ `ldi_data` — ดูข้อจำกัดของระบบและขอบเขตทางเทคนิคใน `ARCHITECTURE.md`) กฎนี้หยุดชั่วคราวเพื่อรอการบูรณาการในอนาคต |

ตรวจสอบการแจ้งเตือนโครงสร้างพื้นฐานโดยเริ่มจาก `NOC Overview` หรือ `Engineering Drill-Down`

## 4. กฎ Prometheus / Alertmanager (`ims-alerts.yml`)

กฎเหล่านี้จะตรวจสอบ **ความสมบูรณ์ของไปป์ไลน์ของ IMS เอง** ไม่ใช่สถานะเครื่องจักรหรือเซิร์ฟเวอร์ — "ระบบตรวจสอบเองทำงานอยู่หรือไม่"

| กฎ                                                                      | ความหมาย                                                                                                                                            | การตอบสนองเบื้องต้น                                                                                                                                                             |
| ------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `PrometheusDown` / `AlertmanagerDown` / `TargetDown` / `HighScrapeErrors` | คอมโพเนนต์ของสแตกการตรวจสอบมีความผิดปกติ                                                                                               | ตรวจสอบ `docker ps` สำหรับคอนเทนเนอร์ที่ได้รับผลกระทบ; ดู `INCIDENT_RESPONSE.md`                                                                                                  |
| `ServiceDown` / `ServiceHighLatency` / `SLABreachWarning`                 | ความล้มเหลวของการสอบสวน blackbox-exporter เทียบกับเอนด์พอยต์ที่ตรวจสอบ (เช่น `/api/health` ของ Grafana เอง)                                                  | ตรวจสอบบริการเป้าหมายโดยตรง; โปรดทราบว่านี่อาจเป็นสิ่งที่เกิดขึ้นชั่วคราวจากการสร้างคอนเทนเนอร์ใหม่โดยเจตนา — ดูหลักฐานการฝึกซ้อม 2 ใน `DR_TEST_PLAN.md` สำหรับตัวอย่างจริง |
| `SSLCertExpiring`                                                         | ใบรับรอง TLS ของเอนด์พอยต์ที่ตรวจสอบใกล้จะหมดอายุ                                                                                                 | ต่ออายุก่อนวันหมดอายุ                                                                                                                                                       |
| `Watchdog`                                                                | Heartbeat ที่ทำงานเสมอซึ่งยืนยันว่าการกำหนดเส้นทาง Alertmanager เองนั้นทำงานได้ — **ไม่ใช่** เหตุการณ์จริง ไม่รวมเข้าด้วยกันเมื่อสแกนหาการแจ้งเตือนที่เกิดขึ้นจริง | N/A - ทำงานตามที่ออกแบบไว้                                                                                                                                                  |
| `PipelineDataStalled` / `PipelineDataDegraded` / `PipelineHighErrorRate`  | ความสมบูรณ์ของไปป์ไลน์การนำเข้าข้อมูล Node-RED — ข้อมูล telemetry หยุดนิ่ง/เสื่อมสภาพ/มีอัตราข้อผิดพลาดสูง                                                              | แดชบอร์ด `Meta-Monitoring`; ตรวจสอบบันทึก `ims-node-red` สำหรับรูปแบบความล้มเหลวเฉพาะ (ดูตัวอย่างขั้นตอนการทำงานใน `INCIDENT_RESPONSE.md`)                                  |
| `CircuitBreakerOpen`                                                      | เซอร์กิตเบรกเกอร์ SNMP ของอุปกรณ์ตัด (CLOSED→OPEN หลังจากเกิดความล้มเหลวซ้ำซาก)                                                                     | ตรวจสอบการเชื่อมต่อของอุปกรณ์เฉพาะ เบรกเกอร์จะรีเซ็ตตัวเองเป็น HALF_OPEN หลังจากคูลดาวน์                                                                           |
