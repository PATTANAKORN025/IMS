## Known unresolved risks (ความเสี่ยงที่ยังไม่ได้รับการแก้ไขที่เป็นที่ทราบ) (ไม่ได้ซ่อมแซมให้ลุล่วงในตัวโปรแกรมนี้, แต่ระบุไว้อย่างตรงไปตรงมา)

1. **บั๊กพูลแครช `client_idle_timeout` ของ PgBouncer** (`SPEC_PG_POOL_RESILIENCE.md`) -- **แก้ไขและใช้งานแล้ว 2026-08-15** (`fe7fa87`) นำเอา `pool.on('error', ...)` เข้าไปผนวกไว้ให้ในสองทางทั้งที่ `node-red` กับฝั่ง `alarm-api`, ไม่เจอปัญหาซ้อนทับ (regression) ส่วนผลกระทบที่แท้จริงของการกู้ชีวิตช่วงว่างที่หมดเวลาเอง (idle-timeout-survival) ยังไม่ได้รันทดสอบในหมวดที่สามารถเอาผลมันเป็นข้อยืนยันเดี่ยวๆ ได้ -- นั่นเป็นความตั้งใจมอบสิทธิ์นี้ให้แก่ Soak Attempt 10 (กำลังดำเนินการอยู่) และในฐานะที่มันเป็นหน้าที่รับผิดชอบของ Fault Injection scenario ที่ 3
2. **เงื่อนไขการแข่งขันรอบทำงานในระยะ Phase A1** (`SCALE_TEST_2026-08-15.md`) -- เป็นเรื่องใหม่, ซึ่งตรวจสอบเจอในบรรยากาศที่มีการเปิดตัวเทสต์ความสามารถในการรับภาระโหลดที่มีการสุ่มหลายๆ ตัวเข้ามา (scale-test concurrency), แทบไม่ได้ส่งผลแง่ลบกับขุมกำลังเดินระบบในกลุ่มเครื่องปฏิบัติงานจริง (fleet) ในโครงข่ายเลย, และยังไม่ได้รับการแก้ไข
3. **อัตรานอกสเปกความชื้น (Humidity)** (9.85%, เฉพาะเครื่อง) -- เป็นเครื่องวัดพารามิเตอร์เพียงตัวเดียวที่กระบวนการตั้งศูนย์เทียบความแม่นยำระบบวัดผลครั้งก่อนๆ หลงหูหลงตาไป (ใครก็ตามที่ทำไว้/ไม่ว่าจะทำไปเมื่อไหร่) 
4. **ส่วนควบคุมสัญญาณแจ้งเตือน (Alarm Console) มียอดใช้งานที่ติดศูนย์** -- อันนี้ไม่ได้เป็นที่ปัญหาในตัวระบบใดๆ, แต่เป็นประเด็นที่ว่าไม่พบผู้ใช้ในระบบปฎิบัติงาน: ค่าชี้วัดความน่าเชื่อถือ MTTA/MTTR จะเชื่อมั่นได้อย่างไรว่าได้วัดผลเสร็จสมบูรณ์จนกว่าเราจะมีหนูทดลองฝั่งผู้ใช้งานซักคนที่เข้ามาเล่นในหน้าการจัดการวงจรขั้นตอนพวก Ack/Resolve เสียก่อน
5. **กระบวนการความหมายตามขั้นลำดับ (Escalation semantics)** -- ตรวจดูแล้วพบว่าทั้งทั้งระบบแทบไม่ได้ติดตั้งไว้เลย (เหลือก็แค่รอบย้ำเตือนส่งของไปในรอบที่ `repeat_interval` จัดการแจ้งโดยตัวระบบ Alertmanager แค่นี้ก็ไม่ใช่เป็น Escalation แบบแท้จริงแล้ว) จำเป็นจะต้องมีการดีไซน์เพิ่มเข้าไป
6. **ตัว Heartbeat panel (ตัวแผงชี้วัดหัวใจสำคัญของระบบ)** ไม่ได้ถูกย้ายออกจากที่ทาง (Alarm Hygiene ตอนที่ 3) -- หน้าที่การทำงานเดิมยังอยู่ครบ, แค่ไม่ได้จับมันตั้งไว้ตรงที่ที่ตามแบบแผนสมควรแนะนำแค่นั้นเอง
7. **ความหนา (Thickness)** ไร้ข้อจำกัดหรือขอบเขตมาตรฐานอ้างอิงเลยทั่วทั้ง repo นี้ -- ดังนั้นจึงแยกประเภทจัดระดับไม่ได้ว่าสมจริงรึเปล่าถ้าไม่ได้อิงตามสักหลักการหนึ่ง
8. **ความหน่วงของ API และแดชบอร์ด** ไม่ได้รวมลงค่าวัดในโปรแกรมครั้งนี้ -- มีแค่ `tests/k6/grafana-query-stress.js` และหากต้องการก็น่าจะมีช่องทางพิเศษไว้ให้วิ่งแยกเฉพาะอีกที
9. **สถิติการใช้งานพูลของ PgBouncer** ไม่ได้อยู่ในฐานะที่เอื้อให้รับค่าข้อมูลโดยตรงในบรรยากาศสิ่งแวดล้อมเช่นนี้ -- เครื่องวัดประสิทธิภาพและค่าวินิจฉัยนี้เลยขาดช่องทางนำส่งไปโดยปริยาย, ซึ่งมันเกินกว่าจะเป็นแค่เมทริกซ์ที่ถูกปล่อยปละละเลยในการวัดผล
10. **ตัวรักษาความเสถียรของ RAM (RAM-stability-over-time)** ของฝั่ง `ims-node-red` ถูกคอยสังเกตการณ์จับตาเพียงระยะเวลาเวลา ~3 นาที เท่านั้น (มันคือลิมิตการตั้งสเกลในตัวของระบบจำลองมันเอง) -- และในระหว่างเวลาวิ่งมาราธอนที่ความอึด 2 ชั่วโมง/6 ชั่วโมง/12 ชั่วโมงนั้นต่างหากที่จะตอบคำถามได้กระจ่างว่าหน่วยความจำของระบบมันล้นทะลักเพดานมานับเป็นชั่วโมงๆ หรือไม่
