# System Trust Report

> ให้คะแนนตามเกณฑ์ 8 ประการที่ "ยากต่อการวิพากษ์วิจารณ์" ที่ตั้งไว้สำหรับแพลตฟอร์มนี้ รวบรวมเมื่อวันที่ 2026-08-14, Evidence Consolidation Pass ทุกๆ แถวอ้างอิงถึงหลักฐานจริงใน `EVIDENCE_PACK.md` -- ไม่มีการอ้างสิทธิ์ใดในที่นี้โดยไม่มีลิงก์กลับไปยังไฟล์หรือคำสั่งที่สามารถทำซ้ำได้ เป็นการรวบรวมแบบอ่านอย่างเดียว ไม่มีการแตะต้องระบบรันไทม์

## มีอะไรเปลี่ยนแปลงบ้างในรอบนี้ ที่ย้ายเกณฑ์ข้อ 6/7/8 จากช่องว่างไปเป็น PASS

- สร้าง `EVIDENCE_PACK.md` -- รวบรวมลิงก์ KPI-ต่อ-หลักฐาน ซึ่งแต่เดิมไม่เคยมีปรากฏในรูปแบบเอกสารเดียวมาก่อน (เกณฑ์ข้อ 6)
- รวบรวมข้อจำกัดที่ทราบไว้ในที่เดียว แทนที่จะกระจัดกระจายอยู่ในเอกสารการตรวจสอบแต่ละฉบับ (เกณฑ์ข้อ 7)
- สร้าง `docs/architecture/DECISION_MATRIX.md` -- ทุกแดชบอร์ดตอนนี้จะระบุการตัดสินใจทางปฏิบัติการที่แดชบอร์ดนั้นๆ มีไว้เพื่อสนับสนุน ไม่ใช่แค่บอกว่าใครเป็นเจ้าของ (เกณฑ์ข้อ 8; เรื่องเจ้าของถูกครอบคลุมโดย `OWNERSHIP.md` ไว้แล้ว)

## ข้อค้นพบที่รอบนี้เผยให้เห็น แต่ไม่ได้ถูกแก้ไขที่อื่น

- `docs/evidence/72H_SOAK_TEST_LOG.md` (ปัจจุบันคือ `72H_SOAK_TEST_LOG.INVALID-FABRICATED.md`) อ้างว่าสามารถทำ soak ผ่านแบบใสสะอาด 72 ชม./1000-VU/1.1 พันล้านแถว ทุกข้ออ้างเฉพาะเจาะจงในนั้น (ชื่อสคริปต์ ชื่อตาราง จำนวนแถว) ไม่สอดคล้องกับสิ่งใดใน codebase หรือฐานข้อมูลนี้เลย มันเคยวางอยู่ใน `docs/evidence/` เคียงข้าง `SOAK_TEST_LOG.md` ที่แท้จริงแต่ถูกทำให้โมฆะอย่างตรงไปตรงมา และอาจถูกอ้างถึงราวกับว่ามันเป็นเรื่องจริง จึงถูกกักกัน (เปลี่ยนชื่อ เพิ่มป้ายเตือน คงเนื้อหาเดิมไว้) แทนที่จะลบทิ้ง เพื่อให้ความคลาดเคลื่อนนี้ยังคงตรวจสอบได้
- `docs/evidence/DR_DRILL_3_EXECUTION.md` (ปัจจุบันคือ `DR_DRILL_3_EXECUTION.INVALID-FABRICATED.md`) อ้างว่าสามารถทำการกู้คืน (restore) แบบใสสะอาดขนาด 45GB ภายใน 12 นาทีจาก "MinIO" ในขณะที่ `DR_DRILL_3_FINDINGS.md` ของจริงระบุอย่างชัดเจนว่าการซ้อมแผนนั้น FAIL เนื่องจากบั๊กของสคีมา เช่นเดียวกับการทดสอบ soak ไฟล์ที่สร้างขึ้นมาลอยๆ นี้ถูกกักกันและปักธงไว้
- **รอบหลังแยกต่างหาก** พบสาเหตุที่แท้จริงของการยุติความพยายามทดสอบ Soak ครั้งที่ 6: เกิดจาก exception ที่ไม่ได้รับการจัดการของพูลการเชื่อมต่อ `pg` (PgBouncer `client_idle_timeout` ทำการปิดการเชื่อมต่อที่ว่างอยู่ โดยที่ทั้ง `node-red` และ `alarm-api` ไม่ได้ดักจับ error ที่เป็นผลลัพธ์) ทำให้ทั้งสองกระบวนการพัง นโยบายการรีสตาร์ทของ Docker ช่วยกู้คืนกระบวนการเหล่านั้นกลับมา — ดู `docs/architecture/specs/SPEC_PG_POOL_RESILIENCE.md` ข้อค้นพบทั้งสองมีบทเรียนร่วมกัน นั่นคือ: ระบบที่ "ยากต่อการวิพากษ์วิจารณ์" จะอยู่รอดได้โดยการตรวจสอบข้อมูลอ้างอิงแต่ละรายการเทียบกับคลังเก็บข้อมูล/ฐานข้อมูล/บันทึกระบบ (repo/database/logs) จริงๆ แทนที่จะเชื่อคำกล่าวอ้างของเอกสารก่อนหน้าหรือตัวอย่างก่อนหน้าแต่เพียงอย่างเดียว

## ข้อจำกัดของระบบ & ขอบเขตทางเทคนิค (System Constraints & Technical Boundaries)

- เกณฑ์ข้อ 5 กำลังประเมินข้อผิดพลาด pg-pool ด้านบน เวลาจริงยังคงต้องดำเนินไป และการแก้ไขปัญหานี้ขึ้นอยู่กับการนำแพตช์ไปปรับใช้ (การปรับใช้เองรอให้ยกเลิกการระงับ/freeze เสียก่อน)
- เกณฑ์ข้อ 3 ในสถานการณ์ "รีสตาร์ทระหว่างการเขียน" โดยเฉพาะ ไม่ได้รับการซ้อมแผน อยู่ใน Backlog ใน `BACKLOG_SIMULATOR_REALISM_AND_ALERT_HYGIENE.md`... อันที่จริง เอกสารสุขอนามัยการแจ้งเตือนไม่ครอบคลุมเรื่องนี้ -- นีคือช่องว่างในการซ้อมแผน DR ซึ่งติดตามที่นี่โดยตรง: **สถานะ Open ยังไม่มีผู้รับผิดชอบ (owner)**
- Debounce ในเกณฑ์ข้อ 4 ยังไม่ได้ผ่านการทดสอบโหลดกับสถานการณ์ที่มีข้อมูลล้นทะลักจริง (เช่น การบังคับให้ทุกเครื่องอยู่นอกสเปกพร้อมกัน) -- นำไปใช้และโค้ดถูกต้องแล้ว แต่ยังไม่ได้รับการทดสอบความเครียด (stress-verified)
- คะแนนความสมจริงของ Alarm (58/100) ล้าสมัยแล้วเมื่อเทียบกับการแก้ไขของเฟส D/E/F (debounce, link_basis, rare-critical) ที่ใช้ไปแล้ว ยังไม่ได้สร้างคะแนนใหม่ อยู่ใน Backlog
- CI ยังไม่ได้ตรวจสอบคอมมิตใดๆ ในเซสชันนี้ (การล็อกการเรียกเก็บเงินของบัญชี GitHub) -- อยู่นอกเหนือการควบคุมทางวิศวกรรม จึงถูกปักธงไว้ทุกครั้งที่มีการพูดถึงการคอมมิต เพื่อไม่ให้มันถูกลืมไปเงียบๆ
- ตัวข้อผิดพลาด pg-pool เอง (ดูด้านบน) ถูกกำหนดสเปกไว้แล้วแต่ยังไม่ได้แก้ไข -- ทำโดยเจตนา เนื่องจากการแก้ไขต้องอาศัยการรีสตาร์ทซึ่งถูกห้ามโดยข้อกำหนดระงับ (freeze) ในปัจจุบัน

## บทสรุป

มีหลักฐานทางวิศวกรรมที่ทำซ้ำได้จริงๆ สำหรับการอ้างสิทธิ์ทุกประการในรายงานฉบับนี้ เกณฑ์ข้อ 5 ยอมรับตามตรงว่ายังไม่บรรลุ และไม่เหมือนช่วงก่อนหน้าในรอบนี้ การปิดจบมันในตอนนี้ขึ้นอยู่กับการแก้บั๊กจริงๆ ไม่ใช่แค่การปล่อยเวลาให้ผ่านไปเพียงอย่างเดียว อีกสองข้อ (3, 4) ถูกนำไปปฏิบัติใช้แล้วแต่ยังไม่ได้ผ่านการตรวจสอบยืนยันตามวิธีที่ระบุไว้อย่างครบถ้วน ไม่มีส่วนใดในรายงานฉบับนี้ที่อ้างสิทธิ์เกินกว่าสิ่งที่เคยวัดผลไว้จริงๆ
