## Drill 3: what actually broke

1. **`postgres/init/034-ldi-statistical-mock.sql`** is a 74 MB, 242k-row mock-data bootstrap script mounted at `/docker-entrypoint-initdb.d`. On any fresh `timescaledb_data` volume, Postgres runs it automatically, before `db-migrate` ever starts. It seeds `ldi_data`/`ldi_alarm_log` with an old fixed dataset (2026-07-18 → 08-01) and a partial schema.
2. `db-migrate` then runs against a database that is **not actually empty**, and 7 of 37 pending migrations fail because they assume a different intermediate schema state than what the init-seed left behind:
   `042-spc-fleet-view.sql`, `043-ldi-data-1m-cagg.sql`, `044-ldi-data-15m-1h-caggs.sql`, `048-ldi-data-real-conversion.sql`, `050-ldi-rca-recent-window-view.sql`, `059-ldi-data-widen-double-precision.sql`, `064-materialize-spc-fleet-rca-views.sql` — all fail with variants of `"X" is not a view` / `is not a materialized view`, i.e. an object already exists in a different shape than the migration expects.
   One knock-on effect: migration 077's `CREATE TABLE IF NOT EXISTS public.ldi_alarm_lifecycle` silently skipped table creation because the init seed already had the table — but _without_ its `PRIMARY KEY (logdate, logid)` / FK, since `IF NOT EXISTS` doesn't check constraints. The table was live with no primary key at all until fixed manually (below).
3. `db-migrate` exits 1. Every service gated on `depends_on: condition: service_completed_successfully` (node-red, proxy, alarm-api) never started — full stack outage, not just a degraded drill result.
4. The drill's own restore step (`psql < snapshot.sql` into the now-partially-migrated live `ims` database) then failed almost completely: 435 errors, mostly `relation "_timescaledb_internal._hyper_N_M_chunk" does not exist`. Root cause: `pg_dump` on a hypertable dumps data through internal per-chunk tables named by TimescaleDB-assigned internal IDs. Those IDs are specific to the database instance that produced the snapshot; they don't exist in a freshly-recreated database where `db-migrate` already created its own hypertables (and therefore its own, different, internal chunk IDs) before the restore ran. Net effect: the live `ims` database was left populated with the **stale init-seed data**, not the real pre-wipe snapshot — dashboards would have shown 2-week-old data as "current."

None of this is something this session introduced. It's a latent gap that a true from-scratch rebuild had apparently never been exercised against until this drill — exactly what DR Drill 3 exists to catch.

## Root-cause fix (2026-08-13, same session, after initial recovery)

The 7-migration failure and the broken restore step were fixed at the source, not worked around:

1. **`postgres/init/034-ldi-statistical-mock.sql` deleted.** It was dead weight -- `scripts/switch-data-mode.sh`'s `mock` case never reads it; mock data comes from the live simulator, not a static seed. Removing it means `db-migrate` runs against a genuinely empty database again, matching what the migrations were actually written against. Verified: 38/38 migrations apply clean on a fresh volume with this alone.
2. **`scripts/dr-test.sh`'s `drill_full_recreate` rewritten.** Old flow: `docker compose up -d` (schema) then `psql < full_snapshot.sql` (restore) into an already-migrated database -- confirmed broken twice (restore-after-migrate: 435 errors; restore-before-migrate: 78 errors), both from the same root cause TimescaleDB's own `pg_dump` output warns about every run: a plain logical dump of a database with continuous aggregates is not reliably restorable once the target already has its own hypertables. New flow: start only `timescaledb`, run `db-migrate` alone (schema from `database/migrations/`, proven clean on empty), then restore **only** the raw `ldi_data`/`ldi_alarm_log` row data -- extracted from the snapshot's per-chunk `COPY` blocks and loaded through the parent table name via the new `scripts/dr-restore-table-data.py`, which sidesteps the internal chunk-ID mismatch entirely -- then start everything else.
3. **Found and fixed a second, independent bug while validating the above**: `docker compose up -d` before an explicit `docker compose up db-migrate` call races two `db-migrate` runs against each other (compose auto-starts it as a dependency of `node-red`/etc.). Fixed by running `db-migrate` explicitly, alone, before anything else starts.
4. **Found and fixed a third bug**: migration `048-ldi-data-real-conversion.sql` added each new continuous aggregate's refresh policy _before_ its own explicit `CALL refresh_continuous_aggregate(...)`, so a background worker could start refreshing the same CAGG the explicit call was still waiting on -- `could not refresh continuous aggregate ... due to a concurrent refresh`, non-deterministic. Fixed by reordering: refresh each CAGG before its policy exists, not after, so nothing else can be racing it. (A first attempt wrapped the `CALL` in a `BEGIN/EXCEPTION` to catch and skip the race -- made it worse: `refresh_continuous_aggregate()` refuses to run inside any subtransaction, including one an exception handler creates. Reordering, not catching, was the real fix.)
5. **Found and fixed a fourth bug**: the drill's own verdict logic trusted the first `db-migrate` exit code, but if that run fails, `docker compose up -d` retries it automatically as a dependency -- the real outcome is whatever that retry left behind. Fixed by re-checking actual final state (`bash scripts/migrate.sh`'s own idempotent pending-count, same logic the CI schema-drift gate uses) plus confirming `node-red`/`proxy`/`alarm-api` actually reached `running`, instead of trusting a possibly-stale variable.

**Verified**: `bash scripts/dr-test.sh all --confirm-destroy` run 3 times after all four fixes. 2 clean PASSes (38/38 migrations, 0 restore errors, all services healthy). 1 run hit a genuine PostgreSQL backend crash mid-migration ("crash of another server process, possibly corrupted shared memory") during migration 059 -- the single heaviest migration in the set (decompress + type-widen ALTER + drop/recreate 13 objects + recompress + 4 CAGG refreshes) -- after this session had already run 7+ consecutive full teardown/rebuild cycles in about 20 minutes. `docker system df` showed 12GB of reclaimable images and 1.6GB of reclaimable volumes at the time; pruned before the next run, which passed clean. Treated as transient local resource pressure from unusually rapid repeated testing, not a defect in the fix -- but flagged here rather than silently omitted, since it wasn't independently re-confirmed beyond "pruning correlated with it not recurring."

Not touched: `postgres/init/036-ldi-alarm-master-mock.sql` and `039-rca-alarm-view.sql` are stale duplicate copies of real migrations (036 missing 2 Critical-severity codes added later; 039 joins on a different column) that still auto-load before `db-migrate`, but `db-migrate`'s own versions are idempotent and correctly overwrite them every run -- confirmed not blocking anything, left alone rather than widening this fix's blast radius further.

## Live recovery performed (2026-08-13, this session, before the root-cause fix above)

The above left the stack down and the database wrong. Fixed manually rather than left broken:

1. `TRUNCATE ldi_data, ldi_alarm_log;` — cleared the stale init-seed data.
2. Extracted the correct rows directly from the snapshot's per-chunk `COPY` blocks (bypassing the internal-chunk-ID mismatch that broke the drill's own restore) and reloaded through the parent tables via `\copy`. Row counts after: `devices=1025, ldi_data=55556, ldi_alarm_log=1057` — exact match to the live pre-wipe snapshot.
3. Added the missing `PRIMARY KEY (logdate, logid)` and matching `FOREIGN KEY ... REFERENCES ldi_alarm_log` to `ldi_alarm_lifecycle` (table was empty at the time, safe to add) so the alarm-insert trigger's `ON CONFLICT (logdate, logid)` clause has a constraint to target. It backfilled to 1057 rows (one `OPEN` lifecycle row per alarm) automatically via the existing trigger.
4. `docker compose up -d --no-deps node-red proxy alarm-api` — force-started the services `db-migrate`'s failure had gated. All 11 services confirmed healthy; Grafana `/api/health` OK; simulator confirmed writing fresh rows again (`ldi_data` rows with `time > now() - 2min`).

**Not fixed, flagged for follow-up:** the 7 migrations themselves are still not idempotent against an init-seeded fresh database (`bash scripts/migrate.sh` on this now-recovered instance still reports `Pending: 7 Applied: 0 Failed: 7` for the same 7 files — their target objects already exist correctly via the recovery above, the migration _files_ just don't know that). A real fix means either making those 7 migrations tolerant of the init-seed's starting state, or changing `drill_full_recreate` to not run `db-migrate` against an init-seeded database at all (e.g. restore the snapshot first, before migrations, and skip migrations that the snapshot's own schema already satisfies). Both are real design decisions, not a one-line patch — deliberately not rushed through here.
