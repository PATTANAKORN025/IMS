# Historical Data Reconciliation (P1, Reliability Test Suite)

> ตรวจสอบช่องว่างของข้อมูลในอดีตที่ได้รับการยืนยันแล้วทุกจุด และดำเนินการตรวจสอบความสมบูรณ์โดยรวม เป็นการอ่านอย่างเดียว (Read-only) ไม่มีการแก้ไขคอนเทนเนอร์

## ช่องว่างที่ระบุ: `sys_metrics` 2026-08-13 ~09:45 → 2026-08-14 ~01:15

**ขอบเขตที่แน่นอน** (ไม่ใช่ขอบเขตโดยประมาณในข้อค้นพบเดิม): ตัวอย่างข้อมูลสุดท้าย `2026-08-13T09:38:54.731941Z`, ตัวอย่างแรกหลังจากนั้น `2026-08-14T01:18:00.205962Z` ความยาวของช่องว่าง: **~15 ชั่วโมง 39 นาที**

**เกิดกับทั้งระบบ ไม่ใช่แค่บางส่วน**: `ldi_data` และ `ldi_alarm_log` แสดงรูปแบบที่เหมือนกันทุกประการ --

| ตาราง | ข้อมูลสุดท้ายก่อนช่องว่าง | ข้อมูลแรกหลังช่องว่าง |
| --------------- | --------------- | --------------- |
| `sys_metrics`   | 09:38:54.73     | 01:18:00.21     |
| `ldi_data`      | 09:38:53.45     | 01:14:05.17     |
| `ldi_alarm_log` | 09:38:33.65     | 01:14:06.86     |

ทั้ง 3 ตารางที่เป็นอิสระต่อกันหยุดทำงานโดยมีระยะเวลาห่างกันไม่เกิน 21 วินาที และกลับมาทำงานต่อโดยมีระยะเวลาห่างกันไม่เกิน ~4 นาที นี่เป็นหลักฐานที่หนักแน่นว่ามีเหตุการณ์เดียวที่ส่งผลกระทบต่อทั้งระบบพร้อมกัน (เช่น การเปิด-ปิดเครื่องโฮสต์, การรัน `docker compose down`/`up` แบบเต็มรูปแบบ หรือที่คล้ายกัน) ไม่ใช่ความล้มเหลวที่เกิดขึ้นแยกกันในแต่ละตารางหรือแต่ละบริการ

**สาเหตุที่แท้จริง: ไม่ทราบ (UNKNOWN)** ตรวจสอบ `public.container_restart_audit` แล้ว (ถูกสร้างขึ้นในภายหลังเพื่อใช้วินิจฉัยเหตุการณ์เช่นนี้ทางนิติวิทยาศาสตร์โดยเฉพาะ) -- บันทึกแรกสุดของระบบนี้คือ `2026-08-14T04:24:25Z` ซึ่งเป็นเวลา**หลังจาก**ช่องว่างนี้สิ้นสุดลง กลไกนี้ยังไม่มีอยู่เมื่อเหตุการณ์นี้เกิดขึ้น ดังนั้นจึงไม่มีหลักฐานเหตุการณ์การรีสตาร์ทโดยตรง ไม่มีบันทึกเวลาเปิดเครื่องโฮสต์ (host-boot-time) ที่เข้าถึงได้สำหรับวันที่ดังกล่าว และไม่มีสิ่งอื่นใดในสคีมา (schema) ปัจจุบันที่บันทึกเหตุการณ์ระดับโฮสต์ย้อนหลังไปไกลขนาดนั้น ตามคำสั่งที่ชัดเจนว่าห้ามคิดค้นคำอธิบายขึ้นเอง: **สาเหตุของช่องว่างนี้คือ ไม่ทราบ (UNKNOWN)** ไม่ใช่ "น่าจะเป็นการรีสตาร์ท" หรือการคาดเดาอื่น ๆ สิ่งที่ได้รับการยืนยัน ไม่ใช่การคาดเดาคือ: มันเป็นการหยุดทำงานจริงทั้งระบบพร้อมกัน ซึ่งกินเวลา ~15 ชั่วโมง 39 นาที ไม่ใช่การสูญหายของข้อมูลที่แฝงตัวมาในรูปแบบช่องว่าง (ไม่พบแถวที่เสียหายหรือมีข้อมูลบางส่วนอยู่รอบๆ) และไม่ใช่ผลจากบั๊กของตารางใดตารางหนึ่ง

## ช่องว่างอื่น ๆ ที่ตรวจสอบในเซสชันนี้ (เพื่อความครบถ้วน ไม่ได้ตรวจสอบใหม่ที่นี่)

- **2026-08-14 ~09:45 → 2026-08-15 ~01:15** (`sys_metrics`, พบระหว่างการตรวจสอบแบบอ่านอย่างเดียวก่อนหน้านี้): หาสาเหตุที่แท้จริงพบแล้วพร้อมหลักฐานโดยตรงในรายงาน `docs/evidence/SOAK_TEST_LOG.md` การปิดงานความพยายามที่ 7 -- ยืนยันเวลาโฮสต์ `LastBootUpTime` ผ่าน `wmic`, ตรงกับเวลา `StartedAt` ของคอนเทนเนอร์ภายในเวลาไม่เกิน 2 วินาที, การทำงานตามกำหนดเวลา `IMS-SoakTest` แสดงค่า `NumberOfMissedRuns` ยืนยันว่าตัวกลไกการรวบรวมข้อมูลเองหยุดทำงาน เหตุการณ์นี้มีสาเหตุที่แท้จริงและมีหลักฐาน (เหตุการณ์เกี่ยวกับพลังงานของโฮสต์); ไม่ใช่ UNKNOWN

## บทสรุปการประนีประนอมข้อมูล (Reconciliation summary)

มีช่องว่างของข้อมูลในอดีตจริงสองจุดใน `sys_metrics` (และสำหรับอันที่เก่ากว่านั้น ก็มีใน `ldi_data`/`ldi_alarm_log` เช่นกัน) อันหนึ่งได้รับการยืนยันสาเหตุแล้ว (โฮสต์รีบูต 2026-08-14→15 มีหลักฐาน) อีกอันหนึ่งไม่มีสาเหตุที่ชัดเจนและถูกทำเครื่องหมายเป็น ไม่ทราบ (UNKNOWN) (2026-08-13→14) เนื่องจากเครื่องมือทางนิติวิทยาศาสตร์ที่ใช้ในการระบุสาเหตุยังไม่ถูกสร้างขึ้นในขณะนั้น ช่องว่างทั้งสองจุดเกิดขึ้นก่อนการแก้ไขทั้งหมดในรอบความน่าเชื่อถือนี้ -- ช่องว่างเหล่านี้ไม่ใช่ความเสี่ยงที่กำลังดำเนินอยู่จากโค้ดที่ติดตั้งในปัจจุบัน การตรวจสอบฟิลด์สำคัญเพื่อหาค่า NULL: สะอาด ไม่มีเลย (0) ใน 5 ฟิลด์ที่ตรวจสอบ การรันตรวจสอบการจับคู่อุปกรณ์แบบสดใหม่ (แทนที่จะอ้างอิงสถานะสดจากแดชบอร์ดที่มีอยู่) ยังคงเป็นเพียงรายการเดียวที่เปิดอยู่จากรอบนี้
