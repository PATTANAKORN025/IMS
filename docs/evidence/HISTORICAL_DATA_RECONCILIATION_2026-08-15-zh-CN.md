# Historical Data Reconciliation (P1, Reliability Test Suite)

> 调查每个已确认的历史数据差距，并进行全面的完整性扫描。只读操作，不修改容器。

## 命名差距：`sys_metrics` 2026-08-13 ~09:45 → 2026-08-14 ~01:15

**精确边界**（非初始发现中的近似值）：最后一个样本 `2026-08-13T09:38:54.731941Z`，之后的第一个样本 `2026-08-14T01:18:00.205962Z`。差距时长：**~15h39m**。

**全栈性，非局部性**：`ldi_data` 和 `ldi_alarm_log` 显示出完全相同的模式 ——

| 表           | 差距前最后记录 | 差距后第一记录 |
| --------------- | --------------- | --------------- |
| `sys_metrics`   | 09:38:54.73     | 01:18:00.21     |
| `ldi_data`      | 09:38:53.45     | 01:14:05.17     |
| `ldi_alarm_log` | 09:38:33.65     | 01:14:06.86     |

所有 3 个独立的表在彼此相差 21 秒内停止，并在彼此相差约 4 分钟内恢复。这有力地证明了是单一事件同时影响了整个堆栈（如主机电源循环，或者完整的 `docker compose down`/`up` 等），而不是单个表或单个服务的独立故障。

**根本原因：未知 (UNKNOWN)**。检查了 `public.container_restart_audit`（在本项目历史后期专门构建，用于对此类事件进行诊断），其最早的记录是 `2026-08-14T04:24:25Z`，在此时段差距**结束**之后。当事件发生时，该机制还不存在，因此没有直接的重启事件证据，没有该日期的主机启动时间日志，并且当前模式中也没有其他记录主机级别事件的信息。根据“不要臆造解释”的明确指示：**该差距的原因是未知 (UNKNOWN)**，而不是“可能是重启”或任何其他猜测。确认的（而非猜测的）是：这是一次真实的、全栈的、持续约 15h39m 的同时中断，而不是伪装成间隙的数据丢失（没有发现包含它的部分/损坏的行），也不是单一表错误的产物。

## 对账摘要

在 `sys_metrics` 中存在两个真实的历史差距（对于较旧的一个，也存在于 `ldi_data`/`ldi_alarm_log` 中）。一个已确认原因（主机重启，2026-08-14→15，有证据）。另一个没有明确原因，标记为 UNKNOWN（2026-08-13→14），因为当时尚未具备确定其原因所需的工具。这两个差距都早于本次可靠性测试的所有修复程序 —— 两个差距都不代表当前部署代码存在持续风险。关键字段 NULL 扫描：干净，5 个被检查的字段均为 0。新鲜的机器映射间隙重跑（相较于参考现有仪表盘的实时状态）是本次测试中唯一未完成的项目。
