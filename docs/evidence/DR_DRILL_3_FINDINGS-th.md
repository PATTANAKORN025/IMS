## การซ้อมที่ 3: สิ่งที่พังจริงๆ

1. **`postgres/init/034-ldi-statistical-mock.sql`** เป็นสคริปต์ตั้งต้นที่มีขนาด 74 MB, มีข้อมูลจำลอง 242k แถว เชื่อมต่อไปที่ `/docker-entrypoint-initdb.d` เมื่อสร้างโวลุ่ม `timescaledb_data` ใหม่ Postgres จะรันสคริปต์นี้อัตโนมัติก่อนที่ `db-migrate` จะเริ่มทำงาน มันจะใส่ชุดข้อมูลเก่าที่กำหนดไว้ (2026-07-18 → 08-01) และสกีมาบางส่วนลงใน `ldi_data`/`ldi_alarm_log`
2. หลังจากนั้น `db-migrate` จะรันบนฐานข้อมูลที่ **ไม่ได้ว่างเปล่าจริงๆ** และการไมเกรต 7 จาก 37 รายการที่รอดำเนินการจะล้มเหลว เนื่องจากพวกมันสันนิษฐานว่าสถานะของสกีมาระหว่างทางแตกต่างจากสิ่งที่ข้อมูลตั้งต้นที่ทิ้งไว้:
   `042-spc-fleet-view.sql`, `043-ldi-data-1m-cagg.sql`, `044-ldi-data-15m-1h-caggs.sql`, `048-ldi-data-real-conversion.sql`, `050-ldi-rca-recent-window-view.sql`, `059-ldi-data-widen-double-precision.sql`, `064-materialize-spc-fleet-rca-views.sql` — ทั้งหมดล้มเหลวด้วยข้อความคลาดเคลื่อนต่างๆ เช่น `"X" is not a view` / `is not a materialized view` ซึ่งหมายความว่าอ็อบเจ็กต์มีอยู่แล้วในรูปแบบที่ต่างจากการไมเกรตคาดไว้
   ผลกระทบต่อเนื่องหนึ่งอย่าง: การสร้างตาราง `CREATE TABLE IF NOT EXISTS public.ldi_alarm_lifecycle` ของการไมเกรตรายการที่ 077 จะถูกข้ามไปอย่างเงียบๆ เพราะข้อมูลตั้งต้นมีตารางนี้อยู่แล้ว — แต่ _ไม่มี_ `PRIMARY KEY (logdate, logid)` / FK ของมัน เนื่องจาก `IF NOT EXISTS` จะไม่ตรวจสอบข้อจำกัด (constraints) ตารางนั้นจึงใช้งานอยู่โดยไม่มี primary key เลยจนกระทั่งได้รับการแก้ไขด้วยตนเอง (ดูด้านล่าง)
3. `db-migrate` ออกด้วยรหัส 1 (exits 1) ทุกบริการที่รอเงื่อนไข `depends_on: condition: service_completed_successfully` (node-red, proxy, alarm-api) จะไม่เริ่มทำงานเลย — ระบบล่มแบบ full stack ไม่ใช่แค่ผลการซ้อมที่ลดประสิทธิภาพลง
4. จากนั้น ขั้นตอนการกู้คืน (restore step) ของการซ้อม (`psql < snapshot.sql` ไปยังฐานข้อมูล `ims` ที่เพิ่งถูกไมเกรตมาบางส่วน) จะล้มเหลวเกือบทั้งหมด: พบข้อผิดพลาด 435 รายการ ส่วนใหญ่คือ `relation "_timescaledb_internal._hyper_N_M_chunk" does not exist` สาเหตุที่แท้จริง: การทำ `pg_dump` บน hypertable จะส่งออกข้อมูลผ่านตารางภายในแต่ละ chunk ที่มีชื่อตาม internal ID ที่กำหนดโดย TimescaleDB ID เหล่านั้นเฉพาะเจาะจงกับอินสแตนซ์ของฐานข้อมูลที่สร้างสแนปชอตนั้นขึ้นมา; พวกมันไม่มีอยู่ในฐานข้อมูลที่สร้างขึ้นมาใหม่ (freshly-recreated) ซึ่ง `db-migrate` ได้สร้าง hypertables ของตัวเอง (และแน่นอนว่า chunk ID ภายในจะแตกต่างกันไป) ก่อนที่จะมีการทำ restore ผลลัพธ์คือ: ฐานข้อมูล `ims` ที่ทำงานอยู่จะเต็มไปด้วย **ข้อมูลตั้งต้นจำลองที่เก่า (stale init-seed data)** ไม่ใช่ข้อมูลของจริงก่อนการถูกล้าง — แดชบอร์ดจะแสดงข้อมูลเมื่อ 2 สัปดาห์ก่อนเป็น "ข้อมูลปัจจุบัน"

ไม่มีสิ่งใดในนี้ที่เกิดจากเซสชันปัจจุบัน มันเป็นช่องโหว่แฝงที่ระบบน่าจะไม่เคยถูกทดสอบสร้างใหม่ตั้งแต่ศูนย์ (from-scratch rebuild) มาก่อนจนกระทั่งการซ้อมครั้งนี้ — ซึ่งนี่คือเป้าหมายของการมี DR Drill 3 เพื่อค้นหาปัญหาเหล่านี้นั่นเอง

2. แยกแถวที่ถูกต้องออกจากบล็อก `COPY` ราย chunk ของสแนปชอต (เพื่อข้าม chunk-ID mismatch ซึ่งทำให้ขั้นตอนกู้คืนของดริลพัง) และโหลดกลับผ่านตารางหลักผ่านคำสั่ง `\copy` จำนวนแถวหลังทำ: `devices=1025, ldi_data=55556, ldi_alarm_log=1057` — ตรงกันแบบ 100% กับสแนปชอตจริงก่อนการล้างข้อมูล
3. เพิ่ม `PRIMARY KEY (logdate, logid)` ที่ขาดหายและทำการจับคู่ `FOREIGN KEY ... REFERENCES ldi_alarm_log` ลงใน `ldi_alarm_lifecycle` (ตารางยังว่างในตอนนั้น ปลอดภัยที่จะเพิ่ม) ดังนั้นอนุประโยค `ON CONFLICT (logdate, logid)` ในตัวสั่งทริกเกอร์แทรกสัญญาณแจ้งเตือนจะมีข้อจำกัดที่มุ่งเป้า มันย้อนหลังกลับไปมี 1057 แถวโดยอัตโนมัติ (เป็นแถว lifecycle 1 รหัสสถานะ `OPEN` ต่อ 1 สัญญาณเตือน) ผ่านทริกเกอร์ที่มีอยู่
4. `docker compose up -d --no-deps node-red proxy alarm-api` — เริ่มการทำงานอย่างบังคับสำหรับบริการที่ถูกพังด้วยความล้มเหลวของ `db-migrate` บริการทั้งหมด 11 รายการ ยืนยันว่าปกติ; Grafana `/api/health` OK; ตัวจำลองยืนยันว่าเริ่มบันทึกข้อมูลแถวใหม่ (fresh rows) ได้อีกครั้ง (แถว `ldi_data` ที่มีเวลา `time > now() - 2min`)

**ยังไม่ได้รับการแก้ไข ปักหมุดสำหรับการติดตามต่อ:** ตัว 7 รายการไมเกรตนั้นก็ยังไม่ใช่ idempotent เมื่อเจอกับฐานข้อมูลที่เพิ่งตั้งต้นใหม่แบบใช้ชุดข้อมูลซีด (`bash scripts/migrate.sh` บนอินสแตนซ์ที่กู้คืนมาแล้วนี้ยังคงรายงานว่า `Pending: 7 Applied: 0 Failed: 7` สำหรับ 7 ไฟล์ดังกล่าว — อ็อบเจกต์เป้าหมายของไฟล์เหล่านี้ก็มีอยู่แล้วจากการกู้คืนด้านบน เพียงแต่ตัว _ไฟล์_ ไมเกรตไม่รับรู้) การแก้ไขอย่างแท้จริงคือการทำให้การไมเกรต 7 รายการนี้รับได้กับสถานะเริ่มต้นของฐานข้อมูลที่ถูกจัดมา หรือต้องเปลี่ยนให้ `drill_full_recreate` ไม่ไปรัน `db-migrate` กับฐานข้อมูลที่ใส่ซีดเอาไว้ (เช่น กู้คืนสแนปชอตก่อนที่จะมีการรันไมเกรต และข้ามการไมเกรตที่สกีมาบนสแนปชอตได้ทำไปแล้ว) ทั้งสองทางล้วนเป็นการตัดสินใจในระดับดีไซน์ ไม่ใช่แค่ทำไปแบบบรรทัดเดียวเสร็จ — จึงตั้งใจไม่รีบทำในตอนนี้

## ข้อค้นพบแยกต่างหาก: CI ไม่ได้ทำงาน

ระหว่างตรวจสอบสิ่งนี้ พบว่า GitHub Actions ขัดข้องล้มเหลวใน **ทุกๆ การพุชของเซสชันนี้** (`417199b`, `da6bdee`, `f9bed7f`, และก่อนหน้า) — ซึ่งไม่เกี่ยวกับปัญหาของโค้ด งานทุกชิ้นล้มเหลวในเวลา ~2 วินาที โดยยังไม่ได้เอ็กซิคิวต์สักสเต็ปเดียว:

> "The job was not started because your account is locked due to a billing issue."

หมายความว่า **ไม่มีคอมมิตใดในเซสชันนี้ที่ถูกตรวจสอบความถูกต้องผ่าน CI เลย** รวมถึงคอมมิต P0 documentation-reconciliation ด้วย สิ่งนี้เป็นปัญหาที่บัญชี/การเรียกเก็บเงินในฝั่งของ GitHub อยู่นอกเหนือความสามารถของเซสชันนี้ในการแก้ไข — จำเป็นต้องมีความสนใจอย่างตรงประเด็นไปที่บัญชี GitHub โดยตรง
