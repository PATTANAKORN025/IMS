# IMS Grafana Design System

> [!IMPORTANT]
> สิ่งนี้ทำให้มั่นใจได้ว่าแดชบอร์ด IMS ทั้งหมด (NOC Overview, Engineering Drill-Down, Capacity Planning และตั้งแต่ระยะที่ 2 เป็นต้นไป — LDI Manufacturing, LDI Engineering Analytics & SPC, LDI Machine Snapshot, LDI Operator Andon Board, LDI Data Readiness) เป็นไปตามมาตรฐานเดียวกัน แก้ไขที่นี่ในที่เดียวเพื่อป้องกันความคลาดเคลื่อนข้ามไฟล์ เพื่อให้มั่นใจว่าระบบจะปรากฏเป็นชุดเดียวกันทันทีเมื่อเปลี่ยนหน้า
>
> เอกสารนี้เป็น **ข้อตกลง** ไม่ใช่เพียงแนวทางปฏิบัติ — ทุกแผง (panel) ใหม่จะต้องปฏิบัติตามกฎเหล่านี้ก่อนที่จะถูกรวม (merge)

---

## 1. Design Principles

1. **Function first, beauty follows** — ความสวยงามที่ไม่ช่วยเร่งความเข้าใจในข้อมูลถือเป็นองค์ประกอบตกแต่งที่ต้องถูกกำจัดออก
2. **Color always has a single meaning** (ความหมายตามบริบท (Semantic), ไม่ใช่การตกแต่ง) — ดูกฎข้อ 3 ด้านล่าง
3. **3-Second Rule** — ใครก็ตามที่เดินผ่านหน้าจอแสดงผล NOC จะต้องสามารถบอกได้ภายใน 3 วินาทีว่า "ตอนนี้ทุกอย่างปกติหรือไม่" โดยไม่ต้องอ่านป้ายกำกับ
4. **Consistency > Novelty** — แผง (Panel) ประเภทเดียวกันต้องมีลักษณะที่เหมือนกันทุกที่ที่ปรากฏ (ผ่าน Library Panels)
5. **Progressive disclosure** — NOC ตอบคำถาม "เราต้องโทรหาใครไหม?", Engineering ตอบคำถาม "ทำไม?", Capacity ตอบคำถาม "จะเกิดอะไรขึ้นต่อไป?" ห้ามผสมระดับความละเอียดของข้อมูลในหน้าเดียวกัน

## 2. Color System

### 2.1 Semantic Palette — ONE table, every dashboard (merged 2026-08-08)

จนถึงปัจจุบัน repository นี้ใช้ชุดสีแยกกัน **สอง** ชุด: §2.1 สำหรับ NOC/Engineering/Capacity
และ "LDI Kiosk" แตกต่างออกไปสำหรับแดชบอร์ด LDI 5 อัน ในทางปฏิบัติทั้งสองชุดได้
เปลี่ยนไปใช้ค่า hex **เดียวกัน** เกือบทุกที่แล้ว (ตรวจสอบโดยการนับ
ค่าตัวอักษร `#RRGGBB` ทุกตัวในไฟล์แดชบอร์ดทั้ง 10 ไฟล์ก่อนเขียนส่วนนี้) —
การแยกตารางสองตารางกลายเป็นเพียงเรื่องแต่งในเอกสาร ไม่ใช่ขอบเขตการออกแบบจริง
รวมกันเป็นตารางเดียว นำไปใช้กับ **แดชบอร์ดทั้ง 15 อัน** รวมถึงชุด LDI kiosk
ไม่มีแดชบอร์ดใดได้รับการยกเว้น

| Token            | Hex Code  | Meaning                             | Used For                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| ---------------- | --------- | ----------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ok`             | `#22C55E` | Healthy / Normal                    | ค่าที่สุขภาพดี (Healthy), กำลังทำงาน, PASS, ลิมิตระดับ Capable+ — หรือการตัดสินที่บ่งบอกว่า "ทุกอย่างปกติดี"                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| `warning`        | `#F59E0B` | Monitor / Non-urgent                | IDLE, Marginal, ลิมิตการเตือน (warning thresholds)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| `critical`       | `#EF4444` | Danger / Immediate action required  | OUT OF SPEC, ลิมิตวิกฤต (critical thresholds), สถานะข้อผิดพลาด                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| `info`           | `#00F2FE` | General data / Non-verdict          | ตัวเลข KPI ธรรมดา, ป้ายชื่อเครื่องจักร, สถิติที่ไม่มีการแจ้งเตือน                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| `accent`         | `#3B82F6` | Highlight / Active UI elements      | ไฮไลต์การนำทาง, องค์ประกอบที่โต้ตอบได้                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| `no_data`        | `#64748B` | Specifically NO_DATA                | ช่องว่างที่แท้จริงในการรายงาน — เป็น _ความหมายที่แตกต่าง_ จาก `critical` ("ยืนยันว่าแย่") "เราไม่รู้" ≠ "มีบางอย่างผิดปกติ" ทุกแผงประเภท stat/gauge/bargauge ต้องมีการจับคู่สีโดยใช้ `type: "special", options.match: "null+nan"` เข้ากับสีนี้อย่างชัดเจน (หรือสำหรับแผงที่แปลงแถวที่ไม่มีข้อมูลให้เป็นค่าพิเศษใน SQL, ให้จับคู่ค่าที่ตรงกันกับข้อความ `NO_DATA`) — Grafana จะไม่ถอยกลับไปใช้สีที่เป็นกลางด้วยตัวเอง ข้อความ `noValue` จะต้องเป็นสตริง `NO_DATA` แบบตรงตัวทุกที่ (ห้ามใช้ `N/A`/`-`/หรือ "No data" ที่เป็นค่าเริ่มต้นของ Grafana) ยกเว้นในกรณีที่ค่า fallback ของแผงนั้นเป็นค่านับจำนวนธุรกิจที่เป็นศูนย์ (zero-count) หรือมีป้ายกำกับความหมายเฉพาะอยู่แล้ว (เช่น `AWAITING TELEMETRY` ของ NOC) |
| `forecast`       | `#4A5568` | Forecast / Regression (dashed line) | การพยากรณ์, การถดถอย, การฉายภาพแนวโน้ม — ต้องเป็นเส้นประเท่านั้น                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| `severity-minor` | `#EAB308` | 4th alarm-severity tier             | ระดับความรุนแรง ISA-18.2 "Minor" โดยเฉพาะ แตกต่างจาก `warning`/Major — ทั้งสองเป็นเฉดสีที่จงใจให้แตกต่างกันเพื่อให้สเกลความรุนแรง 4 ระดับ (Critical/Major/Minor/Warning) สามารถแยกแยะได้ด้วยสายตา ไม่ได้เป็นส่วนหนึ่งของสีหลัก 6 สี จะใช้เฉพาะในการจับคู่ค่าระดับความรุนแรงของการเตือนเท่านั้น                                                                                                                                                                                                                                                                                                                                                                                                                  |

**Strict Rules:**

- **ห้าม** ใช้ชุดสีเริ่มต้นของ Grafana — ให้ใช้เฉพาะโทเค็นในตารางนี้เท่านั้นเพื่อสื่อสารสถานะ
- **ห้าม** ผูกสีคงที่กับชื่อเครื่องจักร/ซีรีส์ที่ระบุเจาะจง ยกเว้นในกรณีเดียว: เครื่องจักรทางกายภาพถาวรในโรงงานที่ต้องถูกแยกแยะด้วยสีคงที่ — การจับคู่จะต้องประกาศใน §8
- สีแดง (`#EF4444`) ต้อง **เสมอ** หมายถึงวิกฤต (critical) — ห้ามใช้สีแดงเป็นเพียงสีของซีรีส์ เนื่องจากจะขัดแย้งกับความหมายของการแจ้งเตือน
- เส้นอ้างอิงพยากรณ์/การถดถอย/ลิมิตจะต้องใช้เส้นประสี `#4A5568` เสมอ ไม่ใช้สีสว่างที่ไปแข่งกับข้อมูลจริง
- สีตกแต่ง (การแยกความแตกต่างของซีรีส์กราฟสำหรับเส้นที่ไม่มีความหมายด้านสถานะ, พื้นหลัง, เส้นขอบ) ได้รับการยกเว้นจากตารางนี้ — แดชบอร์ดไม่สามารถสร้างจากสีที่อิ่มตัวเพียง 6 สีได้ สีคือการ "ตกแต่ง" ก็ต่อเมื่อมันไม่เคยใช้สื่อสาร OK/warning/critical/no-data สำหรับอะไรเลย; หากไม่แน่ใจ ถือว่าเป็นสี semantic
- **Enforcement:** `tests/lint/dashboard-linter.js` (Check 15) ตรวจสอบความถูกต้องของทุก `thresholds.steps[].color` และ `mappings[].options.color` ใน `monitoring/grafana/dashboards/*.json` เทียบกับค่า hex ในตารางนี้ — กำหนดขอบเขตเฉพาะตำแหน่งโครงสร้างสองแห่งนั้น เพราะที่นั่น สีจะมีความหมาย _เสมอ_ แตกต่างจาก `fixedColor` เปล่า ๆ ซึ่งสามารถใช้เพื่อตกแต่งได้อย่างถูกต้อง (การแยกความแตกต่างของซีรีส์) นี่คือกลไก "ส่วนกลาง" ที่แท้จริง — `APPROVED_TOKENS` ในไฟล์นั้นถูกสร้างขึ้นจากตารางนี้; หากคุณเพิ่มโทเค็นที่นี่ ให้เพิ่มที่นั่นด้วย

### 2.1b Accessibility — WCAG AA contrast (audited 2026-08-08)

Stat/Gauge ของ Grafana ที่ตั้งค่า `colorMode: "background"` จะเรนเดอร์ข้อความค่า
เป็นสี **ขาว** เสมอ ไม่ว่าความสว่างจริงของพื้นหลังจะเป็นอย่างไร — พิสูจน์จากการทดลองจริง
ไม่ใช่จากการสันนิษฐานจากเอกสารของ Grafana (ไม่มีสวิตช์ปรับคอนทราสต์อัตโนมัติให้เป็นสีดำ
สำหรับพื้นหลังสีอ่อนในเวอร์ชัน 13.1.1) คำนวณอัตราส่วนคอนทราสต์ของข้อความสีขาว
สำหรับทุกโทเค็นใน §2.1 เทียบกับพื้นหลังสีทึบ:

| Token            | Hex       | White-text ratio | AA large (≥3:1) | AA normal (≥4.5:1) |
| ---------------- | --------- | ---------------- | --------------- | ------------------ |
| `ok`             | `#22C55E` | 2.28             |                 |                    |
| `warning`        | `#F59E0B` | 2.15             |                 |                    |
| `critical`       | `#EF4444` | 3.76             |                 |                    |
| `info`           | `#00F2FE` | 1.39             |                 |                    |
| `accent`         | `#3B82F6` | 3.68             |                 |                    |
| `no_data`        | `#64748B` | 4.76             |                 |                    |
| `severity-minor` | `#EAB308` | 1.92             |                 |                    |

**Fix applied, not just documented:** ทุกแผง stat/gauge/bargauge ที่ใช้
`colorMode: "background"` (31 แผง) ถูกเปลี่ยนเป็น `colorMode: "value"` —
สีโทเค็นเหมือนเดิม ตอนนี้เป็นข้อความหนาขนาดใหญ่บนพื้นหลังแดชบอร์ดสีเข้ม
แทนที่จะเป็นสีทึบอยู่ด้านหลังข้อความสีขาว ในฐานะ _ข้อความ_ เทียบกับพื้นหลังแผงสีเข้ม
(ซึ่งก็คืออัตราส่วนเดียวกันที่ถูกสลับ) โทเค็นทุกตัวผ่านเกณฑ์ AA-large และทุกตัว
ยกเว้น `no_data` ก็ผ่านเกณฑ์ AA-normal ด้วยเช่นกัน (`no_data` มักถูกใช้ใน
ขนาดข้อความสถิติใหญ่ ๆ ที่ระบบนี้ใช้ ดังนั้น AA-large จึงเป็นเกณฑ์ที่นำมาพิจารณา)
สิ่งนี้ยังมีประโยชน์เพิ่มเติม: มันช่วยตอกย้ำด้วยสายตาให้ชัดเจนถึงการแบ่งแยกใน §2.1 ระหว่าง
`ok`/`warning`/`critical` ("นี่คือคำตัดสิน") กับ `info` ("การอ่านค่าที่เป็นกลาง ไม่ใช่คำตัดสิน")
— คำตัดสินเป็นกล่องสีทึบ การอ่านค่าที่เป็นกลางเป็นข้อความสีบนกล่องสีเข้ม —
แทนที่จะมีลักษณะเหมือนกันทั้งหมดและแยกแยะได้เฉพาะจากสีเฉพาะของกล่องสีทึบเท่านั้น

**One deliberate exception:** ไฟสถานะแต่ละเครื่องของบอร์ด Andon
(`monitoring/grafana/dashboards/manufacturing/ims-ldi-operator-andon.json`, แผง
`1000`) ยังคงใช้ `colorMode: "background"` หน้าที่ของมันคือ _การรับรู้_ สี
จากระยะ 3-5 เมตร ไม่ใช่ _การอ่าน_ ข้อความ — บล็อกสีทึบสามารถแยกแยะ
ด้วยการเหลือบมองจากฝั่งตรงข้ามโรงงานได้น่าเชื่อถือกว่าข้อความที่มีสี
ในขนาดแผงใด ๆ ที่ยังคงใส่ไทล์ได้ 10 ไทล์ต่อกันบนหน้าจอ kiosk
ซึ่งตรงกับวิธีการทำงานของไฟ Andon อุตสาหกรรมจริง ๆ เมตริกคอนทราสต์ข้อความของ WCAG ไม่ได้จำลอง
ลักษณะของ "บล็อกนี้เป็นสีแดงหรือสีเขียว" การนำมาประยุกต์ใช้ที่นี่จึงเท่ากับทิ้ง
ความต้องการในการเข้าถึงที่แท้จริง (ความสามารถในการมองผ่าน) ไปเพื่อเมตริกที่ไม่เหมาะกับกรณีใช้งาน

**Enforcement:** `tests/lint/dashboard-linter.js` (Check 17) เตือนเกี่ยวกับแผง
stat/gauge/bargauge ใด ๆ ที่ใช้ `colorMode: "background"` ภายนอก
รายการข้อยกเว้นต่อไฟล์ เพื่อไม่ให้เกิดการถดถอยแบบเงียบ ๆ เมื่อมีการเพิ่มแผงใหม่ ๆ

| ------------------ | ------- | -------- | ------------------------------------------------ |

## 3. Typography & Number Formatting

| Element                                | Rule                                                                                                                                                               |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Panel title                            | สั้น ≤ 4 คำ, ตัวพิมพ์ใหญ่แต่ละคำ (Title Case), ไม่ต้องรวมหน่วยในชื่อ (หน่วยควรอยู่ในแกน/คำอธิบาย).                                                                 |
| Panel description                      | ต้องใส่ให้ทุกแผงเสมอ เพื่ออธิบายว่า "สิ่งนี้คืออะไร + คำนวณอย่างไร", แสดงผลเมื่อเอาเมาส์ไปชี้ (ไอคอน ⓘ).                                                           |
| Stat value font size (NOC / kiosk row) | ≥ 56px สำหรับแถวบนสุดของ KPI บน NOC Overview และ Andon Board (เพิ่มจากเดิม 32px — เพื่อให้อ่านจากระยะไกลบนจอ NOC/kiosk ขนาดใหญ่ได้), จับคู่กับ `titleSize` ≥ 16px. |
| Stat value font size (Others)          | ≥ 32px สำหรับ KPI ทั่วไป.                                                                                                                                          |
| Table `cellHeight` (NOC / kiosk)       | ใช้ค่า `lg` เสมอสำหรับตารางหลักใน NOC Overview และ Andon Board — ค่าเริ่มต้น `sm` เล็กเกินกว่าจะอ่านจากระยะไกล.                                                    |
| Unit                                   | กำหนดหน่วยในทุกฟิลด์เสมอ, ห้ามปล่อยเป็นตัวเลขเปล่าๆ (`%`, `°C`, `GB`, `Mbps`).                                                                                     |
| Decimal                                | ทศนิยม 1 ตำแหน่งเพียงพอสำหรับ % และอุณหภูมิ, 0 ตำแหน่งสำหรับการนับจำนวน.                                                                                           |
| Time                                   | ใช้ `dateTimeFromNow` สำหรับ "พบครั้งล่าสุด" (เช่น "12s ago"), เวลาสัมบูรณ์สงวนไว้ใช้ใน Tooltip เท่านั้น.                                                          |
| Sentinel values                        | ค่าพิเศษ (เช่น 9999 = no growth) ต้องมีการจับคู่ข้อความเสนอ, อย่าแสดงเป็นตัวเลขเปล่าที่ดูคล้ายข้อผิดพลาด.                                                          |

- **Kiosk no-scroll ceiling (2026-08-08):** แดชบอร์ด 3 อันคือบอร์ดสำหรับมอง/คีออสก์ตามหลักการข้อ 5 ใน §1 ("progressive disclosure" — NOC และ Easy Overview จะตอบคำถาม "ทุกอย่างโอเคไหม" Andon คือหน้าจอติดผนังบนพื้นโรงงาน) มีข้อจำกัดความสูงไว้ที่ 20 grid-unit เพดานนี้ระบุอยู่ใน `MAX_HEIGHT` ของ `tests/lint/dashboard-linter.js` และถูกบังคับให้เป็น Error (ไม่ใช่คำเตือน) ทั้ง 3 บอร์ดใช้รูปแบบเดียวกัน: เฉพาะแถวเดียวที่เกี่ยวข้องกับการตัดสินใจมากที่สุดเท่านั้นที่จะยังคงขยายออก (แถบ KPI + ไทล์เครื่องจักร ของ Andon, รายการแจ้งเตือนของ NOC, แถบ KPI ของ Easy Overview) ส่วนอื่น ๆ ทั้งหมดจะเป็นแถวที่ถูกย่อไว้ โดยที่เนื้อหายังอยู่ครบ เพียงแค่คลิกก็เปิดดูได้ ส่วน Engineering/Capacity/Machine-Snapshot/Manufacturing เป็นแดชบอร์ดระดับลึกเชิงลึกจงใจตามหลักการเดียวกัน และ **ไม่มี** ขีดจำกัดความสูงใน `MAX_HEIGHT` หากบีบให้มีแค่ 20 หน่วยจะขัดต่อจุดประสงค์ที่แท้จริงของมัน

## 7. Graph-Specific Data Visualization Rules

- **Time-bounded `spanNulls`** (กฎข้อที่ 6), แทนที่จะเชื่อมทุกช่องว่างเสมอ.
- **Display thresholds as area shading** (`thresholdsStyle: "area"` หรือ `"line+area"`) แทนที่จะใช้แค่เส้นประ — พื้นหลังสีแดงอ่อนๆ มองเห็นจากระยะไกลได้ง่ายกว่าเส้นบางๆ มาก.
- **Accumulated counter values (SNMP errors/drops) ต้องถูกแปลงเป็นอัตรา(rate)ก่อนแสดงผล** โดยใช้ `LAG() OVER (...)` ใน SQL — อย่าแสดงกราฟสะสม (cumulative lines) ที่ไต่ขึ้นตลอดไป เนื่องจากจะไม่สามารถอ่านได้เลยหากสถานการณ์ในปัจจุบันเลวร้ายลง.
- **Data requiring a mirrored axis (เช่น TX ต่ำกว่า RX)** ต้องใช้ฟิลด์ override `custom.transform: "negative-Y"` ที่ระดับการแสดงผลเท่านั้น (visualization layer) — ห้ามคูณด้วย `-1` ใน SQL เนื่องจากคำอธิบาย (legend)/tooltip จะแสดงค่าติดลบอย่างไม่ถูกต้อง.
- **Forecast/regression series** จะต้องใช้เส้นประสีเทาเสมอ (ดูใน §2.1) และ override matcher ต้องใช้ `byRegexp` ไม่ใช้ `byName` เมื่อชื่อซีรีส์มีตัวแปรแทรกอยู่ (เช่น `${machine_id}`) เนื่องจาก `byName` ไม่แทรกตัวแปร(interpolate templates).
- **Legend:** ตั้งค่า `displayMode: table` + `placement: bottom` + เปิดใช้งาน `calcs: [mean, max, last]` เมื่อมีจำนวนซีรีส์มากกว่า 3 ขึ้นไป — สิ่งนี้จะช่วยให้คำอธิบายทำหน้าที่เสมือนตารางขนาดย่อมแทนที่จะเป็นเพียงคีย์แสดงสี.

### 7.1 ECharts panels (`volkovlabs-echarts-panel`) — theming is not optional (added 2026-08-08)

ค่าเริ่มต้นที่ปลั๊กอินนี้ให้มานั้นสร้างมาเพื่อธีมสว่าง (light-mode) สำหรับหน้าแดชบอร์ดที่มีหลากหลายหมวดหมู่
และจะขัดแย้งกับระบบนี้หากปล่อยไว้ไม่ได้แก้ไข: **กรอบข้อความ popup (tooltip) เป็นสีขาว**
ซึ่งขัดกับธีมมืด และ — เมื่อใดที่คุณมีหมวดหมู่มากกว่า 2-3 ขึ้นไป —
**จะใช้สีรุ้งจัดจ้านตามหมวดหมู่** (ฟ้าสด/ม่วง/ชมพู/ส้ม/เป็นต้น)
ที่จะเปลี่ยนแผงหน้าปัดอ่านค่าอุปกรณ์ให้กลายเป็นหน้าจอพักสกรีนเซฟเวอร์ (screensaver) ทั้งสองอย่าง
ได้ถูกส่งมาใช้ในการทำงานครั้งก่อน และต้องทำการเปลี่ยนกลับเนื่องจากรีวิวเห็นว่า
ในส่วน SPC ทั้งหมดดู "รกตา" แม้ว่าหลักการวิศวกรรมพื้นฐานจะ
ถูกต้องก็ตาม — ข้อบกพร่องมาจากตัวธีมล้วนๆ ไม่ใช่จากการเลือกแผนภูมิ

ฟังก์ชัน `getOption` ทุกฟังก์ชันบนระบบนี้จะต้อง:

- กำหนด `tooltip.backgroundColor`/`borderColor`/`textStyle.color` อย่างชัดเจน
  ให้เข้ากับชุดสี panel หน้ามืด (`rgba(18,22,26,0.95)` / `rgba(255,255,255,0.12)`
  / `#E8EDF2`) — ห้ามปล่อยให้ ECharts ใช้ค่าเริ่มต้น (tooltip สีสว่าง) อยู่
- **ห้าม** มอบสีสว่างสดใสให้กับแต่ละซีรีส์เพียงเพราะมีปริมาณซีรีส์เยอะ สำหรับ "สิ่งของ N อย่างที่คล้ายกันเมื่อเวลาผ่านไป"
  เช่น กราฟตัวอย่างดิบจากเครื่องจักร 10 เครื่อง ให้เรนเดอร์ทั้งหมด N ค่าด้วยโทนสีอ่อนและจืด (muted neutral tone) เดียว (`#8B98A9`)
  และใช้สีเฉพาะในส่วนของการตัดสินผลจริงๆ — ตัวอย่างเช่น เครื่องจักรตัวหนึ่งที่กำลัง
  อยู่นอกลิมิตการควบคุมจะแสดงสีแดง `critical` ทุกอย่างอื่นเป็นสี
  เทาหลักการเดียวกันกับกฎ §2.1 ("สีมีความหมายเดียว") ถูกนำไปใช้กับ
  ปลั๊กอินที่ไม่ได้มีการบังคับตั้งค่าให้คุณ
- เมื่อมีความจำเป็นที่สองหมวดหมู่จะต้องเห็นแตกต่างกันจริงๆ (เช่น โครงเรื่องกล่อง Box Plot สำหรับ PE vs JE)
  แต่ไม่มีหมวดหมู่ไหนที่แสดงการตัดสินผล ให้เลือกโทเค็น 2 ตัวจากตระกูล **neutral-readout** (`info` `#00F2FE`, `accent` `#3B82F6`) —
  ห้ามใช้โทเค็นที่เป็น warning/critical และห้ามใช้สีเลขฐานสิบหกทั่วไปที่ไม่ใช่โทเค็น
- กำหนดสไตล์ `xAxis`/`yAxis`/`legend` ตัวอักษรสีเป็น `rgba(224,224,224,0.85)`
  และสีตาราง / เส้นกริด เป็น `rgba(255,255,255,0.06-0.15)` จับคู่กับส่วนอื่นๆ
  ของธรรมเนียมปฏิบัติเกี่ยวกับตาราง(restrained-gridline) ของระบบ (ตามกฎสิ่งรบกวนทางสายตาในข้อ §9)

ตัวอย่างการใช้งานอ้างอิง: `ims-ldi-engineering-analytics.json` panels 17
(Thickness Control Chart) และ 12 (PE/JE Box Plot).

## 9. Reusability — Library Panels

แผงหน้าปัดที่ปรากฏอยู่ข้ามมากกว่า 1 แดชบอร์ด **ต้อง** ถูกติดตั้งเป็น Library Panels (แก้ไขครั้งเดียว อัปเดตทุกที่) — **แต่โดยมีเงื่อนไขอย่างเคร่งครัดว่าตรรกะ(SQL/business logic) ต้องเหมือนกันจริง** ไม่ใช่แค่มีชื่อที่คล้ายกัน:

- **Fleet Health Score** (stat) — Library panel ที่แท้จริง, `ims-lib-fleet-health-score`. ยืนยันผ่าน byte-identical query (`SELECT value FROM public.v_fleet_score`) ระหว่าง `ims-capacity-planning.json` และ `ims-noc-overview.json` แล้วก่อนทำการผสาน (merging)
- **Availability / Critical Alarms / Running / Yield** — ตรวจสอบเมื่อ 2026-08-08 พบว่าไม่ได้ซ้ำกันแม้จะมีชื่อคล้ายกัน: แต่ละเวอร์ชันของแดชบอร์ดมีขอบเขตของ SQL ที่แตกต่างกันจริงๆ (เช่น panel เสนอ Yield ของสายการผลิต จะมีการเพิ่ม template filter ตัวกรองอย่าง `machine_id` รวมไปถึงการคำนวณ "Delta %" ช่วงระยะเวลาต่อช่วงเวลา (period-over-period) ซึ่งเวอร์ชันอย่างง่ายอย่าง Easy Overview ไม่มี; panels ของ Andon/Manufacturing/Easy-Overview อย่าง "Availability"/"Running" มีความต่างกันว่ามันถูกคัดกรองโดย `machine_id` หรือไม่และมันมาพร้อมกับตัวแก้ไขปัญหาข้อบกพร่องการบีบอัดข้อมูลแบบใด(compression-chunk workaround)) การพยายามยัดพวกมันให้กลายเป็นแผงเดียวกัน(shared panel) จะส่งผลต่อค่าที่แต่ละแดชบอร์ดนั้นใช้คำนวณจริง — ซึ่งอยู่นอกขอบเขตของส่วนนี้ (กระบวนการทางธุรกิจ(business logic)ไม่ได้ถูกรวมไว้อย่างชัดเจนในการส่งนี้) หากการตัดสินใจทางธุรกิจภายหลังจะทำการรวมมันให้เป็น query เดี่ยว/คัดกรองร่วมกัน ค่อยทำการตรวจสอบ(audit) ในตอนนั้นและย้ายระบบที่รอดผ่านกลไก library panels ไป

**สิ่งที่เกิดขึ้นจริงใน repo แห่งนี้ (Grafana 13.1.1 ไม่ได้รองรับการจัดหา (provisioning) ไฟล์ตามรูปแบบโครงสร้างเพื่อใช้งานของ Library panels — มีเพียง datasources/dashboards/alerting/plugins ที่ใช้งานได้; ยืนยันจากประสบการณ์จริง, ไม่ใช่จากตัวเอกสารของส่วนจัดเตรียมของ Grafana):**

1. เขียนข้อมูลระบุแผงควบคุม(panel spec) ไว้ใน `monitoring/grafana/library-panels/<uid>.json` — ในรูปแบบ: `{uid, name, kind: 1, model: {...full panel content...}}`. ค่า `uid` ถูกเลือกโดยมือและเสถียร (ไม่ใช่ ค่า auto-generated ที่สร้างโดย Grafana) ดังนั้นในแดชบอร์ดรูปแบบ JSON สามารถอ้างอิงถึงมันก่อนที่มันจะมีอยู่ได้
2. รัน `bash scripts/provision-library-panels.sh` — สคริปต์ HTTP API (สร้างขึ้นผ่าน `POST /api/library-elements` หากขาดไป, `PATCH` หาก uid มีอยู่แล้ว) ใช้รับมือกับ Grafana instance ที่กำลังรัน ไม่ได้ทำงานเชื่อมโยงระบบเข้ากับ `docker-compose` เป็น automatic service (ไม่มีอิมเมจในปัจจุบันที่มาพร้อม curl และ python3 โดยปราศจาก custom build ที่เปราะบาง) — ให้รันแบบกำหนดเองหลังจากใช้งาน `docker compose up` รูปแบบเดียวกับ `scripts/import-real-data.sh`
3. ใน JSON ของแดชบอร์ดที่อ้างอิงถึง ให้แทนที่พาเนลนั้นด้วยแบบจำลองตัวเล็ก: `{"id": <id>, "gridPos": {...}, "libraryPanel": {"uid": "<uid>", "name": "<name>"}}` — โดยปราศจากการใส่โครงร่าง (`type`/`fieldConfig`/`options`/`targets`/`description`) ภายในบรรทัด (inline); ทุกสิ่งเหล่านี้ล้วนมาจากข้อมูลจาก library element
4. `tests/lint/dashboard-linter.js` จัดการตรวจสอบ `library-panels/*.json` (สี, token, คำบรรยาย, noValue) โดยตรง เนื่องจาก panel ที่เป็นตัวอ้างอิง (referencing) ไม่มีข้อมูลภายในบรรทัด(inline) ใด ๆ ให้ตรวจเช็กได้

## 10. Pre-Merge Checklist for New Panels/Dashboards

- [ ] สีที่ใช้ มาจากในตารางข้อ §2.1 เท่านั้น ห้ามไม่มีการจำกัดค่าสี(fixed color) ให้จับคู่เข้ากับซีรีส์ใด เว้นเสียแต่ว่าจะเป็นการนำเสนอให้กับเครื่องจักรทางกายภาพถาวร.
- [ ] ลิมิตข้อจำกัด(Thresholds) เป็นไปตามข้อตกลงใน §2.2 (หากเป็นตัวชี้วัด(metric) ตัวใหม่, ให้เพิ่มแถวลงในตารางนี้ก่อน).
- [ ] `unit` (หน่วย) และ `description` (คำอธิบาย) ต้องมีการแสดงผลใส่ค่าสำหรับทุกๆ พื้นที่ฟิลด์.
- [ ] เลือกประเภท Panel ตามตารางในข้อ §4 ไม่ใช่จากความเคยชิน.
- [ ] ค่าความกว้าง/ความสูง Grid ตอบรับกฎเกณฑ์ข้อ §5.2 ; ต้องไม่มีการผสมผสานความสูงภายในแถวเดียวกัน
- [ ] `spanNulls` ตั้งค่าเป็นตัวเลข (numeric value), และไม่ใช่ `true`.
- [ ] หาก Panel นี้ซ้ำกัน(ถูกลอกแบบ)ไปไว้ที่อื่น → ให้ทำการเปลี่ยนเป็น Library Panel ก่อนทำการผสาน(merge).
- [ ] การสืบค้นสอบถาม(Query) เป็นไปตามหลักการแบ่งชั้น (raw ≤ latest value, minute CAGG ≤ 6h, hourly CAGG > 2d).
- [ ] ทำการทดสอบกับ `make test-visual` และมีผลของสกรีนช็อตที่แสดงผลตามความคาดหมาย
- [ ] `node tests/lint/dashboard-linter.js` แสดงผลโดยไม่มีข้อผิดพลาดแจ้งเตือน (0 error) — Linter ตรวจพบโทเค็นสี Hex ของสีที่ไม่ได้อยู่ในตารางส่วน §2.1 อย่างอัตโนมัติ ซึ่งนี่คือหลักการตัว "token กลาง(central)" จริงๆ และไม่ใช่แค่ตัวเอกสารนี้เท่านั้น
