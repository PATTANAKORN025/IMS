# ชุดทดสอบความน่าเชื่อถือที่ขับเคลื่อนด้วยหลักฐาน

> แทนที่แผนเดิม "รอ 72 ชั่วโมงสำหรับการแช่ระบบที่สะอาด แล้วจึงแก้ไขเป็นชุด" ตัดสินใจเมื่อวันที่ 2026-08-15 หลังจากระยะ A1 (การแก้ไข `sys_metrics` แทรกข้อมูลซ้ำ) พิสูจน์ว่าการแช่เส้นทางการนำเข้าข้อมูลที่ทราบว่าเสียอยู่แล้วเป็นเวลา 72 ชั่วโมงนั้นให้หลักฐานที่ผิดพลาด
>
> **เหตุผลที่ระบุอย่างชัดเจน**: ระยะเวลา 72 ชั่วโมงเพียงอย่างเดียวเป็นแค่ตัวแทนของความน่าเชื่อถือ ไม่ใช่ตัวความน่าเชื่อถือเอง มีสี่คุณสมบัติที่สำคัญกว่าระยะเวลา -- **ความสมบูรณ์ของข้อมูล, ความสามารถในการขยายขนาด, การกู้คืนระบบ, และความทนทาน** -- และแต่ละอย่างสามารถพิสูจน์ได้อย่างอิสระ, เร็วกว่า, ด้วยวงจร แก้ไข→วัดผล→อนุมัติ ที่กระชับกว่าการรอช่วงเวลาที่ไม่มีการขัดจังหวะยาวนานเพียงช่วงเดียว การแช่ระบบ 72 ชั่วโมงถูกลดระดับเป็นทางเลือก (P3) ไม่ได้ถูกลบออก -- ยังคงมีประโยชน์ในฐานะการตรวจสอบความมั่นใจขั้นสุดท้ายในระยะยาวเมื่อรายการ P0/P1/P2 เสร็จสิ้นแล้ว แต่จะไม่ใช่ประตูด่านที่ทุกอย่างต้องรออีกต่อไป

## กฎการทำงาน (ยกยอดมาจากระยะ A1)

- **แก้ไขทีละรายการ** แต่ละการแก้ไข P0/P1 จะได้รับการปรับใช้ วัดผล และรายงานก่อนที่รายการถัดไปจะเริ่มต้น -- นี่คือสิ่งที่ทำให้สามารถพิสูจน์ได้ว่า "การเปลี่ยนแปลงใดแก้ไขปัญหาใด" และทำให้หลักฐานของการแก้ไขแต่ละครั้งน่าเชื่อถือในตัวมันเองแทนที่จะพัวพันกับการแก้ไขอื่นๆ อีก 2-3 รายการ
- **มาตรฐานหลักฐาน 3 ชั้นยังคงมีผลบังคับใช้**: ความแตกต่างของโค้ด (code diff) + การวัดผลขณะรันไทม์ (runtime measurement) + การยืนยันที่ผู้ใช้มองเห็นได้ (user-visible confirmation) ก่อนที่สิ่งใดจะถูกเรียกว่า "แก้ไขแล้ว" หากขาดชั้นใดชั้นหนึ่งไปจะเรียกว่า "ตรวจสอบแล้วบางส่วน (PARTIALLY VERIFIED)"
- **การสืบสวนแบบอ่านอย่างเดียวเทียบกับการแก้ไขที่ต้องมีการรีสตาร์ทอยู่ในระดับการอนุมัติที่แตกต่างกัน** การสืบสวน/การวัดผล (การตรวจสอบความสมบูรณ์ของข้อมูล, _การออกแบบ_ การฉีดข้อผิดพลาด, _การวางแผน_ การทดสอบการขยายขนาด) สามารถดำเนินการได้โดยไม่ต้องขออนุมัติการรีสตาร์ทใหม่ทุกครั้ง สิ่งใดก็ตามที่แก้ไข `nodered_data/flows.json`, `monitoring/snmpsim/*.snmprec` หรือต้องใช้ `docker compose restart`/`recreate` จะต้องรอสัญญาณอนุมัติที่ชัดเจน เช่นเดียวกับที่ทำใน A1
- **จะไม่มีความพยายามแช่ระบบรอบใหม่เริ่มต้นขึ้นจนกว่ารายการ P0/P1 จะเสร็จสิ้น** -- การเริ่มต้นก่อนหน้านั้นจะถูกทำให้เป็นโมฆะด้วยการรีสตาร์ทครั้งถัดไป ดังที่เกิดขึ้นแล้วใน Attempts 1-8
