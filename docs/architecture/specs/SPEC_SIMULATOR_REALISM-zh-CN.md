> 编写本文档未修改任何模拟器代码——下文的所有发现均来自于阅读
> `nodered_data/flows.json` 和 `docs/audit/LDI_ALARM_FIDELITY_AUDIT.md`（2026-08-11），
> 而不是通过不同方式重新运行模拟器得出的。

## 范围，按用户原始顺序（仍具约束力）

> “仅针对应该具有真实噪声/漂移的变量（温度、湿度、真空、PE/JE、微停机、预热漂移）
> 调整模拟器真实度，并保持 scan_speed 作为一个配方设定点。”

`scan_speed` 明确不属于整个轨道范围——它是一个已配置的配方值，
并非真实机器会发生漂移的东西。这里没有任何修改它的提议。

## 项目 1：移除噪声代码的 `logdate` 回溯

**根本原因，已确诊** (`ALARM_LATENCY_MEASUREMENT_NOTE.md`)：
`nodered_data/flows.json`，节点 `almsim_gen`，函数 `generate()`：

```js
rows.push(
  newRow(
    eq,
    code,
    new Date(now - Math.floor(Math.random() * 9000)),
    null,
    "nearest",
  ),
);
```

后台噪声代码报警在 `logdate` 上被回溯随机 0-9000ms，“以模拟报警情况在其被记录前略微提前发生的情况”。这直接引发了本次传递中的一项测量完整性事故——报警延迟仪表板最初显示了一个虚假的 P95=7.6-7.9s。

**设计**：取消回溯，就像事件驱动的分支已经做的那样使用 `new Date(now)`：

```js
// 之前
rows.push(
  newRow(
    eq,
    code,
    new Date(now - Math.floor(Math.random() * 9000)),
    null,
    "nearest",
  ),
);
// 之后
rows.push(newRow(eq, code, new Date(now), null, "nearest"));
```

**为什么说简化它而不是“改进”它是安全的：** 这种回溯从未得到任何真实情况的验证——没有引用，没有供应商规范，也没有测量过的真实世界报警报告延迟分布能支持 `random(0,9000)` 这个范围。它不过是碰巧看起来合理的伪造抖动。移除它并不是在真实度上的*倒退*；它是移除了一个毫无根据的主张。如果稍后获得了真实的报警报告延迟数据，那将是一个由证据支持的独立项目，而不是恢复这个项目。

**部署**：单行修改，重新部署 `node-red` (`docker compose restart node-red`)，
重新运行 `tests/e2e/ingestion-latency-check.js`，以确认 `nearest` 路径的
报警延迟现在与 `causal` 路径相符（大约在个位数毫秒）。更新
`ALARM_LATENCY_MEASUREMENT_NOTE.md` 记录此更改的对比情况，不要
只是把笔记删掉——该事件及其解决方案都是值得保留的真实历史。

## 项目 2：温度、湿度、真空、PE/JE、微停机、预热的真实噪声/漂移

**此处未进行详细设计**——这是本次合并传递中唯一一个真正需要集思广益/设计过程的项目（包含多个独立的变量，每个都有其自身真实的分布情况，在此仓库中没有现成的参考实现可供扩展）。本规范在此承诺的内容是：

- **实施前需逐一回答各变量的设计问题**，每次一个，每个都需要真实的答案而非猜测：
- 温度/湿度：此类硬件的真实传感器本底噪声是多少？（如果有的话，提供规格书；否则提出一个记录在案的合理假设，并明确标记为假设。）
- 真空：同样的问题，外加漂移是否与占空比相关（真实的真空系统通常相关）。
- PE/JE：这些已用于驱动报警相关性（`ALIGN_CODES`）——任何增加的噪声都必须确保不破坏该相关性的信噪比，否则它将无声地击败 RCA 指南本身的主张。
- 微停机（Micro-stop）：目前在模拟器中完全不存在（本次传递未在 `almsim_gen` 或 `ldisim_gen` 中找到 `micro_stop` 或停机事件字段）——这是一个**全新的机制**，而非现有机制的微调。需要为其专门设计：用哪个表/列来表示它，它与现有的 OEE 计算交互的方式（参考 `ims-ldi-manufacturing` 的 OEE 部分）。
- 预热漂移：需要定义“预热窗口”（自上次状态切换到 RUN 以来的时间？），然后才能据此设计任何漂移曲线。
- **在未先通过头脑风暴技能的设计流程之前，不要实施上述任何一项**——与项目 1 一行代码解决不同，该项目存在真正未解决的设计问题。

## 项目 3：重新运行报警保真度审计

属于机械性的工作，并非设计任务——针对当前的模拟器状态（防抖动处理后，位于 Phase D/E/F 后：已应用 debounce、`link_basis` 和罕见的 Critical 码），使用最初 `docs/audit/LDI_ALARM_FIDELITY_AUDIT.md`（附录：使用的查询）中的相同查询重新运行。得出一个全新的分数。这应该在项目 2 开始**之前**进行，而不是之后——如果去抖动/相关性的修复已经使分数大幅超过了原先的 58/100，那将会改变项目 2 的实际紧迫性。

## 项目 4：遥测生成器将 ~25-45% 的读数保持在规范之外

源自 58/100 分审计报告：这解释了_为什么_条件驱动报警几乎持续触发（在审计时，所有报警中有 91.4% 是条件驱动的），而不是作为离散的事件。此事与项目 3 的重新审计绑定在一起——如果去抖动（debounce）修复已经足以抑制这种明显的症状（重复近乎重复的警报），那么潜在的超规格率可能比在初次审计中看起来优先解决度更低。在项目 3 的最新数据出来之前，不要对此项进行设计。

## 本规范故意不做的事情

没有对项目 2 和 4 的实施细节进行设计。这两者都有开放性的问题（如上所述），需要一个适当的设计流程，而不是凭记忆重写审计中记录的内容来撰写规范文档。本文档的职责在于正确地界定范围和排序工作，而不是预先猜测答案，答案应来自证据（项目 3 的最新审计）或一场真实的设计讨论（项目 2 各变量的设计提问）。
