# ข้อกำหนด (Spec): การแก้ไขการแทรกข้อมูลซ้ำ (Duplicate-Insert) ใน sys_metrics (ระยะที่ A1)

**สถานะ: ปรับใช้เมื่อ 2026-08-15, กำลังดำเนินการวัดผล** อนุมัติโดยผู้ใช้ก่อนที่ Soak Attempt 8 จะเสร็จสิ้น ด้วยเหตุผลที่ว่าการรันแช่ (soaking) พาธข้อมูลเข้า (ingestion path) ที่รู้ว่าเสียอยู่แล้วเป็นเวลา 72 ชั่วโมงจะให้หลักฐานที่ผิดพลาด สิ่งนี้สิ้นสุด Soak Attempt 8 -- ดู `docs/evidence/SOAK_TEST_LOG.md`

## สาเหตุที่แท้จริง (แกะรอยแบบโหนดต่อโหนด, `nodered_data/flows.json`)

`sre_parser` (function node, "SRE AIOps Parser v9 (Batch)") ถูกเรียกใช้หนึ่งครั้งต่อการเสร็จสิ้นการสแกนแบบ SNMP-walker (`cpu`, `storage`, `temp`, `net`, `ldi` แต่ละตัวจะทริกเกอร์มันแยกกัน) มันเก็บรักษาอ็อบเจ็กต์ `state` ที่ใช้ร่วมกันแบบต่ออุปกรณ์เพียงตัวเดียว โดยอัปเดตเฉพาะส่วนที่เกี่ยวข้องกับ walker ใดก็ตามที่เพิ่งรายงานเข้ามา ข้อผิดพลาดคือ: ในทุกๆ หนึ่งของ walker 3 ประเภทที่ป้อนข้อมูลให้ `sys_metrics` (`cpu`, `storage`, `temp`) มันได้พุช (push) **สแนปชอตแบบเต็มของสถานะที่ใช้ร่วมกันทั้งหมด** ไปยังบัฟเฟอร์แบทช์ -- ไม่ใช่หนึ่งครั้งต่อรอบการดึงข้อมูลที่แท้จริงประมาณ 30 วินาที (`inject_fleet`, `repeat: 30`) แต่เป็นหนึ่งครั้งต่อ walker ที่เป็นองค์ประกอบ ทั้ง 3 ตัวเข้ามาอยู่ในช่วงเวลาเดียวกัน โดยแต่ละตัวจะพุชสถานะเต็มที่แทบไม่เปลี่ยนแปลงกลับเข้าไปอีก ทุกๆ 10 วินาที (`BATCH_INTERVAL_SEC`) บัฟเฟอร์จะเคลียร์ทิ้งเป็น `INSERT ... VALUES (NOW(),...),(NOW(),...),(NOW(),...)` แบบหลายแถวในครั้งเดียว -- Postgres จะประเมินค่า `NOW()` หนึ่งครั้งต่อสเตตเมนต์ ดังนั้นทุกแถวในการเคลียร์หนึ่งครั้งจึงใช้ค่า `time` เดียวกันทุกประการ ซึ่งนั่นเป็นเหตุผลว่าทำไมข้อมูลที่ซ้ำกันจึงเหมือนกันทุกไบต์จนถึงระดับไมโครวินาที

ยืนยันได้ว่าเกิดเฉพาะกับ `sys_metrics`: ประเภท walker ของ `net` และ `ldi` พุชไปที่บัฟเฟอร์แยกกัน หนึ่งการพุชต่อการเสร็จสิ้นของแต่ละตัว ไม่มีแพตเทิร์นแบบ fan-in -- `net_metrics` และ `ldi_data`/`ldi_alarm_log` ทั้งหมดได้รับการยืนยันอย่างอิสระว่าสะอาด (ข้อมูลซ้ำเป็น 0) ก่อนการแก้ไขนี้

## การแก้ไข

ได้เพิ่มเกตจำกัดรอบ (cycle-gate) แบบต่ออุปกรณ์ลงใน `sre_parser` โดยอิงจากบริบทของ `flow` (`sys_cycle_<device>`):

- เมื่อแต่ละ `cpu`/`storage`/`temp` เสร็จสมบูรณ์ ให้ทำเครื่องหมายประเภทนั้นว่าพบแล้วในอ็อบเจ็กต์รอบ (cycle) ที่รอดำเนินการ แทนที่จะพุชข้อมูลทันที
- พุชแถวข้อมูล (และรีเซ็ตรอบ) ทันทีที่ **ทั้ง 3** ประเภทได้รายงานเข้ามานับตั้งแต่การพุชครั้งล่าสุด
- **เวลาหมดอายุเพื่อความปลอดภัย (Safety timeout), 35 วินาที** (`SYS_CYCLE_TIMEOUT_MS`, สูงกว่าช่วงเวลาการดึงข้อมูล 30 วินาทีเล็กน้อย): หาก walker ตัวใดตัวหนึ่งไม่เคยรายงานเข้ามาเลย (ดาวน์อย่างถาวร, คอนฟิกเป้าหมายผิดพลาด ฯลฯ) ให้พุชข้อมูลเท่าที่รวบรวมได้ออกไปดีกว่ารอตลอดไป นี่เป็นความตั้งใจ -- การยอมแลกเพื่อให้ได้แถวข้อมูลที่อาจไม่สมบูรณ์เพื่อรับประกันว่า _จะไม่มีการสูญหายของข้อมูลแบบเงียบๆ_ คือการแลกเปลี่ยนที่ถูกต้องตามลำดับความสำคัญที่ระบุไว้ (การกำจัดข้อมูลซ้ำจะต้องไม่ทำให้เกิดโหมดความล้มเหลวแบบข้อมูลสูญหายแบบใหม่)

การแก้ไขคือการแทนที่บรรทัดเดียวที่แยกต่างหาก บวกกับค่าคงที่ใหม่หนึ่งค่า -- ไม่มีส่วนอื่นใดใน `sre_parser` ถูกแตะต้อง ตามคำสั่งที่ชัดเจนว่าไม่ให้นำสิ่งนี้ไปรวมกับการแก้ไข RAM/ดิสก์/การแจ้งเตือน

## การนำไปใช้งาน (Deployment)

`docker compose restart node-red` (การรีสตาร์ทบริการเดียว, ไม่ใช่การสร้างสแต็กใหม่ทั้งหมด) -- รัศมีผลกระทบที่แคบที่สุดที่ยังคงรับรู้ถึงการเปลี่ยนแปลงของ flow นี้นี่คือการรีสตาร์ทคอนเทนเนอร์จริงและเป็นการสิ้นสุดการพยายามซ็อก (soak attempt) ในปัจจุบัน; มีเอกสารบันทึกไว้ใน `SOAK_TEST_LOG.md`

## แผนการวัดผล (ก่อน → หลัง, ทั้งหมดมาจากคิวรีจริง, ไม่ใช่การสมมติ)

1. **อัตราการซ้ำ**: `COUNT(*) - COUNT(DISTINCT (device_id,time))` ในหน้าต่างหลังการใช้งานใหม่, ใช้คิวรีเดียวกันกับที่ค้นหาบั๊ก เป้าหมาย: ~0%.
2. **ความครบถ้วนสมบูรณ์**: จำนวนแถวในช่วงเวลาคงที่หลังการปรับใช้ควรสอดคล้องกับจังหวะการดึงข้อมูล ~30 วินาที × จำนวนอุปกรณ์ × ความยาวของหน้าต่าง -- ไม่นับขาด (สูญหายแบบเงียบ) หรือนับเกิน (มีข้อมูลซ้ำหลงเหลืออยู่)
3. **ความละเอียดของ Timestamp**: ค่า `time` ที่แตกต่างกันในแถวต่างๆ ในช่วงหน้าต่างการเคลียร์ (flush window) เดียวกัน (ก่อนหน้านี้ยุบรวมเป็นค่าที่ใช้ร่วมกันหนึ่งค่าต่อการเคลียร์)
4. **ความหน่วง (Latency)**: การกระจายของ `ingest_ts - time` หลังการแก้ไข (คอลัมน์ทั้งสองมีอยู่แล้ว; `ingest_ts` คือ `clock_timestamp()` ซึ่งเป็นแบบรายแถวอยู่แล้วแม้ว่าจะมีบั๊ก -- `time` คือคอลัมน์ที่เสีย)
5. **ทรัพยากร/ความเสถียร**: คอนเทนเนอร์ `ims-node-red` ยังคงทำงานปกติหลังจากการรีสตาร์ท, ไม่มีข้อผิดพลาดใหม่ในล็อก, `pipelineMetrics.inserts_failed` ไม่เพิ่มขึ้น

ผลลัพธ์แนบท้ายด้านล่างเมื่อวัดผลแล้ว
