# 时间戳完整性审计 (P0.3)

**状态：已审计，已记录文档。此项目无需更改代码 —— 下方的发现即为交付成果。**

## 真实的时间戳模型，如其原貌（而非声称的）

```
来源/事件  ->  摄取 (Node-RED/JS)  ->  处理 (Node-RED 批处理缓冲区)  ->  数据库提交  ->  查询  ->  仪表板
```

这个系统**没有**每行 6 个独立的时间戳。每张表实际存在的是：

| 表                           | "事件" 列                                                        | 精度 (Schema)                  | 精度 (实际，测量值)                                                    | "摄取" 列                                        | 精度 (实际)         |
| ---------------------------- | ---------------------------------------------------------------- | ------------------------------ | ---------------------------------------------------------------------- | ------------------------------------------------ | ------------------- |
| `ldi_data`                   | `time` (JS `Date`，Node-RED 端)                                  | `timestamptz(6)` (微秒)        | **仅毫秒** —— 每个样本的微秒字段都以 `000` 结尾                        | `ingest_ts` (`clock_timestamp()`，Postgres 端)   | 真正的微秒          |
| `ldi_alarm_log`              | `logdate` (JS `Date`)                                            | `timestamptz(6)`               | **仅毫秒**，模式相同                                                   | `ingest_ts` (`clock_timestamp()`)                | 真正的微秒          |
| `sys_metrics`                | `time` (SQL `NOW()`，Postgres 端，在批量 INSERT 内部设置)        | `timestamptz(6)`               | **真正的微秒** —— `NOW()` 是 Postgres 原生的，不是 JS 派生的           | `ingest_ts` (`clock_timestamp()`)                | 真正的微秒          |
| `net_metrics`，`ldi_metrics` | 与 `sys_metrics` 相同 (`NOW()`)                                  | `timestamptz(6)`               | 真正的微秒                                                             | `ingest_ts`                                      | 真正的微秒          |

**更正声明**：Schema 各处都声明了微秒精度 (`timestamptz(6)`)，这对于每个 `ingest_ts` 列以及 `sys_metrics`/`net_metrics`/`ldi_metrics` 的 `time` 列来说是真的。但是 `ldi_data.time` 和 `ldi_alarm_log.logdate` —— 这两张其“事件”时间戳源于 Node-RED 的 JavaScript 运行时 (`new Date()` / `Date.now()`) 而不是 Postgres 端的 `NOW()` 调用的表 —— 在实践中仅具有**毫秒**级精度，因为 JavaScript 的原生 `Date` 没有亚毫秒部分。这不是要修复的错误；鉴于当前的架构（Node-RED 在客户端生成事件时间戳），这是对这两张表的精度真正且永久的限制。**不要声称 `ldi_data`/`ldi_alarm_log` 的遥测具有微秒级精度 —— 诚实的声明是：事件时间为毫秒，摄取时间为微秒。**

Schema 中没有任何地方有单独的“处理时间戳”列 —— 批处理缓冲区阶段（`sre_parser` 的 10 秒刷新间隔，或在阶段 A1 中修复的 `BATCH_INTERVAL_SEC` 机制）是真实的，但并没有逐行记录。每行仅记录两个瞬间：事件时间和提交时间。

## 延迟测量（真实的，`tests/e2e/ingestion-latency-check.js`，过去 15 分钟）

**第一阶段 — 来源 → 提交** (`ingest_ts - <事件列>`):

| 表                                         | n   | P50    | P95    | P99    |
| ------------------------------------------ | --- | ------ | ------ | ------ |
| `ldi_data`                                 | 871 | 8ms    | 22ms   | 38ms   |
| `ldi_alarm_log` (因果，真实相关)           | 3   | 5ms    | 5ms    | 5ms    |
| `ldi_alarm_log` (最近，噪声代码)           | 11  | 4204ms | 7172ms | 7173ms |
| `sys_metrics`                              | 108 | 0ms    | 1ms    | 1ms    |
| `net_metrics`                              | 208 | 0ms    | 1ms    | 3ms    |
| `ldi_metrics`                              | 108 | 0ms    | 1ms    | 2ms    |

**第二阶段 — 查询可见延迟**（在最新行的查询上进行真正的 `EXPLAIN ANALYZE`）：所有 5 张表都在 0.07ms-0.31ms 之间。

**不要将 `ldi_alarm_log (最近)` 行与真实的流水线延迟混淆** —— 根据用户自己明确的警告和本次会话早期的工作（`ALARM_LATENCY_MEASUREMENT_NOTE.md`，`docs/architecture/specs/SPEC_SIMULATOR_REALISM.md` 第 1 项）：`almsim_gen` 的噪声代码路径在插入前仍会将其事件时间戳回溯 0-9000 毫秒（`new Date(now - Math.floor(Math.random() * 9000))`，在本次审核中确认存在于 `nodered_data/flows.json` 中，与早期审计相比未变）。4204-7173 毫秒的数字是这种人为延迟表现为表观延迟，而不是流水线变慢。`link_basis` 列（`'causal'` 与 `'nearest'`）正是用于区分真实流水线延迟（因果，5 毫秒）与这种人工痕迹（最近，~4-7 秒）的来源标记 —— 根据不将模拟器事件时间与实际摄取延迟混为一谈的指令，在此处被正确使用。

`sys_metrics`/`net_metrics`/`ldi_metrics` 显示 ~0ms 的第一阶段延迟是一个值得直言不讳地指出的测量方法论误区，而不是真正的“即时”流水线：它们的事件时间戳 (`NOW()`) 和提交时间戳 (`clock_timestamp()`) 都是在同一个 INSERT 语句执行内部设置的，这发生在实际的 SNMP 轮询几秒钟之后 —— 这些表的第一阶段测量的是“事务开始和语句完成之间的时间”，而不是“从现实世界读取 SNMP 到可查询的时间”。这些表的真正端到端延迟（轮询 → 已提交）没有单独配置检测工具；只有 `ldi_data`/`ldi_alarm_log` 有真正的 Node-RED 之前的事件时间戳可供比较。

## 已知限制（直白声明，符合验收规则）

- 尽管 Schema 声明了 `timestamptz(6)`，`ldi_data`/`ldi_alarm_log` 在事件时间列上是**毫秒**精度的，而不是微秒 —— 架构上的天花板 (JS `Date`)，而非本次修复的内容。
- 本次对 `ldi_data`/`net_metrics` 的重复时间戳扫描依赖于早期审计的去重键结果，而不是仅对时间戳进行分组的全新重新运行 —— *同一台*设备中真正的绝对重复时间戳但其他列不同，是不会被任何一种检查捕获的。被标记为真正的盲区，在此处未填补。
- `net_metrics`/`ldi_metrics` 未针对阶段 A1 修复 `sys_metrics` 时解决的批处理时间戳痕迹进行独立检查 —— 从它们当前每周期单行的行为推断为安全，未通过有针对性的测试直接证明。
- 没有对于 `ldi_alarm_log (因果)` 大于 n=3 的 P95/P99 数据 —— 在 15 分钟的时间窗口内，样本量太小以至于无法提供统计意义（与该项目中其他地方一样的 `LDI_RCA_GUIDE.md` 风格警告）。
