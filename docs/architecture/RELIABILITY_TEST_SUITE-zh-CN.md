# 证据驱动的可靠性测试套件

> 替代原有的“等待 72 小时进行干净的系统浸泡测试，然后批量修复”计划。于 2026-08-15 决定，因为在 A1 阶段（`sys_metrics` 重复插入修复）证明，对已知损坏的摄入路径浸泡 72 小时只会产生错误事物的证据。
>
> **理由很简单**：单一的 72 小时周期只是可靠性的代理，而不是可靠性本身。有四个属性比持续时间更重要——**数据完整性、可扩展性、恢复能力和耐久性**——每一个都可以独立地、更快地进行证明，其“修复→测量→批准”循环更加紧凑，而不是等待一个漫长且不间断的窗口期。72 小时浸泡测试降级为可选（P3），并未被删除——一旦 P0/P1/P2 项目完成，它作为最终的长期置信度检查仍然很有用，但它不再是其他所有工作都必须等待的门槛。

## 工作规则（结转自阶段 A1）

- **一次修复一个问题。** 每个 P0/P1 修复在下一个开始之前都会被部署、测量和报告——这就是使“哪个更改修复了什么”具有可证明性的原因，也是使每个修复的证据本身值得信赖，而不是与另外 2-3 个修复纠缠在一起的原因。
- **3 层证据标准仍然有效**：代码差异 (code diff) + 运行时测量 (runtime measurement) + 用户可见的确认 (user-visible confirmation)，然后才能将任何内容称为“已修复”。当缺少某一层时，则为“部分验证 (PARTIALLY VERIFIED)”。
- **只读调查与需要重启的修复属于不同的审批层级。** 调查/测量（数据完整性检查，故障注入**设计**，规模测试**规划**）可以进行，而无需每次都获得新的重启批准。任何编辑 `nodered_data/flows.json`、`monitoring/snmpsim/*.snmprec` 的操作，或者需要 `docker compose restart`/`recreate` 的操作，都需要等待明确的许可，这与 A1 时一样。
- **在 P0/P1 项目完成之前，不会开始新的有编号的浸泡测试**——过早开始只会因为下一次重启而无效，正如 Attempts 1-8 已经发生的那样。
