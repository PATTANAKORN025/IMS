# IMS LDI 制造指挥中心 — 下一阶段实施计划

状态：**仅为计划。尚未实施。** 建立在已批准的审计/规范（`docs/superpowers/specs/2026-08-18-manufacturing-command-center-next-phase-design.md`）之上。以下每个发现都在本次会话中针对实时数据库和实时存储库进行了验证（`docker compose exec timescaledb psql`，`node tests/lint/*.js`，直接读取 JSON/SQL）—— 此处没有任何内容是假设的，也没有未经审计验证就直接沿用的内容。

## 5 个悬而未决问题的解决方案

### Q1 — 仪表板拓扑结构

**决定：制造指挥中心 (Manufacturing Command Center) 将获得一个新的顶部部分，而不是创建一个新的仪表板。** 理由（基于证据）：

- `ims-ldi-manufacturing.json` 已经包含一个执行 HUD（PRODUCTION/QUALITY/RISK 行，y=0–15），这正是为 C 级别 (C-Level) 高管设计的结构：3 行，13 个统计/表格面板，没有每台机器的下钻网格。它只是没有被贴上标签或定位为 C 级别视图。
- 9 个孤立面板（审计的发现 A）已经涵盖了确切位于 y=16+ 位置的生产与合规性 (Production & Compliance)、分析与 SPC (Analytics & SPC)、系统报警 (System Alarms)、RCA 车队摘要 (RCA Fleet Summary) 以及周期时间与可追溯性 (Cycle Time & Traceability)——也就是说，该文件自己的行排序已经编码了“先看 C 级别概览，后看操作/分析细节”，只是它从未被连接起来。
- 一个全新的仪表板要么会复制执行 HUD 的 13 个面板（违反了“不重复仪表板”/“不重复业务逻辑”的原则），要么会使新的 C 级别视图与同一文件中正下方的操作细节脱节。

**最终层级结构：**

```
IMS LDI - 制造指挥中心 (IMS LDI - Manufacturing Command Center)  (已修复，重新排序)
├─ C级别概览 (C-LEVEL AT A GLANCE)          [现有的执行 HUD，重新标记/重新分组 — 没有新面板]
│   生产 / 质量 / 风险 (PRODUCTION / QUALITY / RISK) 行 (13 个面板，已在使用中)
├─ 生产与合规 (PRODUCTION & COMPLIANCE)      [修复 3 个孤立面板]
├─ 系统报警 (SYSTEM ALARMS)                [修复 1 个孤立面板 + 添加影响摘要，第 8 项]
├─ 分析与 SPC (ANALYTICS & SPC)              [修复 2 个孤立面板，仅为摘要 — 链接至工程分析下钻]
├─ 可追溯性 (TRACEABILITY)                 [修复“电路板可追溯性” + “平均周期时间”，成为可追溯性部分]
└─ (下钻链接，而非嵌入面板) → 2D 孪生, 3D 孪生, 机器快照, 报警控制台, 工程分析, 报警响应
```

“RCA 车队摘要” (最高相关报警) 被折叠到 SYSTEM ALARMS 部分，而不是保留为其自己单独的一行——它是报警影响数据（第 8 项），并且第 6 个顶级行会将总高度推高，超过单个滚动指挥中心仪表板在它完全变成工程分析 (Engineering Analytics) 仪表板之前应承受的高度。这仅仅是命名/分组的改变；底层的面板 (id 21) 保持不变。

`ims-easy-overview` 保持原样（零配置操作快捷路径，不同的受众/用例，已经很独特并且工作正常——不触碰，不重复）。

### Q2 — 报警交互性

**决定：指挥中心保持只读状态；报警控制台仍然是唯一的写入界面。** 证据：这正是操作员安灯看板 (Operator Andon Board) 已经建立并证明的先例（`ims-ldi-operator-andon.json` 自己的描述：“只读...作为只读的 IMS LDI - 操作员安灯看板（电视墙信息亭，无交互元素）的配套” vs. `ims-ldi-alarm-console.json`：“交互式报警确认/解决工作流”）。偏离这一点将意味着两个不同的仪表板通过两个不同的 UI 界面独立地写入 `ldi_alarm_lifecycle`——这只是增加了相同的写入路径的表面积，并没有增加新的功能。

- **C 级别最低可用报警视图**：数量 + 严重程度（现有的“严重/主要报警”统计，已在使用中）加上已修复的“最高相关报警”摘要（第 8 项）——这回答了“有多少、有多严重，以及哪些类别实际上正在影响生产”的问题，而无需暴露确认/解决控件。
- **操作员操作工作流**：未改变——`ims-ldi-alarm-console.json` 的 `marcusolsson-dynamictext-panel` → `services/alarm-api` `POST /alarms/ack` / `POST /alarms/resolve` → `public.ldi_alarm_lifecycle`。没有发明新的状态；`OPEN → ACK → RESOLVED`（`status` 列和 `alarm-api` 目前支持的唯一状态）完全保持原样。
- 指挥中心的“最近报警事件”（已修复的面板 14）和 Andon 的“行动队列”都读取 `v_ldi_alarm_context`/从生命周期派生的数据，但服务于不同的目的（完整的最近历史记录 vs. 当前活动的队列）——这不是重复，这与这两个面板今天已经拥有的关系相同。

### Q3 — 2D 与 3D 规范下钻入口

**决定：两者都保留，出于不同原因进入，不发明第三种布局。**

| 用例                                                                                             | 入口点        | 原因                                                                                                                                                                                                          |
| ---------------------------------------------------------------------------------------------------- | ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| "车队现在在做什么，一眼望去，通过指挥中心的一个链接"                   | **2D Canvas 孪生** | 它已经是一个原生的 Grafana 仪表板——具有与此存储库中所有其他仪表板链接相同的身份验证、相同的导航 chrome 以及相同的链接机制。交互成本更低（没有单独的应用程序/会话概念，没有 3D 场景加载）。 |
| "我想在空间上探索/在视觉上展示工厂（例如，电视墙、演练、演示）" | **3D Web 孪生**    | 它自身的价值在于空间/视觉框架（任务 4.1–4.4 的全部重点）——这与“Grafana 导航中的另一个链接”是完全不同的用例，而不是它的替代品。                                       |

两者都从新的 TRACEABILITY 部分（可选择地也从 C-Level 部分）链接出去，作为两个明确的、分别标记的链接——没有切换器 UI，没有嵌入（Canvas 面板和单独的 Three.js 应用程序都太重/具有不同界面的 chrome，无法干净地嵌入到 iframe 面板中，并且这两个孪生应用都不是设计用于 iframe 嵌入的）。**这种集成没有引入虚假的物理坐标**——两个孪生应用已经分别使用了 `is_simulated`/无坐标和模拟网格放置；链接到它们不会改变它们的任何数据模型。3D 孪生保持冻结状态——该计划提议对 `services/factory-twin-3d/` 零代码更改，仅在指挥中心提供*指向*它的链接。

### Q4 — 可追溯性 UX

**完整路径以及支持每次跳转的基础，在本次会话中已针对实时模式/视图进行了验证：**

```
工厂 → 区域 → 机器 → 报警 → 生产 → 机器快照 → 原始记录
```

| 跳转 (Hop)                           | 基础支撑 (实时验证)                                                                                                                                                                                                                                       | 现在可实施？                                        |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| 工厂 → 区域 (Factory → Zone)                | `public.devices.location` (5 个真实的字符串值，无坐标)                                                                                                                                                                                              | 是 — 两个孪生应用已经使用相同的分组方式                |
| 区域 → 机器 (Zone → Machine)                | `public.devices.device_id` 其中 `device_type='ldi'` 且已启用 (`enabled`)，过滤出 10 台报告真实数据的机器                                                                                                                                                | 是 — 已证明的查询形状 (面板 6，实时验证，61.6ms) |
| 机器 → 报警 (Machine → Alarm)               | `v_ldi_alarm_context` (28 列，包含 `severity`, `alarm_id`, `related_log_id`, 规范标志 (spec-flags) — 已实时验证，比审计文档最初读取的旧迁移更丰富)                                                                               | 是 — 实时验证，最近 50 条只需 36.4ms |
| 报警 → 生产 (Alarm → Production)            | `v_ldi_alarm_context` 的规范标志 (行级别) + `v_ldi_rca_recent_window` (类别级别提升/置信度，物化视图，1 分钟刷新，实时验证为 1.5ms)                                                                                              | 是 — 两者均已实时验证                                  |
| 生产 → 机器快照 (Production → Machine Snapshot) | 现有的下钻约定：`/d/ims-ldi-machine-snapshot/set2-machine-snapshot?var-machine_id=...&var-factory=...`，省略 `var-mo`/`var-event_time_ms`，以便默认解析为最新/所有 MO（在本会话的所有 SDD 任务中验证了 4 次） | 是 — 逐字重用，无需新工作                       |
| 机器快照 → 原始记录 (Machine Snapshot → Raw Record) | 机器快照自己的“选定日志 ID 周围的事件时间线”面板已经存在（该仪表板中的面板 12），指挥中心修复的“电路板可追溯性”面板直接暴露了 `log_id`                                                           | 是 — 两端均已存在                             |

**from/to 上下文保留**：上面的每个下钻目标都是标准的 Grafana 仪表板链接，它会自动保留 `from`/`to`，除非链接明确覆盖它——既定的约定（针对 `ims-ldi-machine-snapshot.json` 的变量默认值进行了确认，在任务 2-4.2 中重复了相同的检查）是*明确省略* `var-mo`/`var-event_time_ms`，以便目标解析为“最新”，同时仍然携带真实的 `var-machine_id`/`var-factory` 和仪表板的时间范围。此计划添加的新链接遵循相同的模式——未发明新的链接约定。

**结论**：请求路径中的每一次跳转都由真实的、已验证的数据支持。这 100% 是一个导航/链接布线计划，而不是一个新的查询计划（需要注意的是，“报警 → 生产”摘要面板（第 8 项）需要使用现有查询进行新的面板*展示*——参见面板恢复矩阵，面板 21）。

### Q5 — 孤立面板验证

**方法**：从实时的 `ims-ldi-manufacturing.json` 中提取每个 9 个孤立面板的确切 `rawSql`，在 1 小时和 24 小时的窗口期内，直接在实时数据库上通过 `docker compose exec timescaledb psql ... EXPLAIN (ANALYZE, BUFFERS, TIMING)` 运行每个（使用代表性参数替换），并且——对于两个带有 `QUERY_BUDGET_EXEMPT` 注释声称预算超支的面板——还在完全无界限的范围内运行（当前 `ldi_data` = 总计 97,401 行，所有块）。还独立发现：`tests/lint/dashboard-linter.js` 和 `tests/lint/query-budget-linter.js` 目前根本都没有检查这 9 个面板中的任何一个——这两个 linter 都只遍历仪表板平面、顶级的 `panels[]` 数组，并明确 `continue` 跳过 `type === 'row'`，而没有递归到行的嵌套 `panels[]` 中（通过直接读取 `query-budget-linter.js` 源码确认，并且通过针对这个确切文件重新运行它来确认：尽管下面的面板确实包含进行范围扫描的、原始 `ldi_data` 查询，但显示 `0 errors, 0 warnings`）。**这意味着这 9 个面板实际上从未被 CI 检查过，无论它们是否被孤立**——这是在发现 A 的渲染错误之外，进行恢复之前需要“信任但要重新验证”的第二个独立原因。

## A. 当前状态架构

- **数据平面 (Data plane)**：TimescaleDB（`public.ldi_data` 超表，目前 97,401 行，分块；用于范围查询的 `ldi_data_1m`/`_15m`/`_1h` 连续聚合；用于工厂/区域/机器身份模型的 `public.devices`——5 个真实的 `location` 区域值，23 个注册为 `device_type='ldi'` 的机器中有 10 个正在实际报告）。

- **展示平面 (Presentation plane)**：10 个 Grafana 仪表板（`docs/architecture/DASHBOARD_INVENTORY.md`，自动生成，从不手动编辑）+ `services/factory-twin-3d/`（Express + Three.js，冻结状态，通过与 `alarm-api` 相同的 nginx 模式使用 `auth_request` 门禁）。

## 最终建议 (Final recommendation)

**拓扑结构**：就地修复 `ims-ldi-manufacturing.json` ——不要创建新的仪表板。该文件已经包含了一个排序正确的、C 级别优先的结构；它只是损坏了，并没有丢失。

**实施顺序**：首先单独执行第 1 阶段（面板修复），这证明了这项工作的大部分是合理的——它的成本只是一次 JSON 结构修复加上两个小范围的查询警告，但换来的是找回 9 个早先设计好且已经过实际环境验证的面板。第 2 阶段（重新分组）只是表面装饰，成本低廉，应紧接着完成。第 3 阶段（链接配置）才是该阶段名称所承诺的实际“集成”工作，并且必须建立在第 1、2 阶段的基础上，这样链接才能跳转到正确的位置。第 4 阶段（验证）是不容妥协的，因为我们发现当前的两个 linter 都无法检测到这些面板——恢复后面板通过干净的 linter 检测将是一个极具意义的信号，证明这个仪表板上的 SPC、警报和追溯面板第一次真正在被检验。

建议将实施阶段的第一阶段作为一个独立的 SDD 任务开始，在进入第二阶段之前停下来进行审查，遵循与本会话中每一项任务相同的纪律。
