## 执行摘要

### IMS (基础设施监控系统) 项目

IMS 计划构成了在实习开发项目期间设计的端到端监控架构。主要战略目标是：

1. **设计实时监控架构**，涵盖组织的 IT 基础设施。
2. **执行严格的实习生技术培训**，使用行业标准、生产级的监控工具链。
3. **交付明确的杰作项目**，准备好立即进行生产部署和执行演示。

### 交付成果

| 指标                          | 项目前基准           | 项目后成就               | 增量  |
| ----------------------------- | -------------------- | ------------------------ | ----- |
| **监控覆盖率**                | 0%                   | 100% (5 台服务器)        | +100% |
| **平均检测时间 (MTTD)**       | 30+ 分钟             | < 1 分钟                 | -97%  |
| **平均响应时间 (MTTR)**       | 2+ 小时              | < 15 分钟                | -87%  |
| **可见性**                    | 手动检查             | 实时仪表板               | +100% |
| **警报**                      | 无                   | 自动多渠道               | +100% |

## 项目目标与成就

### 目标 1：实时监控

**状态**：完全实现

**关键交付物：**

- 以严格的 30 秒间隔协调 SNMP 轮询。
- 建立了涵盖 CPU、RAM、磁盘、网络（每个接口）和温度指标的全面遥测。
- 设计了高度可扩展的设备注册表模式，支持 1-1000+ 个实例。
- 集成 LDI 制造遥测（吞吐量、PE、JE、湿度、功率、振动）。

**技术栈：**

- Node-RED 驱动核心数据管道。
- SNMP v2c/v3 促进数据收集。
- TimescaleDB 提供强大的时间序列存储。

### 目标 2：健康监控

**状态**：完全实现

**关键交付物：**

- 实施对服务器、网络设备和关键服务的持续、主动监控。
- 设计了强大的资源使用遥测（CPU、RAM、磁盘、网络）。
- 开发了精确的每接口带宽计算逻辑（Mbps）。
- 部署了实时接口运行状态检测（UP/DOWN）。

**技术栈：**

- HOST-RESOURCES-MIB 映射服务器指标。
- IF-MIB 映射网络接口指标。
- 专门为 LDI 制造指标设计的自定义 MIB 定义。

### 目标 3：减少停机时间

**状态**：完全实现

**关键交付物：**

- 建立了利用线性回归方法的预测性警报模型。

## 挑战与解决方案

### 挑战 1：SNMP Walker 的不可靠性

**问题**：`snmpsim` GETNEXT 操作无法遵守结构化的子树边界 —— 导致 walker 实现灾难性地溢出到无关的 OID 范围。

**解决方案**：完全弃用 SNMP walker 节点，转而利用通过自定义函数节点编排的直接 SNMP GET 操作。

```javascript
// 替代标准的 SNMP walker 节点
const oids = ["1.3.6.1.2.1.25.3.3.1.2.1", "1.3.6.1.2.1.25.3.3.1.2.2"];
session.get(oids, (err, varbinds) => {
  if (err) {
    node.error("SNMP error: " + err.message);
    return;
  }
  // 处理检索到的 varbinds
});
```

### 挑战 2：流 JSON 损坏

**问题**：PowerShell `ConvertTo-Json` cmdlet 灾难性地破坏了嵌入在 Node-RED 函数 `func` 有效负载字段中的 `\n` 转义序列。

**解决方案**：完全绕过 PowerShell，转而利用直接编辑工具，或通过 Node.js 脚本使用原生的 `JSON.parse/JSON.stringify` 逻辑。

```bash
# 错误的方法
$json | ConvertTo-Json -Depth 20

# 正确的方法
const flows = JSON.parse(fs.readFileSync('flows-ubuntu.json', 'utf8'));
fs.writeFileSync('flows-ubuntu.json', JSON.stringify(flows));
```

### 挑战 3：Barrier 超时

**问题**：Join barriers 在错误恢复场景后始终触发超时 —— 因为 `bypass_error` 线本质上无法将执行流反馈回 barrier 逻辑。

**解决方案**：将 `bypass_error` 线从终端死胡同 `[[]]` 直接重新路由回同步流 `[["join_sync"]]`。

### 挑战 4：Grafana 列漂移

**问题**：重新创建连续聚合会从根本上改变列命名法 (例如，`avg_cpu` 会静默突变为 `avg_cpu_load`)，从而破坏下游仪表板。

**解决方案**：设计了整体迁移脚本，在一个事务中以原子方式更新 TimescaleDB 模式和相关的 Grafana 仪表板 JSON 配置。

### 挑战 5：Docker 主机端口冲突

**问题**：Windows 主机端口映射配置引发了严重的绑定冲突 (导致无法恢复的幽灵端口)。

**解决方案**：清除了仅限内部服务的所有主机端口映射 —— 强制严格依赖 Docker 的内部 DNS 解析。
