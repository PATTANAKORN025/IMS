## 1. 执行摘要

**IMS** 代表着 PCB 生产线上 YSPhotec / LDI 机械设备从**手动监控**系统向**基于 AIOps 的持续自动化监控**的转型。

该系统采用了**开源技术栈**架构，并在保持规定的故障预算（在极端混沌负载下保持 >95% 的流水线成功率）的同时，通过了 **1,000 VUs（虚拟用户）** 的负载测试。

---

## 2. 问题 → 解决方案矩阵

### 之前（遗留问题）

| 问题 | 影响 | 每日成本 |
| ----------------------------- | ------------------------------------------------ | ------------------------------ |
| **手动可见性延迟** | 需要定期巡场检查物理仪表 | 2 名员工 × 4 轮 = 8 小时/天 |
| **停机检测缓慢** | 需要 2-4 小时才能发现故障 | 累计缺陷产量 |
| **手动数据录入** | 人为错误率 ~15% | 无法跟踪趋势 |
| **被动维护** | 等待设备故障后才进行维修 | 计划外停机 |

### <img src="../assets/icons/check-circle.svg" width="14" align="center"/> **状态：** 健康 之后（解决方案）

| 解决方案 | 结果 | 影响 |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| **连续 SNMP 轮询** | 每 30 秒自动收集一次遥测数据 | 消除手动抽样检查 |
| **Z-Score 统计告警** | 在机器发生故障前检测到 3σ 的异常 | 主动维护 |
| **15 个仪表板** | 5 个基础设施监控（NOC、工程深入分析、容量、元监控、采集延迟）+ 10 个生产监控（概览、告警控制台、告警字典、告警响应 (MTTA/MTTR)、工程分析、机器快照、制造指挥中心、操作员安灯 (Andon)、数据就绪度、工厂数字孪生） | 跨基础设施和实际生产线的全面可见性 |
| **LINE/Teams Webhooks** | 告警格式化和发送重试逻辑完整且正确；实际发送需要操作员配置凭证（`LINE_CHANNEL_ACCESS_TOKEN`，`TEAMS_WEBHOOK_URL`），且这些凭证未包含在此代码库中 | 配置后响应更快 |
| **预测分析** | 线性回归预测 | 预防故障发生 |

## 3. 投资回报率 (ROI) 指标

### 之前与之后对比

| 指标 | 之前 (手动) | 之后 (IMS) | 提升幅度 |
| ----------------------- | -------------------------- | ----------------------------- | ------------------------------------------------ |
| **检测时间** | 1-4 小时 | **< 10 秒** | 提升 99.97% |
| **平均修复时间 (MTTR)** | > 2 小时 | **~15 分钟** | 缩短 87.5% |
| **人工劳动** | 8 小时/天（2 名员工） | **消除例行检查** | 每年节省 2,920 小时 |
| **数据准确性** | ~85%（人为错误） | **99.9%** | 准确性提升 +17.5% |
| **数据粒度** | 每天 6 次读数 | **每天 2,880 次读数** | 数据量增加 480 倍 |
| **维护模式** | 被动（坏了再修） | **预测（预防）** | 主动维护大幅减少停机时间 |

### 每年成本节约

| 类别 | 之前 | 之后 | 每年节约 |
| ------------------------ | --------------------------------- | ------------------- | ----------------- |
| **许可证费** | 3,000,000 - 10,000,000 泰铢 | 0 泰铢 (开源) | **300 - 1,000 万泰铢** |
| **人工劳动** | 730,000 泰铢（2,920 小时 × 250 泰铢） | 0 泰铢 | **73 万泰铢** |
| **停机成本** | 500,000 泰铢/次 × N | 接近于零 | **200 - 500 万泰铢** |
| **年度节约总额** | | | **570 - 1,570 万泰铢** |

### 投资回收期

```text
初期投资：~200,000 泰铢（实习生劳动力 + 计算资源）
年度节约：~5,700,000 泰铢（保守估计）
投资回收期：< 1 个月
ROI：2,750%（第 1 年）
```

## 4. 技术成就

| 组件 | 交付内容 |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Docker 栈** | 12 个完全编排的容器 |
| **遥测架构** | 两条独立流水线 — 基础设施 (`sys_metrics`/`net_metrics`/`ldi_metrics`) 和 LDI 生产制造 (`ldi_data`，34 个字段：PE1-6, JE1-4, 厚度, 扫描速度, 光刻胶剂量等) — 参见 `docs/architecture/DATABASE_SCHEMA.md` |
| **告警规则** | 30 条规则：6 条特定于 LDI 的规则 + 11 条基础设施规则（Grafana 原生），13 条流水线/平台元监控规则（Prometheus/Alertmanager） |
| **仪表板** | 15 个仪表板（5 个基础设施 + 10 个生产制造） |
| **负载测试** | 最高达 1,000 VUs（`chaos-stress.js`，注入 5% 的故意故障，>90% 的成功率阈值）；`pipeline-stress.js` 的目标是 >95% 的成功率 — 这不是保证 0% 故障，而是定义的容许故障预算 |
| **CI/CD** | 带有安全扫描的 GitHub Actions (Gitleaks) |
| **文档** | 涵盖架构、运维、用户/管理员手册及企业指南的 40+ 份文档 |
