# การตรวจสอบแบบอ่านอย่างเดียว — สุขอนามัยของสัญญาณเตือน + ขอบเขตบัก RAM + ความสมบูรณ์ของข้อมูลย้อนหลัง + ความสมจริงของซิมูเลเตอร์

> **ตรวจสอบเท่านั้น ไม่มีการแก้ไขไฟล์ใดๆ ไม่มีการคอมมิต ไม่มีการสัมผัสคอนเทนเนอร์** สั่งการโดยผู้ใช้โดยตรงให้ทำงานระหว่าง Soak Attempt 8 โดยไม่รบกวน สิ่งที่อยู่ด้านล่างทั้งหมดเป็นผลลัพธ์ของการสืบค้นแบบเรียลไทม์ การตรวจสอบแดชบอร์ด/ภาพหน้าจอแบบเรียลไทม์ หรือการอ่านไฟล์แบบคงที่ — ไม่มีตัวเลขใดที่ถูกประมาณการหรือนำมาจากรอบก่อนหน้าโดยไม่ได้ตรวจสอบซ้ำกับระบบจริง

## 1. สุขอนามัยของสัญญาณเตือน (ตรวจสอบซ้ำจาก `SPEC_ALERT_HYGIENE.md` เขียนเมื่อ 2026-08-14)

ตรวจสอบ 5 รายการทั้งหมดซ้ำกับสถานะ JSON ของแดชบอร์ดและ DB ในปัจจุบัน — ข้อค้นพบในข้อกำหนดนั้นเก่าแล้ว แต่สิ่งนี้เป็นการยืนยันว่ามีอะไรเปลี่ยนแปลงไปตั้งแต่นั้นมาหรือไม่

| รายการ | สิ่งที่ระบุในข้อกำหนด | สิ่งที่ยืนยันวันนี้ |
| --- | --- | --- |
| 1. แดชบอร์ด MTTA/MTTR | ไม่มีอยู่ | **ยังคงไม่มีอยู่** — `grep -ri "MTTA\|MTTR"` ทั่วทั้ง JSON ของแดชบอร์ด: พบ 0 รายการ |
| 2. เปลี่ยนชื่อ 2 พาเนล "Critical Alarms" | 2 ใน 4 ยังคงผิด (`ims-easy-overview`, `ims-ldi-manufacturing`); 2 ได้รับการแก้ไขแล้ว | **ไม่เปลี่ยนแปลง** — grep ยืนยันว่า 2 พาเนลเดิมยังคงชื่อ "Critical Alarms" / "Critical Alarms (1h)"; พาเนลของ `ims-ldi-operator-andon` คือ "Active Critical/Major Alarms (master-code matched)" อย่างถูกต้อง (ยืนยันด้วยสายตาในภาพหน้าจอก่อนหน้านี้ของเซสชันนี้ด้วย) `ims-ldi-alarm-console` ไม่มีพาเนลนับจำนวน Critical-Alarms เลย (ข้อสมมติฐานของข้อกำหนดเกี่ยวกับพาเนลที่ 4 นั้นไม่เป็นความจริง — มีเพียง 3 พาเนลที่มีรูปแบบนี้อยู่จริง ไม่ใช่ 4; ไม่ใช่ปัญหาใหม่ แค่เป็นการแก้ไขการนับของข้อกำหนดเอง) |

| 5. การทดสอบโหลดแบบ Debounce | ไม่มีสคริปต์อยู่ | **ไม่เปลี่ยนแปลง** — ไม่มีไฟล์ที่ตรงกับ `*debounce*` ภายใต้ `tests/` หรือ `scripts/`; มีเพียง migration และ flow logic ที่ _ใช้งาน_ debounce เท่านั้น ไม่มีบททดสอบที่สร้างภาระให้กับมัน |

**สรุป: รายการที่ 4 ทำไปแล้ว 1/3 ส่วนอื่นๆ ทั้งหมดในข้อกำหนดนี้ยังคงเหมือนเดิมบนวันที่ 2026-08-14** ปลอดภัยที่จะทำการแก้ไขแบบกลุ่มหลังจากสิ้นสุดระยะ soak (ทั้ง 5 รายการเป็นเพียงการแก้ไข JSON ของแดชบอร์ด หรือสคริปต์ทดสอบใหม่ — ไม่จำเป็นต้องรีสตาร์ทคอนเทนเนอร์สำหรับรายการใดๆ)

## 3. ความสมบูรณ์ของข้อมูลย้อนหลัง — พบอิสระ 3 รายการ ไม่ใช่ 1

ได้ตรวจสอบหาช่องโหว่ ข้อมูลซ้ำ และตรวจสอบโดยรวมว่าตัวเลขใน `sys_metrics`/`ldi_data`/`net_metrics`/`ldi_alarm_log` สามารถเชื่อถือได้หรือไม่ พบปัญหาจริงแยกจากกัน 3 ปัญหา — ไม่มีข้อใดกระทบกับ telemetry ของการผลิต (`ldi_data`) หรือบันทึกสัญญาณเตือน (`ldi_alarm_log`) ที่ข้อมูลสำหรับ RCA/SPC สร้างขึ้น ซึ่งทั้งคู่มีความสะอาด

### 3a. ช่องว่างในการนำเข้าข้อมูล 2 ช่วงใน `sys_metrics` (เฉพาะ telemetry ของ infra เท่านั้น)

`time_bucket('15 min', time)` ตลอดประวัติของ `sys_metrics` แสดงช่วงเวลาหลายชั่วโมง 2 ช่วงที่ **ไม่มีแถวข้อมูลเลย**: `2026-08-13 09:45` → `2026-08-14 01:15` (~15.5 ชม.) และ `2026-08-14 09:45` → `2026-08-15 01:15` (~15.5 ชม.) ช่องว่างที่ 2 ได้รับการยืนยันโดยอิสระจากการตรวจสอบบันทึก soak ก่อนหน้านี้ของเซสชันนี้ (โฮสต์ปิดเครื่องระหว่างตัวอย่างสุดท้ายของ Attempt-7 และการรีบูตเมื่อ 2026-08-15T01:09:30Z) — นี่คือเหตุการณ์เดียวกันที่เห็นจากแหล่งข้อมูล 2 แหล่งที่แตกต่างกัน ไม่ใช่ความลึกลับใหม่ ช่องว่างแรกไม่ได้รับการตรวจสอบมาก่อน; คุ้มค่าที่จะตรวจสอบอย่างรวดเร็วก่อนการทดสอบ soak ครั้งถัดไปจะเริ่ม (ไม่ได้ทำในรอบนี้ — ขอบเขตแบบอ่านอย่างเดียว และมันคือประวัติ ไม่ใช่เรื่องเร่งด่วน)

### 3b. `sys_metrics` มีแถวข้อมูลซ้ำ 67% — บักจริงที่ไม่เคยพบมาก่อน แยกเฉพาะตารางนี้เท่านั้น

```sql
SELECT COUNT(*) AS total_rows, COUNT(*) - COUNT(DISTINCT (device_id,time)) AS extra_dup_rows FROM public.sys_metrics;
-- total_rows=13317  extra_dup_rows=8911  (66.9%)
```

คู่ของ `(device_id, time)` แต่ละคู่มีข้อมูลตรงกันเป๊ะ 3 หรือ 4 แถว — ไม่เคยมี 1, ไม่เคยมี 2, ไม่เคยมี 5+ (4,307 คู่ที่ 3x, 99 คู่ที่ 4x) แถวข้อมูลที่ซ้ำกันนั้นเหมือนกันทุกระดับไบต์ (ค่า disk/ram/cpu เท่ากัน, timestamp ระดับไมโครวินาทีเดียวกัน) ดังนั้นนี่ไม่ใช่เรื่องการเบี่ยงเบนของเวลาหรือการลองใหม่ด้วยข้อมูลที่แตกต่าง — มันคือตัวอย่างเดียวกันที่ถูกเขียนหลายครั้ง

**สาเหตุที่แท้จริง ตรวจสอบจาก node-by-node จาก `sre_parser` ไปยัง `INSERT` จริง ไม่ต้องอนุมานอีก** (การติดตามรอบที่ 2, 2026-08-15T03:1x Z):

- `sre_parser` (`nodered_data/flows.json`, function node, "SRE AIOps Parser v9 (Batch)") ต่อเชื่อมกับโหนดปลายทางเพียงโหนดเดียว: โหนด `postgresql` ที่ชื่อว่า `TimescaleDB` (`db_insert`), รวมกับดีบักโหนด — ไม่มีการกระจายตัวที่ระดับ DB ดังนั้นการคูณกันนี้เกิดขึ้น _ภายใน_ `sre_parser` เอง ไม่ใช่จากเส้นทางการ insert หลายเส้นทาง อ่านเนื้อหาของฟังก์ชันทั้งหมด:
- `sre_parser` ถูกเรียกใช้หนึ่งครั้งต่อข้อความประเภท SNMP-walker (`walk_cpu`, `walk_storage`, `walk_net_get`, `walk_temp`, `walk_ldi` ทั้งหมดเชื่อมเข้ามาแยกกัน — ยืนยันในรอบก่อนหน้า)
- มันเก็บอ็อบเจกต์ `state` หนึ่งตัวต่ออุปกรณ์ (`flow.get('dev_state_'+ctxKey)`) อัปเดตเฉพาะส่วนที่เกี่ยวข้องกับ `walkerType` ที่เพิ่งเข้ามา (เช่น `walkerType === 'storage'` อัปเดตเฉพาะ `state.ram_*`/`state.disk_*`)
- **บักคือบรรทัดนี้**: `if (walkerType === 'cpu' || walkerType === 'storage' || walkerType === 'temp') { ...; buffer.sys.push({device_id, cpu_cores: state.cpu_cores, ..., ram_total_mb: state.ram_total, ..., disk_total_gb: state.disk_total, ..., temp_c: state.temp}); }` — มันส่ง **สแน็ปช็อตแบบเต็มของ `state` ที่ใช้ร่วมกัน** (cpu + ram + disk + temp รวมกัน) เข้าไปยังบัฟเฟอร์กลุ่ม `sys` เมื่อมีการเสร็จสิ้นของ walker แต่ละประเภท _ทุกอัน_ ใน 3 ชนิด ไม่ใช่เพียงครั้งเดียวต่อรอบการสุ่มถาม (polling cycle) จริง walker 3 ตัวสิ้นสุดในหน้าต่างเวลา ~10 วินาทีเดียวกัน โดยแต่ละตัวทำการส่งสแน็ปช็อตสถานะเดิมที่แทบจะไม่มีการเปลี่ยนแปลงเข้าไปใหม่ — นั่นคือรูปแบบ "มักจะ 3, บางครั้ง 4" (walker ตัวที่ 4 เกิดขึ้นใกล้กับขอบเขตการล้างบัฟเฟอร์) ตรงกันพอดี
- ทุก ๆ `BATCH_INTERVAL_SEC` (10 วินาที), อาร์เรย์ `buffer.sys` ที่สะสมไว้จะถูกล้างเป็น **`INSERT INTO sys_metrics (...) VALUES (NOW(),...),(NOW(),...),(NOW(),...)` แบบหลายแถวข้อมูลในสเตตเมนต์เดียว** (`buildBatchQueries`) Postgres ประเมินค่า `NOW()` หนึ่งครั้งต่อสเตตเมนต์/ทรานแซกชัน ไม่ใช่หนึ่งครั้งต่อแถวข้อมูล — ดังนั้น 3-4 แถวใน INSERT ครั้งนั้นจึงได้รับค่า `time` ที่ _เหมือนกันเป๊ะ_ ซึ่งเป็นเหตุผลที่ข้อมูลซ้ำมี timestamp ระดับไมโครวินาทีเหมือนกันจนถึงตัวเลขสุดท้าย ไม่ใช่แค่ค่าที่ใกล้เคียงกัน
- walker ประเภท `net` และ `ldi` ส่งไปยังบัฟเฟอร์ _แยกกัน_ (`buffer.net`, `buffer.ldi`) เพียงครั้งเดียวเมื่อตัวเองเสร็จสิ้น — ไม่มีรูปแบบหลาย walker เข้าแถวเดียวแบบนี้สำหรับตารางเหล่านั้น ซึ่งเป็นเหตุผลชัดเจนที่ `net_metrics` ตรวจสอบแล้วสะอาดจากผลกระทบด้านล่าง (หมายเหตุ: สาขา `ldi` ของ `sre_parser` เขียนข้อมูลลงในตารางที่ชื่อว่า `ldi_metrics` ไม่ใช่ `ldi_data` — ตาราง telemetry ของการผลิตขนาด 34 คอลัมน์ที่ตรวจสอบข้อมูลซ้ำด้านล่างถูกบันทึกด้วยกลไกที่ต่างกันโดยสิ้นเชิง ไม่ใช่ฟังก์ชันนี้ ไม่ได้เปลี่ยนแปลงข้อค้นพบ เพียงแค่เป็นการชี้แจงชื่อ)

**ตำแหน่งแก้ไขที่แน่นอนสำหรับ Phase A1** (ไม่ได้เขียนในรอบนี้ — ตรวจสอบเท่านั้น): `nodered_data/flows.json`, ไอดีโหนด `sre_parser`, บรรทัด `if (walkerType === 'cpu' || walkerType === 'storage' || walkerType === 'temp') { enforceBufferLimit(buffer.sys, 'sys'); buffer.sys.push({...}); }` จำเป็นต้อง push ข้อมูลเพียงครั้งเดียวต่อรอบ polling จริง (เช่น ควบคุมที่ประเภท walker สุดท้ายที่คาดหวังต่อรอบ หรือติดตามว่าประเภท walker ใดได้รายงานแล้วนับจากการ push ครั้งล่าสุด และ push เพียงครั้งเดียวเมื่อครบทั้ง 3 แบบ) แทนที่จะเป็นหนึ่งครั้งต่อองค์ประกอบประเภท walker

**รัศมีผลกระทบ**: ยืนยันว่าแยกเฉพาะใน `sys_metrics` ตรวจสอบ `ldi_data` (0 รายการซ้ำ / 34,689 แถว), `ldi_alarm_log` (0 รายการซ้ำ / 677 แถว), `net_metrics` (0 รายการซ้ำ / 8,546 แถว) — ทั้งหมดสะอาด เพราะแต่ละตารางถูกเขียนจาก walker ประเภทเดียว (`ldi`, alarm-trigger logic, `net` ตามลำดับ) ไม่ใช่การรวมเข้าด้วยกัน **นี่หมายความว่า พาเนลของแดชบอร์ดทุกตัวที่ทำการ `COUNT(*)` หรือวัดอัตราแถว/วินาที จาก `sys_metrics` โดยตรง (ไม่ใช่การเฉลี่ยอัตราส่วน ซึ่งข้อมูลซ้ำไม่ทำให้บิดเบือน) มีการรายงานเกินไปประมาณ 3 เท่าตัวมาตลอด** ยังไม่ได้ตรวจสอบว่าพาเนลใดที่ใช้ข้อมูลดิบนับจำนวนเทียบกับค่าเฉลี่ย — นั่นคือสิ่งที่จะทำในรอบต่อไป ไม่ใช่รอบนี้

### 3c. การกำหนดค่าดิสก์ของ `ubuntu.snmprec` ถูกตรึงทางคณิตศาสตร์ไว้ที่ 100% — บักที่แยกจากปัญหา RAM

`disk_used_gb == disk_total_gb` สำหรับ `ERP-MASTER-UBUNTU` ใน **ทุก ๆ ตัวอย่างในประวัติทั้งหมด** (ย้อนกลับไปถึง 2026-08-13, ข้อมูลเก่าที่สุด) ยืนยันว่านี่ไม่ใช่บักการสะสม RAM (โค้ดจัดการดิสก์ของ `parser.js` ทำการแทนที่แบบสะอาด `=` ทุกรอบ ไม่ใช่ `+=` — อ่านโดยตรง ไม่ใช่เดา)

สาเหตุหลักอยู่ใน `monitoring/snmpsim/ubuntu.snmprec` เอง:

```
1.3.6.1.2.1.25.2.3.1.5.2|2|52428800          <- hrStorageSize (ดิสก์), คงที่
1.3.6.1.2.1.25.2.3.1.6.2|2:numeric|min=65536000,max=125000000,rate=50000   <- hrStorageUsed (ดิสก์), การสุ่มเดิน
```

_ค่าต่ำสุด_ ของพื้นที่ใช้ไป (65,536,000) มีค่าเกินพื้นที่รวมคงที่ (52,428,800) อยู่แล้ว — พื้นที่ใช้ไปไม่มีทางน้อยกว่า ~125% ของพื้นที่รวมตามการออกแบบ และ `Math.min(diskUsedGb, diskTotalGb)` ใน `parser.js` ก็ทำการบีบให้เท่ากับ 100% พอดีทุกครั้ง ซึ่งเป็นสิ่งที่สังเกตเห็นได้ชัดเจน นำไปเปรียบเทียบกับ `windows.snmprec` ซึ่งใช้รูปแบบของพื้นที่ใช้ไปแบบ **เดียวกัน** (`min=65536000,max=125000000` — ตัวเลขเหมือนกัน) แต่มีพื้นที่รวมที่ถูกต้อง (`200000000`) ซึ่งครอบคลุมค่าใช้อย่างปลอดภัย นี่คือบักจากการคัดลอกและวางการตั้งค่า: เทมเพลตของการใช้นี้ถูกนำมาใช้ซ้ำในไฟล์ `.snmprec` ทั้งสองไฟล์ โดยไม่ได้คำนวณขนาดดิสก์ของ `ubuntu.snmprec` ใหม่อยู่เหนือกว่านั้น

**การแก้ไข (2026-08-15, P0.2 investigation)**: การเติบโต "9,375 → 12,500 GB" ด้านบนนั้นผิดพลาด -- มันเป็นความคลาดเคลื่อนจากการวัดจากการสืบค้น `AVG()` ในส่วนของ `time_bucket('10 min', ...)` ของเอกสารนี้เอง ไม่ใช่เทรนด์จริง ตรวจสอบแถวข้อมูลดิบแบบไม่แบ่งช่วงเวลา: `disk_total_gb` สำหรับ `ERP-MASTER-UBUNTU` มีค่าที่แตกต่างกันเพียง 2 ค่าเท่านั้นในประวัติทั้งหมด -- `0` (9 แถว, จากการเปลี่ยนเป็นศูนย์ตอนสถานะ `isOffline`/`isEmpty` ของ parser ในช่วงที่ walker ขาดหายชั่วคราว) และ `12500` (3,478 แถว, ทุก ๆ ตัวอย่างที่เหลือ) ไม่มีค่าตรงกลางในข้อมูลดิบเลย ช่วงเวลาเฉลี่ย 10 นาทีที่มีแถวข้อมูล `12500` อยู่สามแถวกับแถวข้อมูล `0` หนึ่งแถว จะทำให้ค่าเฉลี่ยเป็น `9375` -- สิ่งนี้เป็นผลพวงจากหน้าต่างการเฉลี่ย ไม่ใช่กระบวนการจริง `disk_total_gb` ถูกตรึงไว้ที่ 12500 เป๊ะ (ตรงกับการคำนวณ `size × au` แบบคงที่) ตั้งแต่ตัวอย่างแรกสุด ไม่มีกลไกที่ 2 อยู่จริง; สิ่งนี้สามารถอธิบายได้อย่างครบถ้วนจากการกำหนดช่วงการใช้งานใน `.snmprec` ที่ผิดพลาดตามที่อธิบายไว้ข้างต้นแล้ว

## 4. ความสมจริงของซิมูเลเตอร์ — ตรวจสอบสถานะซ้ำ ไม่ใช่การตรวจสอบซ้ำเต็มรูปแบบ

`LDI_ALARM_FIDELITY_AUDIT.md` (2026-08-11, คะแนน 58/100) เกิดขึ้นก่อน `Phase D` (debounce, งาน #183) และ `Phase F` (รหัส Critical หายาก, งาน #185) ซึ่งทั้งสองเสร็จสิ้นในภายหลังตามประวัติงาน ตรวจสอบการค้นพบสำคัญสองข้อจากการดำเนินการจริงแทนการอ้างอิงคะแนนที่ล้าสมัย:

- **การค้นพบ #6 (ไม่มี debounce, โจมตีอย่างต่อเนื่อง)**: ตรวจสอบซ้ำแล้ว จากช่วงเวลาระหว่างสัญญาณเตือนแบบเดียวกัน 549 รายการที่วัดได้ในวันนี้ มีเพียง 1 รายการเท่านั้นที่ต่ำกว่า 15 วินาที (ก่อนหน้านี้มีหลายร้อยรายการ บ่อยครั้งในการตรวจสอบดั้งเดิม) **Debounce มีอยู่จริงและทำงานได้ดี**
- **การค้นพบ #8/#9 (ไม่สามารถเกิดสัญญาณเตือนระดับความรุนแรง Critical ได้)**: ตรวจสอบซ้ำแล้ว แค็ตตาล็อกตอนนี้มี 43 แถวแบบ Critical (จากเดิมเป็น 0) และ **มีสัญญาณเตือนความรุนแรง Critical เกิดขึ้นจริงแล้ว 1 รายการ** ในชุดข้อมูลสด (จากเดิมที่เป็นไปไม่ได้ในเชิงโครงสร้าง) **แก้ไขแล้ว ยืนยันด้วยเหตุการณ์ที่ถูกสร้างขึ้นจริง ไม่ใช่แค่การเปลี่ยนแค็ตตาล็อก**

**คะแนน 58/100 ตอนนี้ถือว่าล้าสมัยในทางที่ดีขึ้น** — การตรวจสอบซ้ำเต็มรูปแบบ (ทั้ง 10 หัวข้อ ตามภาคผนวกสืบค้นของ `LDI_ALARM_FIDELITY_AUDIT.md`) มีแนวโน้มว่าจะได้คะแนนที่สูงขึ้นอย่างมีความหมาย แต่ไม่ได้ตรวจสอบซ้ำเต็มรูปแบบในรอบนี้ (นอกขอบเขตสำหรับการตรวจสอบแบบอ่านอย่างเดียว; มันคือขั้นตอนถัดไปที่ถูกต้อง ไม่ได้ทำที่นี่) การวัด RCA Lift ซ้ำก่อนหน้านี้ในเซสชันนี้ (`LDI_RCA_GUIDE.md`, ข้อควรระวังเดียวกัน: กลุ่มตัวอย่างหลังรีเซ็ตมีขนาดเล็ก ประเภทส่วนใหญ่ตัวอย่างต่ำ) เป็นจุดข้อมูลที่เกี่ยวข้องและปัจจุบันอยู่แล้ว — ไม่ขอทำซ้ำที่นี่

ข้อกำหนดรายการที่ 1 แบบเจาะจงของ `SPEC_SIMULATOR_REALISM.md` (การย้อนรอยของโค้ด noise, ได้เขียน diff การแก้ไขที่แน่นอนไว้แล้ว) ถูกอ่านซ้ำโดยเทียบกับ `nodered_data/flows.json` ปัจจุบัน — บรรทัดที่วินิจฉัยไม่เปลี่ยนแปลง, การแก้ไขยังคงแม่นยำ และยังไม่ได้ถูกปรับใช้

## สรุปสำหรับการวางแผนการแก้ไขเป็นกลุ่ม (หลังจาก Soak Attempt 8 เสร็จสิ้น)

เรียงลำดับตามความน่าเชื่อถือของหลักฐานและรัศมีผลกระทบ ไม่ใช่ความพยายาม:

1. **`sys_metrics` ค่านำเข้าซ้ำ 3-4x** (§3b) — จำนวนที่ใหญ่ที่สุด (67% ของทั้งตารางสูญเปล่า, ทุกๆ พาเนลที่นับแบบดิบผิดพลาด ~3x) สาเหตุที่แท้จริงเกิดจากรูปแบบ walker-fan-in แต่การเดินสายเชื่อมต่อกับโหนด insert ที่แน่นอนต้องการการตรวจสอบอีกครั้งก่อนเขียนการแก้ไข ปัญหาใหม่ ไม่อยู่ในเอกสารข้อมูลจำเพาะก่อนหน้า — จำเป็นต้องมีข้อมูลจำเพาะเป็นของตัวเองก่อนแก้ไขเป็นชุด
2. **บักสะสม RAM** (ระบุสเปคไว้แล้ว, `SPEC_RAM_METRIC_ACCUMULATION_BUG.md`) — แก้ไขขอบเขตเป็น 3 แดชบอร์ด
3. **การตั้งค่าดิสก์ที่ผิดพลาดของ `ubuntu.snmprec`** (§3c) — การค้นพบใหม่ เป็นการแก้ไขที่ตัวไฟล์ config เท่านั้น (ไม่จำเป็นต้องเปลี่ยน `parser.js`) ตามหลักการแล้วไม่จำเป็นต้อง deploy โค้ดของ Node-RED ใหม่เลย — แค่แก้ไขไฟล์ `.snmprec` และทำการรีสตาร์ทตัวคอนเทนเนอร์ `snmpsim` เป็นการเฉพาะ ควรตรวจสอบว่าการทำเช่นนั้นเป็นแคบๆ ซึ่งมีความเสี่ยงต่ำกว่าการ redeploy Node-RED เต็มรูปแบบหรือไม่
4. **สุขอนามัยของสัญญาณเตือน รายการที่ 1, 2, 3, 5** (`SPEC_ALERT_HYGIENE.md`) — ทั้งหมดเป็นเพียงการแก้ไข JSON ของแดชบอร์ด หรือสคริปต์ทดสอบใหม่เท่านั้น, ไม่จำเป็นต้องรีสตาร์ทคอนเทนเนอร์เลย; สามารถทำได้ **ก่อน** ที่ 3 รายการอื่นจะเข้ามา, เป็นอิสระจากวงจร soak ถ้าต้องการ
5. **การตรวจสอบรายการที่ 4 ที่เหลืออีก 2 ตัวตรวจสอบ lifecycle** (ติดอยู่-OPEN, แถวข้อมูลที่ไม่ได้ใช้) — หมวดหมู่เดียวกับ #4, บนแดชบอร์ดเท่านั้น
