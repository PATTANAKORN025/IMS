# การสำรองและการกู้คืนข้อมูล

> **กลุ่มเป้าหมาย:** SRE/ฝ่ายปฏิบัติการ, QA/ฝ่ายตรวจสอบ
> **วัตถุประสงค์:** จัดเตรียมขั้นตอนที่ผ่านการตรวจสอบแล้วสำหรับการสำรองและกู้คืนฐานข้อมูล
> **ที่มา:** ขั้นตอนด้านล่างนี้มาจากขั้นตอนการทดสอบ `backup-restore` ใน `scripts/dr-test.sh` ซึ่งได้รับการดำเนินการจริงและบันทึกหลักฐานเมื่อวันที่ 2026-08-10

---

## ขั้นตอนการสำรองข้อมูล

```bash
docker exec ims-timescaledb pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" > backup.sql
```

สแนปชอต `pg_dump` แบบไม่บีบอัดที่ดึงมาจากฐานข้อมูลการผลิต **ประสิทธิภาพจากการวัดผลจริง** (2026-08-10, แถว `ldi_data` ~52,800 แถว + `devices` ~1,025 รายการ + แถว `ldi_alarm_log` ~10,400 แถว): **1 วินาที, 22.3 MB** `pg_dump` จะแจ้งเตือนเกี่ยวกับข้อจำกัดคีย์ต่างประเทศแบบวนซ้ำ (circular foreign-key constraints) ใน `continuous_agg` ซึ่งเป็นเรื่องที่คาดไว้และไม่เป็นอันตรายสำหรับสแต็กนี้ (ตารางแค็ตตาล็อกของ TimescaleDB เอง) และไม่ใช่สัญญาณว่าไฟล์ดัมพ์เสียหาย

## ขั้นตอนการกู้คืนข้อมูล

```bash
docker exec ims-timescaledb psql -U "$POSTGRES_USER" -d postgres -c "CREATE DATABASE ims_dr_test;"
docker exec -i ims-timescaledb psql -U "$POSTGRES_USER" -d ims_dr_test < backup.sql
```

**ประสิทธิภาพจากการวัดผลจริง:** 18 วินาที สำหรับขนาดชุดข้อมูลเดียวกัน

## การตรวจสอบ: การกำหนดช่วงของจำนวนแถว ไม่ใช่ความเท่ากันทุกประการ

นี่คือ **ระบบการนำเข้าข้อมูลแบบสด** ตัวจำลองจะเขียนข้อมูลอย่างต่อเนื่อง การตรวจสอบแบบง่ายๆ ด้วยการหา "จำนวนที่กู้คืน == จำนวนสด" จะทำให้เกิดความคลาดเคลื่อน เนื่องจากข้อมูลจะถูกบันทึกในระหว่างดำเนินการสร้างสแนปชอต `scripts/dr-test.sh` จัดการปัญหานี้อย่างถูกต้อง: โดยจะบันทึกจำนวนแถว _ก่อน_ และ _หลัง_ การสร้างสแนปชอต จากนั้นจึงตรวจสอบว่าจำนวนที่กู้คืนมาอยู่ในช่วงดังกล่าว (รวมค่าขอบเขต) หรือไม่ พฤติกรรมนี้ได้รับการตรวจสอบระหว่างการทดสอบ DR แล้ว สคริปต์การตรวจสอบได้กำหนดช่วงครอบคลุมจำนวนข้อมูลสดระหว่างขั้นตอนการสร้างสแนปชอตได้อย่างถูกต้อง

```bash
./scripts/dr-test.sh backup-restore
```

เรียกใช้การทดสอบแบบ End-to-end เต็มรูปแบบ: การดัมพ์, การกำหนดช่วงจำนวนสด, การกู้คืนลงในฐานข้อมูลการตรวจสอบ `ims_dr_test` แบบชั่วคราว (**ไม่แตะต้องฐานข้อมูลสด**), ตรวจสอบ จากนั้นจึงลบฐานข้อมูลที่สร้างทิ้ง ผลลัพธ์จริงในวันที่ 2026-08-10: **ผ่าน (PASS)** — `devices=1025 ldi_data=52795→52796 (bracket) alarm_log=10405`, โดยจำนวนที่กู้คืนคือ `52795` ซึ่งอยู่ในช่วงที่กำหนด

## สิ่งที่การสำรอง/กู้คืนข้อมูล _ไม่_ ครอบคลุม

- **Continuous aggregates และ materialized views จะไม่ถูกเติมข้อมูลใหม่โดยอัตโนมัติด้วยการกู้คืนแบบธรรมดา** — เอาต์พุตของ `pg_dump` จะรวมคำจำกัดความของสิ่งเหล่านี้ไว้ด้วย แต่เป้าหมายการกู้คืนข้อมูลใหม่จำเป็นต้องมีส่วนขยาย TimescaleDB และตัวกำหนดเวลาการทำงานเบื้องหลังที่ทำงานอยู่ ก่อนที่ CAGGs จะทำการรีเฟรช สำหรับการสร้างสภาพแวดล้อมใหม่ทั้งหมด (ไม่ใช่แค่ข้อมูล) โปรดดูขั้นตอน Full-Stack Recreate ใน `docs/operations/DR_TEST_PLAN.md`
- **แดชบอร์ด Grafana, กฎการแจ้งเตือน และแผงควบคุมไลบรารี** ได้รับการจัดสรรผ่านไฟล์ (`monitoring/grafana/`) ไม่ได้เก็บไว้ในฐานข้อมูล ซึ่งสิ่งเหล่านี้จะกลับมาทำงานโดยอัตโนมัติเมื่อคอนเทนเนอร์เริ่มทำงานจากไฟล์ที่มีการติดตามใน Repository เอง ไม่ใช่จากการสำรองฐานข้อมูล
- **โฟลว์ Node-RED** เป็นแบบอิงตามไฟล์เช่นกัน (`nodered_data/flows/`) และไม่ได้เป็นส่วนหนึ่งของการสำรองฐานข้อมูล

การสำรองฐานข้อมูลเพียงอย่างเดียวไม่ใช่แผนการกู้คืนความเสียหายทั้งหมด โปรดดู `docs/operations/DR_TEST_PLAN.md` และ `docs/operations/INCIDENT_RESPONSE.md` สำหรับภาพรวมที่สมบูรณ์ รวมถึงช่องว่างด้านความน่าเชื่อถือที่เกิดขึ้นจริงซึ่งการทดสอบ DR ของระบบนี้ตรวจพบ (นโยบายการรีสตาร์ทคอนเทนเนอร์ไม่สามารถกู้คืนจากการถูกสั่งยุติการทำงานได้อย่างน่าเชื่อถือ — ดูด้านล่าง)

## ข้อจำกัดของระบบและข้อควรพิจารณาในการปฏิบัติงาน

การทดสอบ DR ในวันที่ 2026-08-10 พบพฤติกรรมการกู้คืนเฉพาะด้วยการใช้ `restart: unless-stopped` สำหรับ `ims-timescaledb` หลังจากการจำลองการสั่งยุติกระบวนการทำงานในสภาพแวดล้อมนี้ (ยืนยันผ่านการสตรีมมิ่ง `docker events` แบบสด) การสำรองข้อมูลเป็นพื้นฐานของการกู้คืน และการกู้คืนกระบวนการฐานข้อมูลก็มีความสำคัญไม่แพ้กัน โปรดดูข้อจำกัดของระบบและขอบเขตทางเทคนิคใน `ARCHITECTURE.md` และ `docs/operations/INCIDENT_RESPONSE.md` สำหรับขั้นตอนการกู้คืนด้วยตนเอง
