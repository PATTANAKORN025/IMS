# Disaster Recovery Test Plan (แผนการทดสอบการกู้คืนระบบจากภัยพิบัติ)

> ตาม `docs/architecture/IMS_MANUFACTURING_PLATFORM_V2.md` §6. การซ้อม 3 ครั้ง จะดำเนินการผ่าน `scripts/dr-test.sh` โดยอิงตามรูปแบบของ `scripts/soak-test-report.sh`: เป็นการใช้คำสั่งจริงกับสแต็กที่กำลังทำงานอยู่จริง เวลาจริง และไม่มีเอาต์พุตจำลอง

## Drill 1 — Backup / Restore (การซ้อม 1 — สำรอง / กู้คืนข้อมูล)

`./scripts/dr-test.sh backup-restore`

ทำ `pg_dump` ฐานข้อมูล `ims` แบบเรียลไทม์ และกู้คืนข้อมูลลงในฐานข้อมูลการตรวจสอบ `ims_dr_test` ชั่วคราว (โดยไม่กระทบข้อมูลจริง) เปรียบเทียบจำนวนแถว (row counts) ของ `devices`/`ldi_data`/`ldi_alarm_log` ระหว่างระบบจริงและระบบที่กู้คืน จากนั้นลบฐานข้อมูลชั่วคราวทิ้ง เกณฑ์ผ่านการทดสอบ: **ใช้ค่าช่วงขอบเขตของจำนวนแถว (row-count bracketing) ไม่ใช่การตรงกันพอดี (exact match)** — เนื่องจากระบบมีการนำเข้าข้อมูลอยู่ตลอดเวลา ดังนั้น `scripts/dr-test.sh` จะจับภาพจำนวนก่อนและหลังจากการ snapshot และยืนยันว่าจำนวนที่กู้คืนนั้นตกอยู่ในช่วงนั้น (ดูรายละเอียดใน `docs/operations/BACKUP_RESTORE.md` ว่าทำไมการใช้การตรงกันพอดีถึงล้มเหลวและให้ผลการทดสอบที่เป็น false negative ในตอนแรก)

## Drill 2 — Single-Container-Loss Recovery (การซ้อม 2 — การกู้คืนกรณีที่ Container หายไปหนึ่งตัว)

`./scripts/dr-test.sh container-loss timescaledb` (หรือ `node-red`)

สั่งหยุดการทำงานของ container ที่ระบุโดยตรง และวนลูปตรวจสอบ (poll) เป็นเวลาไม่เกิน 120 วินาที เพื่อดูว่านโยบาย `restart: unless-stopped` ของ Docker จะทำให้มันกลับมาสู่สถานะ `running` หรือไม่ นี่เป็นการทดสอบการกู้คืนตัวเอง (self-healing) แบบเดียวกับการแก้ไขความน่าเชื่อถือในเซสชั่นนี้ที่ได้อ้างอิงไว้ (การแก้ไข watchdog pg.Pool ของ Node-RED ก่อนหน้านี้ตั้งสมมติฐานว่า container สามารถกู้คืนได้ด้วยตัวเอง; การซ้อมนี้เป็นการพิสูจน์สมมติฐานนั้นแทนที่จะปล่อยให้เป็นที่เข้าใจไปเอง) เกณฑ์ผ่านการทดสอบ: container กลับสู่สถานะ `running` ภายในเวลา 120 วินาที

## Drill 3 — Full-Stack Recreate (การซ้อม 3 — การสร้างสแต็กใหม่ทั้งหมด)

`./scripts/dr-test.sh full-recreate --confirm-destroy`

**เป็นการทำลายล้าง — ต้องระบุ `--confirm-destroy` อย่างชัดเจน** ทำการรัน `docker compose down -v` (ลบ named volume ทุกตัว: `timescaledb_data`, `prometheus_data`, `alertmanager_data`, `grafana_data`) จากนั้นสร้างสแต็กใหม่ทั้งหมดจาก `docker-compose.yaml` รัน migrations และกู้คืนข้อมูลจากการสำรองที่ทำไว้ในการซ้อมที่ 1 หากไม่มีแฟล็กนี้ จะข้ามการซ้อมนี้พร้อมแสดงคำอธิบายแทนที่จะทำงานโดยไม่แจ้งให้ทราบ — การทำงานนี้จะทำลายสิ่งที่ทำงานอยู่ในสภาพแวดล้อมที่มันดำเนินการทดสอบ ดังนั้นจึงควรทำงานเฉพาะเมื่อตั้งใจจริง ๆ (สภาพแวดล้อมที่คลีนอย่างแท้จริง หรือเมื่อได้รับการอนุมัติอย่างชัดเจนว่าสามารถทิ้งสถานะปัจจุบันได้)

**อัปเดตแก้ไขเมื่อ 2026-08-13** (พบในการรันจริงครั้งแรก หาสาเหตุและแก้ไขในวันเดียวกัน — ดูเรื่องราวเต็มๆ ใน `docs/evidence/DR_DRILL_3_FINDINGS.md`): `postgres/init/034-ldi-statistical-mock.sql` ได้ทำการกำหนดข้อมูลจำลองชุดเก่าที่ล้าสมัย (stale mock dataset) ใน volume ใหม่ๆ โดยอัตโนมัติก่อนที่ `db-migrate` จะทำงาน ทำให้ migrations เข้าสู่สถานะ schema ที่ไม่ได้คาดไว้; นอกจากนี้ ขั้นตอนการกู้คืนข้อมูลของการซ้อมยังได้กู้คืน `pg_dump` แบบเต็มลงในฐานข้อมูลที่ทำการ migrate เรียบร้อยแล้ว ซึ่ง TimescaleDB ไม่รองรับการทำงานในลักษณะนี้อย่างเสถียรเมื่อมีการใช้งาน continuous aggregates ปัญหานี้ได้รับการแก้ไขโดยการลบข้อมูลเริ่มต้นที่ล้าสมัยทิ้ง และเขียน `drill_full_recreate` ใหม่เพื่อกู้คืนเฉพาะข้อมูลดิบในแต่ละแถว (raw row data) เท่านั้น (ไม่มี schema) หลังจากที่ `db-migrate` สร้าง schema จาก `database/migrations/` เพียงอย่างเดียว ยืนยันผล: รันผ่านอย่างสมบูรณ์ 2 จาก 3 ครั้ง (ครั้งที่ 3 เจอ Postgres แครช ซึ่งมีความสัมพันธ์กับการทดสอบซ้ำจำนวนมากที่ระดับเครื่องโลคัล ไม่ใช่สาเหตุจากการแก้ไข — ดูที่เอกสารข้อค้นพบ) ปัจจุบัน การซ้อมนี้เป็นส่วนหนึ่งที่ถือว่าปกติและคาดว่าจะผ่านในแผนป้องกันภัยพิบัติ (DR posture) และไม่ถือว่าเป็นช่องโหว่ที่ทราบอีกต่อไป
