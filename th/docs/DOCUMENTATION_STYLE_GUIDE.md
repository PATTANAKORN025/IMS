## 1. หลักการสำคัญและกฎ "Auto-Clarity" (ความชัดเจนทันที)

เอกสารทางเทคนิคทั้งหมดในระบบ IMS ยึดถือมาตรฐานวิศวกรรมระดับชั้นนำของโลก (Google SRE, AWS Architecture, Stripe API docs) เอกสารจัดทำขึ้นเพื่อให้เจ้าหน้าที่ปฏิบัติงาน, สถาปนิกวิศวกรรมระบบ และเอเจนต์อัตโนมัติเข้าใจและแก้ไขปัญหาได้ตรงจุดโดยไร้ความกำกวม

### กฎ "Auto-Clarity"

- **ตัดคำเยิ่นเย้อทิ้งทั้งหมด**: ตัดคำสร้อยหรือคำเชื่อมที่ไม่มีเนื้อหาทางเทคนิคออก (เช่น `โดยพื้นฐาน`, `จริงๆ แล้ว`, `เพียงแค่`, `เห็นได้ชัดว่า`) ให้ระบุข้อเท็จจริงทางเทคนิคโดยตรง
- **ใช้ประโยคเน้นประธาน (Active Voice)**: เขียนคำสั่งโดยระบุประธานและกริยาที่ชัดเจน
  - ❌ *ประโยคกรรม*: "เพย์โหลด Telemetry จะถูกประมวลผลโดยฟังก์ชัน Node-RED และบันทึกลงในฐานข้อมูล"
  - ✅ *ประโยคประธาน*: "Node-RED ตรวจสอบความถูกต้องของเพย์โหลด Telemetry และบันทึกลง TimescaleDB"
- **เอกสารเชิงโค้ด (Code-First Architecture)**: คำอธิบายเชิงแนวคิดทุกจุดต้องมีตัวอย่างโค้ดหรือคำสั่งที่นำไปรันได้จริงกำกับเสมอ (คำสั่ง cURL, แบบสอบถาม SQL, คำสั่ง CLI, นิพจน์ PromQL)

## 2. ความเท่าเทียมกันของเอกสาร 3 ภาษา (EN, TH, ZH-CN)

ระบบ IMS รักษาความสมบูรณ์ของเนื้อหาแบบ 1:1 ครอบคลุม 3 ภาษา เพื่อรองรับทีมวิศวกรรมและฝ่ายผลิตข้ามชาติ:

```
c:\Projects\IMS
├── docs/               # เอกสารภาษาอังกฤษต้นแบบ (Source of Truth)
├── th/docs/            # เอกสารฉบับแปลภาษาไทย
└── zh-CN/docs/         # เอกสารฉบับแปลภาษาจีนตัวย่อ
```

### กฎการดูแลรักษาเอกสารทั้งสามภาษา

1. **อัปเดตพร้อมกันเสมอ (Synchronous Updates)**: เอกสารใดก็ตามที่สร้างขึ้นหรือแก้ไขใน `docs/` **ต้อง** ได้รับการปรับปรุงใน `th/docs/` และ `zh-CN/docs/` ไปพร้อมกันในรอบเดียวกันเสมอ
2. **โครงสร้าง Header มาตรฐาน**: ทุกไฟล์ Markdown ต้องเริ่มต้นด้วยบล็อก `GLOBAL_NAV` และปุ่มสลับภาษาตรงกลาง:
   ```html
   <!-- GLOBAL_NAV -->
   <div align="right">
     <a href="../../README.md"><img src="../assets/icons/home.svg" width="16" align="center" /> <b>หน้าหลัก</b></a> &nbsp;|&nbsp;
     <a href="../README.md"><img src="../assets/icons/book.svg" width="16" align="center" /> <b>ดัชนีเอกสาร</b></a>
   </div>
   <br/>
   <div align="center">
     <h1>หัวข้อหลัก</h1>
     <p><b>หัวข้อย่อย</b></p>
     <p>
       <a href="FILE.md">English</a> |
       <a href="../../th/docs/.../FILE.md">ไทย</a> |
       <a href="../../zh-CN/docs/.../FILE.md">简体中文</a>
     </p>
   </div>
   ```
3. **ความถูกต้องของ Anchor และ Slug**: ตั้งชื่อหัวข้อให้มี Anchor Slug ที่สม่ำเสมอ เมื่อทำการลิงก์ข้ามไฟล์ ให้ใช้รูปแบบ GitHub Markdown Slug มาตรฐาน

## 3. การใช้ GitHub Alerts เพื่อเน้นย้ำความสำคัญ

ใช้บล็อกข้อความแจ้งเตือนตามมาตรฐาน GitHub-flavored Markdown เพื่อเน้นย้ำขอบเขตการปฏิบัติงาน, อันตราย และคำแนะนำ:

> [!NOTE]
> บริบทเบื้องหลัง, เหตุผลการออกแบบทางสถาปัตยกรรม หรือเอกสารอ้างอิงเพิ่มเติมที่ช่วยให้เข้าใจเชิงลึกโดยไม่รบกวนขั้นตอนการปฏิบัติงานหลัก

> [!TIP]
> การปรับแต่งเพื่อเพิ่มประสิทธิภาพ, เคล็ดลับทางลัดในการทำงาน และแนวทางปฏิบัติที่ช่วยเพิ่มความน่าเชื่อถือหรือประสิทธิภาพการพัฒนา

> [!IMPORTANT]
> ข้อกำหนดเบื้องต้นที่จำเป็น, พารามิเตอร์การตั้งค่าภาคบังคับ และกฎทางสถาปัตยกรรมที่ห้ามละเว้นโดยเด็ดขาด

> [!WARNING]
> การปฏิบัติงานที่มีความเสี่ยงสูง, ความเสี่ยงต่อการสูญหายของข้อมูล, การหยุดชะงักของบริการคอนเทนเนอร์ หรือการเปลี่ยนแปลงค่าคอนฟิกที่กระทบระบบ

> [!CAUTION]
> การกระทำที่ไม่สามารถกู้คืนได้, คำสั่ง DROP ฐานข้อมูล, อันตรายจากการหลุดของรหัสลับ หรือการปฏิบัติการที่ฝ่าฝืนกฎความปลอดภัยบนระบบจริง

## 4. โครงสร้างระดับหัวข้อและมาตรฐานตัวอักษร

- **ความลึกสูงสุด**: ห้ามสร้างหัวข้อย่อยลึกเกิน H3 (`###`) หากต้องการจำแนกหัวข้อที่ละเอียดยิ่งขึ้น ให้ใช้ตัวหนา (`**ชื่อข้อย่อย**`) หรือรายการแบบตัวเลข/สัญลักษณ์แทน
- **การอ้างอิงไฟล์และเส้นทาง**: ต้องครอบชื่อไฟล์, เส้นทางโฟลเดอร์, ตัวแปรสภาพแวดล้อม, คำสั่งเทอร์มินัล และชื่อตาราง SQL ด้วยเครื่องหมาย Backtick เสมอ (เช่น `public.ldi_data`, `docker-compose.yaml`, `TIMESTAMPTZ`)
- **สมการทางคณิตศาสตร์**: จัดรูปแบบสูตรคณิตศาสตร์ด้วยรูปแบบ KaTeX:
  - แบบแทรกในบรรทัด: `$\text{SLI} = \frac{A}{B} \times 100\%$`
  - แบบแสดงแยกบรรทัด:
    $$\text{Burn Rate} = \frac{\text{Budget Consumed (\%)}}{\text{Window Duration / 30 Days}}$$

## 5. แผนภาพสถาปัตยกรรมและเวิร์กโฟลว์ (Mermaid)

สถาปัตยกรรม ลำดับการทำงาน และ state machine ต้องวาดเป็นแผนภาพ Mermaid ที่ฝังใน Markdown ทุกแผนภาพใช้มาตรฐานเดียวกัน ซึ่งบังคับใช้โดย `tests/lint/mermaid-lint.js` (pre-commit และ CI) และ `scripts/check-mermaid-render.js` (CI, เบราว์เซอร์แบบ headless)

- **โมเดล**: ใช้ระดับของ C4 สำหรับโครงสร้าง (context → container → component ใน `docs/architecture/ARCHITECTURE_DIAGRAM.md`) ใช้ sequence diagram สำหรับพฤติกรรมขณะทำงาน และ state diagram สำหรับ lifecycle ลูกศรแสดงทิศทางที่ข้อมูลไหลเสมอ
- **ข้อเท็จจริงมาจากโค้ด**: บริการ พอร์ต ไฟล์ ตาราง status code และช่วงเวลาทุกอย่างในแผนภาพต้องมีอยู่จริงใน compose, flow, migration หรือฐานข้อมูลจริง lint จะปฏิเสธชื่อไฟล์ `*.json` / `*.js` / `*.sh` / `*.sql` ที่ไม่มีใน repository และ `public.<name>` ที่ไม่มี migration ใดสร้าง ห้ามใส่จำนวนที่เปลี่ยนได้ (จำนวนแถว จำนวน query)
- **ภาษาภาพเดียวกัน**: บรรทัดแรกของทุกบล็อกต้องเป็น `INIT` ที่ใช้ร่วมกันจาก `scripts/lib/mermaid-theme.js` (อ่านได้ทั้งหน้าสว่างและมืดของ GitHub) ใส่สีโหนดผ่านคลาสเชิงความหมายใน `CLASS_DEFS` เท่านั้น (`actor`, `ext`, `ingress`, `app`, `flow`, `store`, `viz`, `obs`, `notify`, `future`) และเพิ่มคำอธิบายสัญลักษณ์เมื่อใช้คลาส เพื่อไม่ให้ความหมายขึ้นกับสีเพียงอย่างเดียว
- **การเข้าถึง**: ต้องประกาศ `accTitle` และ `accDescr` ในทุกแผนภาพ (ยกเว้น mindmap เท่านั้นเพราะ parse ไม่ได้)
- **ความอ่านง่าย**: ให้แผนภาพกว้างไม่เกินประมาณ 1,600 px (การตรวจ render จะเตือนเมื่อเกิน 2,400 px) ใช้ `flowchart TB` เป็นหลัก ไม่เกินประมาณ 5 โหนดต่อแถว ป้ายสั้นและขึ้นบรรทัดด้วย `<br/>` และแยกมุมมองแทนการยัดทุกอย่างในภาพเดียว
- **กับดักทางไวยากรณ์**: ครอบป้ายที่มีอักขระพิเศษด้วยเครื่องหมายคำพูด (`A["PgBouncer (:5432)"]`, `-->|"label (x)"|`) ห้ามใส่ `;` ในข้อความของ sequence diagram (จะเป็นการจบคำสั่ง) และ `direction` ของ subgraph จะถูกละเลยเมื่อโหนดภายในเชื่อมออกไปนอก subgraph
- **สามภาษา โครงสร้างเดียว**: ฉบับ th/ และ zh-CN/ ต้องมีแผนภาพเดียวกัน ลำดับเดียวกัน และ node id เดียวกัน แปลเฉพาะป้ายกำกับ
- **ไฟล์ `.mermaid` แบบแยก**: `docs/architecture/ims-system-architecture.mermaid` ต้องตรงกับแผนภาพภาพรวมใน `README.md` (lint เปรียบเทียบให้)

## 6. ข้อกำหนดการเขียนบล็อกโค้ด (Code Blocks)

ทุกบล็อกโค้ดต้องระบุชื่อภาษาสำหรับการจัดสีไวยากรณ์ (Syntax Highlighting) เสมอ:

- **บล็อก SQL** (`sql`): ต้องระบุสกีมา `public` อย่างชัดเจนเสมอ (กฎเหล็กทางสถาปัตยกรรม: ห้ามใช้ `ims.*`)
  ```sql
  SELECT bucket AS "time", machine_id, ROUND(avg_temp::numeric, 2)
  FROM public.ldi_data_15m
  WHERE bucket > NOW() - INTERVAL '24 hours';
  ```
- **บล็อก Bash** (`bash`): จัดให้อ่านง่ายโดยใช้เครื่องหมาย `\` สำหรับตัดขึ้นบรรทัดใหม่ และใช้ `jq` จัดรูปแบบผลลัพธ์ JSON
- **บล็อก JSON** (`json`): ต้องเป็น JSON ที่ถูกต้องตามมาตรฐาน RFC 8259 และไม่มีเครื่องหมายจุลภาคตกค้าง (No trailing commas)

## 7. ขั้นตอนการตรวจสอบคุณภาพและเครื่องมือ Linting อัตโนมัติ

ก่อนทำการคอมมิตหรือพุชเอกสารขึ้นกิ่ง `main` จะต้องรันการทดสอบและผ่านเกณฑ์การตรวจสอบทั้งหมด:

```bash
# 1. ตรวจสอบความถูกต้องของลิงก์และ Anchor ครอบคลุมไฟล์ Markdown กว่า 690 ไฟล์
node scripts/find-broken-links.js

# 2. ตรวจสอบข้อความอวดอ้างและคำศัพท์เกินจริง (Overclaim Linter)
node tests/lint/doc-overclaim-linter.js

# 3. สแกนหาข้อมูลส่วนตัวหลุด, IP ภายใน หรือ Secret ที่เผลอใส่ลงไป
node tests/lint/private-data-leak-scanner.js

# 4. รันชุดทดสอบ Pre-commit ทั้งหมด (53 รายการ)
node scripts/pre-commit.js
```
