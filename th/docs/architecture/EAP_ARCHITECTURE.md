# สถาปัตยกรรมชั้นการรวมอุปกรณ์ (Equipment Integration Layer Architecture - EAP)

> **EAP = Equipment Automation Program** — การรวมอุปกรณ์สไตล์ SECS/GEM ตามขอบเขตที่ได้รับการยืนยันเมื่อวันที่ 2026-08-10 (ไม่ใช่ "Enterprise Application Platform") ดูแผนงานที่เอกสารนี้ตอบสนองได้ใน `docs/architecture/IMS_MANUFACTURING_PLATFORM_V2.md` §3
>
> **การตรวจสอบความเป็นจริง แจ้งให้ทราบล่วงหน้า:** ระบบ IMS เป็นเพียงการตรวจสอบ (monitoring-only) เท่านั้น ระบบจะอ่านข้อมูลโทรมาตร (telemetry) และแจ้งเตือน (alarms) โดยจะไม่มีการเขียนคำสั่ง (writes commands) ดาวน์โหลดสูตรการผลิต (downloads recipes) หรือเก็บสถานะของอุปกรณ์ (holds equipment state) ปัจจุบันไม่มีเครื่องมือที่รองรับ SECS/GEM ทางกายภาพใด ๆ ในระบบนี้ เครื่อง LDI ใช้วิธีดึงข้อมูลผ่าน SNMP/จำลอง (SNMP-polled/simulated) ไม่ใช่การเชื่อมต่อแบบ SECS/GEM เอกสารนี้ **ไม่ได้** อ้างว่าสอดคล้องกับมาตรฐาน SECS/GEM ไม่ได้มีการจัดการเซสชัน HSMS และไม่ได้จำลองอุปกรณ์ SECS/GEM เอกสารนี้จัดทำขึ้นเพื่อบันทึกข้อมูลของอแดปเตอร์ (adapters) สองตัวที่มีอยู่จริง และกำหนดข้อตกลง (contract) สำหรับตัวที่สามที่ยังไม่มีอยู่
>
> **แหล่งที่มา:** คำอธิบายของอแดปเตอร์ SNMP และ HTTP/JSON ด้านล่างนี้ได้รับการตรวจสอบโดยตรงจาก `nodered_data/flows/ingestion.json` และ `nodered_data/flows/ldi_ingestion.json` เมื่อวันที่ 2026-08-10 ไม่ได้เขียนขึ้นจากความทรงจำ

---

## รูปแบบ: สามอแดปเตอร์ หนึ่งทะเบียนอุปกรณ์

งานของอแดปเตอร์ทุกตัวจะเหมือนกันโดยไม่คำนึงถึงโปรโตคอล นั่นคือการนำข้อมูลโทรมาตรและเหตุการณ์การแจ้งเตือนจากอุปกรณ์ทางกายภาพหรืออุปกรณ์จำลองเข้าสู่ตาราง `public.devices` / ตารางโทรมาตรของอุปกรณ์ โดยใช้ `device_id` เป็นคีย์สำหรับเชื่อมโยง (join key) ในทั่วทั้งระบบ (แดชบอร์ด, มุมมอง SPC/RCA, ระบบจัดการการแจ้งเตือนหลัก) อแดปเตอร์ถูกกำหนดโดยวิธีที่มันใช้ในการดึงข้อมูล ไม่ใช่ด้วยสิ่งที่มันส่งข้อมูลไปให้

### อแดปเตอร์ 1 — SNMP (อุปกรณ์รุ่นเก่า/โครงสร้างพื้นฐาน)

- **ตำแหน่ง:** `nodered_data/flows/ingestion.json` (แท็บ "IMS Ingestion Pipeline")
- **โมเดลอุปกรณ์:** แถวใน `public.devices` ที่มี `device_type IN ('server','workstation','network')` โดยเก็บข้อมูล `hostname`, `ip_address`, `snmp_community`, `snmp_port`, `poll_interval`
- **แผนการรวบรวมข้อมูล:** ทุก ๆ 30 วินาที `fork_5_ways` จะส่งตัวอ่านข้อมูล SNMP v2c (walkers) แบบขนาน (CPU, Storage, Network, Temperature, LDI OIDs) ไปยังอุปกรณ์ที่ลงทะเบียนไว้แต่ละเครื่อง
- **การรวบรวมเหตุการณ์/การแจ้งเตือน:** ไม่มีในระดับโปรโตคอล — อแดปเตอร์นี้มีไว้สำหรับข้อมูลโทรมาตรเท่านั้น การแจ้งเตือนจะถูกสร้างขึ้นในขั้นตอนถัดไป (downstream) จากเกณฑ์ที่ตั้งไว้ (thresholds) บนเมตริกที่ถูกนำเข้า ไม่ได้ถูกส่งมาในรูปแบบ SNMP traps ดั้งเดิม
- **แผนการรวบรวมข้อมูล → การแมปโทรมาตร:** `sre_parser` จะรักษาสถานะต่ออุปกรณ์และแทรกข้อมูลเป็นชุด (batch-inserts) ลงใน `sys_metrics` / `net_metrics` / `ldi_metrics` โดยมีคีย์คือ `device_id`

### อแดปเตอร์ 2 — HTTP/JSON (โทรมาตรการผลิต LDI)

- **ตำแหน่ง:** `nodered_data/flows/ldi_ingestion.json` (แท็บ "IMS LDI Ingestion")
- **โมเดลอุปกรณ์:** แถวใน `public.devices` ที่มี `device_type='ldi'`, `process_type='ldi'` (การย้ายข้อมูล migration 067/068)
- **แผนการรวบรวมข้อมูล:** อุปกรณ์ (หรือเครื่องจำลอง) จะทำ POST ส่ง JSON array batch ไปที่ `POST /ldi-telemetry` โดยมีการตรวจสอบสิทธิ์ผ่านเฮดเดอร์ `x-api-key` ซึ่งจะถูกตรวจสอบเทียบกับ `INGEST_API_KEY` แต่ละรายการในชุดจะพกพา `eqp_id` (แมปกับ `device_id`) พร้อมด้วยชุดพารามิเตอร์ LDI ทั้งหมด (PE1-6, JE1-4, thickness, scan_speed, resist_dosage, ...)
- **การรวบรวมเหตุการณ์/การแจ้งเตือน:** เส้นทางโปรดิวเซอร์/เครื่องจำลองคู่ขนาน (`ldi_alarm_simulator.json`) จะเขียนลงใน `public.ldi_alarm_log` โดยเชื่อมโยงกับข้อมูลโทรมาตรผ่าน `device_id` + `event_id` (ไม่ได้ถูกส่งมาใน POST เดียวกัน — เป็นสตรีมเหตุการณ์แยกต่างหาก แต่เป็นเอกลักษณ์ของอุปกรณ์เดียวกัน)
- **แผนการรวบรวมข้อมูล → การแมปโทรมาตร:** การแทรกชุดข้อมูลโดยตรงด้วยคำสั่ง `INSERT INTO public.ldi_data`, ใช้ `ON CONFLICT (log_id, "time") DO NOTHING` เพื่อความเป็น idempotent (idempotency)

### อแดปเตอร์ 3 — SECS/GEM (ข้อตกลงที่ยังไม่ได้ดำเนินการ สำหรับเครื่องมือจริงในอนาคต)

ยังไม่มีโค้ดสำหรับอแดปเตอร์นี้ หากในอนาคตมีอุปกรณ์ของประเภทกระบวนการที่สื่อสารด้วย SECS/GEM ได้จริง อุปกรณ์นั้นจะต้องปฏิบัติตามข้อตกลงนี้เพื่อเชื่อมต่อเข้ากับทะเบียน (registry) และมุมมอง/แดชบอร์ดด้านปลายทาง (downstream) แบบเดียวกัน โดยไม่ต้องเปลี่ยนแปลงอย่างอื่น:

| แนวคิด EAP                               | สิ่งที่อแดปเตอร์ 3 ต้องจัดเตรียม                                                                                                                                                                                                                                                                     | แมปกับ (รูปแบบที่มีอยู่)                          |
| ---------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------- |
| **การลงทะเบียนโมเดลอุปกรณ์**             | ลงทะเบียนเครื่องมือเป็นแถวใน `public.devices` ด้วย `device_id`, กำหนด `device_type` ที่เหมาะสม, และ `process_type` (ตาม `MANUFACTURING_DOMAIN.md`) — ใช้ข้อตกลงเกี่ยวกับเอกลักษณ์ (identity contract) แบบเดียวกับอแดปเตอร์ 1 และ 2                                                                   | `public.devices`                                  |
| **รายงานเหตุการณ์ → การแมปการแจ้งเตือน** | แปลงรายงานเหตุการณ์ SECS/GEM (รหัสเหตุการณ์การรวบรวมข้อมูล, CEIDs) เป็นแถวในตารางแจ้งเตือนหลัก + ตารางบันทึกการแจ้งเตือนของกระบวนการนั้น ๆ โดยใช้คีย์ `device_id` — รูปแบบเดียวกับ `ldi_alarm_ms_code`/`ldi_alarm_log`                                                                               | เส้นทางการแจ้งเตือนของอแดปเตอร์ 2                 |
| **แผนการรวบรวมข้อมูล → การแมปโทรมาตร**   | แปลงรายงานตัวแปร SECS/GEM SVID/ECID เป็นแถวในตารางไฮเปอร์ (hypertable) สำหรับโทรมาตรของกระบวนการนั้น โดยใช้คีย์ `(device_id, time)` — รูปแบบเดียวกับ `ldi_data`                                                                                                                                      | เส้นทางโทรมาตรของอแดปเตอร์ 2                      |
| **การจัดการเวอร์ชัน (Versioning)**       | จัดส่งเป็นข้อตกลงที่มีการกำหนดเวอร์ชันอย่างชัดเจน (เช่น `adapter-contract-v1`) ตาม `IMS_MANUFACTURING_PLATFORM_V2.md` §7 — ซึ่งเป็นจุดเชื่อมต่อเดียวในพื้นที่จัดเก็บนี้ (repo) ที่หากมีการเปลี่ยนแปลงที่ก่อให้เกิดการหยุดชะงัก (breaking change) จะไม่ถูกตรวจจับโดย linter หรือแบบทดสอบที่มีอยู่ใด ๆ | ข้อกำหนดใหม่, ไม่มีสิ่งที่เทียบเคียงได้ในปัจจุบัน |

การสร้างอแดปเตอร์ 3 อยู่นอกเหนือขอบเขตจนกว่าจะมีเครื่องมือที่สื่อสารด้วย SECS/GEM จริงและจำเป็นต้องเชื่อมต่อ — ปัจจุบันยังไม่มีสิ่งใดให้รวมเข้าด้วยกันหรือทดสอบ และสแตก SECS/GEM จำลองนั้นจะเป็นโครงสร้างพื้นฐานเชิงคาดเดาที่ไม่มีข้อกำหนดรองรับ

## หมายเหตุขอบเขตความปลอดภัย

การเชื่อมต่อเครื่องมือผ่านอแดปเตอร์ 3 ที่ใช้งานจริง จะเป็นการข้ามเครือข่ายอุปกรณ์บนชั้นปฏิบัติการในโรงงาน (plant-floor equipment network) — ซึ่งเป็นขอบเขตความน่าเชื่อถือภายนอก (external trust boundary) ใหม่ที่ยังไม่มีในระบบนี้ปัจจุบัน ดูเพิ่มเติมที่ `IMS_MANUFACTURING_PLATFORM_V2.md` §8 (Boundary 3) — การเชื่อมต่อดังกล่าวจำเป็นต้องมีการทบทวนเรื่องการเสริมความปลอดภัย (hardening review) เป็นการเฉพาะก่อนที่จะมีการเชื่อมต่ออุปกรณ์จริงใด ๆ เข้ามา เอกสารนี้กำหนดเพียงข้อตกลงด้านข้อมูลเท่านั้น (data contract) ไม่ได้ครอบคลุมการเสริมความปลอดภัยด้านเครือข่าย/ข้อมูลประจำตัว (network/credential hardening) สำหรับการเชื่อมต่อในอนาคตนั้น
