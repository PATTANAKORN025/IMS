# แพลตฟอร์มการผลิต IMS V2 — สถาปัตยกรรมและแผนการเปิดตัว (IMS Manufacturing Platform V2 — Architecture & Rollout Plan)

> **สถานะ:** เอกสารการออกแบบ รอการอนุมัติ ยังไม่มีการนำส่วนใดในเอกสารนี้ไปดำเนินการจริง
>
> **ที่มา:** ทุกข้อเรียกร้องเกี่ยวกับ "สถานะปัจจุบัน" ด้านล่างนี้ได้รับการตรวจสอบโดยตรงกับพื้นที่เก็บข้อมูลจริงเมื่อวันที่ 2026-08-10 (`git status`, dashboard JSON, `database/migrations/`, `.github/CODEOWNERS`, `docs/architecture/ARCHITECTURE.md`) — ไม่ใช่การคาดเดา เอกสารนี้ไม่ได้ใช้แทนที่ `ARCHITECTURE.md` (โครงสร้างระบบ / การไหลของข้อมูล ยังคงมีความแม่นยำ) — แต่เป็นเอกสารเพิ่มเติม: ขอบเขตของโดเมน, โครงสร้างข้อมูลการผลิตในอนาคต, สถาปัตยกรรมการรวมอุปกรณ์ และความเป็นเจ้าของ ซึ่งทั้งหมดนี้ `ARCHITECTURE.md` ปัจจุบันยังไม่ครอบคลุม
>
> **ขอบเขตที่ได้รับการยืนยัน (ผู้ใช้อนุมัติเมื่อ 2026-08-10):**
>
> - EAP = **Equipment Automation Program** (การรวมอุปกรณ์ในรูปแบบ SECS/GEM) ไม่ใช่ "Enterprise Application Platform"
> - การแยกส่วนระหว่างโครงสร้างพื้นฐาน (Infrastructure) และการผลิต (Manufacturing) เป็นเพียง **ตรรกะ/การจัดการเท่านั้น** — ใช้ Repo เดียว, Grafana อินสแตนซ์เดียว, ฐานข้อมูลเดียว ไม่มีการแยกทางกายภาพ
> - **Repo เดียว** ยังคงเป็น Repo เดียว ความเป็นเจ้าของถูกกำหนดให้ชัดเจนผ่าน `CODEOWNERS`/เอกสารความเป็นเจ้าของ ไม่ใช่ผ่านการแยก Repo
> - เอกสารฉบับนี้เป็นผลงานชิ้นเดียวที่ครอบคลุมงานทั้งหกส่วน เพื่อขออนุมัติก่อนเริ่มดำเนินการใด ๆ
> - ลำดับการดำเนินการเมื่อได้รับการอนุมัติ: **Phase A → Phase B → Phase C → Soak Test → DR Test** โดยแต่ละเฟสจะปิดท้ายด้วยการแนบหลักฐานการทดสอบ (มาตรฐานหลักฐานเดียวกับ `docs/operations/LDI_VALIDATION_PROTOCOL.md` — เป็นผลลัพธ์คำสั่งจริง ไม่ใช่เพียงคำกล่าวอ้าง)

## 0. ข้อมูลพื้นฐาน (ตรวจสอบเมื่อ 2026-08-10)

- แดชบอร์ด Grafana จำนวน 10 รายการ ทั้งหมดถูกจัดเตรียมในโฟลเดอร์แบบแบน `IMS` โฟลเดอร์เดียว (`monitoring/grafana/provisioning/dashboards/*.yml`, `foldersFromFilesStructure: false`) ไม่มีโครงสร้างโฟลเดอร์ย่อย **การแก้ไข (พบระหว่างการใช้งาน Phase A):** แดชบอร์ดมีอาร์เรย์ `tags` ที่ไม่ว่างเปล่าอยู่แล้ว (เช่น `["ims","noc"]`, `["IMS","LDI","set-2",...]`) — ข้อเรียกร้องเดิมที่ระบุว่า "ไม่มีแดชบอร์ดที่ตั้งค่าแท็ก" นั้นไม่ถูกต้อง สิ่งที่ขาดหายไปคือแท็ก _โดเมน_ (`infrastructure`/`manufacturing`) ไม่ใช่แท็กทั้งหมด
- `public.devices.device_type` คือ `server | workstation | ldi | network` (migration 013) — `ldi` เป็นค่าการผลิต/กระบวนการเพียงค่าเดียว ยังไม่มีมิติของ `process_type` หรือเทียบเท่า
- ไปป์ไลน์การวัดและส่งข้อมูลทางไกล (Telemetry) อิสระ 2 เส้นทางมีอยู่แล้วในระดับข้อมูล (`ARCHITECTURE.md` §System Context): ไปป์ไลน์ LDI (`ldi_data`, `ldi_alarm_log`) คือฝั่งการผลิต; ไปป์ไลน์ SNMP (`sys_metrics`, `net_metrics`, `ldi_metrics`) คือโครงสร้างพื้นฐาน **การแบ่งแยกมีอยู่แล้วในระดับโครงสร้างผ่านสคีมา (Schema) และกระบวนการนำเข้าข้อมูล (Ingestion) — ขาดเพียงระดับการนำเสนอ (โฟลเดอร์/แท็ก Grafana) และเอกสารประกอบเท่านั้น**
- ปัจจุบันมี `.github/CODEOWNERS` แต่ยังคงเป็นแบบแบน: มีเจ้าของหนึ่งคน (`@PATTANAKORN025`) สำหรับพื้นที่เก็บข้อมูลทั้งหมด พร้อมบรรทัดระบุเส้นทางเฉพาะ (`/database/`, `/nodered_data/flows/`, `/.github/`) ที่ไม่ได้แยกแยะระหว่างโครงสร้างพื้นฐานกับการผลิต
- `git status` ปัจจุบันสะอาดหมดจด — ไม่มีเศษซากพื้นที่เก็บข้อมูลที่ต้องจัดการตามแผนนี้ (ล้างไฟล์ขยะชั่วคราวจากเซสชันนี้เรียบร้อยแล้ว)
- ไม่มีการทดสอบ DR (Disaster Recovery) หรือคู่มือปฏิบัติงาน (Runbook) ในพื้นที่เก็บข้อมูล `scripts/soak-test-report.sh` มีอยู่ (สร้างไว้ก่อนหน้านี้ในเซสชัน) แต่ไม่เคยทำงานในช่วงระยะเวลาที่ยาวนาน

## 1. การแบ่งแยกโดเมน โครงสร้างพื้นฐาน / การผลิต (เชิงตรรกะ)

**เป้าหมาย:**

- เพิ่ม `"folder": "Infrastructure"` / `"folder": "Manufacturing/LDI"` ผ่านการเตรียมโฟลเดอร์ย่อยของ Grafana (Grafana 13.x รองรับฟิลด์ `folder` ต่อผู้ให้บริการแดชบอร์ด หรือต่อแดชบอร์ดผ่าน API `meta` — การใช้งานจะยืนยันว่ากลไกใดที่รูปแบบไฟล์ที่เตรียมไว้รองรับโดยไม่ต้องแก้ไขแดชบอร์ดด้วยตนเองใน UI)
- เพิ่ม `"tags": ["infrastructure"]` หรือ `["manufacturing", "ldi"]` ใน JSON ของแดชบอร์ดทั้ง 10 รายการ — รูปแบบแท็กที่สามารถค้นหาและตรวจสอบผ่าน Linter ได้ โดยไม่ขึ้นกับกลไกของโฟลเดอร์
- **ชุดโครงสร้างพื้นฐาน (4 รายการ):** NOC Overview, AIOps & Capacity Forecast, Engineering Drill-Down, Meta-Monitoring
- **ชุดการผลิต (6 รายการ):** LDI Manufacturing, LDI Operator Andon, LDI Engineering Analytics, LDI Machine Snapshot, LDI Data Readiness, Fleet at a Glance (`ims-easy-overview.json` — คำอธิบายของแดชบอร์ดยืนยันว่าสร้างขึ้นจากมุมมองที่ใช้ร่วมกันเฉพาะ LDI ทั้งหมด (`v_ldi_machine_latest_full`, `v_ldi_alarm_context`, `f_ldi_yield_pct`) ไม่ใช่ภาพรวมโครงสร้างพื้นฐานทั่วไปแม้ชื่อจะฟังดูทั่วไป; `scripts/generate-dashboard-inventory.js` ได้จัดประเภทสิ่งนี้ผ่าน allowlist ที่ชัดเจนก่อนที่แผนนี้จะเกิดขึ้น)
- ขยาย `dashboard-linter.js` ด้วยการตรวจสอบว่าทุกแดชบอร์ดมีทั้งรายการ `tags` และอยู่ในชุดที่คาดหวัง (ป้องกันไม่ให้รูปแบบแท็กเกิดการเบี่ยงเบนเหมือนที่ `timezone` เคยเป็นก่อนหน้านี้ในเซสชัน)

**สิ่งที่ไม่อยู่ในเป้าหมาย:** ไม่มีองค์กร/อินสแตนซ์ Grafana ที่สอง, ไม่มีสแต็ก docker-compose แยกต่างหาก, ไม่มีการแยก `sys_metrics`/`ldi_data` ที่ระดับฐานข้อมูล (เพราะถูกแยกอยู่แล้ว)

## 2. สถาปัตยกรรมโดเมนการผลิต (AOI / Plating / Etching / Drilling ในอนาคต)

**ปัญหา:** "การผลิต (Manufacturing)" ในโค้ดเบสปัจจุบัน *คือ* LDI ตามชื่อ — `device_type='ldi'`, ตารางข้อมูลการวัดและส่ง (telemetry table) หนึ่งตาราง (`ldi_data`), มาสเตอร์การแจ้งเตือน (alarm master) หนึ่งรายการ, ชื่อคอลัมน์เฉพาะ LDI (`pe_setting`, `je_setting`) ไม่มีสคีมาใดที่ส่งสัญญาณว่าส่วนใดที่เฉพาะเจาะจงกับ LDI และส่วนใดที่สามารถนำกลับมาใช้ใหม่ได้โดยกระบวนการในอนาคต

**เป้าหมาย (สคีมา + รูปแบบที่บันทึกไว้ ไม่ใช่แดชบอร์ดใหม่หรือข้อมูลปลอม):**

- เพิ่ม `public.devices.process_type TEXT DEFAULT 'ldi'` (ค่าเริ่มต้นที่รองรับ nullable จะเติมเต็มในแถวที่มีอยู่; เป็น migration แบบเพิ่มเข้า ไม่มีผลกระทบ (breaking change) ต่อมุมมองที่มีอยู่ใด ๆ — `device_type='ldi'` ยังคงเป็นคีย์การเชื่อมต่อ (join key) ในทุกที่ที่ใช้ในปัจจุบัน)
- เขียน `docs/architecture/MANUFACTURING_DOMAIN.md` เพื่อบันทึกรูปแบบทั่วไปที่กระบวนการผลิตประเภทใหม่ๆในอนาคตจะต้องปฏิบัติตาม โดยใช้ LDI เป็นตัวอย่าง:
  - ไฮเปอร์เทเบิลข้อมูลการวัดหนึ่งตาราง (telemetry hypertable) จัดเรียงด้วยคีย์ `(device_id, process_type, time)`
  - มาสเตอร์รหัสการแจ้งเตือนหนึ่งรายการต่อกระบวนการ โดยทำตามรูปแบบ `ldi_alarm_ms_code` (รหัส, ความรุนแรง, คำอธิบาย)
  - รูปแบบมุมมอง SPC/RCA หนึ่งรายการต่อกระบวนการ โดยทำตามรูปแบบ materialized-view ทั่วไปของ migration 064 (`v_machine_spc_fleet` กรองด้วย `device_type` อยู่แล้ว ดังนั้นจึงขาดแค่เงื่อนไข `WHERE` เดียวในการทำให้เป็นแบบหลายกระบวนการ)
  - แดชบอร์ดชุดละ 3 รายการต่อกระบวนการ (Andon / Engineering Analytics / Manufacturing Overview) ตามโครงสร้างชุด LDI
  - "รายการตรวจสอบเบื้องต้น (onboarding checklist)" สั้นๆ สำหรับการเพิ่มกระบวนการประเภทใหม่: migration, alarm master seed, แดชบอร์ดชุดละ 3 รายการ, และการลงทะเบียน Linter

**สิ่งที่ไม่อยู่ในเป้าหมายอย่างชัดเจน:** ไม่มีการสร้างตาราง แดชบอร์ด ตัวจำลอง หรือข้อมูลปลอมสำหรับ AOI/Plating/Etching/Drilling ในขณะนี้ ยังไม่มีข้อกำหนดสำหรับกระบวนการเหล่านั้น — การสร้างตอนนี้จะเป็นเพียงการคาดเดา ส่วนนี้เพียงแค่ทำให้กระบวนการประเภท *ถัดไป* เป็นแบบเพิ่มเติมแทนที่จะเป็นการเขียนใหม่

## 3. สถาปัตยกรรม EAP (Equipment Automation Program)

**การตรวจสอบความเป็นจริง:** ปัจจุบัน IMS เป็นระบบเฝ้าระวังเท่านั้น — อ่านข้อมูลและแจ้งเตือน แต่ไม่เคยส่งคำสั่ง ดาวน์โหลดสูตรการผลิต (recipe) หรือควบคุมสถานะของอุปกรณ์ ไม่มีเครื่องมือที่รองรับ SECS/GEM ทางกายภาพในระบบนี้ (เครื่อง LDI จำลอง/ดึงข้อมูลผ่าน SNMP) การนำ SECS/GEM ไปใช้งานเต็มรูปแบบ (การจัดการเซสชัน HSMS, แผนรวบรวมข้อมูล SVID/ECID, การสั่งงาน/รันสูตรการผลิตระยะไกล, โมเดลสถานะรูปแบบ E30/E37/E40) จะไม่มีเป้าหมายที่แท้จริงให้ผสานรวมหรือทดสอบ — การสร้างตอนนี้จะเป็นเพียงสถาปัตยกรรมเชิงคาดเดา

**เป้าหมาย:** `docs/architecture/EAP_ARCHITECTURE.md` — เอกสารสถาปัตยกรรม **Equipment Integration Layer** ให้อยู่ในขอบเขตที่เป็นไปได้จริงและขยายได้:

- บันทึกการทำงานของอะแดปเตอร์สองตัวที่มีอยู่ในปัจจุบันเป็นตัวอย่างของรูปแบบทั่วไป: อะแดปเตอร์ SNMP (`ingestion.json`, อุปกรณ์รุ่นเก่า/โครงสร้างพื้นฐาน) และอะแดปเตอร์ HTTP/JSON (`ldi_ingestion.json`, ข้อมูล LDI)
- กำหนดสัญญาระหว่างอะแดปเตอร์ตัวที่สาม **ที่ยังไม่ได้สร้าง** สำหรับเครื่องมือที่สื่อสารผ่าน SECS/GEM ในอนาคต: อินเทอร์เฟซที่ต้องตอบสนองคืออะไร (การลงทะเบียนโมเดลอุปกรณ์, การจับคู่รายงานเหตุการณ์ → การแจ้งเตือน, แผนรวบรวมข้อมูล → การจัดเรียงแถวข้อมูล telemetry) เพื่อให้สามารถเชื่อมต่อกับ registry ของ `devices` เดิม และมุมมอง/แดชบอร์ดปลายทางได้โดยไม่ต้องเปลี่ยนแปลงส่วนอื่น
- แมปอะแดปเตอร์ทั้งสามเข้ากับคำศัพท์มาตรฐานของ EAP (โมเดลอุปกรณ์, การรวบรวมเหตุการณ์/แจ้งเตือน, แผนการรวบรวมข้อมูล, ECID/SVID) เพื่อให้เอกสารเข้าใจง่ายสำหรับผู้ที่รู้จัก SECS/GEM โดยไม่กล่าวอ้างถึงความสอดคล้องกับ SECS/GEM ในส่วนที่ยังไม่มีอยู่จริง

**สิ่งที่ไม่อยู่ในเป้าหมายอย่างชัดเจน:** ไม่มีโค้ดโปรโตคอล SECS/GEM, ไม่มีการจัดการเซสชัน HSMS, ไม่มีอุปกรณ์จำลอง SECS/GEM เอกสารนี้เป็นเพียงเอกสารข้อตกลงการผสานรวม (integration-contract) เท่านั้น

## 6. การตรวจสอบ, การทดสอบระบบทนทาน (Soak Test), และ DR Test

- **การตรวจสอบ:** เสร็จสมบูรณ์และถูกต้องแล้ว (`docs/operations/LDI_VALIDATION_PROTOCOL.md`) ไม่จำเป็นต้องดำเนินการเพิ่มเติม
- **การทดสอบระบบทนทาน (Soak test):** เครื่องมือพร้อมใช้งาน (`scripts/soak-test-report.sh`) แต่ไม่เคยออกรายงานจริง สั่งรันตามระยะเวลาจริง (เป้าหมาย: ขั้นต่ำ 24 ชม., เหมาะสมที่ 72 ชม.) กับสแต็กที่ทำงานอยู่และแนบผลลัพธ์ `--summarize` จริงเป็นหลักฐาน
- **การทดสอบ DR:** ยังไม่มีอยู่ในระบบ ให้สร้าง Runbook การทดสอบ DR + สคริปต์ตามรูปแบบเครื่องมือทดสอบ soak-test (`scripts/dr-test.sh` + `docs/operations/DR_TEST_PLAN.md`) ครอบคลุม:
  1. การฝึกซ้อมกู้คืนฐานข้อมูล (Backup/restore drill) (`pg_dump` → drop/recreate → restore → นับแถวข้อมูล + ตรวจสอบความถูกต้อง)
  2. การจำลองคอนเทนเนอร์ตัวใดตัวหนึ่งล้มเหลว (ปิด `ims-timescaledb` / `ims-node-red` กลางคัน และวัดผลการกู้คืนอัตโนมัติ — นี่เป็นการทดสอบกลไกเชื่อมต่อ Node-RED ใหม่ที่ถูกปรับปรุง)
  3. การทดสอบสร้างระบบใหม่ทั้งหมดจาก `docker-compose.yaml` + ข้อมูลสำรองล่าสุดบน volume ใหม่ แล้วจับเวลา

- สั่งรันในสภาพแวดล้อมจริงพร้อมบันทึกผล/เวลา ไม่ใช่แค่ Runbook เชิงทฤษฎี

## 7. นโยบายการกำหนดเวอร์ชัน (Versioning Policy)

- **การอัปเดตฐานข้อมูล (Database migrations)** (`database/migrations/*.sql`): ลำดับตามหมายเลขที่เพิ่มขึ้นเรื่อยๆ (ปัจจุบันถึง `066`) ถูกเรียกใช้ตามลำดับโดย `scripts/migrate-entrypoint.sh` และจะไม่มีการแก้ไขหรือเปลี่ยนหมายเลขหลังจากถูก merge — การแก้ไขคือหมายเลข *ถัดไป* เสมอ (เช่น `064` → `065` → `066`) นโยบายนี้ไม่เปลี่ยนแปลง; คอลัมน์ `process_type` ใน §2 จะกลายเป็นหมายเลข migration ลำดับถัดไป
- **แดชบอร์ดในรูปแบบโค้ด (Dashboards-as-code)** (`monitoring/grafana/dashboards/*.json`): Grafana เป็นเจ้าของฟิลด์ `schemaVersion` (เพิ่มจำนวนอัตโนมัติ) และประวัติของ Git — ไม่ใช่ระบบการกำหนดเวอร์ชัน (semver) แยกต่างหาก — จะเป็นตัวยืนยันความถูกต้อง; ส่วน `monitoring/grafana/dashboard-backups/` จะเก็บข้อมูลการส่งออกเป็นช่วงเวลา ไม่ใช่กลไกของการจัดทำเวอร์ชัน
- **เอกสารสถาปัตยกรรม** (ไฟล์นี้, `ARCHITECTURE.md` ฯลฯ): การจัดทำเวอร์ชันผ่านข้อตกลงสถานะ ("Status"/"Provenance"/วันที่) ดังที่ทำไปก่อนหน้านี้แล้ว ไม่ใช่ผ่านระบบ (semver) เอกสารนี้มีชื่อว่า "V2" เพื่อให้เข้าใจขอบเขต — ไม่มีการวางแผน "V3"
- **ข้อตกลงการผสานรวม (Integration/adapter contracts)** (§3, EAP): จุดเดียวที่การกำหนดเวอร์ชันที่มีความหมาย (semver) เป็นสิ่งสำคัญ หากอะแดปเตอร์ที่สามถูกสร้างขึ้น จะต้องส่งมอบในรูปแบบที่ระบุเวอร์ชันชัดเจน (เช่น `adapter-contract-v1`) เนื่องจากการเปลี่ยนแปลงข้อตกลงสามารถทำให้การเชื่อมต่อล้มเหลวได้โดยที่ไม่แจ้งผ่าน Linter ใด ๆ นโยบายข้อนี้เป็นข้อกำหนดล่วงหน้า ยังไม่ได้เริ่มสร้างในขณะนี้

## 8. ขอบเขตความปลอดภัย (Security Boundary)

`SECURITY.md` ยังคงเป็นเอกสารมาตรฐาน (ครอบคลุมข้อจำกัด, การจัดการข้อมูลที่ละเอียดอ่อน) — ส่วนนี้เพิ่มขอบเขตของความปลอดภัยเชิงสถาปัตยกรรม

- **ขอบเขต 1 — Host ↔ เครือข่าย Docker (มีอยู่เดิม ไม่เปลี่ยนแปลง):** เฉพาะ Grafana (3000), Node-RED (1880), Prometheus (9090) และ Alertmanager (127.0.0.1) เท่านั้นที่อนุญาตให้เปิดเผยพอร์ตหลัก ส่วน PgBouncer, TimescaleDB, และแบบจำลอง SNMP เป็นการใช้งานภายในเท่านั้น เอกสารฉบับนี้ไม่มีการเปลี่ยนแปลงในส่วนนี้
- **ขอบเขต 2 — โดเมน Infrastructure ↔ โดเมน Manufacturing (การปรับมุมมองใหม่, สิ่งที่มีอยู่จริง):** ตามที่ระบุใน §1, การแบ่งแยกนี้เป็นเพียงข้อมูลเชิงตรรกะ/การจัดการเท่านั้น — ทั้งสองโดเมนแบ่งปันฐานข้อมูลร่วมกัน, Grafana ตัวเดียวกัน, การประมวลผล Node-RED ด้วยกัน **ไม่มีขอบเขตความปลอดภัยแบบแข็งแกร่ง (hard security boundary) ระหว่างโดเมนทั้งสองในปัจจุบัน** และแผนนี้ก็ยังไม่มีการเพิ่มขอบเขตดังกล่าว (ได้รับการยืนยันจากผู้ใช้) เป็นความเสี่ยงที่ยอมรับได้สำหรับการใช้งานที่มีผู้ดูแลเพียงคนเดียว
- **ขอบเขต 3 — เครือข่ายการรวมอุปกรณ์ (Equipment Integration Layer) (ใหม่, โครงการในอนาคต, §3):** ในวันที่เครื่องจักร SECS/GEM ถูกผสานรวมกับอะแดปเตอร์ตัวที่สามที่ยังไม่ได้สร้าง จะเกิดการแบ่งขอบเขตใหม่ที่จะต้องใช้ขั้นตอนการทบทวนด้านความปลอดภัย (การรับรองสิทธิ์, เครือข่าย ฯลฯ) *ก่อน* ที่อุปกรณ์จริงจะเริ่มเชื่อมต่อ
- **CODEOWNERS ในฐานะเครื่องมือควบคุมความปลอดภัย:** บรรทัดเส้นทางรักษาความปลอดภัยที่มีอยู่ (`/.env.example`, `docker-compose*.yaml`, `/database/`, `/.github/`) ได้จำกัดการควบคุมไว้เรียบร้อยแล้ว เส้นทางโดเมนจาก §4 จึงเข้ามาเพิ่มขอบเขตการทำงานโดยไม่กระทบหรือลดทอนความปลอดภัยที่มีอยู่แต่แรก

**นี่สะท้อนเกณฑ์ชั่วคราว** ได้สืบค้นสาเหตุของค่าที่ผิดปกติ 3 ตัวแทนที่จะแค่อ้างอิงตัวเลข:

- **ค่า `NaN` เป็นผลจากสคริปต์ ไม่ใช่หลักฐานของความล้มเหลว:** 24 จาก 57 ตัวอย่างมี `NaN` สำหรับ inserts/failures/overflows/db_size (สองช่วง: 2026-08-11T14:00-17:20 และ 2026-08-12T08:05-10:35, แต่ละช่วง ~2.5-3.5 ชม. ของตัวอย่างต่อเนื่อง) เพราะ `node-red:1880/metrics` หรือ `psql` size query ไม่ตอบสนองในเวลาเก็บข้อมูล `sort -n` จัดเรียงสตริง `"NaN"` ไว้ท้ายสุด ดังนั้น `MAX_FAILED`/`MAX_OVERFLOW` จึงแสดง `NaN` แม้ว่าทุกตัวอย่าง _ที่เป็นตัวเลข_ ในบันทึกจะแสดง `0` สำหรับทั้งคู่ เป็นช่องว่างในการเก็บข้อมูล ไม่ใช่หลักฐานว่าการนำเข้าข้อมูลล้มเหลว
- **`ANY_RESTART=4`, ทั้งหมดเกิดก่อนงานของวันนี้**, ยืนยันจาก timestamp: `2026-08-11T04:22:14Z`, `2026-08-11T05:45:06Z`, `2026-08-12T08:05:15Z`, `2026-08-12T10:50:14Z` ไม่มีตัวใดตรงกับการทดสอบ DR ของเซสชันนี้ (ซึ่งรันราว ~2026-08-12T12:57-13:03Z) -- DR drills ใช้ `docker start` หลัง `docker kill` ซึ่งไม่เพิ่ม `RestartCount` ของ Docker เอง นี่คือ 4 เหตุการณ์ restart จริงตลอด 52.5 ชม. ที่ต้องสืบสวนเป็นรายกรณี
- **`ANY_FIRING=37` ตัวอย่างที่มี >=1 non-Watchdog alert ทำงาน** -- สาเหตุหลักของ FAIL ยังไม่ได้หาสาเหตุรากในรอบนี้ (ต้องใช้ประวัติ alert ต่อตัวอย่าง ซึ่ง Alertmanager ไม่เก็บย้อนหลังเกินสถานะปัจจุบัน ทำได้เพียงนับยอดรวมใน log นี้) alert ที่ทำงานอยู่ _ตอนนี้_ (`PipelineDataStalled`, critical) น่าจะเป็นผลตกค้างจากการทดสอบ DR container-kill ของเซสชันนี้เมื่อไม่กี่นาทีก่อนการรัน summarize นี้ ซึ่งคาดว่าจะเคลียร์ตัวเองได้ในการเก็บตัวอย่างตามกำหนดการครั้งถัดไป -- แต่นั่นไม่สามารถอธิบายการแจ้งเตือนที่ทำงานในอดีตอีก 36 ครั้งที่เหลือได้ ซึ่งเกิดขึ้นก่อนการทำงานของเซสชันนี้และเป็นข้อค้นพบที่แท้จริงที่ยังต้องแก้ไข

**เพื่อปิดเฟสนี้:** ปล่อยให้ scheduled task ทำงานต่อจนถึง 72 ชม. แล้วรัน `--summarize` อีกครั้ง การแจ้งเตือน 37 ครั้งและการ restart 4 ครั้งเป็นผลการค้นพบจริงที่ต้องสืบสวนแยกต่างหาก

### Drill 2 — การกู้คืนจากคอนเทนเนอร์ล้มเหลว (`ims-timescaledb`, `ims-node-red`): หาสาเหตุรากและแก้ไขแล้ว 2026-08-12, ตอนนี้ **PASS**

**การค้นพบเดิม (2026-08-10), ทำซ้ำและหาสาเหตุราก (2026-08-12):** `docker kill ims-timescaledb` (SIGKILL) ถูกรันอีกครั้ง คราวนี้เฝ้าดูเต็ม 5 นาทีผ่าน `docker inspect` polling ซ้ำ ผลลัพธ์: `RestartCount` อยู่ที่ `0` ตลอด 5 นาที — ไม่ใช่ช้า แต่ไม่เคยทำงานเลย ตัดปัญหาการตั้งค่า compose ก่อน: `docker inspect` ยืนยัน `RestartPolicy=unless-stopped, MaximumRetryCount=0` ถูกต้อง สิ่งที่เสียคือเครื่องยนต์ restart-policy ของ Docker Desktop (WSL2 backend, server 29.6.2) ที่ไม่ถูกเรียกใช้หลังจากนั้น

**แก้ไข:** `scripts/container-watchdog.sh` — watchdog ภายนอกที่ poll ทุกคอนเทนเนอร์ที่มี `restart: unless-stopped` และสั่ง `docker start` บนสิ่งที่ไม่ได้ `running` เพื่อชดเชยช่องว่างของเครื่องยนต์ restart ของ Docker

**รันซ้ำกับ watchdog ที่ทำงานอยู่ (`--loop 5`), 2026-08-12, 6 trials ข้ามคอนเทนเนอร์สำคัญทั้งสอง:**

```text
timescaledb: PASS -- recovered in 6s
node-red: PASS -- recovered in 6s
timescaledb: PASS -- recovered in 8s
node-red: PASS -- recovered in 3s
timescaledb: PASS -- recovered in 5s
node-red: PASS -- recovered in 6s
```

6/6 PASS, กู้คืนในหลักวินาทีเดียวทุกครั้ง **ช่องว่าง restart-policy ของ Docker Desktop ไม่ได้ถูกแก้ไข** (อยู่นอกเหนือการควบคุมของ repo นี้) — สิ่งที่เปลี่ยนคือสภาพแวดล้อมนี้มีมาตรการชดเชยที่ทำงานได้จริง

**การค้นพบที่สอง ผลกระทบต่อเนื่อง:** หลังจาก `docker start` TimescaleDB กลับมาปกติ การนำเข้าข้อมูล LDI **ไม่** กู้คืนตัวเองเป็นเวลาหลายนาที — เป็นพฤติกรรม `server_login_retry` failure-caching ของ PgBouncer watchdog (`ldiDbConnFailureStreak`, เกณฑ์ 5 ครั้งต่อเนื่อง) **ไม่** กระตุ้นการ restart Node-RED อัตโนมัติภายใน ~6 นาทีที่สังเกต — `max(ldi_data.time)` ค้างที่ timestamp ของเหตุขัดข้องจนกว่าจะรัน `docker restart ims-node-red` ด้วยตนเอง **บันทึกเป็นข้อจำกัดสำหรับการทำซ้ำในอนาคต**

**สิ่งที่ทำงานถูกต้อง:** ไปป์ไลน์การแจ้งเตือน Blackbox exporter ตรวจจับ `timescaledb:5432` ล่มได้ถูกต้อง, Alertmanager ส่งต่อ, และ flow การส่งแจ้งเตือนของ Node-RED บันทึก notification "ServiceDown" ถูกต้อง (LINE/Teams ข้าม — ไม่มี credentials ตามที่ออกแบบ)

**`scripts/dr-test.sh` ปรับปรุงจากผลนี้:** drill container-loss ตอนนี้ fallback เป็น `docker start` ด้วยตนเองถ้า restart policy ไม่ทำงานภายใน 120s

**เวลาหยุดทำงานจริงทั้งหมดจาก drill นี้:** timescaledb ~2-3 นาทีต่อ kill (2 kills) + ~6 นาทีช่องว่างกู้คืน ingestion = ประมาณ 10 นาทีของ downtime จริงในสภาพแวดล้อม dev นี้ กู้คืนเต็มที่และยืนยันแล้ว (0 lint errors, 0 e2e errors หลังกู้คืน)
