# แฝดดิจิทัลโรงงาน — สถาปัตยกรรมขณะรันไทม์ (Factory Twin — Runtime Architecture)

โครงสร้างของเซอร์วิสขณะทำงาน: ระบบใดสื่อสารกับระบบใด, โมดูลใดเป็นผู้ถือสิทธิ์การตัดสินใจเรื่องใด, และขอบเขตการทำงานที่เอกสารส่วนที่เหลือของดิจิทัลทวินใช้อ้างอิงนั้นถูกบังคับใช้จริงที่จุดใด

เอกสารประกอบสำหรับ **[ระเบียบวิธีสร้างขึ้นใหม่ (Reconstruction Methodology)](FACTORY_TWIN_RECONSTRUCTION.md)** (กระบวนการสร้างแบบจำลองเรขาคณิต), **[โมเดลความปลอดภัย (Security Model)](FACTORY_TWIN_SECURITY_MODEL.md)** (สิ่งใดได้รับการปกป้องและปกป้องอย่างไร) และ **[คู่มือผู้ปฏิบัติงาน (Operator Guide)](FACTORY_TWIN_OPERATOR_GUIDE.md)** (วิธีอ่านและตีความผลลัพธ์)

> [!NOTE]
> เอกสารฉบับนี้ไม่มีการระบุข้อมูลเรขาคณิต มิติ หรือพิกัดตำแหน่งทางกายภาพใดๆ เอกสารนี้อธิบายเฉพาะโครงข่ายท่อส่งและการเชื่อมต่อของระบบ (plumbing) ไม่ใช่ข้อมูลเพย์โหลด (payload)

## 1. เส้นทางคำขอ (Request path)

```text
browser
  └─ proxy  (nginx)
       ├─ location = /auth-check      internal; ตรวจสอบสิทธิ์กับ Grafana /api/user
       └─ location /factory-twin-3d/  auth_request /auth-check
            └─ factory-twin-3d  (express, :4100, ไม่มี host port)
                 ├─ static  public/ + three.js ที่รวมมาในตัว (vendored)
                 ├─ /api/*  JSON ที่ถูกจัดรูปแบบ (shaped JSON)
                 ├─ pg pool  ->  pgbouncer  ->  TimescaleDB   (บทบาทอ่านอย่างเดียว read-only role)
                 └─ private/  อ่านเฉพาะฝั่งเซิร์ฟเวอร์เท่านั้น ไม่ถูกเมานต์เป็นสแตติก
```

คุณสมบัติสำคัญสามประการของเส้นทางนี้ที่ต้องคงไว้เพื่อความมั่นคงของระบบ:

- **ดิจิทัลทวินไม่มีการเปิดเผย host port สู่ภายนอก** เซอร์วิสมีอยู่เฉพาะบนเครือข่ายภายในของ docker-compose เท่านั้น เส้นทางเดียวที่เข้าถึงได้คือผ่าน location `/factory-twin-3d/` ของพร็อกซี
- **location ดังกล่าวถูกควบคุมด้วย `auth_request`** โดยตรวจสอบกับคุกกี้เซสชันของ Grafana โดยตรง ไม่มีระบบยืนยันตัวตนชุดที่สองที่ต้องคอยซิงค์: ผู้ปฏิบัติงานที่ล็อกอินเข้าสู่แดชบอร์ดแล้วจะถือว่าล็อกอินเข้าสู่ทวินด้วย และผู้ที่ยังไม่ได้ล็อกอินจะได้รับรหัส 401 ตั้งแต่ก่อนที่คำขอจะส่งถึงทวิน
- **Three.js ถูกรวมมาในอิมเมจ (vendored) ไม่ได้ดึงมาจาก CDN** คอนเทนเนอร์ที่อยู่หลังเกตยืนยันตัวตนจะต้องไม่พึ่งพา origin ภายนอกที่เป็นบุคคลที่สามขณะเรนเดอร์

## 2. แผนผังโมดูล (Module map)

| ไฟล์ | หน้าที่และความรับผิดชอบ |
|---|---|
| `server.js` | เส้นทางเราต์ (Routes), พูลการเชื่อมต่อ pg, การรีเฟรชอุปกรณ์, ตัวโหลดไฟล์ไพรเวต และรายการอนุญาต (serving allowlists) |
| `lib/contracts.js` | ข้อกำหนดสถานะเครื่องจักรและธีมการแสดงผล นิยามเดียวใช้งานร่วมกันระหว่าง API และเรนเดอเรอร์ |
| `lib/diagnostics.js` | การแปลงข้อมูลวินิจฉัยให้อยู่ในรูปอนุกรม (serialization) ปลอดภัยตามโครงสร้างด้วย allowlist-by-construction |
| `lib/wire.js` | การฉายข้อมูลเรขาคณิตส่วนตัวออกสู่เครือข่าย (wire projection): สร้างสล็อต เสา โซน และกรอบอาคารขึ้นใหม่ทีละฟิลด์ |
| `lib/mapping.js` | สัญญาการแมปตำแหน่งทางกายภาพกับอุปกรณ์ รวมทั้งกฎการปฏิเสธการแมป |
| `lib/mes-import.js` | ขอบเขตการนำเข้าข้อมูลการผลิตจากภายนอก (MES) |
| `lib/evidence.js` | ทะเบียนแหล่งที่มาของหลักฐานและสัญญาการเลื่อนระดับความน่าเชื่อถือ |
| `public/app.js` | การสร้างฉาก 3D, ระบบเลเยอร์/มุมมอง, การคลิกเลือกวัตถุ (picking), ตัวตรวจสอบข้อมูล (inspector) |
| `public/index.html` | ส่วนแสดงผลหน้าจอ (HUD), ตัวควบคุม, คำอธิบายหลักฐาน, การจัดรูปแบบหน้าจอ |

`lib/evidence.js` เป็น **สัญญา (contract) ไม่ใช่คลังข้อมูล (inventory)** โมดูลนี้ไม่เก็บระเบียนข้อมูลเครื่องจักรและไม่ทำสำเนาข้อมูลที่มีอยู่ในฐานข้อมูล หน้าที่ของมันคือตัดสินว่าแหล่งข้อมูลในอนาคตได้รับอนุญาตให้อ้างสิทธิ์อะไรได้บ้าง กฎเกณฑ์ถูกบันทึกไว้ใน [ข้อกำหนดด้านหลักฐาน (Evidence Requirements)](FACTORY_TWIN_EVIDENCE_REQUIREMENTS.md)

## 3. หน้าต่างการให้บริการ HTTP (HTTP surface)

| เส้นทาง (Route) | ข้อมูลที่ส่งกลับ | หมายเหตุ |
|---|---|---|
| `GET /api/state` | สถานะสดของเครื่องจักรต่ออุปกรณ์ที่ถูกมอนิเตอร์ | เส้นทางเดียวที่ติดต่อกับฐานข้อมูล ใช้บทบาทอ่านอย่างเดียว (read-only role) |
| `GET /api/build` | ลายนิ้วมือการบิลด์ (fingerprint) และค่าแฮชรายไฟล์ | คำนวณตอนบูตจากไบต์ต้นฉบับในอิมเมจที่กำลังทำงาน ไม่สามารถถูกเขียนทับด้วยตัวแปรสภาพแวดล้อมหรือบิลด์สคริปต์ที่ไม่ได้รัน |
| `GET /api/floors` | แคตตาล็อกชั้นที่ติดตั้ง: id, ลำดับ ordinal, เลเบลที่คำนวณได้, การมีอยู่ของโซน | ส่งเฉพาะ id และ ordinal เท่านั้น ไม่มีการอ่านเลเบล ลำดับ หรือคำอธิบายจากเอกสารส่วนตัว |
| `GET /api/floor-geometry` | กรอบอาคาร (envelope), รูปร่างฐานราก (footprint), กริดโครงสร้าง, เสา, ผนัง, **แนวหน้าตัดผนังที่ยังไม่จับคู่**, ช่องเปิด, **อุปกรณ์ CAD**, โซนการทำงานที่ผ่านการตรวจสอบ | รองรับ `?floor=`; หากไม่ระบุจะหมายถึงชั้นดีฟอลต์และคืนค่าเรขาคณิตที่เหมือนกันทุกไบต์ ส่งคืนข้อมูลรูปร่างว่างที่ถูกต้องเมื่อไม่มีข้อมูลเรขาคณิตส่วนตัว (ซึ่งเป็นค่าปกติของการโคลนใหม่ ไม่ถือเป็นข้อผิดพลาด) ส่วน `slots` จะ **ไม่** ถูกส่งออกมาอย่างเด็ดขาด |
| `GET /api/floor-raw-cad` | ลายเส้นตรงจากแบบ CAD จัดกลุ่มตาม **บทบาทเลเยอร์ (layer roles)** ที่กำหนดไว้ | เป็นข้อมูลอ้างอิง ไม่ใช่หลักฐานยืนยันสภาพชั้น ส่งในกรอบพิกัดของ **CAD** — มิลลิเมตร, +y ขึ้นบน, ไม่มีการสะท้อนภาพ — เพื่อให้ไคลเอนต์แปลงพิกัดตามมาตรฐานเอง และหากมีความคลาดเคลื่อนของกรอบพิกัดจะปรากฏให้เห็นบนโอเวอร์เลย์แทนที่จะถูกฝังตายในข้อมูล แต่ละบทบาทส่งเฉพาะ `id`, `segment_count` และ `segments`; ชื่อเลเยอร์จริงของแบบจะไม่หลุดออกจากเซิร์ฟเวอร์ มีการรายงานสิ่งที่คัดออก ดึงข้อมูลเมื่อเปิดโอเวอร์เลย์เท่านั้น |
| `GET /api/floor-schematic` | การถอดแบบร่างแผนผังแรสเตอร์ (raster schematic transcription) | ยังคงเก็บรักษาไว้และมีการควบคุม แต่ **ไม่มีหน้าใดนำไปวาด**: ทวินมาตรฐานอย่างเป็นทางการคือชั้นที่ได้จาก CAD |
| `GET /api/diagnostics` | จำนวนนับ ค่าบูลีน และค่า enum คงที่เท่านั้น | ไม่มีพิกัด ตัวระบุ เส้นทาง ชื่อกระบวนการ หรือชื่อผู้ผลิตหลุดออกไปอย่างเด็ดขาด |
| `GET /healthz` | การตรวจสอบความพร้อมทำงาน (liveness) รวมถึงการทดสอบคิวรีฐานข้อมูลแบบไปกลับ | |

### ชั้นถูกระบุด้วย id ไม่ได้ถูกคอมไพล์ฝังตาย

`lib/floors.js` เป็นผู้จัดการพื้นที่ id ของชั้น และเป็นโมดูลเดียวที่ได้รับอนุญาตให้สร้างพาธเข้าไปยัง `private/` ชั้นที่ 1 เป็นชุดข้อมูลแรกที่ผ่านการตรวจสอบความถูกต้อง การเพิ่มชั้นที่สองที่สำรวจแล้วจึงเป็นเพียงการวางไฟล์ ไม่ใช่การแก้ไขโค้ด

id ของชั้นรับมาจาก query string ดังนั้นจึงถือเป็นอินพุตที่ผู้โจมตีควบคุมได้และถูกนำไปสร้างเป็นพาธในระบบไฟล์ มีเกตป้องกันสองชั้นตามลำดับ:

1. ต้องตรงกับรูปแบบ `^floor[1-5]$` อย่างเคร่งครัด — รูปแบบปิดที่ไม่อนุญาตให้มีจุด สแลช หรือตัวแบ่งใดๆ ทั้งสิ้น
2. ต้องปรากฏอยู่ในแคตตาล็อกที่เซิร์ฟเวอร์สร้างขึ้นจากการอ่านไดเรกทอรีของตนเองอยู่แล้ว

เกตชั้นที่สองคือสิ่งที่ทำให้ระบบเป็นแบบ allowlist-by-construction: **พาธจะถูกสร้างขึ้นจากสำเนา id ในแคตตาล็อกเท่านั้น ไม่ได้สร้างจากสตริงที่ผู้เรียกส่งเข้ามา** ดังนั้นชั้นที่เซิร์ฟเวอร์ตรวจไม่พบจึงไม่สามารถถูกเข้าถึงได้แม้ว่าคำขอจะถูกจัดรูปแบบมาอย่างถูกต้องก็ตาม ชั้นที่ระบุชื่อแต่ยังไม่ได้ติดตั้งจะตอบกลับด้วย `404` พร้อมบอดีคงที่ — จะไม่ส่งรูปร่างเรขาคณิตว่างออกมา เพราะการส่งโครงร่างว่างจะเป็นการยืนยันว่ามีชั้นนั้นอยู่จริงแต่ว่างเปล่า

พารามิเตอร์ `?floor=` เป็นตัวเลือกเสริม หากละเว้นจะหมายถึงชั้นดีฟอลต์ และชุดทดสอบการถดถอยจะตรวจสอบยืนยันว่าการตอบกลับทั้งสองกรณีตรงกันทุกไบต์ ดังนั้น URL เก่าทั้งหมดที่ใช้งานมาก่อนระบบหลายชั้นจึงยังคงมีความหมายเดิม

### การส่งข้อมูลใช้รายการอนุญาต (allowlist) ไม่ใช้การกระจายออบเจกต์ (spread)

เอกสารส่วนตัว (private documents) เป็นทรัพย์สินที่มีความละเอียดอ่อน การเผยแพร่ข้อมูลด้วยการกระจายฟิลด์ (spreading) หมายความว่า **ฟิลด์ใดก็ตามที่เพิ่มเข้าไปในไฟล์ส่วนตัวจะถูกส่งออกไปทันทีที่เขียนลงไฟล์** ซึ่งอาจรวมถึงพาธต้นฉบับ ชื่อจริง หรือบันทึกภายใน

รายการอนุญาตจึงถูกบังคับใช้ที่ **ทั้งสองระดับ**: เส้นทางเราต์ระบุชื่อฟิลด์ระดับบนสุดอย่างชัดเจน และ `lib/wire.js` จะสร้างสล็อต เสา กล่องโซน กรอบอาคาร โซนการทำงาน และความขัดแย้งขึ้นมาใหม่ทีละฟิลด์ ระบบจะส่งออกเฉพาะตัวเลขจำกัด โทเค็นที่ผ่านการตรวจสอบรูปแบบ และ enum คงที่เท่านั้น ข้อความอิสระจึงไม่มีช่องทางรั่วไหลออกไป — บันทึกข้อความ พาธ หรือชื่อกระบวนการจะไม่ผ่านเกตตรวจจับโทเค็นแทนที่จะถูกส่งผ่านออกไป ฟิลด์ใหม่จะต้องถูกเพิ่มเข้าสู่ projection อย่างตั้งใจก่อนจึงจะสามารถส่งออกสู่สายสัญญาณได้

สิ่งใดที่ไม่สามารถฉายภาพได้จะถูก **ระงับการส่ง แทนที่จะถูกแปลงค่าโดยพลการ**: ทรัพย์สินที่ไม่มีตำแหน่งที่ใช้งานได้จะไม่ถูกส่งออกด้วยพิกัดสำรอง เพราะการสร้างตำแหน่งขึ้นมาเองสร้างความเสียหายมากกว่าการไม่แสดงผล กฎเดียวกันนี้บังคับใช้กับ *ขนาดขอบเขต (extent)* ด้วย: ระเบียนอุปกรณ์ที่มี `footprint_status` เป็น `UNRESOLVED` จะถูกส่งด้วย `footprint: null` และตัวฉายภาพจะปฏิเสธการส่ง footprint ออกไปแม้ว่าเอกสารส่วนตัวจะมีขนาดระบุไว้ก็ตาม ตัวฉายภาพรุ่นก่อนหน้าเคยใช้แพดขนาด 1 ม. แทนขนาดที่ขาดหายไป ซึ่งทำให้เกิดขนาดที่แต่งขึ้นบนเครือข่ายโดยมีรูปร่างเหมือนกับขนาดที่วัดได้จริง — บนชั้นที่อ่านจาก CAD สิ่งนี้ไม่สามารถแยกแยะได้ด้วยสายตา

`projectSlot` และเลเยอร์ `slots[]` ที่มันเคยให้บริการถูก **ลบทิ้ง ไม่ใช่แค่ไม่ถูกใช้งาน** ดังนั้นการแอบเพิ่ม `slots: wire.projectAll(...)` กลับเข้าไปในเราต์จะไม่สามารถทำงานได้อย่างเงียบๆ

กฎสองข้อที่เส้นทางเราต์บังคับใช้จริงในโค้ด ไม่ใช่แค่บันทึกไว้ในเอกสาร:

- **เรขาคณิตที่ไม่ผ่านการตรวจสอบความถูกต้องจะไม่สามารถเรนเดอร์ได้** API จะทำการคำนวณตัวกรองสิ่งที่เรนเดอร์ได้ใหม่เองแทนที่จะเชื่อถือแฟล็กของไฟล์ส่วนตัว และเรนเดอเรอร์จะใช้เกตป้องกันเดียวกันนี้ซ้ำอีกครั้ง
- **ไม่มีการอนุมานการแมปใดๆ ทั้งสิ้น** สล็อตจะถือเป็น `UNMAPPED` เว้นแต่จะมีบันทึกที่มีอำนาจระบุเป็นอย่างอื่น ตำแหน่ง ตัวเลขลำดับ หรือการตรงกันของจำนวนนับจะไม่สามารถนำมาสร้างการแมปได้โดยเด็ดขาด

## 4. โมเดลการเรนเดอร์ (Rendering model)

### เลเยอร์และเลเยอร์ย่อย (Layers and sub-layers)

วัตถุจะถูกจัดกลุ่มตามประเภทของข้ออ้างสิทธิ์ เลเยอร์ระดับบนสุดสี่เลเยอร์ (`structural`, `functional`, `operational`, `telemetry`) แต่ละเลเยอร์จะบรรจุกลุ่มเลเยอร์ย่อยซ้อนอยู่ภายใน ทำให้ตัวควบคุมสามารถเปิดปิดข้ออ้างสิทธิ์ทั้งคลาสหรือเลือกเปิดปิดสมาชิกเฉพาะตัวได้:

| เลเยอร์ระดับบน | เลเยอร์ย่อย |
|---|---|
| `structural` | `shell` (แผ่นพื้น, กริดระบุทิศทาง, โครงร่างกรอบที่วัดได้), `columns` |
| `operational` | `machines`, `slots`, `presentation` (ดีฟอลต์ปิด) |
| `functional` | ไม่มี; จัดเป็นคลาสเดี่ยว |
| `telemetry` | ไม่มี; จัดเป็นคลาสเดี่ยว |

การประมวลผลการแสดงผลรองรับทั้งสองระดับ ทำให้ปุ่มสลับของผู้ปฏิบัติงานทั้งหกปุ่มสามารถแมปลงบนทรีโครงสร้างเดียวกันได้โดยไม่ต้องมีตารางค้นหาคู่ขนาน

### โหมดการแสดงผล (Modes)

แอปพลิเคชันเดียว มีห้าโหมด สามโหมดเปลี่ยนว่าข้ออ้างสิทธิ์ใดจะปรากฏบนหน้าจอ และอีกสองโหมดเปลี่ยนปริมาณเครื่องมือที่ล้อมรอบข้ออ้างสิทธิ์เดียวกันนั้น

| โหมด | 3D | แผนผัง (Drawing) | สิ่งที่ต้องมี |
|---|---|---|---|
| `executive` | ✓ | | ชั้นที่วัดค่าได้; จัดเฟรมกว้างที่สุด, ซ่อนแผงควบคุม |
| `physical` | ✓ | | ชั้นที่วัดค่าได้ |
| `schematic` | | ✓ | แผนผังที่ถอดแบบแล้ว |
| `split` | ✓ | ✓ | มีทั้งสองอย่าง |
| `inspection` | ✓ | | ชั้นที่วัดค่าได้; แสดงแผงควบคุมทุกตัว |

โหมดคือคลาสของ body ร่วมกับค่าพรีเซ็ตของกล้อง **ไม่มีโหมดใดเปลี่ยนแปลงค่าพิกัด** และการทดสอบการถดถอยพิสูจน์สิ่งนี้ด้วยการสแนปชอตพิกัดระดับไบต์ในทุกการสลับโหมด โหมดที่ต้องการภาพวาดจะถูก **ปิดการใช้งานพร้อมแสดงเหตุผล** เมื่อไม่มีข้อมูลติดตั้ง แทนที่จะถูกซ่อนไว้ — การแจ้งว่า "มีมุมมองเปรียบเทียบแบบเคียงข้างกันแต่ระบบนี้ไม่มีข้อมูลสำหรับแสดงผล" เป็นสิ่งที่ควรทราบ

โหมด `split` วางสองหน้าต่างชนกันด้วยเส้นแบ่งแข็ง ไม่ใช้นำภาพมาซ้อนทับกัน (overlay): การนำมาซ้อนทับจะเป็นการยืนยันการลงทะเบียนพิกัด (registration) ระหว่างสองระบบที่ไม่ได้ใช้กรอบอ้างอิงร่วมกัน แถบประกาศจะระบุว่า `PHYSICAL + SCHEMATIC — UNREGISTERED` แทนที่จะระบุว่าเป็นข้ออ้างสิทธิ์เดี่ยวตัวใดตัวหนึ่ง

ทุกการวัดขนาดที่ใช้จัดเลย์เอาต์ฉาก — ขนาดเรนเดอเรอร์, ระยะฟิตของกล้อง, ระยะฟิตของแบบ — จะวัดเทียบกับ **บานหน้าต่าง (pane)** เท่านั้น ไม่วัดเทียบกับหน้าต่างเบราว์เซอร์ ในมุมมองเคียงข้างกัน บานหน้าต่างจะมีความกว้างเพียงครึ่งหนึ่งของหน้าต่างและเริ่มต้นที่ด้านขวาของ HUD ดังนั้นการวัดเทียบกับหน้าต่างจะทำให้แผงควบคุมไปทับพื้นที่ที่ไม่ได้อยู่บนบานหน้าต่างนั้น

### ความหมายของกล้องและมุมมอง (Camera and view semantics)

พรีเซ็ตทั้งสามแบบ (operator, building, overview) เป็นเพียง **การจัดเฟรมภาพเท่านั้น** การสลับมุมมองจะกำหนดตำแหน่งกล้อง จุดเป้าหมาย และช่วงความลึก โดยไม่แตะต้องทรานส์ฟอร์มของวัตถุเลย ชุดทดสอบการถดถอยพิสูจน์สิ่งนี้: มีการเก็บสแนปชอตพิกัดที่เรนเดอร์ทั้งหมดด้วยความแม่นยำคงที่ก่อนการสลับครั้งแรก และเปรียบเทียบไบต์ต่อไบต์หลังจากการสลับครบทั้งสามมุมมองและรีเซ็ตกลับมา

รายละเอียดสองประการที่ควรทราบก่อนแก้ไขโค้ดการปรับระยะฟิต:

- **ระยะฟิตได้มาจากการวัดจริง ไม่ใช่การคำนวณสูตรปิด** กล้องมุมเอียงจะมองเห็นโครงร่างเงามืด (silhouette) ของกล่อง ไม่ใช่ขอบเขตตามแนวแกน ดังนั้นสูตรตรีโกณมิติแบบปิดที่เคยใช้อยู่เดิมจึงประเมินระยะทางต่ำเกินไปและตัดขอบมุมของพื้นทิ้ง — ซึ่งแย่ที่สุดที่มุมมองเอียงระดับตื้นที่ช่วยให้มองเห็นพื้นได้ชัดเจน ตอนนี้การปรับระยะฟิตจะฉายมุมทั้งแปดของกรอบผ่านกล้องทดลองและปรับสเกลจนกว่ามุมเหล่านั้นจะอยู่ภายในพื้นที่ว่างที่โอเวอร์เลย์ไม่บดบัง วิธีนี้ให้ผลลัพธ์ที่แม่นยำสำหรับทุกมุม ทุกอัตราส่วนหน้าจอ และทุกความกว้างของแผงควบคุม
- **Overview จัดเฟรมครอบคลุมยูเนียนของขอบเขต ไม่ใช่การลงทะเบียนพิกัดร่วม** ขอบเขตอาคารที่วัดได้และขอบเขตเครื่องจักรจำลองเป็นระบบพิกัดที่แยกจากกัน ยูเนียนจะนำทั้งสองระบบเข้ามาในเฟรมภาพเดียวกันโดยไม่ได้หมายความว่ามีความสัมพันธ์ตรงกันระหว่างทั้งสอง ดูคำเตือนใน [คู่มือผู้ปฏิบัติงาน (Operator Guide)](FACTORY_TWIN_OPERATOR_GUIDE.md)

การจัดเฟรมจะถูกคำนวณใหม่เมื่อโหลดข้อมูล เมื่อเรขาคณิตมาถึง และเมื่อปรับขนาดหน้าต่างผ่านเส้นทางเดียวกัน ดังนั้นการเปลี่ยนขนาดวิวพอร์ตจะไม่ทำให้สองมุมมองถูกปรับระยะจากอินพุตที่ต่างกัน พรีเซ็ตที่ข้อมูลอินพุตยังมาไม่ถึงจะคงสถานะปิดการใช้งานแทนที่จะแอบถอยกลับไปใช้การจัดเฟรมอื่น

### การนำทรัพยากรกลับมาใช้ใหม่และการเรนเดอร์ตามความต้องการ (Resource reuse and render on demand)

เรขาคณิตและวัสดุจะถูกแคชและแชร์ข้ามเมชต่างๆ แทนที่จะสร้างใหม่ต่อวัตถุ และงานปรับขนาดจะถูกรวมเป็นการเรียกครั้งเดียวต่อเฟรม

**เฟรมจะถูกวาดเมื่อมีความต้องการเท่านั้น (on demand)** มุมมองนี้ถูกจำกัดด้วยอัตราการเติมพิกเซล (fill-rate bound) ไม่ใช่ขอบเขตเรขาคณิต: ตั้งแต่ความละเอียด 1366×768 ไปจนถึง 3840×2160 เวลาเฉลี่ยของแต่ละเฟรมจะแปรผันตามจำนวนพิกเซลเกือบสมบูรณ์แบบในขณะที่จำนวนสามเหลี่ยมไม่เปลี่ยนแปลง และฉากจะอยู่นิ่งไม่มีการเคลื่อนไหวระหว่างการมีปฏิสัมพันธ์ — มันไม่เคยมีแอนิเมชัน และการโพลค่าโทรมาตรทุกห้าวินาทีจะเปลี่ยนสีของวัตถุเพียงไม่กี่ชิ้น การวาดซ้ำหกสิบครั้งต่อวินาทีจึงเป็นการผลาญงบประมาณเฟรมทั้งหมดไปกับการสร้างภาพเดิมซ้ำๆ เสียเวลาประมวลผลกว่า 200 ms ต่อเฟรมที่ระดับ 4K โดยที่ไม่มีสิ่งใดเปลี่ยนแปลง

ตอนนี้เฟรมจะถูกวาดเมื่อมีสิ่งใดเปลี่ยนแปลงจริงเท่านั้น: การเคลื่อนไหวของกล้อง, การเปิดปิดเลเยอร์, การเปลี่ยนโหมดหรือมุมมอง, การปรับขนาดหน้าต่าง, การโฮเวอร์เมาส์, การอัปเดตโทรมาตร คำขอใดๆ จะวาดเฟรมต่อเนื่องสั้นๆ แทนที่จะเป็นเฟรมเดียวพอดี เพราะคำว่า "เปลี่ยนแปลง" ไม่สามารถสังเกตเห็นได้ในรอบสัญญาณเดียวเสมอไป — เช่น เท็กซ์เจอร์กำลังถอดรหัสเสร็จ, สไปรต์กำลังจัดเลย์เอาต์, หรือการอัปโหลดวัสดุเสร็จสิ้น

ผลการวัดจริง: **วาด 0 เฟรมในเวลาอยู่นิ่ง 2 วินาที** ที่ 1080p และ 4K; **วาด 102 เฟรมระหว่างการลากหมุนมุมกล้อง 0.8 วินาที** ประสบการณ์ตอบสนองไม่ลดลง และช่วงเวลาอยู่นิ่งไม่มีการใช้ทรัพยากร อัตราส่วนพิกเซลของอุปกรณ์ (device pixel ratio) ถูกจำกัดไว้ที่ 2 ด้วยเหตุผลด้านขีดจำกัด fill-rate เช่นเดียวกัน

เลเยอร์ **presentation** ใช้วิธี instancing — หนึ่ง `InstancedMesh` ต่อคู่ (form, part), รวม 21 วัตถุและ 21 draw calls สำหรับทั้งชั้น องค์ประกอบที่วัดได้ในปัจจุบันบันทึกไว้ใน **[การประกันคุณภาพทางสายตา (Visual QA)](FACTORY_TWIN_VISUAL_QA.md)**

## 5. รูปแบบการติดตั้ง (Deployment shape)

- อิมเมจถูกสร้างด้วยคำสั่ง **`COPY` แบบระบุรายการอนุญาต** (`server.js`, `lib`, `public`) ไดเรกทอรี `private/` จะไม่ถูกคัดลอกลงในเลเยอร์ของอิมเมจอย่างเด็ดขาด
- `private/` จะถูกไบนด์เมานต์ (bind-mounted) แบบ **อ่านอย่างเดียว (read-only)** ในขณะรันไทม์ โฮสต์ในสภาพแวดล้อมโปรดักชันสามารถวางไฟล์จริงลงในพาธนั้นได้โดยไม่ต้องแก้โค้ดและไม่ต้องบิลด์ใหม่
- **โค้ดแอปพลิเคชันถูกฝังลงในอิมเมจ** การเปลี่ยนแปลงใต้ `public/` หรือ `lib/` จำเป็นต้องทำการบิลด์ใหม่และสร้างคอนเทนเนอร์ของเซอร์วิสนี้ขึ้นมาใหม่ก่อนจึงจะเห็นผล มีเพียง `private/` เท่านั้นที่เมานต์แบบสด สิ่งนี้มักสร้างความประหลาดใจให้กับทีมงานอยู่เสมอ
- nginx จะทำการรีโซลฟ์ชื่อโฮสต์ต้นทางตอนเริ่มต้นระบบ ดังนั้นหลังจากสร้างคอนเทนเนอร์นี้ใหม่ พร็อกซีจำเป็นต้องทำการ reload หนึ่งครั้ง

คำสั่งที่แน่นอนและอาการข้อผิดพลาดถูกบันทึกไว้ใน **[คู่มือการปฏิบัติการ (Operations Runbook)](../operations-runbook.md)**

## 6. เส้นทางมาตรฐานอย่างเป็นทางการ และวิธีที่บิลด์ค้างเคยแอบซ่อนอยู่เบื้องหลัง

### มีแฝดดิจิทัลโรงงานที่ให้บริการผู้ใช้เพียงหนึ่งเดียวเท่านั้น

```text
browser
  -> http://localhost:3000/factory-twin-3d/
  -> ims-proxy (nginx:1.31-alpine, คอนเทนเนอร์เดียวที่เปิด host port)
       location /factory-twin-3d/  { auth_request /auth-check;
                                     proxy_pass http://factory-twin-3d:4100/; }
       location = /auth-check      { internal; proxy_pass http://grafana:3000/api/user; }
  -> ims-factory-twin-3d (ไม่มี host port, อยู่ในเครือข่าย ims-internal เท่านั้น)
  -> /app/server.js  +  /app/private (read-only bind mount)
```

พอร์ต `127.0.0.1:4199` มีไว้สำหรับ **การตรวจสอบและทดสอบชั่วคราวเท่านั้น** เป็นคอนเทนเนอร์แบบใช้แล้วทิ้งที่เริ่มต้นด้วย `scripts/twin-direct-container.ps1` ผูกไว้กับ loopback โดย **ไม่มีเกตตรวจสอบสิทธิ์** มันไม่ใช่ตัวโปรดักต์ และต้องไม่เป็นสถานที่ที่ผลลัพธ์ปรากฏขึ้นในขณะที่เส้นทางมาตรฐานอย่างเป็นทางการยังคงเป็นบิลด์เก่า

### ความผิดพลาดที่ส่วนนี้ถูกเขียนขึ้นเพื่อป้องกัน

อิมเมจที่ถูกบิลด์ใหม่ไม่ได้หมายความว่าเซอร์วิสถูกดีพลอยใหม่ `docker compose build` ทำการแท็กอิมเมจใหม่ แต่ **คอนเทนเนอร์ที่กำลังทำงานอยู่จะยังคงใช้อิมเมจเดิมที่มันถูกสร้างขึ้นมา** จนกว่ามันจะถูกสร้างใหม่ (recreated) นั่นคือสาเหตุที่การติดตั้งนี้เคยให้บริการบิลด์ที่ล้าหลังไปถึงหกคอมมิต ทั้งที่รีโพซิทอรี ชุดทดสอบ และแท็กอิมเมจได้เดินหน้าไปแล้ว — และทำให้เกิดความเข้าใจผิดว่าพอร์ตตรวจสอบที่ถูกบิลด์ใหม่คือพอร์ตโปรดักชันที่ถูกบิลด์ใหม่แล้ว

ไม่มีสิ่งใดบนหน้าเว็บที่จะเปิดเผยปัญหานี้ได้: ส่วนหน้าเป็นไฟล์สแตติกที่ไม่มีเลขเวอร์ชันระบุอยู่

### สิ่งที่ทำให้มองเห็นได้ชัดเจนในปัจจุบัน

`GET /api/build` ส่งคืนลายนิ้วมือ (fingerprint) ที่คำนวณ **ตอนบูตจากไบต์บนดิสก์ในอิมเมจที่กำลังทำงาน** — ได้แก่ `server.js`, `lib/` และ `public/` ค่านี้ไม่สามารถถูกกำหนดโดยตัวแปรสภาพแวดล้อมและไม่สามารถแอบอ้างเวอร์ชันที่โค้ดจริงไม่ได้รัน ส่วนหัวของหน้าเว็บจะแสดงค่านั้นเป็นชิป `build …`

การตรวจสอบยืนยันการติดตั้งจึงเป็นการเปรียบเทียบคำสั่งเดียว:

```sh
# ตรวจสอบสิ่งที่โปรดักชันกำลังรันอยู่จริง
docker exec ims-proxy wget -qO- http://factory-twin-3d:4100/api/build

# ตรวจสอบสิ่งที่คอนเทนเนอร์ตรวจสอบกำลังรันอยู่
curl -s http://127.0.0.1:4199/api/build
```

**ลายนิ้วมือตรงกันหมายถึงโค้ดเหมือนกันทุกประการ** หากลายนิ้วมือต่างกันแสดงว่าตัวใดตัวหนึ่งล้าสมัย ไม่ว่าแท็กของอิมเมจจะระบุอย่างไรก็ตาม

### การดีพลอยใหม่

```sh
docker compose build factory-twin-3d
docker compose up -d --force-recreate --no-deps factory-twin-3d
```

แฟล็ก `--force-recreate` คือแฟล็กสำคัญที่ต้องมีเสมอ หากไม่มีแฟล็กนี้ compose อาจปล่อยให้คอนเทนเนอร์ที่สมบูรณ์ยังคงทำงานบนอิมเมจเก่าต่อไป

### การควบคุมการเข้าถึง และความหมายต่อการตรวจสอบยืนยัน

`/factory-twin-3d/` ถูกควบคุมด้วย `auth_request` เทียบกับเซสชันของ Grafana เช่นเดียวกับ `/alarm-api/` คำขอที่ไม่ผ่านการยืนยันตัวตนจะได้รับรหัส **401 จากเกต** ไม่ใช่จากเซอร์วิส — หากได้รับ 404 หรือ 502 จะหมายถึงความผิดพลาดของการกำหนดเส้นทางแทน

พฤติกรรมของฉากและหลักฐานจึงถูกตรวจสอบผ่านคอนเทนเนอร์ตรวจสอบบน loopback ซึ่งรัน **อิมเมจเดียวกัน** และได้รับการพิสูจน์แล้วว่าเหมือนกันทุกประการด้วยลายนิ้วมือ ส่วนการควบคุมการเข้าถึงจะถูกตรวจสอบแยกต่างหากเทียบกับเส้นทางมาตรฐานอย่างเป็นทางการ โดยการตรวจสอบขอบเขตแบบไม่ระบุตัวตนในชุดทดสอบการถดถอย
