# ข้อบกพร่องการสะสมตัวชี้วัด RAM — สาเหตุที่แท้จริง + การออกแบบการแก้ไข

**สถานะ: แก้ไขและปรับใช้แล้วเมื่อ 2026-08-15 (P0.1 ของ Reliability Test Suite)** ดูส่วนผลลัพธ์ที่ด้านล่าง

**ลำดับความสำคัญ:** สูง — กำลังสร้างสัญญาณที่ผิดพลาดแบบ "ทุกอย่างอยู่ในขั้นวิกฤต" บนแดชบอร์ดโครงสร้างพื้นฐานทุกแห่งที่แสดง Fleet Health Score หรือ RAM % อย่างต่อเนื่องในขณะนี้ สำหรับอุปกรณ์ทุกเครื่อง

## ห่วงโซ่หลักฐาน (3 เลเยอร์)

**เลเยอร์ 3 (UI):** แผง "Fleet Health Score" ของแดชบอร์ด `ims-capacity` แสดงผล `0%` เป็นสีแดง ภาพหน้าจอ: `.playwright-mcp\page-2026-08-15T02-24-50-863Z.png`

**เลเยอร์ 2 (runtime/DB):** อุปกรณ์ทุกเครื่องใน `public.sys_metrics` ณ วันที่ 2026-08-15T02:2x UTC มีค่า `ram_used_mb` เท่ากับ `ram_total_mb` พอดี ซึ่งเท่ากับ `1048576` พอดี:

```
     device_id      | ram_used_mb | ram_total_mb
--------------------+-------------+--------------
  ERP-MASTER-UBUNTU  |     1048576 |      1048576
  ERP-MASTER-WINDOWS |     1048576 |      1048576
  EXPOSURE LDI-2      |     1048576 |      1048576
  EXPOSURE LDI-2B     |     1048576 |      1048576
```

`disk_used_gb`/`disk_total_gb` สำหรับแถวเดียวกันนั้นไม่ได้ค้าง (12500/12500, 116415.32/186264.51, 476.84/500, 476.84/500) -- มีค่าที่แตกต่างกันและสมเหตุสมผล เฉพาะ RAM เท่านั้นที่ถูกตรึงไว้ และตรึงด้วยตัวเลขเดียวกันทุกประการสำหรับอุปกรณ์ทุกเครื่อง ซึ่งนั่นคือเบาะแส

**เลเยอร์ 1 (code):** ไฟล์ `nodered_data/lib/parser.js`, ฟังก์ชัน `parseAll`:

- บรรทัด 15: `let ramTotalMb = state.ram_total || 0, ramUsedMb = state.ram_used || 0, ...` -- ตัวสะสมค่า RAM **ถูกกำหนดค่าเริ่มต้น (seeded) จากสถานะของรอบการโพล (poll) ครั้งก่อนหน้า** ไม่ได้เริ่มจากศูนย์
- บรรทัด 31 (ภายใน `if (type === 'storage')`): `ramTotalMb += bytesTotal / 1048576; ramUsedMb += bytesUsed / 1048576;` -- ในแต่ละรอบการโพลจะ **เพิ่ม** ไบต์ตารางพื้นที่เก็บข้อมูลที่จัดประเภทเป็น RAM ของรอบนี้เข้าไปในสิ่งที่ได้สะสมไว้จากทุกรอบก่อนหน้า ในทางตรงกันข้าม ค่า disk ทำการแทนที่ค่าโดยตรงในอีกสองบรรทัดถัดมา (`diskTotalGb = largestDiskBytes / 1073741824`) ไม่ใช่ `+=` -- ความไม่สมมาตรนี้คือสาเหตุที่ disk ไม่ค้าง แต่ RAM ค้าง
- บรรทัดเดียวกัน ต่อมา: `ramTotalMb = Math.min(ramTotalMb, 1048576);` -- เพดานความสมเหตุสมผลที่ 1TB เห็นได้ชัดว่าถูกเพิ่มเข้ามาเพื่อเป็นตัวหนีบ (clamp) ป้องกันข้อมูล SNMP ที่ผิดพลาด เนื่องจาก `ramTotalMb` เติบโตอย่างไม่มีขอบเขตในทุกการโพล (ไม่เคยรีเซ็ต) ในที่สุดมันก็จะเกินเพดานนี้และถูกหนีบไว้ที่ `1048576` พอดี
- บรรทัด 33 (คำสั่ง return): `ramUsedMb: Math.max(0, Math.min(ramTotalMb, ...ramUsedMb...))` -- หนีบ `ramUsedMb` ใหม่อีกครั้งให้เทียบกับ `ramTotalMb` _ที่ถูกหนีบไปแล้ว_ เมื่อ `ramTotalMb` อิ่มตัวที่ `1048576` แล้ว ค่า `ramUsedMb` (ซึ่งเติบโตควบคู่กันไป ในสัดส่วนที่พอๆ กัน) ก็จะถูกหนีบลงมาที่ `1048576` ในบรรทัดเดียวกันด้วย ทั้งสองค่ามาหยุดที่ตัวเลขที่เหมือนกัน -- ซึ่งเป็นการเสริมแรงตัวเอง (self-reinforcing) เพราะในรอบถัดไปจะอ่าน `state.ram_total` กลับออกมาที่ `1048576` และเพิ่มเข้าไปอีกบนค่านั้น จากนั้นหนีบกลับไปที่ `1048576` ทันทีอีกครั้ง เมื่ออุปกรณ์เครื่องใดถึงเพดานครั้งหนึ่งแล้ว มันจะค้างอยู่ที่นั่นอย่างถาวรจนกว่า Node-RED จะรีสตาร์ท และ `state` จะรีเซ็ต

สิ่งนี้อธิบายข้อมูลที่สังเกตได้อย่างสมบูรณ์: อุปกรณ์ทุกเครื่องที่ทำการโพลมานานพอได้อิ่มตัวที่ 100% "RAM used" ซึ่งเป็นเหตุผลที่ว่าทำไมสาขาเงื่อนไข `CASE WHEN ... ram_pct > 95 ... THEN 0` ของ `Fleet Health Score` จึงทำงานสำหรับอุปกรณ์ทุกเครื่อง ทุกครั้ง ส่งผลให้คะแนนระดับ fleet ลดลงเหลือ `0%` อย่างถาวร

## การแก้ไข (ยังไม่ได้ปรับใช้)

มีปัญหา 2 ประการที่เป็นอิสระจากกัน ซึ่งทั้งคู่จำเป็นต้องได้รับการแก้ไข:

1. **อย่าตั้งต้น (seed) จากสถานะก่อนหน้า** ตัวสะสม RAM ควรเริ่มต้นที่ `0` ในแต่ละรอบการโพลสำหรับการเดินสาย SNMP ชนิดพื้นที่เก็บข้อมูล เช่นเดียวกับ `largestDiskBytes` ของ disk (`let largestDiskBytes = 0` เป็นแบบโลคัลของแต่ละรอบ) การตั้งต้น `state.ram_total || 0` / `state.ram_used || 0` ในบรรทัดที่ 15 มีอยู่เพื่อให้ค่าคงอยู่ข้ามการโพลที่ _ไม่ได้_ รวมการเดินสายพื้นที่เก็บข้อมูล (สาขาประเภท walker ที่ `isEmpty` จะตั้งค่าเหล่านี้เป็นศูนย์โดยเจตนาอยู่แล้วสำหรับ `walkerType === 'storage'` -- ดูบรรทัดด้านบนก่อนหน้า `if (walkerType === 'storage') { state.ram_total = 0; ... }`) บั๊กคือเส้นทาง _ที่ถูกเติมข้อมูล_ (เส้นทางที่บั๊กนี้อยู่) ใช้ `+=` แทน `=` เมื่อการเดินสายพื้นที่เก็บข้อมูลสำเร็จ ดังนั้นมันจึงนำไปทบยอดแทนที่จะแทนที่

   การแก้ไข: เปลี่ยน `ramTotalMb += bytesTotal / 1048576; ramUsedMb += bytesUsed / 1048576;` เป็น `ramTotalMb = bytesTotal / 1048576; ramUsedMb = bytesUsed / 1048576;` (ยกเลิกการอ่าน seed จากสถานะสำหรับตัวแปรสองตัวนี้โดยเฉพาะ หรือรีเซ็ตค่าเป็น `0` ก่อนเริ่มลูป storage แทนการ seed จาก `state.ram_total`/`state.ram_used`)

2. **การหนีบที่ 1TB เป็นตัวซ่อนอาการ ไม่ใช่การแก้ไข** เมื่อข้อ (1) ได้รับการแก้ไข ยอดรวม RAM ที่ถูกต้องจะไม่เกิน 1TB อีกต่อไปในการทำงานปกติ ดังนั้นตัวหนีบจึงกลายเป็นค่าที่ไม่มีการทำงาน (ปล่อยทิ้งไว้เป็นกำแพงป้องกันก็ได้ไม่เป็นอันตราย) -- ไม่มีข้อบังคับให้เปลี่ยนแปลงที่นี่อย่างเคร่งครัด แต่ควรเขียนความคิดเห็นระบุว่าขณะนี้มันเป็นขอบเขตป้องกันลำดับสุดท้าย ไม่ใช่พาธของโค้ดปกติ

## การเปิดตัว (Rollout)

ปรับใช้โดย `docker compose restart node-red` (บริการเดียว, รูปแบบรัศมีผลกระทบแคบแบบเดียวกับ Phase A1) เมื่อ 2026-08-15T04:13:49Z ไฟล์ `nodered_data/lib/parser.js` ถูกเรียกใช้ผ่าน `require()` ครั้งเดียวเข้าไปที่ `functionGlobalContext.parser` โดย `nodered_data/settings.js` ตอนเริ่มกระบวนการ ซึ่งได้รับการยืนยันจากการอ่านไฟล์ `settings.js` โดยตรงที่บรรทัด 31 ก่อนการปรับใช้ -- การรีสตาร์ทเป็นการดำเนินการทั้งจำเป็นและเพียงพอเพื่อให้รับรู้ถึงการแก้ไขนี้

## ผลลัพธ์

เส้นฐานก่อนการแก้ไข (บันทึกช่วงเวลาเล็กน้อยก่อนการรีสตาร์ท): `ERP-MASTER-WINDOWS`, `EXPOSURE LDI-2`, `EXPOSURE LDI-2B` ล้วนถูกตรึงที่ `ram_used_mb = ram_total_mb = 1048576` สำหรับ `ERP-MASTER-UBUNTU` อยู่ระหว่างการเพิ่มขึ้นที่ `637440/679936` (93.7%) -- ซึ่งตัวมันเองเป็นหลักฐานยืนยันเพิ่มเติมสำหรับทฤษฎีการสะสม เนื่องจากมันยังไม่กลับมาอิ่มตัวที่เพดานอีกครั้งหลังจากที่การรีสตาร์ท A1 ได้รีเซ็ตบริบท `flow` ของอุปกรณ์ทั้งหมดกลับเป็นศูนย์

ไม่มีอุปกรณ์ใดแสดงค่า `1048576` อีกต่อไป ไม่มีอุปกรณ์ใดกำลังเพิ่มขึ้น ค่าแตกต่างกันอย่างมีนัยสำคัญในแต่ละอุปกรณ์ (46.9%-93.75%) ไม่ได้ยุบรวมเป็นตัวเลขเดียวที่เหมือนกัน -- เป็นการยืนยันว่าตอนนี้คือ snapshot ต่ออุปกรณ์จริงๆ ไม่ใช่ผลลัพธ์ที่เกิดจากการสะสมทบ

**CPU/ดิสก์/อุณหภูมิ ไม่ได้รับผลกระทบ ยืนยันได้จากการเปรียบเทียบโดยตรงกับแถวเดียวกัน**: `cpu_load_percent` (50 / 88.25 / 83.75 / 83.75) และ `temp_c` (65 / 95 / 92 / 92) ตรงกับเส้นฐานก่อนแก้ไขของเซสชันก่อนหน้านี้พอดี ส่วน `disk_total_gb`/`disk_used_gb` ไม่มีการเปลี่ยนแปลงเช่นกัน -- `ERP-MASTER-UBUNTU` ยังคงแสดงข้อบกพร่องดิสก์ `12500/12500` (100%) ที่แยกต่างหากและได้รับการวิเคราะห์แล้ว (`READ_ONLY_AUDIT_2026-08-15.md` §3c, ได้รับการแก้ไขแยกต่างหากใน P0.2) -- ซึ่งพิสูจน์ว่าการแก้ไข RAM นี้นี้ส่งผลต่อสิ่งที่สมควรถูกส่งผลกระทบเท่านั้น

การทดสอบย่อย (Unit tests) ถูกรันซ้ำหลังการแก้ไขและก่อนการปรับใช้: `tests/unit/parser.test.js` (22/22) และ `tests/unit/v2-parser.test.js` (27/27) ต่างก็ผ่านทั้งหมด รวมถึงการทดสอบขอบเขตที่มีอยู่ของ "จำกัดความจุ RAM รวมสูงสุดที่ 1TB" และ "RAM ที่ใช้ไปห้ามเกิน RAM ทั้งหมด" -- เป็นการยืนยันว่าการหนีบเพื่อป้องกัน (ที่เก็บไว้ ไม่ได้ลบออก -- ดูข้อ 2 ด้านบน) ยังคงทำงานอย่างถูกต้อง และการแก้ไขนี้ไม่ได้ทำให้เกิดการถดถอย (regress)

## บันทึกขอบเขต (แก้ไขแล้ว)

`disk_used_gb == disk_total_gb` สำหรับ `ERP-MASTER-UBUNTU` ที่ถูกตั้งข้อสังเกตไว้ที่นี่ว่าเป็นบันทึกขอบเขตที่ "ยังไม่ได้สืบสวน" -- ค้นพบสาเหตุที่แท้จริงแยกต่างหากแล้วใน `READ_ONLY_AUDIT_2026-08-15.md` §3c (บั๊กของคอนฟิก `.snmprec` ซึ่งไม่เกี่ยวข้องกับปัญหาการสะสมตัว RAM นี้) และได้รับการแก้ไขแล้วตาม P0.2
