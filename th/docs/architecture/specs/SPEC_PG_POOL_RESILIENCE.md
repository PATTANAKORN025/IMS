## สาเหตุที่แท้จริง

การกำหนดค่าสดของ `ims-pgbouncer` (`docker exec ims-pgbouncer cat
/etc/pgbouncer/pgbouncer.ini`) มีการระบุว่า:

```ini
# Connection sanity checks, timeouts
server_idle_timeout = 300
# Dangerous timeouts
client_idle_timeout = 300
```

`client_idle_timeout = 300` ถูกทำเครื่องหมายว่า "Dangerous timeouts" ใน
ความคิดเห็นของไฟล์การกำหนดค่า -- ผู้ที่เขียนสิ่งนี้รู้แล้วว่ามีความเสี่ยง 
PgBouncer จะปิดการเชื่อมต่อไคลเอ็นต์ที่ไม่มีการใช้งาน (idle) เป็นเวลา 300 
วินาทีอย่างบังคับ ทั้ง `pg.Pool` ของ `node-red` (ที่สร้างขึ้นแบบอินไลน์ต่อ
โหนดฟังก์ชัน เช่น ผ่าน `global.get('pgPool')`) และ `pool = new Pool({...})` ของ 
`services/alarm-api/server.js` ไม่ได้ลงทะเบียนตัวจัดการ `pool.on('error', ...)`
เมื่อ PgBouncer ฆ่าการเชื่อมต่อที่ไม่มีการใช้งาน ข้อผิดพลาดที่เกิดขึ้นจะแสดงเป็น 
**เหตุการณ์ `error` ที่ไม่ได้รับการจัดการบนพูล** ซึ่ง Node.js จะถือว่าเป็น
ข้อยกเว้นที่ไม่สามารถดักจับได้ -- ทำให้กระบวนการทั้งหมดถูกฆ่า ไม่ใช่เพียงการค้นหานั้น

นโยบาย `restart: unless-stopped` ของ Docker นำคอนเทนเนอร์กลับมาทำงาน
ภายใน 1-2 วินาที ไม่มีหลักฐานการสูญหายของข้อมูล (ทั้งสองคอนเทนเนอร์แสดง
การทำงานปกติทันทีหลังจากรีสตาร์ทในบันทึก) แต่นี่คือลักษณะของ "การรีสตาร์ทที่ไม่คาดคิด"
ที่ Soak Attempt 6 ตั้งใจจะดักจับ และมันก็จับได้แล้ว

**นี่เป็นไปได้อย่างมากว่าจะเป็นสาเหตุที่แท้จริงที่อยู่เบื้องหลังความไม่เสถียร
อย่างน้อยบางส่วนในความพยายาม soak ก่อนหน้านี้ และอาจเป็นสาเหตุของเหตุการณ์
16 ชั่วโมงแต่เดิมซึ่งเป็นที่มาของความพยายามในการสังเกตการณ์ของเซสชันนี้ทั้งหมด**
-- ไม่ได้รับการยืนยัน (การเก็บรักษาบันทึกของ Docker ไม่ได้ครอบคลุม
ไปถึงช่วงเวลาดังกล่าว ตาม `SOAK_TEST_LOG.md` Attempt 1) แต่ลักษณะความล้มเหลว
ตรงกัน: บริการ Node.js แครชและรีสตาร์ทอย่างเงียบๆ โดยไม่มีสาเหตุ
ในระดับแอปพลิเคชัน

## การออกแบบ

เพิ่มตัวจัดการ `pool.on('error', ...)` ในทุกที่ที่มีการสร้าง `pg.Pool` 
เพื่อที่เมื่อการเชื่อมต่อที่ไม่ได้ใช้งานถูกดรอป (จาก PgBouncer, จากเครือข่ายกระตุก,
หรือจากการรีสตาร์ท Postgres) จะถูกบันทึกไว้ และพูลสามารถกู้คืนไปยังไคลเอ็นต์ถัดไปได้
แทนที่จะทำให้กระบวนการแครช:

```js
// services/alarm-api/server.js
const pool = new Pool({/* ... การกำหนดค่าเดิม ... */});
pool.on("error", (err) => {
  console.error(
    "pg pool idle-client error (non-fatal, pool recovers):",
    err.message,
  );
});
```

```js
// node-red: ที่ไหนก็ตามที่ global.set('pgPool', ...) สร้างพูลส่วนกลาง
// (น่าจะเป็นโหนดฟังก์ชันการเริ่มต้น/การตั้งค่าส่วนกลาง) -- รูปแบบเดียวกัน:
pgPool.on("error", (err) => {
  node.warn(
    "pg pool idle-client error (non-fatal, pool recovers): " + err.message,
  );
});
```

นี่คือการแก้ไขมาตรฐานที่มีเอกสารประกอบสำหรับรูปแบบความล้มเหลว `node-postgres`
ลักษณะนี้โดยเฉพาะ (`pool.on('error')` มีอยู่เพื่อให้ข้อผิดพลาดของไคลเอ็นต์ที่ไม่มีการใช้งาน
ไม่ทำให้กระบวนการแครช) -- ไม่ใช่การออกแบบใหม่ แต่เป็นระบบป้องกันมาตรฐานที่ขาดหายไป

**ข้อพิจารณารอง ไม่ใช่การแก้ไขหลักของข้อกำหนดนี้**: ไม่ว่า 
`client_idle_timeout = 300` จะเป็นค่าที่เหมาะสมหรือไม่ เทียบกับการปิดใช้งาน
(`0`) หรือการเพิ่มค่า เมื่อทั้ง `node-red` และ `alarm-api` เก็บการเชื่อมต่อในพูล
ที่มีอายุการใช้งานยาวนาน ซึ่งอาจไม่ได้ใช้งานจริงๆ เป็นเวลานานกว่า 5 
นาทีระหว่างแบตช์ LDI ตัวจัดการ `on('error')` ทำให้การ *แครช* หยุดลง; 
มันไม่ได้จัดการกับ *เหตุผล* ที่การเชื่อมต่อไม่มีการใช้งานนาน
พอที่จะถึงกำหนดหมดเวลาตั้งแต่แรก ควรวัดระยะเวลาว่างที่แท้จริง 
(หลักฐานจริง ไม่ใช่การคาดเดา) ก่อนที่จะตัดสินใจว่าจะ
แตะต้องค่าคอนฟิก PgBouncer ด้วยหรือไม่ -- และการแตะต้องคอนฟิก PgBouncer จะต้องมี
การรีสตาร์ท ดังนั้นอีกครึ่งหนึ่งจะอยู่นอกขอบเขตอย่างชัดเจนจนกว่าการระงับ (freeze) 
จะถูกยกเลิก ไม่ว่าจะอย่างไรก็ตาม

## แผนการเปิดตัว

1. เพิ่มตัวจัดการ `pool.on('error', ...)` ลงในทั้ง `server.js` และการตั้งค่า
   พูลโกลบอลของ node-red -- เป็นการเปลี่ยนแปลงเล็กน้อยและแยกต่างหากสองจุด
2. ปรับใช้ใหม่ (`docker compose restart node-red alarm-api`) -- **ต้องไม่ทำ
   ก่อนที่ soak freeze จะถูกยกเลิก** เนื่องจากนี่เป็นการรีสตาร์ท
3. รัน `tests/e2e/ingestion-latency-check.js` อีกครั้งเพื่อยืนยันว่าไม่มี
   อะไรถดถอย
4. เริ่มความพยายาม soak ใหม่พร้อมกับใช้การแก้ไขนี้ -- หากการแก้ไข
   ถูกต้อง การดรอปของ `client_idle_timeout` จะต้องหยุดปรากฏเป็น
   เหตุการณ์ `any_container_restarted=yes` โดยสิ้นเชิง (พูลจะบันทึกเป็น
   คำเตือนและทำงานต่อไปแทน)

## แผนการทดสอบ

- Unit/manual: บังคับให้เกิด `client_idle_timeout` โดยเปิดการเชื่อมต่อพูลค้าง
  ไว้เกิน 300 วินาทีในการทดสอบทิ้ง ยืนยันว่ากระบวนการ
  ไม่แครชและการค้นหาครั้งถัดไปยังคงสำเร็จ
- Regression: ชุดการทดสอบที่มีอยู่ทั้งหมด (`Unit Tests`, `Parser v2
 Tests` ตาม pre-commit hook) -- การเปลี่ยนแปลงนี้กระทบกับการตั้งค่า
  พูลร่วม มีความเสี่ยงต่ำแต่ไม่ควรสันนิษฐานว่าปราศจากความเสี่ยง
- Soak: การทดสอบที่แท้จริงคือเวลา -- ความพยายามในการ soak ครั้งถัดไปที่รัน
  ผ่านช่วงเวลาว่างใดๆ 5 นาทีโดยไม่มีเหตุการณ์รีสตาร์ท คือบทพิสูจน์
  ที่แท้จริงว่าการแก้ไขนี้ได้ผล ซึ่งน่าเชื่อถือมากกว่า unit test ใดๆ

ปรับใช้โดย `docker compose restart node-red alarm-api` เมื่อ 2026-08-15T05:59:41Z (ทั้งสองบริการ เนื่องจากทั้งสองจำเป็นต้องได้รับการแก้ไข -- ในครั้งนี้ไม่สามารถแบ่งเป็นการรีสตาร์ทบริการเดียวแบบแคบๆ ได้) ทั้งคู่กลับมาทำงานได้อย่างสะอาด: `docker logs` แสดงการสตาร์ทปกติ (`Started flows`, `alarm-api listening on :4000`), ไม่มีข้อผิดพลาด การตรวจสอบความถดถอยตามขั้นตอนที่ 3 ของแผนการเปิดตัว (`tests/e2e/ingestion-latency-check.js`) ถูกรันซ้ำหลังการปรับใช้: `ldi_data` P95 8ms (ก่อนหน้านี้ 22ms ในการวัดเซสชันก่อนหน้า อยู่ในความแปรปรวนปกติ ไม่ใช่การถดถอย), `sys_metrics`/`net_metrics`/`ldi_metrics` ยังคงอยู่ที่ ~0-1ms, ส่วนความคลาดเคลื่อนจากการจำลองความล่าช้าที่เป็นที่รู้จักของ `ldi_alarm_log (nearest)` ยังคงเดิม (ไม่เกี่ยวข้องกับการแก้ไขนี้) การทดสอบระดับย่อย: `parser.test.js` และ `v2-parser.test.js` ผ่านทั้งคู่ 0 ความถดถอย

**สิ่งที่การปรับใช้นี้ยังไม่ได้พิสูจน์ ระบุชัดเจนตามบาร์ความซื่อสัตย์ในแผนการทดสอบ**: สถานการณ์การแครชจาก `client_idle_timeout` จริง (PgBouncer บังคับปิดการเชื่อมต่อพูลที่ไม่ได้ใช้งานหลังจากผ่านไป 300 วินาที) ยังไม่ได้ถูกบังคับและสังเกตว่ารอดจากการทดสอบรอบนี้ -- นั่นจำเป็นต้องมีการทดสอบที่บังคับให้ไม่ได้ใช้งานเป็นเวลา 5+ นาทีขึ้นไปโดยเฉพาะ หรือรอให้การแก้ไขนั้นเจอช่วงว่างในการใช้งานปกติจริงๆ การรันความทนทาน (endurance run) ที่เริ่มต้นขึ้นทันทีหลังจากปรับใช้นี้ (`SOAK_TEST_LOG.md` Attempt 10) คือบทพิสูจน์ในโลกแห่งความเป็นจริงที่สะสมเมื่อเวลาผ่านไป: หากการแก้ไขถูกต้อง การดรอปของ `client_idle_timeout` ในระหว่างการรันหลายชั่วโมงจะปรากฏเป็นเพียงบรรทัดบันทึกที่ไม่เป็นอันตราย ไม่ใช่เหตุการณ์ `any_container_restarted=yes` นี่เป็นหน้าที่ของสถานการณ์ที่ 3 ใน `FAULT_INJECTION_PLAN.md` ด้วยเช่นกัน เมื่อได้รับการอนุมัติอย่างชัดเจนให้ดำเนินการ
