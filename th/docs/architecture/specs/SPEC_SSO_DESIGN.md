# ข้อกำหนด (Spec): การออกแบบ SSO สำหรับ Grafana / alarm-api

> สถานะ: **เป็นเพียงข้อกำหนด (spec) เท่านั้น ยังไม่ได้นำไปใช้งานจริง** จัดเตรียมแบบออฟไลน์ในช่วงหยุดการเปลี่ยนแปลง (freeze) ของ Soak Attempt ครั้งที่ 6/7 เมื่อวันที่ 2026-08-14 ไม่มีการแตะต้องระบบรันไทม์ใดๆ ในการจัดทำเอกสารนี้

## สถานะปัจจุบัน, ตรวจสอบแล้วในรอบนี้

- การตรวจสอบสิทธิ์ (Auth) ของ Grafana เป็นแบบโลคัล (local-only) เท่านั้น: `GF_SECURITY_ADMIN_USER` /
  `GF_SECURITY_ADMIN_PASSWORD` (บัญชีผู้ดูแลระบบบัญชีเดียว), ไม่มีการตั้งค่าตัวแปรสภาพแวดล้อม `GF_AUTH_GENERIC_OAUTH_*` หรือ SAML ใดๆ ใน
  `docker-compose.yaml` และ `GF_AUTH_ANONYMOUS_ENABLED: "false"` (ดีแล้ว --
  ไม่มีการเข้าถึงแบบไม่ระบุตัวตน)
- อิมเมจที่ใช้คือ `grafana/grafana:13.1.1` -- **เป็นเวอร์ชัน OSS**, ไม่ใช่
  `grafana-enterprise` ทาง Grafana ทำให้รองรับ SAML ได้ฟรีในเวอร์ชัน OSS โดยเริ่ม
  ตั้งแต่เวอร์ชัน 10.1 เป็นต้นมา (ควรตรวจสอบกับ release notes ของเวอร์ชัน 13.1.1 ก่อนที่จะ
  อ้างอิงถึงตอนนำไปใช้งานจริง -- ข้อมูลนี้มาจากความรู้ทั่วไป,
  ไม่ได้ตรวจสอบซ้ำกับเอกสารของเวอร์ชันนี้โดยเฉพาะในรอบนี้)
  ส่วน Generic OAuth2/OIDC (`auth.generic_oauth`) นั้นเป็นฟีเจอร์หลักของ OSS
  มาโดยตลอด ไม่ขึ้นอยู่กับเอดิชัน
- `alarm-api` ไม่มีการล็อกอินเป็นของตัวเอง -- มันเชื่อถือเซสชันของ Grafana ใดๆ ก็ตามที่
  `auth_request` ของบริการ `proxy` ได้ทำการตรวจสอบความถูกต้องแล้ว
  (ขอบเขต 1a ของ `SECURITY_MODEL.md`) ดังนั้น SSO บน Grafana จึง
  ถูกส่งต่อไปยัง `alarm-api` "ได้ฟรี" โดยไม่จำเป็นต้อง
  บูรณาการ SSO แยกต่างหากในบริการนั้น
- `GF_SECURITY_COOKIE_SECURE: "false"` -- ใช้ได้สำหรับสภาพแวดล้อมโลคัล/จำลองนี้ แต่เป็น **ข้อกำหนดเบื้องต้นที่แท้จริงสำหรับการเปิดใช้งาน SSO
  ในโปรดักชัน**: คุกกี้ที่ปลอดภัย (แฟล็ก `Secure`, ต้องใช้ HTTPS) ควรจะ
  เปิดใช้งานก่อนที่ตัวตนระดับองค์กรจริงจะไหลผ่านระบบนี้ ไม่ใช่
  มาคิดได้ทีหลัง

## ทำไมถึงต้องใช้ SSO อย่างเจาะจง

ปัจจุบัน: **บัญชีแอดมินที่แชร์บัญชีเดียว, เจ้าของคนเดียว** (`OWNERSHIP.md`:
`@PATTANAKORN025` สำหรับทุกอย่าง) `${__user.login}` ในปุ่มรับทราบ (ack)/แก้ไข (resolve) ของหน้าจอ Alarm Console (`SPEC_ALARM_ACTOR_IDENTITY.md`) ใน
ปัจจุบันจะยังคงเป็นชื่อผู้ใช้ของบัญชีเดียวนั้นเสมอ -- ยังไม่มี
ตัวตนต่อผู้ปฏิบัติงาน (per-operator identity) ที่จะระบุการกระทำได้ SSO จึงเป็น
ข้อกำหนดเบื้องต้นสำหรับ `SPEC_ALARM_ACTOR_IDENTITY.md` เพื่อให้มีความหมาย
มากกว่าคำว่า "ใช่บัญชีแอดมินหรือไม่" -- ด้วยตัวตนต่อผู้ใช้จริงจาก
IdP แล้ว `acknowledged_by`/`resolved_by` จะกลายเป็นชื่อจริง ไม่ใช่
ชื่อของข้อมูลรับรอง (credential) ที่ใช้ร่วมกัน

## การออกแบบ: OIDC แบบทั่วไป (generic) ผ่าน `auth.generic_oauth` ที่มีมาให้ของ Grafana

แนะนำให้ใช้แทน SAML สำหรับรีโพสิทอรีนี้โดยเฉพาะ: OIDC ตั้งค่าได้ง่ายกว่า
(มีส่วนประกอบที่เคลื่อนไหวน้อยกว่าการแลกเปลี่ยนข้อมูลเมตา XML ของ SAML), ใช้งาน
ได้กับ IdP สมัยใหม่แทบทุกตัว (Azure AD/Entra ID, Okta, Google
Workspace, Keycloak, Authentik -- อะไรก็ได้ที่รองรับ OIDC) และเป็น
ฟีเจอร์หลักของ OSS โดยไม่มีความคลุมเครือเรื่องเอดิชันที่ต้องแก้ไขก่อน

```yaml
# docker-compose.yaml, สภาพแวดล้อมของบริการ grafana (เป็นการเพิ่ม, ไม่ได้
# แทนที่บัญชีแอดมินโลคัลที่มีอยู่ -- ดูแผนการเปิดใช้งาน)
GF_AUTH_GENERIC_OAUTH_ENABLED: "true"
GF_AUTH_GENERIC_OAUTH_NAME: "Company SSO"
GF_AUTH_GENERIC_OAUTH_CLIENT_ID: ${SSO_CLIENT_ID:?set SSO_CLIENT_ID in .env}
GF_AUTH_GENERIC_OAUTH_CLIENT_SECRET: ${SSO_CLIENT_SECRET:?set SSO_CLIENT_SECRET in .env}
GF_AUTH_GENERIC_OAUTH_SCOPES: "openid profile email"
GF_AUTH_GENERIC_OAUTH_AUTH_URL: ${SSO_AUTH_URL:?set SSO_AUTH_URL in .env}
GF_AUTH_GENERIC_OAUTH_TOKEN_URL: ${SSO_TOKEN_URL:?set SSO_TOKEN_URL in .env}
GF_AUTH_GENERIC_OAUTH_API_URL: ${SSO_API_URL:?set SSO_API_URL in .env}
GF_AUTH_GENERIC_OAUTH_ALLOWED_DOMAINS: ${SSO_ALLOWED_DOMAINS:-}
GF_AUTH_GENERIC_OAUTH_ROLE_ATTRIBUTE_PATH: "contains(groups[*], 'ims-admins') && 'Admin' || 'Viewer'"
```

ค่าที่แท้จริงและคาดเดาไม่ได้ (`SSO_CLIENT_ID` ฯลฯ) จะขึ้นอยู่กับ
ว่าเลือก IdP ตัวไหนจริงๆ -- ข้อกำหนดนี้จงใจที่จะไม่กำหนด
ค่าคอนฟิกของโพรไวเดอร์เฉพาะตัวใดตัวหนึ่ง เนื่องจากนั่นเป็นการตัดสินใจระดับองค์กร
ที่อยู่นอกขอบเขตของรีโพสิทอรีนี้ ไม่ใช่การตัดสินใจทางวิศวกรรม

**การแมปบทบาท (Role mapping)** (`ROLE_ATTRIBUTE_PATH` ด้านบน) เป็นส่วนเดียวที่
ต้องการการตัดสินใจจริงก่อนที่จะนำไปใช้งาน: กลุ่ม/เคลม (claim) ใดของ IdP ที่
แมปกับ `Admin` เทียบกับ `Editor` เทียบกับ `Viewer` ของ Grafana ส่วนที่เป็นตัวยึดตำแหน่ง (placeholder)
(กลุ่ม `ims-admins`) แสดงให้เห็นเพียงรูปแบบเท่านั้น ไม่ใช่คำแนะนำให้ใช้
ชื่อกลุ่มนั้นตรงๆ

## แผนการเปิดใช้งาน (เป็นขั้นตอน, ไม่ใช่การตัดจบในครั้งเดียว)

1. **เพิ่ม OIDC ควบคู่ไปกับบัญชีแอดมินโลคัลที่มีอยู่ อย่าเพิ่ง
   ลบมันออก.** `GF_AUTH_DISABLE_LOGIN_FORM` คงไว้ที่ `false` (หรือ
   ไม่ได้ตั้งค่า) ในตอนแรก -- แอดมินโลคัลจะยังคงเป็นทางเลือกสำรองฉุกเฉิน (break-glass)
   หากไม่สามารถเข้าถึง IdP ได้ การสูญเสียการล็อกอินเดียวที่ใช้งานได้เนื่องจาก
   การตั้งค่า OIDC ผิดพลาดระหว่างการเปิดใช้งาน จะทำให้ระบบล่มด้วยน้ำมือของตัวเอง
2. ทดสอบกับบัญชี IdP จริงหนึ่งบัญชีแบบ end-to-end: การเปลี่ยนเส้นทางล็อกอิน
   ถูกต้อง, สร้างเซสชันของ Grafana ได้, `auth_request` ของ `/alarm-api/`
   ยังคงผ่าน (มันไม่ได้สนใจว่าเซสชันของ Grafana ถูกสร้างขึ้นมา _อย่างไร_
   สนใจเพียงว่ามีเซสชันอยู่ -- ไม่ควรต้องทำการเปลี่ยนแปลงใดๆ ใน
   ฝั่ง proxy/alarm-api เลย)
3. ยืนยันว่า `${__user.login}` ในปุ่มของ Alarm Console ตอนนี้แสดงผลเป็น
   ตัวตน IdP จริง (เช่น อีเมลหรือชื่อผู้ใช้องค์กร) แทนที่จะเป็น
   บัญชีแอดมินที่แชร์กัน -- นี่คือผลตอบแทนที่แท้จริง จงตรวจสอบมัน
   อย่างชัดเจนแทนที่จะทึกทักเอาเองว่าการล็อกอิน OIDC เพียงอย่างเดียวจะรับประกันได้
4. หลังจากยืนยันว่าขั้นตอนที่ 3 ทำงานได้สำหรับผู้ใช้จริงอย่างน้อยหนึ่งคนแล้วเท่านั้น
   จึงค่อยตัดสินใจว่าจะปิดการใช้งานฟอร์มล็อกอินแบบโลคัลหรือไม่
   (`GF_AUTH_DISABLE_LOGIN_FORM: "true"`) และใช้ SSO เพียงอย่างเดียว นั่นคือ
   การตัดสินใจระดับองค์กร (ผู้ปฏิบัติงานจริงทั้งหมดอยู่ใน IdP หรือยัง?)
   ไม่ใช่เรื่องของวิศวกรรม -- อย่าตัดสินใจฝ่ายเดียวในฐานะที่เป็นส่วนหนึ่งของ
   "การทำฟีเจอร์ SSO ให้เสร็จสิ้น"

## แผนการทดสอบ

- การทดสอบจำลอง (Dry run) เฉพาะการตั้งค่า: เนื่องจากสิ่งนี้ต้องการข้อมูลรับรองไคลเอ็นต์
  ของ IdP จริงเพื่อทดสอบแบบ end-to-end, การจับมือ (handshake) ของ OIDC ที่แท้จริงไม่สามารถ
  ตรวจสอบได้หากไม่ได้เลือก IdP จริง (หรือ sandbox) ก่อน -- นั่นคือ
  ตัวขัดขวางที่แท้จริงในการย้ายสิ่งนี้จากข้อกำหนด (spec) ไปสู่การใช้งานจริง (implementation) ไม่ใช่
  ความพยายามทางวิศวกรรม
- เมื่อเลือก IdP แล้ว: ทดสอบการล็อกอินของผู้ใช้จริงหนึ่งคน (ขั้นตอน 2/3 ด้านบน)
  จากนั้นทดสอบครั้งที่สองเพื่อยืนยันว่าระบบสำรองแอดมินโลคัลยังคงใช้งานได้
  (ไม่ได้ถูกล็อกไม่ให้เข้าโดยบังเอิญจากการตั้งค่าใหม่)
- การถดถอย (Regression): การ ack/resolve ของ `/alarm-api/` ยังคงทำงานแบบ end-to-end ผ่าน
  เซสชันที่ตรวจสอบสิทธิ์ด้วย SSO -- มาตรฐานการถดถอยเดียวกันกับ
  `SPEC_ALARM_ACTOR_IDENTITY.md` เนื่องจากข้อกำหนดทั้งสองนี้เกื้อหนุนกัน (SSO
  ให้ตัวตนจริง, การตรวจสอบ actor-identity ทำให้ตัวตนนั้น
  เชื่อถือได้ในระดับการเขียน)

## สิ่งที่อยู่นอกขอบเขตอย่างชัดเจนสำหรับข้อกำหนดนี้

- การเลือก IdP เฉพาะ -- การตัดสินใจระดับองค์กร, ไม่ได้ทำในที่นี้
- SAML เป็นทางเลือกแทน OIDC -- แนะนำให้ใช้ OIDC ด้านบนเพื่อ
  ความเรียบง่าย; SAML ยังคงเป็นไปได้ใน Grafana เวอร์ชันนี้ หาก
  IdP เฉพาะมีความต้องการ, แต่ไม่ได้ออกแบบไว้ที่นี่เนื่องจากไม่มีสิ่งใดในปัจจุบัน
  ที่ชี้ให้เห็นถึงความต้องการนั้น
- สิทธิ์ของแดชบอร์ดแบบผู้เช่าหลายราย (Multi-tenancy) / ต่อทีม นอกเหนือไปจากการ
  แมปบทบาท Admin/Editor/Viewer พื้นฐาน -- รีโพสิทอรีนี้กำหนดไว้อย่างชัดเจนว่า
  มีเจ้าของคนเดียวในปัจจุบัน (`OWNERSHIP.md`), การออกแบบการเข้าถึง
  ระดับทีมแบบละเอียดตอนนี้ จะเป็นการแก้ปัญหาที่ยังไม่มีอยู่จริง
