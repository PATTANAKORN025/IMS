# ข้อกำหนด: การปรับความสมจริงของตัวจำลอง (Simulator Realism Pass)

> สถานะ: **เฉพาะข้อกำหนดเท่านั้น ยังไม่ได้นำไปใช้งาน** จัดเตรียมแบบออฟไลน์ระหว่าง
> ช่วงระงับ (freeze) ของ Soak Attempt 6, 2026-08-14 ไม่ได้มีการปรับแก้โค้ดตัวจำลองใดๆ
> ในการจัดทำเอกสารนี้ -- ข้อค้นพบทั้งหมดด้านล่างมาจากการอ่าน
> `nodered_data/flows.json` และ `docs/audit/LDI_ALARM_FIDELITY_AUDIT.md`
> (2026-08-11) ไม่ใช่จากการรันตัวจำลองซ้ำในรูปแบบที่แตกต่างไป

## ขอบเขต ตามลำดับเดิมของผู้ใช้ (ยังคงมีผลผูกพัน)

> "ปรับความสมจริงของตัวจำลองเฉพาะตัวแปรที่ควรมี noise/drift ที่สมจริง
> (อุณหภูมิ, ความชื้น, สุญญากาศ, PE/JE, micro-stop, warm-up drift)
> และคงค่า scan_speed ไว้เป็น setpoint ของ recipe"

`scan_speed` อยู่นอกขอบเขตอย่างชัดเจนสำหรับแผนงานทั้งหมดนี้ -- มันเป็น
ค่าการกำหนดค่าของ recipe ไม่ใช่สิ่งที่เครื่องจักรจริงจะเกิดการ drift (การเบี่ยงเบน)
ไม่มีข้อเสนอใดในเอกสารนี้ที่จะแตะต้องมัน

## รายการที่ 1: นำการลบล้างเวลา (backdating) ที่เป็น noise-code ใน `logdate` ออก

**สาเหตุหลักที่ได้วิเคราะห์แล้ว** (`ALARM_LATENCY_MEASUREMENT_NOTE.md`):
ในไฟล์ `nodered_data/flows.json`, โหนด `almsim_gen`, ฟังก์ชัน `generate()`:

```js
rows.push(
  newRow(
    eq,
    code,
    new Date(now - Math.floor(Math.random() * 9000)),
    null,
    "nearest",
  ),
);
```

Alarm ที่เกิดจาก noise-code พื้นหลังมี `logdate` ที่ถูกลบล้างย้อนหลังแบบสุ่ม
ตั้งแต่ 0-9000ms "เพื่อจำลองสภาพการเกิด alarm ให้เกิดขึ้นก่อน
ที่มันจะถูกบันทึกเล็กน้อย" สิ่งนี้เป็นสาเหตุโดยตรงของเหตุการณ์เรื่องความสมบูรณ์ในการวัด
ในการส่งมอบครั้งนี้ -- ซึ่งก่อนหน้านี้ แดชบอร์ดแสดงค่าความล่าช้าของ alarm เผยให้เห็น
ค่า P95 ปลอมที่ 7.6-7.9 วินาที

**การออกแบบ**: นำการลบล้างเวลาย้อนหลังออก และใช้ `new Date(now)` เช่นเดียวกับ
ที่สาขาที่ขับเคลื่อนด้วยเงื่อนไข (condition-driven) ทำอยู่แล้ว:

```js
// ก่อนแก้ไข
rows.push(
  newRow(
    eq,
    code,
    new Date(now - Math.floor(Math.random() * 9000)),
    null,
    "nearest",
  ),
);
// หลังแก้ไข
rows.push(newRow(eq, code, new Date(now), null, "nearest"));
```

**ทำไมถึงปลอดภัยที่จะทำให้อ่านง่ายขึ้น แทนที่จะ "ปรับปรุง":** การลบล้างเวลาย้อนหลังนี้
ไม่เคยได้รับการตรวจสอบความถูกต้องกับของจริงใดๆ เลย -- ไม่มีแหล่งอ้างอิง, ไม่มีสเปกของผู้ผลิต, ไม่มี
การแจกแจงความล่าช้าในการรายงาน alarm ในโลกแห่งความเป็นจริงที่วัดได้
เพื่อรองรับช่วง `random(0,9000)` มันเป็นเพียง jitter ที่ถูกสร้างขึ้นซึ่ง
บังเอิญดูเหมือนสมเหตุสมผล การนำมันออกไม่ใช่ความถดถอย
ในแง่ *ความสมจริง*; แต่มันคือการลบข้ออ้างอิงที่ไม่มีมูลความจริง หากภายหลังมีข้อมูล
เรื่องความล่าช้าของการรายงาน alarm ของจริง สิ่งนั้นจะเป็นรายการใหม่ที่
สนับสนุนโดยหลักฐาน ไม่ใช่การนำรายการนี้กลับมาใช้ใหม่

**แผนการเปิดตัว**: เปลี่ยนแปลงเพียงบรรทัดเดียว, ปรับใช้ `node-red` ใหม่
(`docker compose restart node-red`), รัน
`tests/e2e/ingestion-latency-check.js` อีกครั้ง เพื่อยืนยันว่าพาธความล่าช้าของ alarm ฝั่ง `nearest`
ตรงกับพาธ `causal` แล้ว (ตัวเลขหลักเดียว ms) อัปเดตไฟล์
`ALARM_LATENCY_MEASUREMENT_NOTE.md` เพื่อบันทึกก่อน/หลังแก้ไข
อย่าลบบันทึกทิ้ง -- เหตุการณ์และวิธีแก้ไขล้วนเป็นประวัติศาสตร์จริง
ที่ควรค่าแก่การเก็บรักษา

## รายการที่ 2: Noise/Drift จริงของอุณหภูมิ, ความชื้น, สุญญากาศ, PE/JE, micro-stop, warm-up

**ยังไม่ได้ออกแบบโดยละเอียดที่นี่** -- นี่คือรายการเดียวในการส่งมอบ
รวบรวมทั้งหมดนี้ที่ต้องการกระบวนการระดมความคิด/กระบวนการออกแบบ
อย่างแท้จริง (ตัวแปรอิสระหลายตัว แต่ละตัวมีการแจกแจงที่สมจริงในแบบของตัวเอง
ไม่มีการอ้างอิงการนำไปปฏิบัติในที่เก็บข้อมูล (repo) นี้ให้ต่อยอด) สิ่งที่
ข้อกำหนดนี้จะผูกมัดแทน:

- **คำถามการออกแบบต่อตัวแปร ที่ต้องตอบก่อนเริ่มดำเนินการสร้างจริง** ทำ
  ทีละรายการ แต่ละตัวต้องการคำตอบจริงไม่ใช่การเดา:
- อุณหภูมิ/ความชื้น: อะไรคือฐาน (floor) ของ sensor noise จริงสำหรับฮาร์ดแวร์
  ระดับนี้? (Spec sheet, หากมี; มิฉะนั้นให้เป็นการสันนิษฐานที่มีเหตุผล
  โดยต้องบันทึกไว้ชัดเจนว่านี่คือการสันนิษฐาน)
- สุญญากาศ: คำถามเดียวกัน บวกกับความสัมพันธ์ของ drift กับ duty
  cycle ด้วยหรือไม่ (ระบบสุญญากาศจริงมักมีความสัมพันธ์)
- PE/JE: สิ่งเหล่านี้ช่วยขับเคลื่อนสหสัมพันธ์ของ alarm อยู่แล้ว (`ALIGN_CODES`) --
  noise ที่เพิ่มเข้ามาต้องไม่ทำลายอัตราส่วนสัญญาณต่อสัญญาณรบกวน (SNR) ของสหสัมพันธ์นั้น
  มิฉะนั้นมันจะล้มล้างข้อเรียกร้องตามคู่มือ RCA อย่างเงียบๆ
- Micro-stop: ขาดหายไปอย่างสมบูรณ์ในเครื่องจำลอง (ไม่พบเขตข้อมูล
  `micro_stop` หรือ downtime-event ใน `almsim_gen` หรือ
  `ldisim_gen` ในการรันครั้งนี้) -- สิ่งนี้เป็น **กลไกใหม่**
  ไม่ใช่การจูนปรับค่าที่มีอยู่แล้ว จำเป็นต้องมีการออกแบบย่อย: ตาราง/คอลัมน์ใด
  เป็นตัวแทนของมัน, ปฏิสัมพันธ์กับกระบวนการคำนวณ OEE
  ที่มีอยู่แล้วจะเป็นอย่างไร (ส่วน OEE ของ `ims-ldi-manufacturing`)
- Warm-up drift: ต้องการคำจำกัดความของ "ช่วงเวลาการวอร์มอัพ" (เวลาตั้งแต่
  สถานะล่าสุดเปลี่ยนเป็น RUN?) ก่อนที่เส้นโค้งการเบี่ยงเบน (drift curve) ใดๆ จะถูกออกแบบ
  ตามนั้น
- **ห้ามนำข้อใดข้อหนึ่งข้างต้นไปดำเนินการโดยไม่ผ่าน
  กระบวนการออกแบบ (skill design process) หรือระดมความคิดเสียก่อน** -- รายการนี้
  มีคำถามการออกแบบจริงที่ยังไม่ได้รับการแก้ไข ต่างจากรายการที่ 1 ที่เป็นแค่การแก้ไขบรรทัดเดียว

## รายการที่ 3: ทำการตรวจสอบความเที่ยงตรงของ Alarm ใหม่อีกครั้ง

เรื่องเชิงกลไก ไม่ใช่งานออกแบบ -- ให้รันคิวรีเดียวกันกับที่
`docs/audit/LDI_ALARM_FIDELITY_AUDIT.md` ใช้งานตอนแรก (ภาคผนวก:
คิวรีที่ใช้) กับสถานะปัจจุบันของตัวจำลอง (หลังจาก Phase D/E/F:
การแก้ปัญหา debounce, `link_basis`, โค้ด Critical ที่หายาก -- ทุกอย่างที่มีการปรับใช้ไปแล้ว)
และสร้างคะแนนสดใหม่ ซึ่งต้องเกิดขึ้น **ก่อน** รายการที่ 2 จะเริ่ม
ไม่ใช่หลัง -- หากการแก้ไขปัญหา debounce/สหสัมพันธ์ผลักดันคะแนนให้ขึ้น
สูงกว่า 58/100 อย่างมีความหมาย นั่นย่อมเปลี่ยนความเร่งด่วนที่แท้จริง
ของรายการที่ 2 ได้

## รายการที่ 4: ตัวสร้างระบบข้อมูลจากระยะไกล (Telemetry) คงการอ่านค่าที่ผิดสเปกไว้ที่ ~25-45%

จากการตรวจสอบสถานะด้วยคะแนน 58/100: นี่คือ _สาเหตุที่ว่าทำไม_ alarm ที่ถูกขับเคลื่อนด้วยเงื่อนไข
จึงทำงานอย่างเกือบต่อเนื่อง (91.4% ของ alarm ทั้งหมดเป็นแบบนี้ ณ
เวลาที่ตรวจสอบ) แทนที่จะเป็นเหตุการณ์ที่ไม่ต่อเนื่อง (discrete) มันผูกติดอยู่กับ
การตรวจสอบซ้ำของรายการที่ 3 -- หากการแก้ไขปัญหา debounce ระงับอาการที่
มองเห็นได้ (การแจ้ง alarm เกือบซ้ำๆ กัน) มากพอ อัตราการผิดสเปกที่
ซ่อนอยู่ข้างใต้อาจมีความสำคัญในการแก้ไขต่ำกว่าที่ปรากฏใน
การตรวจสอบเบื้องต้น อย่าออกแบบเรื่องนี้จนกว่าตัวเลขสดใหม่ของ
รายการที่ 3 จะเข้ามา

## สิ่งที่ข้อกำหนดนี้เจตนาไม่ทำ

ออกแบบรายการที่ 2 และ 4 ในรายละเอียดเพื่อไปนำไปปฏิบัติ ทั้งสองรายการมีคำถามปลายเปิด
จริงจัง (ระบุไว้ด้านบน) ที่ต้องการการส่งผ่านทางเทคนิคและการออกแบบที่เหมาะสม
ไม่ใช่เอกสารข้อกำหนดที่เขียนจากความทรงจำว่าข้อมูลการตรวจสอบกล่าวไว้อย่างไร 
หน้าที่ของเอกสารนี้คือการจัดขอบเขตและการลำดับงานอย่างถูกต้อง 
ไม่ใช่การคาดเดาคำตอบล่วงหน้าที่ควรมาจากหลักฐาน (ข้อมูลตรวจสอบใหม่ของรายการที่ 3) 
หรือการสนทนาการออกแบบจริง (คำถามต่อตัวแปรของรายการที่ 2)
