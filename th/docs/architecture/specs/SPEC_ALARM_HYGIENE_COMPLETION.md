# Alarm Hygiene — Completion Pass (2026-08-15) (การจัดการความสะอาดของระบบแจ้งเตือน — รอบดำเนินการเสร็จสิ้น)

> ปิดรายการที่เหลือจาก `SPEC_ALERT_HYGIENE.md` รวมถึงขอบเขตเพิ่มเติมจากโปรแกรมความน่าเชื่อถือในรอบนี้ (การตรวจจับการแจ้งเตือนซ้ำ, การตรวจจับพายุการแจ้งเตือน, รูปแบบความหมายของการเลื่อนระดับการแจ้งเตือน)

## รายการที่ 1: แดชบอร์ด MTTA/MTTR — **เสร็จสิ้น**

แดชบอร์ดใหม่ `monitoring/grafana/dashboards/manufacturing/ims-ldi-alarm-response.json` (uid `ims-ldi-alarm-response`, 8 แผง): แผงสถิติ MTTA/MTTR (24 ชม. + ตลอดเวลา), แผนภูมิแนวโน้มรายวัน และตารางคัดกรอง "ปัจจุบันยังเปิดอยู่ — รอนานที่สุด"

**ข้อค้นพบที่แท้จริงและตรงไปตรงมาที่พบระหว่างการสร้างสิ่งนี้**: `public.ldi_alarm_lifecycle` ครอบคลุมระยะเวลาประมาณ 2 วัน (782 แถว) และ **ทุกแถวยังคงมีสถานะเป็น `OPEN` (เปิด)** -- ไม่มีแถวใดที่เคยได้รับการรับทราบ (acknowledged) หรือได้รับการแก้ไข (resolved) นี่ไม่ใช่ความผิดพลาดจากการรีเซ็ตข้อมูล (ตรวจสอบแล้ว: `MIN(logdate)` ของตารางคือ 2026-08-13 ซึ่งเกิดขึ้นก่อนการรีเซ็ตครั้งล่าสุดนานมาก) แต่นี่คือความจริงที่ไม่ได้บันทึกไว้ก่อนหน้านี้เกี่ยวกับสภาพแวดล้อมนี้: ไม่มีใครใช้ปุ่ม Acknowledge/Resolve ของ Alarm Console เลยตลอดช่วง 2 วันที่มีการสร้างการแจ้งเตือนอย่างต่อเนื่อง แผงสถิติ MTTA/MTTR ทั้ง 4 แผงคืนค่า `NULL` (แสดงเป็น `NO_DATA`) อย่างถูกต้อง -- ไม่ได้ถูกปลอมแปลง หรือซ่อนเร้น แต่แสดงออกมาอย่างที่ควรจะเป็นเมื่อไม่มีแถวข้อมูลใดเข้าเกณฑ์เลย ตารางคัดกรองมีสัญญาณที่แท้จริง: สัญญาณเตือนที่ค้างเปิดเก่านานที่สุดรอมาแล้ว **~44 ชั่วโมง** (2637 นาที)

เป้าหมาย SQL ทั้ง 6 รายการได้รับการทดสอบโดยตรงกับฐานข้อมูลจริงก่อนการติดตั้ง (ดูค่าด้านบน) ทั้ง dashboard-linter และ query-budget-linter ผ่านได้อย่างสมบูรณ์ (ข้อผิดพลาด 0 รายการ, คำเตือน 0 รายการสำหรับไฟล์นี้)

## รายการที่ 2: ความสอดคล้องในการตั้งชื่อ Critical Alarm — **เสร็จสิ้น** (ในคอมมิตก่อนหน้า `f39afa9`)

## รายการที่ 3: ย้ายแผง Heartbeat — **ยังไม่เสร็จสิ้นในรอบนี้**

ยังคงเป็นแผง watchdog เชิงฟังก์ชันขนาด 1x1 บน `ims-ldi-manufacturing`/`ims-ldi-operator-andon` ไม่ได้ถูกย้ายไปที่ `ims-meta-monitoring` ถูกเลื่อนออกไปก่อน -- มีความสำคัญต่ำกว่ารายการด้านล่าง และการย้ายหมายถึงการต้องแก้ไขไฟล์แดชบอร์ดถึง 3 ไฟล์ (นำออกจาก 2, เพิ่มใน 1) พร้อมกับอัปเดต gridPos ในแดชบอร์ดปลายทาง ซึ่งไม่ใช่เรื่องเล็กพอที่จะเบียดแทรกเข้ามาในรอบนี้ จึงควรดำเนินการในรอบที่แยกต่างหาก

## รายการที่ 4: ปัญหาค้างสถานะ OPEN / ค้างสถานะ ACKNOWLEDGED / วงจรชีวิตกำพร้า — **เสร็จสิ้น** (ในคอมมิตก่อนหน้า `f39afa9`; การตรวจสอบ ACKNOWLEDGED มีอยู่แล้วก่อนหน้านี้)

## รายการที่ 5: การตรวจสอบระบบหน่วงเวลา (Debounce) — **เสร็จสิ้น โดยใช้หลักฐานการทำงานตามปกติที่มีอยู่ ไม่มีการสร้างการทดสอบความเครียด (stress test) ใหม่**

ข้อกำหนดเดิมระบุให้สร้างการทดสอบความเครียดแบบสังเคราะห์ (บังคับให้ระบบส่งข้อมูลทางไกลของเครื่องจักรทุกเครื่องอยู่นอกข้อกำหนดพร้อมกันในโหมดจำลอง และตรวจสอบการจำกัดการแจ้งเตือนซ้ำของระบบ debounce) แต่ได้ตัดสินใจไม่สร้างและรันในรอบนี้ เนื่องจากการบังคับให้เกิดสภาวะที่อยู่นอกเกณฑ์ทั่วยานพาหนะ (fleet) จะไปทำให้เส้นฐานความสมบูรณ์ของข้อมูลที่โปรแกรมความน่าเชื่อถือนี้เพิ่งพิสูจน์ว่าเป็นคลีนในระดับ P0 ต้องปนเปื้อน และเราได้คำตอบที่แท้จริงอยู่แล้วจากการปฏิบัติงานตามปกติ --

```
docker exec ims-timescaledb psql -c "
  WITH gaps AS (SELECT equipmentid, errorcode, logdate,
    logdate - LAG(logdate) OVER (PARTITION BY equipmentid, errorcode ORDER BY logdate) AS gap
    FROM ldi_alarm_log)
  SELECT count(*) FILTER (WHERE gap < INTERVAL '15 seconds'), count(*)
  FROM gaps WHERE gap IS NOT NULL;"
-- มีช่องว่างเพียง 1 จาก 549 รายการที่น้อยกว่า 15 วินาที (วัดผลในช่วงต้นของเซสชันนี้ ซึ่งเป็นงานใกล้เคียงกับระดับ P0.3)
```

อัตราส่วน 1/549 ถือเป็นหลักฐานชิ้นสำคัญที่แสดงว่าระบบหน่วงเวลา (debounce) ยังคงทำงานได้ดีภายใต้สภาพแวดล้อมจริงที่มีการดำเนินงานในกลุ่มเครื่องจักรอย่างต่อเนื่อง (ไม่ใช่เพียงแค่การเกิดปัญหาพุ่งสูงขึ้นแบบจัดฉากขึ้นมาเพียงครั้งเดียว) -- ซึ่งเรียกได้ว่าเป็นหลักฐานที่หนักแน่นกว่าการใช้การทดสอบแบบสังเคราะห์ (synthetic test) มากนัก เนื่องจากมันสะท้อนถึงรูปแบบการปฏิบัติงานแบบต่อเนื่องหลายวันมากกว่าการจำลองสภาวะแหลมคมเทียมเพียงอย่างเดียว การทดสอบความเครียดแบบสังเคราะห์ยังคงเป็นสิ่งสำคัญที่ควรดำเนินการต่อในภายหลัง หากพบกรณีเฉพาะเจาะจงที่จำเป็นต้องพิสูจน์เป้าหมายอย่างชัดเจน (ตัวอย่างเช่น ความผิดพลาดที่สัมพันธ์กันในเครื่องจักรหลายเครื่องพร้อมกัน) แต่จะยังไม่ถูกนำมาพิจารณาในขณะนี้

## การตรวจจับการแจ้งเตือนที่ซ้ำซ้อน — **เสร็จสิ้น, พบและแก้ไขข้อบกพร่องจริงหนึ่งรายการ**

ตรวจสอบเส้นทางของ webhook ทั้งหมด: การกำหนดเส้นทางของ `alertmanager.yml` → `POST /alert-webhook` (โหนด HTTP-in ของ Node-RED แบบเดี่ยว ไม่มีการกระจาย) → `Format Alert Text` → `Format LINE`/`Format Teams` (แบบคู่ขนาน ไปยัง 2 ช่องทางที่แตกต่างกัน ไม่ซ้ำซ้อน) พบและแก้ไขบักแฝงจริง: เส้นทาง `severity="critical"` มีค่า `continue: true` ส่งผลให้ตัวรับและตัวรับตั้งต้นถูกกำหนดไปยัง URL ของ webhook เดียวกัน โดยไม่มีการลบข้อมูลที่ซ้ำซ้อนในปลายทาง แม้ว่าในปัจจุบันจะยังไม่มีการแจ้งเตือนซ้ำเกิดขึ้นจริง (เนื่องจากไม่มีเส้นทางพี่น้องอื่นๆ ที่ตรงกับเงื่อนไข `severity="critical"`) แต่นับว่าเป็นระเบิดเวลาที่อาจก่อปัญหาได้ทันทีที่เพิ่มเส้นทางใหม่ในอนาคต ปัญหานี้ได้รับการแก้ไขแล้วในคอมมิต `be8db54`

ไม่พบความเสี่ยงด้านการแจ้งเตือนที่ซ้ำซ้อนในส่วนของ LDI-alarm -- ปัจจุบันการแจ้งเตือนเหล่านั้นไม่ได้ผ่านเส้นทาง webhook นี้เลย (แสดงผลบนแดชบอร์ด/Andon เท่านั้น ไม่มีการแจ้งเตือนแบบพุช) จึงไม่มีส่วนที่ต้องขจัดความซ้ำซ้อนที่จุดนั้น

## การตรวจจับพายุการแจ้งเตือน — **มีอยู่แล้ว ยืนยันว่าใช้งานได้ และไม่มีการสร้างกลไกใหม่**

การหน่วงเวลา 12 นาทีในคูลดาวน์ (`public.ldi_alarm_state`, ไมเกรชัน 069) *คือ* ระบบป้องกันพายุ/น้ำท่วม (storm/flood guard) -- ยืนยันผ่านคอมเมนต์ในโค้ดของ `nodered_data/flows.json`: "debounce below is the primary flood guard" การสร้างตัวตรวจจับพายุ (storm-detector) ที่แยกต่างหากจะกลายเป็นการทำซ้ำกับโครงสร้างพื้นฐานที่มีอยู่และใช้งานได้ดีอยู่แล้ว -- ซึ่งขัดกับคำแนะนำที่ให้เลือกใช้สถาปัตยกรรมที่มีอยู่เดิมแทนการเพิ่มกลไกใหม่ หลักฐานว่าใช้งานได้: คือตัวเลข 1/549 ชุดเดียวกับรายการตรวจสอบ debounce ข้างต้น

## รูปแบบความหมายของการเลื่อนระดับ — **ยืนยันว่ามีช่องโหว่ ยังไม่ได้สร้าง**

ค้นหาผ่านคำสั่ง grep ใน `nodered_data/flows.json` เพื่อหาตรรกะการเลื่อนระดับ (escalation logic): ผลลัพธ์คือ 0 ตรงกัน สิ่งที่มีอยู่แทนคือ `repeat_interval` ของ Alertmanager (แจ้งเตือนซ้ำสำหรับการแจ้งเตือนที่ยังไม่ได้รับการแก้ไขทุกๆ 30 นาทีสำหรับระดับ critical, 2 ชั่วโมงสำหรับระดับ warning, 4 ชั่วโมงสำหรับค่าเริ่มต้น) -- นี่คือการแจ้งเตือนซ้ำตามช่วงเวลาในช่องทาง *เดิม* ที่ระดับความรุนแรง *เดิม* ไม่ใช่การเลื่อนระดับ (เช่น การเปลี่ยนเส้นทางไปยังช่องทางอื่น/ช่องทางที่มีความเร่งด่วนสูงกว่า หรือการเพิ่มระดับความรุนแรงเมื่อเวลาผ่านไปโดยไม่มีการรับทราบ) **ยังไม่มีกลไกการเลื่อนระดับอยู่ในระบบในปัจจุบัน** นี่คือช่องโหว่ที่เกิดขึ้นจริงที่ได้รับการยืนยัน ซึ่งไม่ได้ถูกสร้างขึ้นในรอบนี้ -- มันคือฟีเจอร์ใหม่ที่แท้จริง (ต้องมีการออกแบบ: สิ่งที่กระตุ้นให้เกิดการเลื่อนระดับ, ช่องทางที่จะเลื่อนระดับไป, จะโต้ตอบกับข้อมูล MTTA ที่เพิ่งทำให้มองเห็นในรอบนี้หรือไม่) ไม่ใช่การแก้ไขข้อบกพร่อง และสมควรที่จะได้รับการออกแบบแยกต่างหากแทนที่จะเร่งรีบเพิ่มเข้ามาที่นี่

## งานการจัดการความสะอาดของระบบแจ้งเตือนที่เหลืออยู่ (ไม่ได้ทำในรอบนี้)

- รายการที่ 3 (ย้ายแผง Heartbeat)
- การทดสอบความเครียดของการหน่วงเวลา (debounce) แบบสังเคราะห์สำหรับกรณีเฉพาะที่นอกเหนือจากหลักฐานจากการทำงานตามปกติ
