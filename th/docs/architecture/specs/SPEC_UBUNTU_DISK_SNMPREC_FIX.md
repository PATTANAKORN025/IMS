# ข้อมูลจำเพาะ: การแก้ไขความสมจริงของดิสก์ Ubuntu SNMP (P0.2)

**สถานะ: แก้ไขและติดตั้งใช้งานเมื่อ 2026-08-15**

## สาเหตุที่แท้จริง (ระบุไว้แล้วใน `READ_ONLY_AUDIT_2026-08-15.md` §3c)

ค่าสำหรับดิสก์ใน `monitoring/snmpsim/ubuntu.snmprec` (`hrStorageSize`, OID `.5.2`) คือ `52428800`, ในขณะที่ช่วงการสุ่มเดินของ `hrStorageUsed` (`.6.2`) คือ `min=65536000,max=125000000` -- ซึ่งถูกคัดลอก-วาง มาจาก OID ตัวเดียวกันใน `windows.snmprec` โดยไม่ได้คำนวณค่ารวมที่อยู่เหนือค่านั้นใหม่ ค่าที่ถูกใช้ (used) ไม่มีทางน้อยกว่า ~125% ของค่ารวม ทำให้ตัวบีบ `Math.min(diskUsedGb, diskTotalGb)` ของ `parser.js` ตรึงดิสก์ไว้ที่ 100% สำหรับทุกการสุ่มตัวอย่างโดยปริยาย

## การแก้ไขปริศนาเรื่องการเติบโต (ก่อนดำเนินการแก้ไขให้สิ้นสุด ตามที่ต้องการ)

ข้อความก่อนหน้านี้ในเซสชันนี้อ้างว่า `disk_total_gb` "เติบโตจาก 9,375 เป็น 12,500 GB" เมื่อเวลาผ่านไป ซึ่งบ่งบอกถึงบักตัวที่สอง ตรวจสอบซ้ำด้วยการสืบค้นแบบดิบ (ไม่จัดกลุ่ม): `disk_total_gb` มีเพียง 2 ค่าที่แตกต่างกันในประวัติทั้งหมด -- `0` (9 แถว, จากการเปลี่ยนเป็นศูนย์ตอนสถานะ offline/empty-walker ของ parser) และ `12500` (3,484 แถว) ไม่มีการแสดงค่าระหว่างกลาง การ "เติบโต" เป็นผลพวงจากการเฉลี่ยแถว `12500` ที่มีอยู่จริงเข้ากับแถว `0` ที่เกิดขึ้นประปรายภายในบักเก็ต 10 นาที ได้รับการแก้ไขในที่ของ `READ_ONLY_AUDIT_2026-08-15.md` แล้ว ไม่มีกลไกที่สอง -- การกำหนดค่าพื้นที่ใช้งานที่ผิดพลาดเพียงอย่างเดียวเป็นคำอธิบายโดยสมบูรณ์ถึงพฤติกรรมที่สังเกตได้

## การแก้ไข

เปลี่ยนเพียง `hrStorageSize` (`.5.2`): `52428800` → `180000000`. `au` (หน่วยการจัดสรร, `.4.2` = `256000`) และช่วงของค่าพื้นที่ที่ใช้ (`.6.2`) ไม่ถูกแตะต้องเลย -- เป็นการเปลี่ยนแปลงที่น้อยที่สุดเท่าที่จะเป็นไปได้ และลักษณะรูปแบบของพื้นที่ใช้งาน (รูปแบบความผันแปรของมัน) ก็ถูกรักษาไว้อย่างสมบูรณ์ ไม่ถูกแทนที่

เหตุผลในการกำหนดขนาด ทำงานจากหลักการพื้นฐานแทนที่จะคัดลอกตัวเลขจาก `windows.snmprec`: เลือก `180000000` เพื่อให้ `total_bytes = 180000000 × 256000 = 46,080,000,000,000` ไบต์ ≈ 42,915 GB ซึ่งมากกว่าช่วงสูงสุดของการใช้งาน (`125000000 × 256000 / 1073741824` ≈ 29,802 GB) ได้อย่างสบาย ผลลัพธ์แถบการใช้งาน: **36.4% (ต่ำสุด) – 69.4% (สูงสุด)** -- เป็นช่วงที่อยู่ในระดับที่ดีและสมจริง มีรูปแบบคล้ายกับความกว้าง 32.8%-62.5% ใน `windows.snmprec` แบบคร่าวๆ (ใช้เป็นตัวเปรียบเทียบความสมเหตุสมผลเฉยๆ ไม่ได้คัดลอกมา) และมีตัวเลขจริงที่แตกต่างออกไป เนื่องจากโปรไฟล์ "การใช้ทรัพยากรที่ต่ำกว่า" ของ Ubuntu (ตามคอมเมนต์ที่ส่วนหัวของไฟล์นั้น) มีความเหมาะสมที่จะมีค่าเป็นของตัวเองมากกว่าจะใช้ร่วมกับ Windows

นอกจากนี้ ยังตรวจสอบพื้นที่ RAM ในไฟล์เดียวกันระหว่างการสืบสวนด้วย: `size=8388608, au=1024` ให้พื้นที่รวม 8192 MB, ช่วงการใช้งาน `4194304-7864320` ให้พื้นที่ 4096-7680 MB (50%-93.75%) -- อยู่ในระดับที่ดีอยู่แล้ว ไม่ได้อยู่ในส่วนของบักนี้ และไม่ถูกแตะต้อง

## การนำไปใช้

`docker compose restart snmpsim` -- **เป็นการรีสตาร์ทที่แคบที่สุดเท่าที่เป็นไปได้ ตามคำแนะนำที่ให้เลือกวิธีนี้แทนการรีสตาร์ท Node-RED** `snmpsim` จะโหลดไฟล์ `.snmprec` หนึ่งครั้งเมื่อเริ่มกระบวนการ (`--force-index-rebuild`); Node-RED จะทำการดึงข้อมูลใหม่ผ่านเครือข่ายทุกรอบโดยไม่มีการแคชทางฝั่งไคลเอนต์ ดังนั้นจึงไม่จำเป็นต้องรีสตาร์ท Node-RED ยืนยันผ่าน `docker logs ims-snmpsim`: รีสตาร์ทสมบูรณ์ โปรไฟล์อุปกรณ์ทั้ง 3 รายการ (`apex_mock`, `windows`, `ubuntu`) เปิดขึ้นใหม่และตอบสนอง
