## 1. สรุปสำหรับผู้บริหาร (Executive Summary)

**IMS (Industrial Monitoring System)** ทำหน้าที่เป็นโครงสร้างพื้นฐานการตรวจสอบ NOC ระดับองค์กรสำหรับ APEX Circuit — ปัจจุบันดำเนินการอยู่ใน **เฟสที่ 12 (Apex SRE Optimization)** ซึ่งหมายถึงสถานะที่ **พร้อมสำหรับใช้งานจริง / มีเสถียรภาพ (Production-ready / Stable)** อย่างชัดเจน

### การประเมินสถานะปัจจุบัน (2026-08-04)

| โดเมน (Domain)   | รายละเอียด (Details)                                                                               |
| ---------------- | ----------------------------------------------------------------------------------------- |
| **สถาปัตยกรรม**  | SNMP v2c → Node-RED → PgBouncer → TimescaleDB → Grafana + Prometheus/Alertmanager         |
| **อุปกรณ์**      | อุปกรณ์มากกว่า 1,000 ชิ้น (เซิร์ฟเวอร์ Linux, สวิตช์ Juniper EX4000, เครื่องจักรผลิต LDI PCB)    |
| **แดชบอร์ด**   | แดชบอร์ด 9 รายการ (NOC Overview, Engineering, Capacity, Meta-Monitoring, 5× LDI Manufacturing) |
| **การแจ้งเตือน**     | Prometheus + Alertmanager → LINE Notify + MS Teams                                        |
| **เครื่องมือ AI**   | 12 เซิร์ฟเวอร์ MCP, 90 ทักษะ, 8 ปลั๊กอิน (MiMo Code + Claude Code + OpenCode + Copilot)       |
| **การทดสอบ**        | การทดสอบหน่วย (Unit tests), K6 stress tests, Playwright visual regression, dashboard linter               |
| **CI/CD**        | ยังไม่ได้ดำเนินการ — `flows.json` ถูกปรับใช้ผ่านการดำเนินการด้วยตนเอง                             |

## 3. แผนงานการพัฒนาหลัก (Master Development Roadmap)

### เฟสที่ 13: การเพิ่มความแข็งแกร่งสำหรับโปรดักชั่น (สัปดาห์ที่ 1–2)

**วัตถุประสงค์:** เปลี่ยนระบบจากสถานะพร้อมสำหรับการพัฒนา เป็นพร้อมสำหรับการใช้งานจริง (production-ready) อย่างสมบูรณ์

#### 3.1 ไปป์ไลน์ CI/CD — GitHub Actions

**ปัญหาหลัก:** `flows.json` ปัจจุบันถูกปรับใช้ด้วยตนเอง (`make deploy-flows`) ปราศจากระบบอัตโนมัติ → ส่งผลให้มีความเสี่ยงสูงต่อความผิดพลาดของมนุษย์, การดำเนินการย้อนกลับที่ช้า และไม่มีร่องรอยการตรวจสอบ (audit trails)

**แผนการดำเนินการ:**

| ขั้นตอน | งาน                                            | ไฟล์เป้าหมาย | รายละเอียด                                                         |
| ---- | ---------------------------------------------- | ----------- | --------------------------------------------------------------- |
| 1    | สร้าง `.github/workflows/deploy-flows.yml` | ใหม่         | ทริกเกอร์: ผลักดันไปที่ `main` โดยปรับเปลี่ยน `nodered_data/flows/*.json`   |
| 2    | เพิ่มงาน `validate-flows`                    | workflows   | รัน `make validate-flows` ก่อนการปรับใช้               |
| 3    | เพิ่มงาน `snapshot-flows`                    | workflows   | สำรอง `flows.json` ก่อนการปรับใช้ (`make snapshot-flows`) |
| 4    | เพิ่มงาน `deploy-flows`                      | workflows   | รัน `make deploy-flows` ผ่าน SSH หรือ API                      |
| 5    | เพิ่มงาน `verify-pipeline`                   | workflows   | รัน `make verify` หลังการปรับใช้ → ล้มเหลว = ทริกเกอร์ย้อนกลับ (rollback) |
| 6    | เพิ่มงาน `rollback`                          | workflows   | เมื่อการตรวจสอบล้มเหลว → คืนค่าอัตโนมัติจาก snapshot  |

**สถาปัตยกรรม:**

```text
push to main (flows/*.json changed)
  → validate-flows (make validate-flows)
  → snapshot-flows (make snapshot-flows)
  → deploy-flows (make deploy-flows)
  → verify-pipeline (make verify)
  → [if fail] rollback (restore snapshot)
```

**เกณฑ์ความสำเร็จ:**

- ปรับใช้ `flows.json` อัตโนมัติเมื่อมีการพุชที่ตรงตามเงื่อนไข
- การรันการตรวจสอบ ความถูกต้อง, snapshot, และการตรวจทาน สำเร็จเสร็จสิ้นก่อนการปรับใช้ขั้นสุดท้าย
- ดำเนินการย้อนกลับโดยอัตโนมัติเมื่อการตรวจสอบล้มเหลว
- ประวัติการปรับใช้ทิ้งร่องรอยการตรวจสอบที่ไม่สามารถแก้ไขได้ภายใน GitHub Actions

#### 3.3 K6 Stress Test — 10,000 req/sec

**ปัญหาหลัก:** ขีดจำกัดความเร็วสูงสุดของ PgBouncer ยังไม่ได้กำหนด → ขีดจำกัดความสามารถในการรับโหลดของระบบนั้นเป็นเพียงทฤษฎีล้วนๆ

**แผนการดำเนินการ:**

| ขั้นตอน | งาน                               | ไฟล์เป้าหมาย                     | รายละเอียด                                              |
| ---- | ---------------------------------- | ------------------------------- | ---------------------------------------------------- |
| 1    | พัฒนาสคริปต์ K6 สำหรับ 10K VUs      | `tests/k6/throughput-stress.js` | ลำดับการไต่ระดับ: 50 → 200 → 1000 → 5000 → 10000 VUs    |
| 2    | วัดผลโทรมาตรหลัก             | —                               | เวลาแฝง p95, อัตราข้อผิดพลาด, ปริมาณงานทั้งหมด (แถว/วินาที) |
| 3    | เพิ่มประสิทธิภาพการตั้งค่า PgBouncer   | `docker-compose.yaml`           | ตั้งค่า MAX_CLIENT_CONN=500, DEFAULT_POOL_SIZE=50        |
| 4    | เพิ่มประสิทธิภาพการตั้งค่า TimescaleDB | `database/migrations/`          | ตั้งค่า shared_buffers=2GB, work_mem=256MB               |
| 5    | รัน stress test ซ้ำหลังการปรับแต่ง | `tests/k6/throughput-stress.js` | วัดปริมาณความแตกต่างของประสิทธิภาพ                           |
| 6    | บันทึกผลลัพธ์เชิงประจักษ์         | `docs/PERFORMANCE.md`           | บันทึกเกณฑ์มาตรฐานเทียบกับตัวชี้วัดที่ปรับให้เหมาะสมแล้ว                |

**เกณฑ์ความสำเร็จ:**

- สามารถรองรับ 10,000 req/sec ได้อย่างต่อเนื่อง โดยไม่เกินเกณฑ์ข้อผิดพลาด 0.1%
- คงเวลาแฝง (latency) ของ p95 < 500ms
- ป้องกันสถานการณ์การล้น (overflow) ของการเชื่อมต่อพูล (connection pool) ใน PgBouncer

| 4    | ตรวจสอบการเชื่อมต่อ SNMP          | `scripts/snmp-discover.js`                                              | ยืนยันความเข้ากันได้ของ SNMP v2c กับฮาร์ดแวร์จริง                   |
| 5    | ดำเนินการทดสอบ canary deployment           | —                                                                       | เริ่มต้นกับ 5 เครื่องแบบแยกเดี่ยว → ตรวจสอบ → ดำเนินการเปิดตัวเต็มรูปแบบ |
| 6    | ติดตามข้อมูลโทรมาตรของไปป์ไลน์          | `monitoring/grafana/dashboards/infrastructure/ims-meta-monitoring.json` | สังเกตอัตราการดึงข้อมูลและข้อผิดพลาดอย่างละเอียด                          |

**เกณฑ์ความสำเร็จ:**

- การดำเนินงานแบบดึงข้อมูล (polling) ของ SNMP เสถียร โดยรันบนฮาร์ดแวร์จริง
- ไม่มีการสูญเสียข้อมูลโดยเด็ดขาดตลอดช่วงการเปลี่ยนแปลง
- กลไก Circuit breaker ทำงานตามปกติบนปลายทางของเซิร์ฟเวอร์จริง
