# P0 — ตัวชี้วัดที่ขัดแย้งกัน (วิกฤตที่สุด)

## P0-1 · ตัวชี้วัดผลผลิต (Yield) สำหรับระบบเดียวกัน เบี่ยงเบนไปถึง 87 จุดเปอร์เซ็นต์ ระหว่างสองอินเทอร์เฟซ

| แดชบอร์ด (Dashboard) | ค่าที่แสดง (Displayed Value)    | สูตรที่ใช้อยู่เบื้องหลัง (Underlying Formula) |
| ----------------- | ----------------------------- | ----------------------------------------- |
| **ภาพรวม NOC**  | **87.10%** (สีแดง — วิกฤต)   | `ABS(pe_1) > 10 OR ABS(je_1) > 10`        |
| **การผลิต (Manufacturing)** | **99.6%** (สีเขียว — ยอดเยี่ยม) | `GREATEST(ABS(pe_1..pe_6)) <= pe_setting` |

**สาเหตุที่แท้จริง — ความแตกต่างพื้นฐานสามประการในตรรกะ:**

1. **NOC ใช้ค่าขีดจำกัดที่ฝังตัวในโค้ด (hardcoded) คือ `10`** ในขณะที่ค่า `pe_setting` จริงคือ **25 / 50 / 75** ขึ้นอยู่กับผลิตภัณฑ์
   → NOC ระบุอย่างไม่ถูกต้องว่าผลิตภัณฑ์ "มีข้อบกพร่อง" ทั้งที่ความจริงแล้วตรงตามข้อกำหนด
2. **NOC ประเมินเฉพาะ `pe_1` และ `je_1`** โดยไม่สนใจจุดวัดทั้ง 6 จุด → สิ่งนี้ไม่ได้เป็นตัวแทนของตัวชี้วัดที่ใช้สำหรับกำหนดคุณภาพที่แท้จริง
3. **NOC วัด "ความเสี่ยง (Risk)" ขณะที่ระบบการผลิตวัด "ผลผลิต (Yield)"** — ทั้งสองมีความหมายแตกต่างกันอย่างชัดเจน แต่ผู้ใช้ปลายทางตีความว่าเป็นตัวชี้วัดเดียวกัน

**ผลกระทบทางธุรกิจ:** หากผู้บริหารดูที่ NOC พวกเขาจะมองเห็นอัตราข้อบกพร่องถึง 87% ในคุณภาพการผลิต
หากพวกเขาดูแดชบอร์ดการผลิต พวกเขาจะเห็นอัตราความยอดเยี่ยมถึง 99.6% — **สิ่งนี้นำไปสู่การตัดสินใจที่ผิดพลาดโดยตรง**
นอกจากนี้ เมื่อมีการค้นพบความขัดแย้งนี้ ความน่าเชื่อถือของ **ระบบทั้งหมด** จะถูกทำลายไปในทันที

**การแก้ไข:** บังคับให้ NOC ทำการคิวรีด้วยตรรกะเดียวกันกับที่ระบบการผลิตใช้ผ่านมุมมองส่วนกลาง (centralized view)

```sql
CREATE OR REPLACE VIEW public.v_ldi_yield_1h AS
SELECT ROUND(100.0 * COUNT(*) FILTER (
         WHERE GREATEST(ABS(pe_1),ABS(pe_2),ABS(pe_3),
                        ABS(pe_4),ABS(pe_5),ABS(pe_6)) <= pe_setting)
       / NULLIF(COUNT(*) FILTER (WHERE pe_1 IS NOT NULL), 0)::NUMERIC, 1) AS yield_pct
FROM public.ldi_data
WHERE "time" > NOW() - INTERVAL '1 hour' AND COALESCE(pe_setting,0) > 2.0;
```

ต่อจากนั้น แดชบอร์ดทั้งสองจะใช้มุมมองส่วนกลางนี้ — **ตัวชี้วัดจะซิงโครไนซ์กันอย่างสม่ำเสมอด้วยการออกแบบทางสถาปัตยกรรม แทนที่จะเป็นความบังเอิญ**

# P0-2 · การทดสอบความจริงของ RCA (Root Cause Analysis) รายงานว่า "ไม่มีความสัมพันธ์" — และนั่นเป็นสิ่งที่ถูกต้อง

หลักฐานจากวิศวกรรมการวิเคราะห์ (Engineering Analytics) & SPC:

| หมวดหมู่การแจ้งเตือน | หน้าต่างการแจ้งเตือน % | เส้นฐาน (Baseline) % | **ค่า Lift** | เหตุการณ์ (Events) | การตีความ (Interpretation)    |
| ---------------- | -------------- | ---------- | -------- | ------ | --------------------------- |
| ALIGNMENT/PE-JE  | 49.0%          | 44.8%      | **1.09** | 251    | ไม่มีนัยสำคัญทางสถิติ            |
| VACUUM (91009)   | 96.8%          | 100.0%     | **0.97** | 95     | **อัตราส่วนต่ำกว่า 1 (Sub-1 ratio)** |
| THERMAL (91008)  | 13.8%          | 16.6%      | **0.83** | 29     | อัตราส่วนต่ำกว่า 1                 |
| HUMIDITY (91008) | 3.4%           | 9.9%       | **0.34** | 29     | ต่ำกว่า 1 อย่างมีนัยสำคัญ        |
| MOTION (70004)   | 0.0%           | 0.0%       | **0.00** | 19     | ข้อมูลไม่เพียงพอ                |

**การตีความ:** ค่า `Lift = 1` บ่งชี้ว่าไม่มีความสัมพันธ์ ค่า `Lift < 1` บ่งชี้ถึงความสัมพันธ์ใน **ทิศทางตรงกันข้าม (inverse correlation)**

**นี่ไม่ใช่บั๊กของ RCA — กลไก RCA ทำงานได้อย่างถูกต้องและเปิดเผยความจริงที่สำคัญ:**

> เครื่องกำเนิดข้อมูลจำลอง (mock data generator) สร้างการแจ้งเตือนแบบสุ่มตามความถี่ **โดยไม่ได้ผูกมัดกับค่าพารามิเตอร์ที่แท้จริง**
> ด้วยเหตุนี้ การแจ้งเตือน "vacuum" จึงไม่ถูกกระตุ้นในระหว่างที่เกิดความผิดปกติของ `air_vacuum` จริง

**คุณค่าที่ได้รับ:** การทดสอบความจริงของ RCA ประสบความสำเร็จในการตรวจสอบความสามารถของตัวเองในการ **ตรวจจับความสัมพันธ์ที่เป็นเท็จ (false correlations)**
หากมีการรายงานค่า Lift ที่สูงในข้อมูลที่ขาดความสัมพันธ์ที่แท้จริง หมายความว่าเครื่องมือวิเคราะห์เองที่มีข้อบกพร่อง — แต่มันก็ทำงานได้อย่างถูกต้อง

**สิ่งที่ต้องทำ (Action Item):** แก้ไขที่ **เครื่องจำลอง (simulator)** ไม่ใช่แก้ไขตรรกะของ RCA

```javascript
// ldi_simulator.js — ตรวจสอบให้แน่ใจว่าการแจ้งเตือนเกิดจากความผิดปกติของพารามิเตอร์ที่แท้จริง
if (rec.air_vacuum > -10 && p.process === "DF INNER") emitAlarm("91009");
if (maxPE > rec.pe_setting * 0.9) emitAlarm("90005");
if (rec.temperature < 20 || rec.temperature > 24) emitAlarm("91008");
```

หลังจากการปรับเปลี่ยน ค่า Lift ควรจะพุ่งสูงขึ้นไปที่ **> 2** หากไม่เป็นเช่นนั้น จะบ่งชี้ว่ามีบั๊กพื้นฐานที่แท้จริงภายในเอนจิน RCA ซึ่งต้องมีการสืบสวนเพิ่มเติม

# P1 — พาเนลแสดงผลโดยไม่มีข้อมูล (ตรวจพบ 15 กรณี)

## Engineering Drill-Down — ได้รับผลกระทบหนักที่สุด (10 พาเนล)

```text
ภาระของ CPU (CPU Load) · การใช้ RAM · ความจุข้อมูลที่เต็ม (Storage Saturation) · อุณหภูมิ      → "ไม่มีข้อมูล (No data)"
ความหนาแน่นของหน่วยความจำ (Memory Saturation) · แบนด์วิดท์เครือข่าย · เซ็นเซอร์อุณหภูมิ   → "ไม่มีข้อมูล"
ปริมาณงาน LDI (LDI Throughput) · ประสิทธิภาพการเชื่อม LDI (LDI Junction Efficiency) · การกระจายคุณภาพ LDI → "ไม่มีข้อมูล"
คะแนนความผิดปกติของ CPU · คะแนนความผิดปกติของอุณหภูมิ → "ข้อมูลไม่มีฟิลด์เวลา (Data does not have a time field)"
```

**สาเหตุที่แท้จริงสองประการ:**

- **"ไม่มีข้อมูล"** — คิวรีมีไวยากรณ์ที่ถูกต้อง แต่ให้ผลลัพธ์เป็นศูนย์แถวที่ตรงตามเงื่อนไข (ตัวแปรของเครื่องจักร/อินเทอร์เฟซไม่ถูกเลือก)
- **"ข้อมูลไม่มีฟิลด์เวลา"** — คิวรีส่งคืนผลลัพธ์ แต่ **ขาดคอลัมน์ `time`** แม้ว่าพาเนลจะถูกกำหนดค่าเป็นอนุกรมเวลา (timeseries) → นี่คือบั๊ก SQL ที่แท้จริง

## AIOps & Capacity Forecast — ตัวชี้วัด KPIs 3 ใน 4 ตัวล้มเหลว

```text
DISK: จำนวนวันก่อนจะเต็ม  → ไม่มีข้อมูล
RAM:  จำนวนวันก่อนจะเต็ม  → ไม่มีข้อมูล
CPU:  จำนวนวันก่อนความหนาแน่นเต็ม → ไม่มีข้อมูล
จำนวนวันก่อนจะเต็ม (ความจุทรัพยากร) → ไม่มีข้อมูล
คะแนนสุขภาพส่วนรวมของระบบ (Fleet Health Score) 91.30% →  ยังคงทำงาน (Operational)
```

## ภาพรวม NOC — ตัวชี้วัดไม่น่าเชื่อถือ

```text
ภาระของ CPU (CPU Load) (ขอบเขตส่วนรวม)  → 0.00% คงที่แนวระนาบโดยสมบูรณ์   ← ไม่ควรเป็น 0
ความหนาแน่นของ RAM (RAM Saturation)             → "รอรับข้อมูลโทรมาตร (AWAITING TELEMETRY)"
อุณหภูมิ (Temperature) ขอบเขตส่วนรวม → 65.0°C คงที่แนวระนาบ          ← สะท้อนอุณหภูมิเซิร์ฟเวอร์ ไม่ใช่ของ LDI
```

## Operator Andon — 2 พาเนลว่างเปล่าอย่างสมบูรณ์

```text
การผลิตสด (LIVE PRODUCTION)            → ไม่มีเนื้อหาใดๆเลย
PE/JE เทียบกับขีดจำกัดสเปค (PE/JE VS SPEC LIMIT)        → ไม่มีเนื้อหาใดๆเลย
```

**ผลกระทบต่อการดำเนินงานอย่างรุนแรง** เนื่องจาก Andon ทำหน้าที่เป็นอินเทอร์เฟซหลักที่แสดงข้อมูลสดสำหรับผู้ปฏิบัติงานตลอดกะของตน และสองพาเนลเฉพาะเจาะจงนี้ เป็นตัวกำหนด "สถานะการผลิตในปัจจุบัน" และ "ตัวชี้วัดคุณภาพแบบเรียลไทม์"

## คีย์บอร์ด (Board Keys) ที่ซ้ำซ้อน — แยกต่างหากเฉพาะใน 2 เครื่องเท่านั้น

```text
LDI-01:  43,667 แถว → 43,510 ที่ไม่ซ้ำ → คีย์บอร์ดที่ซ้ำกัน 157 คีย์
LDI-04:  28,683 แถว → 28,562 ที่ไม่ซ้ำ → ที่ซ้ำกัน 121 คีย์
LDI-02,03,05..10:                        ซ้ำซ้อน 0
```

**น่าสงสัยเป็นอย่างยิ่ง** — หากนี่เป็นบั๊กของตัวจำลอง มันควรจะเกิดขึ้นเหมือนๆ กันในทุกเครื่องจักร
ข้อเท็จจริงที่ว่ามันเกิดขึ้นเฉพาะที่ LDI-01 และ LDI-04 แสดงนัยยะของความแตกต่างในตรรกะ
(ทั้งสองเป็นเครื่องจักร DF INNER อย่างไรก็ตาม LDI-02 และ LDI-03 ก็เป็น DF INNER และแสดงให้เห็นปัญหา 0 ประการ)

**ต้องมีการสืบสวน:** `UNIQUE INDEX idx_logid (log_id, time DESC)` ควรจะป้องกันการซ้ำซ้อนโดยเนื้อแท้
→ สิ่งนี้แสดงนัยยะว่าการซ้ำซ้อนนั้นอยู่ในระดับ `(mo, board_no)` มากกว่า `log_id` = **มันอาจชี้ให้เห็นถึงการนับแผงวงจรซ้ำกันในทางกายภาพ**

## ความสามารถของเซ็นเซอร์ที่อนุมานได้ — การสังเกตการณ์ระบบแบบอิสระ

```text
LDI-01..04:  Vacuum "คงที่ - ตรวจสอบ (CONSTANT - VERIFY)"   Scan Speed "คงที่ - ตรวจสอบ (CONSTANT - VERIFY)"
LDI-05..10:  Vacuum "เป็นศูนย์ทั้งหมด - ตรวจสอบ (ALL ZERO - VERIFY)"
```

ระบบตั้งค่าสถานะเหล่านี้เป็น "ค่าคงที่ที่คงอยู่ยาวนาน — แนะนำให้ทำการสืบสวน" ซึ่งถือว่า **ถูกต้องตามข้อมูลดิบ**
(การตั้งค่าสูตร (recipe setting) เป็นแบบคงที่ตามธรรมชาติ ไม่ใช่การวัดแบบไดนามิก) อย่างไรก็ตาม ควรแก้ไขข้อความให้เป็น
`"คงที่ (การตั้งค่าสูตร — เป็นไปตามที่คาดหวัง)"` เพื่อป้องกันการตีความผิดว่าเป็นความผิดปกติ

# กรอบการตรวจสอบอย่างต่อเนื่อง (Continuous Audit Framework)

## ผสานรวม Layer C เข้ากับ Automated Pipelines — ช่องว่างที่สำคัญที่สุด

ระบบปัจจุบันมีการทดสอบหน่วยและ linter ที่ครอบคลุม แต่ **ขาดกลไกใดๆ ในการตรวจสอบความถูกต้องว่าพาเนลทำการแสดงข้อมูลเพย์โหลด (payload) จริงๆ**

```javascript
// tests/e2e/panel-data-check.js  (New)
// ดำเนินการคิวรี SQL จริงสำหรับทุกๆ พาเนลเทียบกับฐานข้อมูล และตรวจสอบผลลัพธ์ของแถว
for (const panel of allPanels) {
  const rows = await pg.query(resolveMacros(panel.rawSql));
  if (rows.length === 0)
    fail(`${dashboard}/${panel.title}: query returned 0 rows`);
  if (panel.type === "timeseries" && !rows.fields.includes("time"))
    fail(`${dashboard}/${panel.title}: timeseries lacks a 'time' column`);
}
```

**เกณฑ์การผ่าน (Pass Criteria):** ทุกพาเนลจะต้องให้ผลลัพธ์ ≥1 แถว และพาเนลอนุกรมเวลา (timeseries) ทุกตัวจะต้องมีคอลัมน์ `time`
→ การตรวจสอบอัตโนมัตินี้ จะช่วยจับพาเนลที่ทำงานผิดปกติ 15 พาเนลได้อย่างน่าเชื่อถือโดยไม่ต้องใช้การแทรกแซงจากมนุษย์

## ใช้การตรวจสอบความสอดคล้องกันข้ามแดชบอร์ด (Cross-Dashboard Consistency Verification)

```sql
-- ตัวชี้วัดที่มีชื่อเหมือนกันบนแดชบอร์ดต่างๆ จะต้องดึงข้อมูลจากมุมมอง (view) เดียวกัน.
-- ห้ามใช้ขีดจำกัดแบบฝังตัว (hardcoded) ซึ่งโดยธรรมชาติควรจะจับคู่กับ pe_setting/je_setting.
```

**เกณฑ์การผ่าน (Pass Criteria):** คิวรีต้องมีการใช้ขีดจำกัดทางตัวเลขแบบฝังตัวสำหรับตัวชี้วัด PE/JE เป็นศูนย์
(พวกมันจะต้องอ้างอิงถึง `pe_setting` / `je_setting` จากชั้นข้อมูล (database layer) อย่างไม่มีเงื่อนไข)

# บทสรุปสำหรับผู้บริหารและผู้มีส่วนได้ส่วนเสีย

**คณะกรรมการบริหาร:** ระบบมีการทำงานอย่างเต็มรูปแบบครอบคลุม 5 จาก 9 อินเทอร์เฟซ อย่างไรก็ตาม มี 1 ปัญหาสำคัญที่ต้องการการแก้ไขอย่างเร่งด่วน:
ความขัดแย้งอย่างรุนแรงในการรายงาน Yield (87% เทียบกับ 99.6%) ซึ่งทำลายการตัดสินใจเชิงกลยุทธ์โดยตรง

**SRE / การปฏิบัติการด้านไอที:** ปัจจุบันมี 15 พาเนลที่ไม่สามารถแสดงข้อมูลได้ การปรับใช้การตรวจสอบ E2E เป็นสิ่งจำเป็น เนื่องจาก linter ปัจจุบัน
ตรวจสอบไวยากรณ์อย่างเคร่งครัด แต่ล้มเหลวในการรับประกันการดึงข้อมูลที่แท้จริง

**วิศวกรรม QA (QA Engineering):** ตรวจพบคีย์บอร์ด (board keys) ซ้ำกัน 157 และ 121 คีย์ แยกต่างหากเฉพาะบน LDI-01 และ LDI-04
ต้องมีการสืบสวนทันที เพื่อตรวจสอบว่านี่เป็นข้อผิดพลาดของการนับซ้ำทางกายภาพ หรือความผิดปกติภายในเครื่องจำลองข้อมูล

**วิศวกรรมกระบวนการ (Process Engineering):** การทดสอบความจริงของ RCA ทำงานได้อย่างสมบูรณ์และรายงานอย่างถูกต้องว่า
ในปัจจุบันไม่มีความสัมพันธ์ที่มีนัยสำคัญทางสถิติ (Lift ≈ 1) — การวิเคราะห์สาเหตุที่แท้จริงที่สามารถนำไปปฏิบัติได้ ต้องใช้ข้อมูลจริง หรือเครื่องจำลองที่ได้รับการแก้ไข
Cpk (PE) อยู่ที่ 1.253 ซึ่งถูกจัดอยู่ในหมวดหมู่ "ยอมรับได้ (Acceptable)" แต่ยังต่ำกว่าเกณฑ์มาตรฐานอุตสาหกรรมที่เข้มงวดที่ 1.33
