## ระเบียบวิธี (Methodology)

การตรวจสอบนี้สืบเนื่องโดยตรงจาก `IMS-FULL-SYSTEM-AUDIT.md` (ซึ่งครอบคลุม LDI Grafana dashboards ทั้ง 9 ตัว, Node-RED simulator/ingestion flows, และ DB views หลายตัว — ที่ได้รับการตรวจสอบ, แก้ไข, และผสานรวมเข้าสู่ `main` ไปแล้วในการดำเนินการก่อนหน้าของเซสชันนี้) การกลับไปตรวจสอบขอบเขตเดิมนั้นจะเป็นความพยายามที่สูญเปล่า ดังนั้นการดำเนินการในครั้งนี้จึงจงใจครอบคลุมส่วนที่การตรวจสอบครั้งก่อนไม่ได้ทำ:

| พื้นที่ (Area)                                                                                                                          | ครอบคลุมโดย (Covered by) |
| ----------------------------------------------------------------------------------------------------------------------------- | ---------- |
| การตั้งค่าระบบการติดตาม/โครงสร้างพื้นฐาน (Prometheus, Alertmanager, Blackbox, SNMP sim, PgBouncer, Grafana provisioning/library panels) | Fork 1     |
| โฟลว์การแจ้งเตือน Node-RED, ไปป์ไลน์ CI/CD (นอกเหนือจาก `ci.yml`), ไดเรกทอรี `scripts/`, บริการ `db-migrate`                          | Fork 2     |
| ประวัติการย้ายข้อมูลฐานข้อมูลแบบเต็มรูปแบบ (23 ไฟล์), `postgres/init/`, และชุดเอกสาร `docs/`                                             | Fork 3     |

ทั้งสามทำงานแบบอ่านอย่างเดียว (read-only) คู่ขนานกันไป โดยตรวจสอบข้ามเนื้อหาไฟล์เทียบกับสถานะระบบสด (`docker logs`, คิวรี `psql` แบบอ่านอย่างเดียว, การตรวจสอบคอนเทนเนอร์ที่กำลังทำงานอยู่) แทนที่จะพึ่งพาการตรวจสอบแบบสถิตเพียงอย่างเดียว — ซึ่งเป็นหลักการ "layer C" (ตรวจสอบผลลัพธ์ของคิวรี ไม่ใช่แค่ไวยากรณ์) แบบเดียวกับที่ผลักดันให้เกิดการค้นพบที่มีค่าที่สุดจากการตรวจสอบครั้งก่อน

**นี่คือการตรวจสอบเท่านั้น (audit-only pass)** ไม่มีการเปลี่ยนแปลงโค้ด ไม่มีการคอมมิต และไม่มีการแก้ไขใดๆ ทุกสิ่งที่อยู่ด้านล่างนี้คือสิ่งที่ค้นพบเพื่อนำไปจัดลำดับความสำคัญ (triage) ไม่ใช่การแก้ไขที่เสร็จสิ้นแล้ว

## P0 — วิกฤต (Critical)

### P0-1 · กฎการแจ้งเตือนของโปรดักชั่นหนึ่งข้อ กำลังล้มเหลวทุกๆ รอบการประเมิน ในขณะนี้

`ldi-machine-alarm-005` (ถูกจัดเตรียมผ่าน `monitoring/grafana/provisioning/alerting/ldi-rules.yml`) ไม่มี `ORDER BY time` ในคิวรีของมัน — ซึ่งจำเป็นสำหรับการแปลง dataframes ข้อมูลอนุกรมเวลา (time-series) ของ Grafana ยืนยันว่าเกิดขึ้นจริงใน `docker logs ims-grafana`:

```text
level=error msg="Failed to evaluate rule" ... error="...failed to convert long to wide series...not sorted in ascending order by time"
level=info msg="Sending alerts to local notifier" count=1
```

สิ่งนี้เกิดซ้ำทุกๆ รอบการประเมิน ~5 นาที สิ่งที่แย่กว่านั้นคือ: ดูเหมือนว่ามันจะส่งการแจ้งเตือนในทุกๆ ข้อผิดพลาดในการประเมิน (_error_) ไม่ใช่ในเงื่อนไขที่แท้จริงของเครื่องจักร — หมายความว่าปัจจุบันกฎนี้กำลังสร้างเสียงรบกวนของการแจ้งเตือนที่ไม่เกี่ยวข้องกับสถานะ LDI ของเครื่องจักรจริง ตามตารางเวลา

**การแก้ไข:** เพิ่ม `ORDER BY time` (หรือเทียบเท่ากับการเรียงลำดับแบบ bucketing) ลงในคิวรีของกฎ

### P0-2 · สคริปต์ migration-runner สามสคริปต์ไม่สอดคล้องกัน — นี่คือ _เหตุผล_ ที่ schema_migrations เกิดการคลาดเคลื่อน

สคริปต์แยกกันสามชุดทำหน้าที่รันการย้ายข้อมูล (migrations) โดยแต่ละชุดมีการติดตามข้อมูลที่แตกต่างกัน:

- `scripts/migrate.sh` (ทำเอง/เครื่องจัดการ) — `schema_migrations(version, filename, applied_at, checksum)`.
- `scripts/migrate-entrypoint.sh` — **เส้นทางการรันอัตโนมัติที่แท้จริง**: `db-migrate` service ของ docker-compose เป็นตัวรัน และ `node-red` มี `depends_on: db-migrate: condition: service_completed_successfully` (`docker-compose.yaml:396-400`). ตารางเดียวกัน **ไม่มีคอลัมน์ `checksum`**.
- `scripts/init-migrations.sh` — ไม่มีตารางการติดตามเลย; สคริปต์รันซ้ำไฟล์ `.sql` ทุกไฟล์ทุกครั้งที่ถูกเรียกใช้งานแบบสุ่มสี่สุ่มห้า และจัดการกับข้อผิดพลาดในการรันครั้งที่สองของ migration ที่ไม่ใช่แบบ idempotent ว่าเป็นสถานะ "ล้มเหลว (FAILED)" ที่แท้จริง

ไม่ว่าสคริปต์ใดสร้าง `schema_migrations` ขึ้นมาก่อนก็จะเป็นผู้กำหนดรูปแบบที่แท้จริงของตาราง (`CREATE TABLE IF NOT EXISTS` จะไม่มีผล (no-op) หลังจากนั้น) ในการใช้งาน `docker compose up` แบบมาตรฐาน `migrate-entrypoint.sh` มักจะทำงานก่อนเสมอ — ดังนั้น **ตาราง `schema_migrations` ที่ใช้งานจริงของการปรับใช้แบบมาตรฐานทุกครั้ง จึงขาดคอลัมน์ `checksum` อย่างสิ้นเชิง** นี่คือสาเหตุโดยตรงทางกลไกของความผิดปกติในการติดตาม "pre-seeded checksum" ที่การตรวจสอบครั้งก่อนพบและทำการเลี่ยงปัญหา (workaround) ไปแล้ว (migration 038): มันไม่ใช่ความผิดพลาดในการ seeding แบบครั้งเดียว แต่มันเป็นผลลัพธ์ทางโครงสร้างของการมีสคริปต์สามชุดที่ไม่เห็นพ้องต้องกันเกี่ยวกับความหมายของคำว่า "applied (ถูกนำไปใช้)"

**การแก้ไข:** ยุบรวมเหลือเพียง migration runner เดียวที่เป็นมาตรฐาน (canonical) ใช้ทุกที่ (คู่มือ, `db-migrate` service, และเส้นทางเริ่มต้นอื่นใดในอนาคต)

### P0-3 · ไปป์ไลน์การแจ้งเตือนปัจจุบันไม่มีการส่งมอบให้ใครเลย (สังเคราะห์จากทั้งการตรวจสอบ Infra และ Flow)

ช่องทางการส่งมอบการแจ้งเตือนที่ถูกกำหนดค่าไว้ทุกช่องทางเสียทั้งหมด โดยแต่ละช่องทางมีปัญหาแตกต่างกัน:

- **Slack** (`monitoring/alertmanager/alertmanager.yml`, ผู้รับ `ims-slack-critical`): URL webhook ยังคงเป็นเพียงข้อความแทนที่ตามตัวอักษร (placeholder) `https://hooks.slack.com/services/YOUR/WEBHOOK/URL`.
- **LINE Messaging API / MS Teams** (`nodered_data/flows/alerting.json`, ฝั่งรับของ webhook ที่แท้จริง และถูกเชื่อมต่ออย่างถูกต้องของ Alertmanager ไปยัง `node-red:1880/alert-webhook`): ฟังก์ชันการส่งมอบทั้งสองถูกนำไปใช้อย่างถูกต้อง แต่ `LINE_CHANNEL_ACCESS_TOKEN`, `LINE_USER_ID`, และ `TEAMS_WEBHOOK_URL` ทั้งหมดนั้นมีอยู่แต่ว่างเปล่าในไฟล์ `.env` ที่ใช้งานจริง ฟังก์ชันทั้งสองมีการแจ้ง `node.warn(...); return null;` ในกรณีที่มีค่าการกำหนดค่า (config) เป็นค่าว่าง — ไม่มีการขัดข้อง ไม่มีข้อผิดพลาดปรากฏขึ้นที่ใดเลยนอกจากแท็บตรวจสอบ (debug sidebar) ของ Node-RED ซึ่งไม่มีใครเฝ้าดูในการดำเนินงานจริง (production)
- **ผู้รับ `line_notify`** (`alertmanager.yml`): เป้าหมายคือ Notify API ของ LINE ซึ่ง LINE หยุดให้บริการไปในปี 2025 ยิ่งไปกว่านั้น ไม่เคยมีเส้นทางไหนกำหนดให้ส่งข้อมูลไปที่นี่ ถือว่าตายซ้ำซ้อน (Doubly dead)
- **ผู้รับ `ims-deadman`**: ถูกกำหนดไว้แล้ว แต่ไม่เคยมีใครเรียกใช้เลย (เส้นทาง Watchdog กลับชี้ไปที่ `'null'` แทน)

โดยส่วนตัวแล้ว นี่เป็นความผิดพลาดของการตั้งค่าระดับ P1 แต่เมื่อมองภาพรวมแล้วหมายความว่า: **หากระบบมีข้อผิดพลาดร้ายแรงเกิดขึ้นในตอนนี้ จะไม่มีมนุษย์คนใดได้รับการแจ้งเตือนนอกเหนือจากระบบ UI ของ Grafana** นั่นคือความเสี่ยงในการดำเนินงานที่แท้จริง และมันรุนแรงพอที่จะยกมาพูดเป็นประเด็นหลัก แทนที่จะปล่อยให้สูญหายไปในฐานะรายการระดับปานกลาง 4 รายการที่แยกกัน

**การแก้ไข:** เลือกช่องทางจริง 1 ช่องทาง (Slack webhook ถือเป็นช่องทางที่ใช้ความพยายามน้อยที่สุด — เพียงแค่ต้องการ URL ที่ใช้งานได้จริง), ทำให้มันสามารถส่งมอบจากต้นทางถึงปลายทาง, และตรวจสอบด้วยการส่งการแจ้งเตือนทดสอบจริงก่อนที่จะพิจารณาปิดปัญหานี้ ถอดเอา LINE Notify ที่ตายไปแล้ว / deadman ที่ตกค้างออก

## <img src="../../../docs/assets/icons/circle-check.svg" width="18" height="18" align="center" /> P1 — สูง (High)

### P1-1 · การปรับแต่งสคีมาในเซสชันนี้ใช้งานไม่ได้ตั้งแต่เริ่มต้นสำหรับการปรับใช้ครั้งใหม่

Migration 020 (การปรับแต่ง `DOUBLE PRECISION → REAL` ในเซสชันนี้, และช่วง chunk interval 1 วัน → 1 ชั่วโมง) และ `postgres/init/001-init-timescaledb.sql` ทั้งคู่ทำ `CREATE TABLE IF NOT EXISTS public.ldi_data`. `init/001` จะทำงานก่อนเสมอเมื่อทำการบูตใหม่ และยังคงมีการตั้งค่าจากช่วงก่อนการปรับแต่ง — ดังนั้น migration 020 จะทำการเงียบหาย (silently no-ops) ในการปรับใช้การติดตั้งครั้งใหม่ทุกๆครั้ง สิ่งที่น่าขันก็คือ นี่เป็นหลักการ "ให้ init/ และ migrations/ สอดคล้องกัน" ที่ migrations 041/047 ได้ให้ความเห็นเชิงแสดงความเคารพอย่างชัดเจน; 020 ไม่ได้มีความเห็นเหล่านั้น และก็ไม่ได้สอดคล้องกัน

**การแก้ไข:** ใช้การเปลี่ยนแปลงชนิดคอลัมน์/ช่วงเวลาย่อย (column-type/chunk-interval change) เดียวกันกับ `postgres/init/001-init-timescaledb.sql`.

### P1-2 · `../architecture/ARCHITECTURE.md` ล้าสมัยอย่างรุนแรงและมีความขัดแย้งในตัวเอง

- อ้างว่ามี "3-4 แดชบอร์ด" ถึงสามครั้งแยกกัน; ระบบจริงที่ใช้งานอยู่มี 9 แดชบอร์ด แดชบอร์ดสำหรับสายการผลิต LDI (Manufacturing, Andon, Engineering Analytics & SPC, Machine Snapshot, Data Readiness) ไม่ได้รับการกล่าวถึงเลย
- ไฟล์นี้คือ **สถาปัตยกรรมสองไฟล์ที่นำมาต่อกัน** — บรรทัดที่ 159 เริ่มต้นในส่วนที่เรียกว่า "Detailed System Architecture" ซึ่งมีรูปแบบและสไตล์แตกต่างจากส่วนบน โดยมีทั้งแผนภาพ Mermaid ซ้ำซ้อน แผนภาพโฟลว์การแจ้งเตือนซ้ำซ้อน และตารางส่วนประกอบที่ซ้ำซ้อน ดูเหมือนเป็น bad merge ที่ยังไม่ได้รับการแก้ไข
- มีความขัดแย้งในตัวเองเกี่ยวกับรอบการดึงข้อมูลของ SNMP: ในเนื้อหาระบุว่า 10 วินาที (บรรทัดที่ 48) เทียบกับตารางรอบเวลาที่ 30 วินาที (บรรทัดที่ 467) และในตาราง walker (บรรทัด 322-326)
- บรรยายว่าข้อมูลจากโทรมาตร LDI จะมาถึงผ่านการค้นหา SNMP — ที่จริงแล้วมันมาถึงผ่านทางคำสั่ง HTTP POST จาก `ldi_simulator.json` ไปที่ `/ldi-telemetry` ซึ่งไม่ใช่ SNMP แต่อย่างใด

**การแก้ไข:** ไฟล์นี้ต้องการการเขียนใหม่ ไม่ใช่แค่การแก้ (patch) — แนะนำให้ทำการเขียนโครงสร้างใหม่จากศูนย์ ทันทีหลังจากการแก้ไขในระดับโค้ดข้างต้นเสร็จสิ้น เพื่อไม่ให้มันล้าสมัยในทันทีอีกครั้ง

### P1-3 · กฎเตือนวิกฤตที่อิงกับ `ldi_metrics.vibration` ไม่สามารถเกิดการกระตุ้นได้เลยในทางโครงสร้าง

`ims-ldi-vibration-critical` (เกณฑ์ `vibration > 12`) — `vibration` มีค่าเท่ากับ 0 พอดีสำหรับทั้ง ~2,300 แถว ข้ามทั้ง 10 เครื่องจักร LDI ต้นตอเดียวกันกับช่องว่างระหว่าง `ldi_metrics.throughput`/`power_watt` ที่ทราบแล้วว่าการตรวจสอบพบในการตรวจหา LDI-dashboard (ไปป์ไลน์ k6-synthetic ingestion ไม่เคยเติมข้อมูลเหล่านี้ให้กับอุปกรณ์คลาส LDI) — การค้นพบนี้ขยายจากสิ่งนั้นเข้าไปยังการเตือนภัย ไม่ใช่แค่แดชบอร์ด การแจ้งเตือนที่ "วิกฤต" ที่ไม่สามารถกระตุ้นได้ แย่ยิ่งกว่าไม่มีสัญญาณเตือน: มันสร้างความมั่นใจผิดๆว่าความสั่นสะเทือน (vibration) กำลังถูกเฝ้าติดตามอยู่

### P1-4 · `ci-flows.yml` โครงสร้างในรูปแบบนี้ไม่มีวันที่จะผ่าน

ทำงานเมื่อมีการส่งข้อมูล (push/PR) ถึง `main` มันสร้าง `flows.json` โดยผ่าน `node scripts/build-flows.js` (ย่อหน้า JSON โดยเว้นวรรค 2 ค่า) แล้วจึงตรวจผ่าน `git diff --exit-code` เทียบกับไฟล์ `flows.json` ที่ถูกคอมมิตไว้ (การย่อหน้าเว้นวรรค 4 ค่า, ได้รับการยืนยัน) จุดต่างของความแตกต่างนี้ จะไม่สามารถทำให้มันสะอาดหมดจดได้ไม่ว่าจะมีส่วนประกอบยังไง — ช่องว่างหน้าสุดของแต่ละบรรทัดก็มีความแตกต่างแล้ว ก่อนที่จะพิจารณาถึงความคลาดเคลื่อนในการวางตำแหน่ง (`x`/`y`/`g`) ระหว่างต้นทางของการแยกแท็บ (per-tab) และผลที่ได้แบบอัปเดตเรียลไทม์ (live-edited) `flows.json` ที่อาจเป็นตัวจุดชนวนได้ด้วย

### P1-5 · แนวทางการดำเนิน "ผสาน flows.json" สองแนวทางที่คลาดเคลื่อนกัน; มีเพียงแบบที่ CI ไม่ได้ใช้ที่มีการเขียนอธิบายไว้ใน README

`scripts/build-flows.js` (มีการยืนยันข้อมูล ID ซ้ำกัน, ถูกนำมาใช้งานจริงใน `ci-flows.yml`) แตกต่างกันกับ `scripts/build-flows.sh` (`jq -s 'add'`, ซึ่งไม่มีการตรวจสอบอะไรเลย) — ทั้งไฟล์ `README.md` และ `.agents/skills/deploy-node-red-flow/SKILL.md` ได้ระบุให้ `build-flows.sh` เป็นข้อมูลบัญญัติ (canonical) รูปแบบ "การดัดแปลงในแบบคู่ขนานของการปฏิบัติงานเดียว (parallel drifting implementations of one operation)" คล้ายคลึงกับ Migration runners ในแบบ P0-2 — สิ่งนี้น่าจะเป็นลักษณะนิสัยที่เกิดขึ้นซ้ำๆ ใน codebase นี้ ซึ่งถือว่าสมควรแก่การประเมินชี้ชัดให้ชัดเจน ไม่ใช่เพียงการซ่อมปัญหาที่เกิดให้เสร็จในรูปแบบเคสต่อเคส (case-by-case)

## <img src="../../../docs/assets/icons/circle-check.svg" width="18" height="18" align="center" /> P3 — ต่ำ (Low)

- Prometheus, Alertmanager, Blackbox exporter, SNMP simulator, และเครื่องมือการแปลงภาพหรือแสดงผล (Grafana renderer) ไม่มี block แบบ `healthcheck:` (แต่ PgBouncer และตัว Grafana กลับมี) — สะท้อนให้เห็นความไม่ลงรอยกัน/ไม่สอดคล้องกัน (inconsistent) ของสภาวะข้อมูลในคลัง (observability stack) และสามารถขัดขวาง `depends_on: condition: service_healthy` ที่เป็นประตูผ่านไปสู่อนาคตให้กับของเหล่านี้
- คอมเมนต์ `contactpoints.yml` ได้ระบุเกี่ยวโยงไปยังรูปแบบ `flows-ubuntu.json` ซึ่งไม่มีอยู่จริง (ไฟล์ ณ ปัจจุบันนี้ได้เปลี่ยนไปใช้เป็น `alerting.json` แล้ว) — หมายถึงเป็นแค่เพียงข้อความให้การ (comment) ตกค้างเท่านั้น ไม่ได้มีผลทางลบต่อกลไก webhook เนื่องจากยังเป็นกลไกและรูปแบบที่ถูกต้อง
- โมดูล `dns_resolution` บนรูปแบบ `blackbox.yml` คือข้อมูลที่ให้คำจำกัดความไว้แต่ระบบกลับไม่เคยนำข้อมูลไปถูกรวบรวมแบบขูดเพื่อสกัด (scraped) ข้อมูลจาก `prometheus.yml` — สภาพเด็กกำพร้าไร้พิษภัย (harmless orphan)
- มีรายงานสรุปตรวจสอบข้อมูลความสอดคล้องที่มีการเชื่อมต่อและไม่เคยมีความเกี่ยวโยงใดๆทั้ง 3 รายการ อยู่ด้วยกันณ ขณะนี้ (`docs/IMS-audit-report-2026-08-04.md`, `docs/world-class-audit-report.md`, สาระสำคัญส่วน root `IMS-FULL-SYSTEM-AUDIT.md`) — พิสูจน์และยืนยันแล้วว่าทั้งสามส่วนของความขอบเขตข้อมูลเป็นคนละส่วนกัน ไม่ใช่ส่วนซ้ำ (not duplicates), แต่ผู้ดูรายงานอาจไม่อาจสามารถแยกความเชื่อมโยงของความเป็นปัจจุบันจนกว่าได้ทำการเปิดพิจารณามันทั้ง 3 รายการ
- ไฟล์ในโฟลเดอร์ `database/migrations/archive/README.md` กำหนดให้สถานะในรูปแบบการอพยพข้อมูลนี้คือรูปแบบที่มีการ “ถูกลบออกไปอย่างถาวร” ("permanently deleted"); ตัวของโฟลเดอร์หลักอย่างแท้จริงกลับเป็นเจ้าภาพครอบครองไฟล์ SQL รวมแล้วกว่า 8 ข้อมูลพร้อมทั้ง table dumps ทั้งหมด 3 ข้อมูล ได้รับการตรวจสอบเพื่อความถูกต้องถึงสภาพไร้พิษภัยแล้ว (การรวม glob สำหรับการเรียกคืนรูปแบบของ migrate.sh ไม่ใช่เส้นทางและกลไกหลัก ไม่เคยก้าวข้ามมาแตะต้อง) — ความเป็นมาทั้งหมดจึงบ่งบอกชัดเจนว่าคือความเป็นปัญหาที่สื่อถึงความเข้าใจคลาดเคลื่อนต่อข้อมูลที่มีบนตัวระบบเอง (misleading README).
- ข้อมูลความเห็นในส่วนต้นของส่วนตาราง (header comment) จาก `database/migrations/013-normalized-schema.sql` ถูกสร้างมาเพื่อระบุไว้ว่า “Migration 011" — เป็นส่วนตกค้างที่เกิดจากการจัดทำระบบหมายเลขใหม่ (renumbering).
- การเรียงลำดับการทำหมายเลข (numbering sequences) ทั้งคู่สองแบบต่างกันแบบไม่มีอะไรข้องกัน (`database/migrations/032-*` และ `postgres/init/032-*`) แชร์ผลของการอ้างอิงผ่านเครื่องหมายอ้างอิง "032" ให้เข้ากันแต่ข้อมูลทั้งหมดมีความไม่เกี่ยวข้องกันเลย (unrelated objects) — ก่อให้เกิดสร้างความปวดหัวให้กับบรรดาการทำกรอง (grepping) ผ่านตัวอักษรของระบบได้อย่างแท้จริง.
- การเปลี่ยนแปลงจาก `scripts/migrate.sh` ในรูปแบบคำสั่ง (stdout/stderr) ชี้เป้าเปลี่ยนไปยังศูนย์ (`/dev/null`) ก่อนหน้าการตรวจสอบรหัสเพื่อค้นหาการเกิดข้อผิดพลาดในการตกหล่น (exit code on failure) — เป็นเหตุส่งผลต่อผู้ที่เข้าไปดำเนินการมองเห็นแค่ “ความล้มเหลว (FAILED)” ที่เกิดขึ้นต่อหน้าแต่ไม่มีเหตุผลว่าเกิดจากอะไรเป็นรูปแบบที่มองเห็นเป็นหลักเป็นฐาน (no visible reason).
- คิวข้อมูล (k6-test.yml) สร้างขึ้นบนแนวทางแบบ (`secrets/postgres_password.txt`/`secrets/grafana_admin_password.txt`) เป็นอะไรก็ไม่ได้เกี่ยวข้องกันกับการมีอยู่ในระบบของแฟ้ม (`docker-compose.yaml`) ไม่เคยก้าวเข้ามาทำความคุ้นเคยด้วยตลอด — ร่องรอยที่ตกค้างอยู่ในระบบของการจัดลำดับรูปแบบรหัส Docker (Docker-secrets) เก่าในอดีต (dead leftover).
- รูปแบบจาก `release.yml` ติดตั้งการเรียกคืนของ 2 จุดที่ระบุเกี่ยวการเปิดเผย (semantic-release plugins) แบบ (`changelog`, `git`) ที่ซึ่ง `package.json` ของ `release.plugins` ไม่เคยได้รับการบันทึกข้อมูลนำเข้าเลย; นำไปสู่การดำเนินการติดตั้งในระดับตัวของมันอย่าง `semantic-release` ซึ่งตามติดมาเป็นรูปแบบของ `--no-save` โดยที่ไม่ได้ทำการควบคุมตัวผ่านรหัส/หมายเลขใดๆ, สิ่งที่เกิดขึ้นนำมาสู่ผลคือการเกิดปัญหาถูกหมางเมิน (ignoring) จากส่วนระบบล็อคข้อมูลของล็อคไฟล์ (lockfile).
- ผลรูปแบบ `scripts/snmp-discover.js` จะส่งค่าผูกรูปแบบรหัสฝัง (hardcodes) เข้าสู่ค่าหลักของการตั้งกลุ่มสำหรับ SNMP community (SNMP community string) แบบที่เรียกว่าค่าไอพีของโครงสร้าง IP ของความผูกมัดตามข้อตกลงที่ให้ไว้ในระดับปานกลาง (medium finding) ซึ่งมันเป็นการเข้าไปเพิ่มพื้นที่ผลกระทบให้ไฟล์เพิ่มมากไปถึงอีกแฟ้มหนึ่งได้เลย (extends that finding's footprint to one more file).
- การโอนรูปแบบข้อมูลในฐานของ `scripts/migrate.sh` เป็นผลพวงของรูปแบบทำรายการที่ไม่ได้ผูกเข้ากับรูปแบบความรับผิดชอบ (transaction-wrap) ในระดับที่ว่า "เอาไปใช้สำหรับอพยพฐานข้อมูล (apply migration)" + "มีบันทึกความเชื่อมโยงในแบบระบบ (record in tracking table)" — ปัญหาข้อนี้เป็นสาเหตุของการล้ม (crash) สำหรับกลุ่มโครงสร้างหากพบระหว่างตัวดำเนินการทั้งคู่ว่าจะเป็นเหตุผลหลักที่จะจุดรูปแบบเพื่อรันระบบในคราวหน้า (re-run next time) เหตุผลทางแคบที่นำมาซึ่งขอบเขตเฉพาะทาง.

## ตรวจสอบแล้วและพบว่าดีเยี่ยมจริงๆ (Checked and found genuinely fine)

- **ความทนทานต่อการนำไปใช้งาน (Migration idempotency)**, แบบครอบคลุม: การนำรูปแบบข้อมูลเพื่อนำไปทดแทนในส่วนที่มากกว่า ~19 จากทั้งหมดในหลักกว่า 23 ตัวเลือก นำรูปแบบหลักการของ `IF NOT EXISTS`/`CREATE OR REPLACE`/`ON CONFLICT DO NOTHING`/exception-swallowing `DO $$` อย่างถูกต้องเข้ามาช่วยงานทั้งหมด. ข้อที่ไม่ได้ตั้งตัวไว้เป็นในแบบ idempotent ก็ตั้งไว้แบบข้อพึงระวังเป็นข้อยกเว้นไว้, ซึ่งนั่นก็หมายถึงไม่ใช่รูปแบบกฎของมัน (ดูกรณี P2-2).
- **ข้อมูลภายในตัวแฟ้ม `archive/` อยู่ในรูปแบบไม่สามารถก้าวล่วงได้อย่างปลอดภัย (safely inert)** — เป็นการเชื่อมรวมแบบสากลผ่านกระบวนแบบทางฝั่ง (`migrate.sh's glob`) ไม่เป็นในรูปแบบทำซ้ำ (non-recursive), และไม่มีใครมาข้ามแตะต้อง.
- **การเลือกจุดของตารางข้อมูลในแฟ้ม `schema_migrations` ว่าเป็นอะไรที่ซ้ำหรือมีความเกี่ยวโยงทางคลาดเคลื่อนได้ไกลมากกว่าเคสเดิมก่อนหน้าในครั้งเดียว (already-known 038 case)**: คิวข้อมูลระดับย้ายฐาน `v_machine_spc_ranking` จากโหมด 041 นำมาเปรียบและเห็นเป็นแนวโน้มทางบวกต่อ `postgres/init/001` แบบเป็นเส้นเดียวกันและการย้ายข้อมูลจากตัวรูปแบบก็เห็นผล — ไม่มีข้อกังขาหรือจุดที่จะสามารถก่อสร้างผลคลาดเคลื่อนได้. 16 ตัวอย่างที่เตรียมมาและมีโครงสร้างนำเข้าร่วมกันถึงเรื่องแบบเป็นช่วงของเวลาที่ถูกกำหนดไว้แล้วว่าอยู่ในเงื่อนเวลาการทำงานที่เหมือนกันในเวลาเดียวกัน (identical bulk-insert timestamp) นำมาซึ่งข้อคิดเห็นว่าเรื่องของฐาน P0-2 ไม่ใช่เรื่องที่ต้องอาศัยกลไกการป้อนข้อมูลแยกเป็นสัดเป็นส่วนทั้ง 16 รายการเดี่ยวตามความอิสระ (independent seeding mistakes).
- **คิวของปัญหาทางความจริงต่อ `docs/TROUBLESHOOTING.md`** รับการปรับแต่งให้มีความแม่นยำสูงขึ้น — แนวทางการนำไปประยุกต์ใช้งานคาดคะเนทิศทางของรูปแบบปัญหาที่จะทำให้ระบบการจัดการการแสดงผลแผงรายงาน (dashboard-refresh-rate fix) ได้ถูกสร้างการทำงานไปพร้อมกันในตอนต้น.
- **ระบบในแฟ้ม `nodered_data/flows/alerting.json`** มั่นคงแข็งแกร่งด้วยโครงสร้างของมันเอง: มีข้อเท็จจริงเกี่ยวข้องกันในฐานข้อมูลของ Alertmanager webhook ถูกต้อง, กำหนดค่าเงื่อนไขผ่าน `env-var-only` อย่างเป็นระบบในจุดของการยืนยันเข้าระบบ (ปราศจากโค้ดลับที่จะมาผูกติดไว้/no hardcoded secrets), การรับมือกับรูปแบบความคลาดเคลื่อนและการกระจายข้อมูลทำออกมาดีในทุกจุด. ช่องโหว่ของปัญหาที่เจอก็คงมีแค่ปัญหาความว่างเปล่าจากชุดค่า `env vars` ทั้งหมด และความไม่มีประสิทธิผลจากส่วนบนของกระบวนทิศทางการไหลจากต้นตอแบบ `Slack config` ไม่ใช่จากส่วนการนำส่งรหัสนี้ทั้งหมดจากภายในกระบวนเอง.
- **ระบบความปลอดภัยและการจัดการเงื่อนไขสองส่วน (Two Z-score anomaly alert rules)** (`ims-cpu-zscore-anomaly`, `ims-temp-zscore-anomaly`) ป้องกันจุดพลาดเพื่อไม่ให้หารศูนย์ (`WHERE sigma > 0`) — ทำตามขั้นตอนแบบเพื่อป้องกัน (fail safe) ได้ดี, ไม่มีรอยร้าวในระบบ (not broken), นิ่งไร้การเคลื่อนไหวในช่วงเวลานั้นแบบเป็นระบบโดยที่กำหนดตัวแบบ (mock data's zero-variance server temperature) ตามระบบเอาไว้เลย.
- **กลไกโครงสร้างใน `datasources.yml`**: ข้อมูลรหัสผ่านในหลัก UID แบบ timescaledb แสดงผลเหมือนตัวแฟ้มอื่นๆ แบบเหมือนเป๊ะ (exactly); ส่วนรหัสผ่านก็ทำการแปลงอ้างผ่านกระบวน `env-var` อย่างเหมาะเจาะและไม่มีการผูกติด.
- **ปราศจากข้อผูกมัดหรือผูกติดลับแบบตั้งเป้า (No hardcoded secrets)** นอกเหนือไปจากการเจอข้อความลับในการเข้าถึงส่วนประมวลกลาง (SNMP community-string issue) ที่ได้รับการเปิดเผยก่อนหน้าและแจ้งไปล่วงหน้าว่าเห็นตรงกันเป็นจุดของ P3 ในเอกสารที่นำส่งไปให้ด้วย (confirmed in a second file too, see P3).
- กลไกระบบของการจัดการในคิว (backup-db.sh`/`restore-db.sh`/`enable-stress-test.sql) กะทัดรัด, ไร้ข้อกังขาในการใช้งานจริงและรวบรวมทำตามหน้างานออกมาได้ดี.
- ขั้นตอนการทำงานที่รัดกุมของ `k6-test.yml` สำหรับกำหนดเวลาโหลดข้อมูล (load-test logic) ถือว่ามีการทำงานที่ดีในขีดการรับส่งที่สามารถยอมให้ความเสียหายในข้อบกพร่องตามสภาพเป็นจริงที่ (>5% HTTP error rate).
- การรันเงื่อนของข้อมูลเข้าสู่การดำเนินการเพื่อพุชแฟ้ม (workflow files triggering) บนระบบเดียวกันที่มีข้อมูลผ่าน (push/PR event) เพื่อประมวลเข้าหลักระบบของ `GitHub Actions practice` จัดอยู่ในประเภทที่เป็นกลไกตามระบบปกติไม่ใช่ปัญหาความซ้ำซ้อนในโค้ด (redundancy bug).

**จุดที่ยังไม่ได้รับการพิจารณาตรวจสอบเชิงลึก (Not deeply reviewed)** (ปักธงให้รู้ว่ายังไม่ได้ตรวจสอบ, ไม่ใช่อ้างว่าสะอาด/เคลียร์): `docs/admin/`, `docs/business/`, `docs/user/`, `GRAFANA_DESIGN_SYSTEM.md`, `PANEL_TOKENS.md`, `phase2-baseline-metrics.md`, `phase2-benchmark-report.md`, `scaling-plan.md`, `deployment-readiness.md`, `IMS-master-development-plan.md`, และจุดการเฝ้าระวังที่เกี่ยวข้องเชื่อมโยงจากฝั่งของเครื่องจักร LDI ตลอด (LDI-specific alert rules) ถึง 5 องค์รวม (`ldi-quality-drift-001`, `ldi-process-capability-002`, `ldi-je-drift-003`, `ldi-je-capability-004`, `ldi-temp-high-006` — กวาดสำรวจเพื่อดูโครงสร้างภายนอก, ปราศจากธงเตือน, แต่ไม่ได้ตรวจเช็กอย่างละเอียดในลักษณะบรรทัดต่อบรรทัดแบบเรียลไทม์ (line-by-line) เหมือนที่ `ldi-machine-alarm-005` เคยผ่าน).

## สรุปตามผู้ชมแต่ละฝ่าย (Summary by audience)

**ฝ่ายบริหาร (Management):** สิ่งค้นพบระดับวิกฤตสามเรื่อง ไม่มีเรื่องใดเกี่ยวกับ LDI manufacturing dashboards ที่แก้ไขไปแล้วในช่วงต้นของเซสชันเลย — แต่เป็นเรื่องเกี่ยวกับระบบโครงสร้างการปฏิบัติงาน _ที่อยู่ล้อมรอบ_ ระบบ สิ่งสำคัญที่สุดที่ต้องใส่ใจ: **หากมีอะไรพังเสียหายอย่างรุนแรงในตอนนี้ จะไม่มีใครได้รับการแจ้งเตือน (paged)** ช่องทางการส่งมอบการแจ้งเตือนทุกช่องทางที่ตั้งค่าไว้ในระบบนี้ ล้วนเป็นเพียงข้อมูลแทนที่ชั่วคราว มีคีย์การเข้าถึง (credentials) ว่างเปล่า หรือชี้เป้าไปยัง API ที่ถูกยกเลิกไปแล้ว นั่นคือการแก้ไขที่ให้ผลตอบแทนสูงที่สุด (highest-leverage fix) ที่ทำได้ในตอนนี้

**SRE / ไอที (SRE / IT):** ความไม่สอดคล้องกันของ migration-runner (P0-2) คือรางวัลที่แท้จริงในครั้งนี้ — มันคือคำอธิบายทางกลไกสำหรับการคลาดเคลื่อนในการติดตาม ที่ก่อนหน้านี้ทำได้เพียงแค่หาทางเลี่ยงปัญหา (worked around) แบบเคสต่อเคส การแก้ไขมันอย่างถูกต้อง (ให้เหลือ runner หลักอันเดียว) จะป้องกันไม่ให้บั๊กประเภทนี้เกิดซ้ำอีก อีกสิ่งที่ควรได้รับความสนใจทันที: `ci-flows.yml` ไม่สามารถผ่านได้ไม่ว่าจะอยู่ภายใต้สถานการณ์ใดๆ ซึ่งหมายความว่ามันกำลังถูกเมินเฉย (แย่) หรือไม่ก็มันกำลังขัดขวางการผสานโค้ด (merge) โดยไม่มีเหตุผลอันสมควร (ก็แย่เช่นกัน) — สมควรอย่างยิ่งที่จะตรวจสอบดูว่าเป็นแบบไหน

**QA:** สัญญาณเตือนการสั่นสะเทือน (vibration) ระดับ "วิกฤต" ที่ไม่สามารถกระตุ้นได้เลยในทางโครงสร้าง และเอกสารสถาปัตยกรรมที่ล้าสมัย (Cpk-adjacent), ทั้งสองกรณีเป็นตัวอย่างของรูปแบบ (pattern) พื้นฐานเดิมที่โปรเจกต์นี้เคยเจอมาแล้วหลายครั้ง: สิ่งที่ _ดูเหมือน_ ว่ามันกำลังตรวจสอบอะไรบางอย่าง แต่ในทางโครงสร้างมันทำไม่ได้ ควรตั้งเกณฑ์การตรวจสอบข้อนี้ไว้เป็นหลักเลย (ข้อมูลพื้นฐานของเกณฑ์นั้นเคยมีการเปลี่ยนแปลงจริงๆ หรือไม่?) ทุกครั้งที่มีการเพิ่มการแจ้งเตือนใหม่ หรือพาเนลแดชบอร์ดใหม่

**วิศวกรกระบวนการ (Process Engineer):** ไม่มีส่วนใดในการตรวจสอบครั้งนี้ที่แตะต้องตรรกะด้านกระบวนการ/คุณภาพของ LDI โดยตรง — นั่นคือส่วนที่ทำการตรวจสอบครั้งก่อนไปแล้ว รายการเดียวที่เกี่ยวข้องกับกระบวนการคือสัญญาณเตือนการสั่นสะเทือน (P1-3): หากคาดหวังให้การตรวจสอบความสั่นสะเทือนทำงานแบบเรียลไทม์ ปัจจุบันมันยังไม่ได้ทำงาน ด้วยเหตุผลเดียวกับที่เคยพบว่าการรายงานผลผลิต PE/JE พังทลายสำหรับเครื่องจักร LDI ในการตรวจสอบครั้งก่อน (ช่องโหว่ของ k6-synthetic ingestion pipeline)
