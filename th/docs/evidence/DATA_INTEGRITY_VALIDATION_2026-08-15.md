# การตรวจสอบความสมบูรณ์ของข้อมูล (Data Integrity Validation, P0, Reliability Test Suite)

> "ต้องพิสูจน์ได้ว่าไม่มีข้อมูลสูญหาย" อ่านอย่างเดียว (Read-only) ไม่มีการแตะต้องคอนเทนเนอร์ ช่วงเวลา: 2026-08-15T03:31:22Z → 04:05:21Z (~34 นาที), ทันทีหลังจากการแก้ไข `sys_metrics` ในระยะ Phase A1 -- เลือกช่วงเวลานี้โดยเจตนาเพื่อให้การตรวจสอบครอบคลุมไปป์ไลน์ที่ได้รับการแก้ไขแล้ว ไม่ใช่ก่อนการแก้ไข

## วิธีการ

สำหรับแต่ละตารางการนำเข้าข้อมูล (ingestion table) จะใช้ (a) การเปรียบเทียบจำนวนแถวกับค่าที่คาดหวังตามรอบการดึงข้อมูลที่คงที่ (fixed poll interval) หรือ (b) การวิเคราะห์การกระจายตัวของช่องว่าง (gap-distribution analysis) เมื่อรอบเวลาไม่คงที่ -- รวมถึงการตรวจสอบตัวนับข้อผิดพลาดภายในของไปป์ไลน์ (buffer overflows, circuit-breaker trips) เพื่อหาสัญญาณการสูญหายเงียบ (silent-loss) ที่จะไม่ปรากฏเป็นช่องว่างในจำนวนแถว

## `ldi_data` (ความถี่แปรผันตามเครื่อง -- มีการแก้ไขระเบียบวิธีระหว่างการตรวจสอบ)

**การตรวจสอบครั้งแรกผิดพลาดและถูกบันทึกไว้ที่นี่โดยตั้งใจ ไม่ได้แก้ไขอย่างเงียบๆ**: สมมติฐานที่ว่าความถี่คือ 2 วินาทีอย่างสม่ำเสมอ (จาก `ldisim_tick` inject node) ได้ตัวเลขที่ดูเหมือน 3.5%-34% ของ "ที่คาดหวัง" -- ซึ่งดูน่าตกใจมาก สมมติฐานนั้นผิด: `ldisim_tick` ขับเคลื่อนนาฬิกาภายในของตัวจำลองสำหรับเครื่องทั้ง 10 เครื่อง ไม่ใช่ "หนึ่งแถวต่อเครื่องต่อ tick" แบบ 1:1 ได้ทำการตรวจสอบซ้ำด้วยการวิเคราะห์การกระจายตัวของช่องว่าง (gap-distribution analysis) แทนการใช้อัตราที่สมมติขึ้น:

| Machine   | Rows    | Min gap | Avg gap | Max gap |
| --------- | ------- | ------- | ------- | ------- |
| LDI-01/02 | 337     | 5.998s  | 6.026s  | 8.007s  |
| LDI-03/04 | 221     | 7.999s  | 9.181s  | 10.008s |
| LDI-05/06 | 348-350 | ~4.0s   | ~5.8s   | ~6.0s   |
| LDI-07/08 | 74      | 26.007s | 27.039s | 28.019s |
| LDI-09/10 | 33      | 58.020s | 58.814s | 60.031s |

แต่ละเครื่องมี**ความถี่ที่แน่นหนาและสอดคล้องกันภายใน**ของตัวเอง (min ≈ avg ≈ max, ไม่มีค่าผิดปกติปลายยาว/long-tail outliers) -- เครื่องแต่ละเครื่องสุ่มตัวอย่างในอัตราจริงที่แตกต่างกันอย่างแท้จริง (สอดคล้องกับการค้นพบก่อนหน้านี้บน readiness dashboard ที่ปริมาณข้อมูลโทรมาตรต่อเครื่องแตกต่างกัน ซึ่งผูกกับประเภทของกระบวนการ/สูตร -- "DF INNER" vs "SM" เป็นต้น) ไม่มีช่องว่างใดที่บ่งบอกถึงการสูญหายของตัวอย่าง **สะอาดเรียบร้อย เมื่อวัดด้วยวิธีที่ถูกต้อง**

## สัญญาณข้อผิดพลาดภายในไปป์ไลน์

```text
docker logs ims-node-red --since 2026-08-15T03:31:22Z | grep -i "overflow|failed"  -> 0 matches
docker logs ims-node-red --since 2026-08-15T03:31:22Z | grep -i "circuit"          -> 0 matches
```

ไม่มี buffer overflows (เส้นทางการดรอปเพื่อความปลอดภัย `BUFFER_MAX=200` ไม่เคยถูกทริกเกอร์) ไม่มีการทริปของ circuit-breaker (ไม่มีอุปกรณ์ใดถูกทำเครื่องหมายว่าไม่สมบูรณ์/ข้ามการทำงาน) ในช่วงเวลานี้

## สิ่งที่ไม่ได้ครอบคลุมในการตรวจสอบนี้

- `ldi_alarm_log` -- ยืนยันแล้วว่าไม่มีข้อมูลซ้ำซ้อนเลย (0 duplicates) ใน `READ_ONLY_AUDIT_2026-08-15.md` §3; ไม่ได้ตรวจสอบซ้ำที่นี่ด้วยวิธีใหม่ เนื่องจากการแจ้งเตือนทำงานตามเหตุการณ์ (event-driven) ไม่ใช่ความถี่รอบ (cadence-based) และปัญหาข้อมูลซ้ำซ้อน (ไม่ใช่ความครบถ้วน) คือความเสี่ยงที่เกี่ยวข้องในส่วนนั้น
- การตรวจสอบข้ามระหว่างตัวนับ `pipelineMetrics.inserts_ok` ที่ไปป์ไลน์รายงานเองกับผลรวมแถวใน DB -- ได้พยายามแล้ว แต่ HTTP path `/metrics` ไม่สามารถเข้าถึงได้ตามที่คาดไว้ และแผงควบคุมของ `ims-meta-monitoring` อ่านค่าจาก Prometheus ไม่ได้อ่านจากตัวนับในหน่วยความจำโดยตรง จึงไม่ได้ติดตามต่อ: วิธีนับจำนวนแถว/ช่องว่าง ที่ใช้ด้านบนนั้นเป็นหลักฐานที่หนักแน่นกว่าอยู่แล้ว (เป็นความจริงพื้นฐานหรือ ground truth ของ DB เอง ไม่ใช่ตัวนับของแอปพลิเคชันที่รายงานตัวเองซึ่งอาจผิดพลาดได้)
- นี่คือช่วงเวลา 34 นาที ไม่ใช่การทดสอบความทนทาน (endurance test) เป็นการยืนยันว่าไม่มีการสูญเสียข้อมูลภายใต้สภาวะปัจจุบัน แต่ไม่ได้รับประกันความเสถียรเป็นเวลาหลายชั่วโมง (ซึ่งอยู่ในรายการความทนทาน 2h/6h/12h ใน `RELIABILITY_TEST_SUITE.md`)

## คำตัดสิน (Verdict)

**ไม่พบการสูญหายของข้อมูล** ในทั้ง 3 ตารางที่ตรวจสอบ โดยใช้วิธีการที่ถูกต้องสองวิธี (การเปรียบเทียบอัตราคงที่และการวิเคราะห์การกระจายตัวของช่องว่าง) รวมกับสัญญาณตัวนับข้อผิดพลาดภายในที่เป็นศูนย์ รายการ P0 "Data integrity validation": **เสร็จสิ้น** สำหรับช่วงเวลานี้; ยังจำเป็นต้องทำการทดสอบความทนทานเพื่อการรับประกันในระยะเวลาที่ยาวนานขึ้น
