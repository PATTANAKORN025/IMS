# การนำเข้าข้อมูลจริง (Real-data import)

ที่เก็บข้อมูล (Repo) นี้ติดตามเฉพาะสกีมา (Schema) มุมมอง (Views) ฟังก์ชัน (Functions) และแดชบอร์ดเท่านั้น ข้อมูลโปรดักชัน LDI จริง (ข้อมูลเทเลเมทรี, ประวัติการแจ้งเตือน และข้อมูลส่งออกรหัสการแจ้งเตือนเสริม) จะไม่มีการคอมมิต — ข้อมูลเหล่านี้จะถูกเก็บไว้ในเครื่องที่โฟลเดอร์ `data/real/` (ซึ่งอยู่ใน gitignore) และจะถูกโหลดเข้าสู่ฐานข้อมูลสด (Live database) โดยใช้สคริปต์ `scripts/import-real-data.sh`

CI และสภาพแวดล้อมการพัฒนาในเครื่องใหม่ๆ จะไม่เห็นข้อมูลจริง: ตัวจำลอง Node-RED จะสร้างข้อมูลจำลองแถว `ldi_data`/`ldi_alarm_log` เป็นค่าเริ่มต้น (`LDI_SIMULATOR_ENABLED=true` เว้นแต่จะถูกกำหนดทับ) และ `docker-compose.yaml` จะทำการใส่ข้อมูล (Seed) รหัสแจ้งเตือนจำลองชุดเล็กผ่านไมเกรชันที่ติดตาม ตัวระบุอุปกรณ์จริง (ชื่อเครื่องจักรเช่น `LDI-B01`) *จะ*ถูกติดตาม ในไมเกรชัน 040 — ข้อมูลเหล่านั้นคือข้อมูลเมตา (Metadata) อ้างอิงสำหรับอุปกรณ์ ไม่ใช่ข้อมูลทางธุรกิจ ไมเกรชัน 040 ยังได้ลงทะเบียนอุปกรณ์จำลอง 10 เครื่อง ได้แก่ `LDI-01`..`LDI-10` ที่ตัวจำลองเขียนขึ้น เพื่อให้อุปกรณ์ทั้งสองชุดมีอยู่ในทุกการติดตั้งไม่ว่าจะใช้โหมดข้อมูลใด (ซึ่งจำเป็นสำหรับข้อกำหนด FK ของไมเกรชัน 055)

## การสลับระหว่างข้อมูลจำลองและข้อมูลจริง

`scripts/switch-data-mode.sh` เป็นคำสั่งเดียวสำหรับการย้ายระหว่างโหมดในเครื่องโลคัล ซึ่งจะไม่แตะต้องโฟลเดอร์ `data/real/` เลย (ข้อมูลจริงจะอยู่ในเครื่องเสมอและสามารถสร้างซ้ำได้จากไฟล์เหล่านั้น):

```bash
bash scripts/switch-data-mode.sh mock # ค่าเริ่มต้นสำหรับการพัฒนา
bash scripts/switch-data-mode.sh real # จำเป็นต้องมีไฟล์ data/real/*_clean.sql อยู่ในเครื่อง
bash scripts/switch-data-mode.sh status # จำนวนแถว + สถานะปัจจุบันของ LDI_SIMULATOR_ENABLED
```

โหมด `mock` จะล้างข้อมูล (`truncate`) ตาราง `ldi_data`/`ldi_alarm_log` และรีเซ็ต `ldi_alarm_ms_code` กลับเป็นแค็ตตาล็อกจำลอง 19 รหัส (ไมเกรชัน 036 — ซึ่งเป็นรหัสเดียวกับที่ `almsim_gen` ใน `nodered_data/flows.json` สามารถสร้างออกมาได้ ถูกรักษาให้ซิงค์กันโดย `tests/lint/alarm-sync-linter.js`) และเปิดการทำงานของตัวจำลองอีกครั้ง
โหมด `real` จะปิดตัวจำลอง เรียกคืนแค็ตตาล็อกผู้ขายแบบเต็ม 1,820 แถว (ไมเกรชัน 061) และรัน `scripts/import-real-data.sh` อีกครั้ง ทั้งสองทิศทางจะสร้างคอนเทนเนอร์ `node-red` ขึ้นใหม่เพื่อให้การเปลี่ยนแปลงตัวแปรสภาพแวดล้อม `LDI_SIMULATOR_ENABLED` มีผลจริง (Node-RED จะอ่านค่านี้ครั้งเดียวในตอนที่มีการใช้งานโฟลว์)

แดชบอร์ดที่จำเป็นต้องมีแผงหน้าปัด (Panel) ต่อเครื่อง จะใช้ตัวแปรเทมเพลต `machine_id` (`SELECT DISTINCT eqp_id FROM ldi_data ...`) พร้อมกับฟีเจอร์ `repeat` แผงหน้าปัดของ Grafana แทนที่จะเข้ารหัสแผงหน้าปัดตายตัวหนึ่งแผงต่อชื่ออุปกรณ์ — ซึ่งทำให้ไทล์แต่ละเครื่องของบอร์ด Andon สามารถทำงานได้โดยไม่ต้องแก้ไขเลยในโหมดใดๆ ก็ตาม แค็ตตาล็อกจำลองในไมเกรชัน 036 เคยหลุดการซิงค์จากรหัสจริงของตัวจำลอง (10 จาก 19 ไม่สามารถแก้ไขได้) หลังจากการสลับรหัสที่ไม่เกี่ยวข้องกัน — หากคุณเคยเปลี่ยนรหัสที่ `almsim_gen` สามารถส่งออกมา ให้รัน `node tests/lint/alarm-sync-linter.js` อีกครั้งบนโหมด mock เพื่อจับการตกค้างในประเภทเดียวกันนี้

## ไฟล์ต้นฉบับ

นำไฟล์ 3 ไฟล์นี้ (ไฟล์ส่งออก "Copy with SQL INSERT statements" จาก pgAdmin) มาวางใน `data/real/`:

- `ldi_data_clean.sql` — ข้อมูลเทเลเมทรีจริง (10,000 แถว ในไฟล์ส่งออกอ้างอิง)
- `ldi_alarm_log_clean.sql` — ประวัติการแจ้งเตือนจริง (10,000 แถว)
- `ldi_alarm_ms_code_clean.sql` — ไฟล์ส่งออกรหัสการแจ้งเตือนของฐานข้อมูลสดเพิ่มเติม
  (892 แถว; มีขนาดเล็กกว่าและมีความน่าเชื่อถือมากกว่าแค็ตตาล็อกผู้ขายแบบ 1,820 แถวที่อยู่ในไมเกรชัน 061 เนื่องจากไฟล์นี้สะท้อนถึงรหัสที่โรงงานพบเจอจริงๆ ไม่ใช่เพียงแค่รายการรวมจากผู้ขาย)

หากไฟล์ส่งออกของคุณยังอยู่ในรูปแบบ INSERT ที่ห่อด้วย CSV แบบดิบๆ ของ pgAdmin (คอลัมน์ `insert_sql` แถวเดียว โดยแต่ละแถวเป็นคำสั่ง SQL หลายบรรทัดเต็มรูปแบบ) ให้แกะข้อมูล (unwrap) ก่อน:

```bash
python3 scripts/unwrap-pgadmin-export.py <input.csv> data/real/<name>_clean.sql
```

## การดำเนินการนำเข้า

```bash
bash scripts/import-real-data.sh
```

สคริปต์นี้เป็นประเภท Idempotent (ทำงานซ้ำได้โดยไม่มีผลข้างเคียง) และปลอดภัยที่จะรันซ้ำ ลำดับการทำงานคือ:

1. ลงทะเบียนรหัสอุปกรณ์ (Equipment IDs) 3 รหัส ที่ปรากฏเฉพาะในบันทึกการแจ้งเตือนจริงเท่านั้น ไม่เคยปรากฏในไฟล์ส่งออกเทเลเมทรี (`LDI-B05`, `LDI-B06`, `LDI-B07`) — ถูกครอบคลุมไปแล้วในไมเกรชัน 040 สำหรับการติดตั้งระบบใหม่ แต่ถูกตรวจสอบและกำหนดค่าตรงนี้อีกครั้งเผื่อว่าการนำเข้าข้อมูลจะถูกรันบนฐานข้อมูลที่เก่ากว่าไมเกรชันนั้น
2. คลายการบีบอัดก้อนข้อมูล (chunks) ของ `ldi_data` (เนื่องจากก้อนข้อมูลที่บีบอัดจะปฏิเสธการแทรกข้อมูล) ทำการล้างข้อมูล (`truncate`) `ldi_data`/`ldi_alarm_log` หากมีข้อมูลอยู่ และโหลดแถวข้อมูลจริงลงไป
3. รวมรหัสแจ้งเตือน 892 แถวใน `ldi_alarm_ms_code` ผ่านกระบวนการ `UPSERT` ประมวลผลระดับความรุนแรง (`severity`) ด้วยกฎเดียวกันกับที่ระบุในไมเกรชัน 061 (การจำแนกประเภท Critical/Major/Minor/Warning โดยใช้คีย์เวิร์ดหรือชนิดแจ้งเตือน (AlarmType)) เพื่อให้ข้อมูลจากทั้งสองแหล่งได้รับการปฏิบัติอย่างสม่ำเสมอ
4. รีเฟรชส่วนการรวมผลลัพธ์แบบต่อเนื่อง (continuous aggregates) ทั้ง 4 ส่วน บีบอัดก้อนข้อมูลที่มีอายุเก่ากว่า 7 วันอีกครั้ง และรัน `ANALYZE`

ก่อนที่จะดำเนินการสำหรับข้อมูลจริง ให้หยุดตัวจำลองเพื่อที่มันจะไม่เขียนทับข้อมูลจริง: ตั้งค่า `LDI_SIMULATOR_ENABLED=false` ในไฟล์ `.env` ของคุณ (ซึ่งอยู่ใน gitignored) และสร้างคอนเทนเนอร์ `node-red` ขึ้นมาใหม่

## ข้อจำกัดที่ทราบ: ช่วงเวลาส่งออกข้อมูลอ้างอิงไม่ทับซ้อนกัน

ข้อมูลอ้างอิงส่งออกแบบ 10,000 แถว สำหรับตาราง `ldi_data` และ `ldi_alarm_log` ที่ใช้ในการสร้างและทดสอบไปป์ไลน์นี้ คือภาพถ่ายข้อมูล 2 ชุดอิสระ ไม่ใช่ชุดคู่กัน: `ldi_data` ครอบคลุมเพียงแค่ช่วงเวลา 2026-07-19 21:23–02:53 (~5.5 ชั่วโมง) ในขณะที่ `ldi_alarm_log` ครอบคลุมตั้งแต่ 2026-04-10 ถึง 2026-07-16 — สัญญาณเตือนล่าสุดเกิดขึ้นก่อนหน้าข้อมูลเทเลเมทรีทั้งหมด ด้วยเหตุนี้การเชื่อมโยง RCA การแจ้งเตือน→เทเลเมทรี (`v_ldi_alarm_context.match_type`) จึงมีค่าความถูกต้องตามระบบเป็น `NULL` สำหรับทุกๆ แถวเมื่อใช้ข้อมูลชุดนี้ นี่เป็นลักษณะของข้อมูล ไม่ใช่บั๊กของคิวรีเชื่อมต่อ สำหรับข้อมูลในฝั่งโปรดักชัน (Production) ที่มีช่วงเวลาทับซ้อนกันจริง การเชื่อมโยงดังกล่าวจะสามารถทำงานได้ตามปกติ ระบบการรายงานความรุนแรง/จำแนกประเภทของการแจ้งเตือนและ Cpk/SPC นั้นไม่ต้องพึ่งพาการเชื่อมโยงนี้และจะไม่ได้รับผลกระทบ

## การตรวจสอบ (Auditing)

- `scripts/import-real-data.sh` เป็นทางเดียวที่เขียนข้อมูลจริง — อ่านจากบนลงล่างเพื่อดูว่าทำงานอะไรบ้าง
- ไมเกรชัน 061 (ซึ่งคอมมิตไปแล้ว) ทำการฝังแค็ตตาล็อกผู้ขายแบบ 1,820 แถวเป็นข้อความ — ซึ่งได้รับการยอมรับว่าเป็นข้อยกเว้นข้อมูลประวัติศาสตร์ที่มีความอ่อนไหวต่ำ ซึ่งมีมาก่อนนโยบาย "ห้ามข้อมูลนอกระบบ Git" จะไม่มีสิ่งใดเกิดขึ้นหลังจากเกิดกรณีรูปแบบเดียวกันนี้
- `git log -- data/real/` และ `git check-ignore -v data/real/anything` ยืนยันว่าไดเรกทอรีนี้ไม่เคยถูกคอมมิตและไม่สามารถถูกคอมมิตโดยบังเอิญได้
