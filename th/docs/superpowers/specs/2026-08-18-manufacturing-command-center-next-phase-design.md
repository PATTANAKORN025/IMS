# IMS LDI Manufacturing Command Center — การตรวจสอบและออกแบบสำหรับระยะถัดไป

สถานะ: **เป็นเพียงการออกแบบ/สเปคเท่านั้น ไม่มีการนำไปติดตั้งใช้งานจริง** เขียนขึ้นหลังจาก 3D Factory Digital Twin ถูกแช่แข็ง (frozen) ให้เป็นเส้นฐาน (baseline) ที่ผ่านการตรวจสอบแล้ว (งาน 4.1–4.4 ทั้งหมดได้รับการตรวจสอบ/อนุมัติแล้ว, ยังไม่ได้ commit, และจะไม่มีการแก้ไขเพิ่มเติมในเอกสารนี้)

## 0. วัตถุประสงค์

ตรวจสอบสิ่งที่มีอยู่แล้วในแพลตฟอร์มที่เกี่ยวข้องกับประเด็นสำคัญที่ร้องขอมา 9 ด้าน จากนั้นเสนอแบบสำหรับการดำเนินการในระยะถัดไปก่อนที่จะมีการแก้ไขไฟล์ใดๆ:

1. ภาพรวมโรงงานระดับผู้บริหาร (C-Level)
2. การผลิตและความสอดคล้อง (Production & Compliance)
3. การวิเคราะห์และ SPC (Analytics & SPC)
4. การแจ้งเตือนระบบ (System Alarms)
5. การผสานรวม 2D Factory Digital Twin
6. การผสานรวม 3D Factory Digital Twin
7. การเจาะลึกข้อมูลโดยพนักงานคุมเครื่อง (Operator drill-down)
8. ผลกระทบของการแจ้งเตือนต่อการผลิต
9. การตรวจสอบย้อนกลับ: โรงงาน → โซน → เครื่องจักร → การแจ้งเตือน → การผลิต

นี่ไม่ใช่การออกแบบจากศูนย์ การค้นพบที่สำคัญที่สุดจากการตรวจสอบคือสิ่งเหล่านี้ส่วนใหญ่เคยถูกออกแบบมาแล้ว และบางส่วนกำลังใช้งานอยู่ ถูกทิ้งร้าง หรือเชื่อมต่อไว้แค่ครึ่งเดียว ดังนั้นระยะถัดไปส่วนใหญ่จะเป็น **การซ่อมแซมและการผสานรวม** ไม่ใช่การสร้างใหม่ทั้งหมด

### 1.2 การค้นพบ A — Manufacturing Command Center มี 5 ส่วนที่ออกแบบไว้แล้ว แต่ใช้งานไม่ได้อย่างเงียบๆ

`ims-ldi-manufacturing.json` มีพาเนลแบบแถว (row panels) ที่มีชื่อตรงกันดังนี้:

- `◈ PRODUCTION & COMPLIANCE` (row id 10001)
- `◈ ANALYTICS & SPC` (row id 10003)
- `◈ SYSTEM ALARMS` (row id 10004)
- `◈ RCA FLEET SUMMARY` (row id 10006)
- `◈ CYCLE TIME & TRACEABILITY` (row id 10013)

เหล่านี้ตรงกับประเด็นในระยะต่อไปเกือบแบบ 1:1 คือ 2, 3, 4, 8, 9 ทุกแถวมีค่า `collapsed: false` แต่พาเนลเนื้อหาภายในกลับอาศัยอยู่ในอาร์เรย์ (array) `panels: [...]` ที่เก่าและไม่ได้ใช้งาน ซึ่งซ้อนอยู่ _ข้างใน_ ออบเจกต์ (object) ของแถว — โครงสร้างนี้ Grafana จะแสดงผลก็ต่อเมื่อแถวมีค่า `collapsed: true` เมื่อค่าเป็น `collapsed: false` Grafana คาดหวังให้พาเนลเหล่านั้นอยู่ในระดับเดียวกันในอาร์เรย์ `panels[]` ระดับบนสุด (top-level) ของแดชบอร์ด พร้อมกับ `gridPos` ของตัวเอง ซึ่งมันไม่อยู่ตรงนั้น **ผลลัพธ์สุทธิ: มี 9 พาเนลที่สร้างเสร็จสมบูรณ์อยู่ใน JSON แต่ไม่ปรากฏในแดชบอร์ดที่ใช้งานจริง** ยืนยันโดยตรง (ไม่ใช่การอนุมาน) จากการแยกวิเคราะห์ JSON และเปรียบเทียบความแตกต่าง (diffing) ระหว่าง `panels[]` (แบบแบนเรียบ มี 21 รายการ ตรงกับจำนวนพาเนลใน inventory) กับอาร์เรย์ย่อย `panels` ที่ถูกทิ้งร้างในแต่ละแถว:

| แถว (Row)                       | พาเนลที่ถูกทิ้งร้าง (Orphaned panel)                  | ประเภท (Type)  |
| ------------------------- | ------------------------------- | -------------- |
| PRODUCTION & COMPLIANCE   | Production & Process Table      | table          |
|                           | Temperature Compliance (22±2°C) | state-timeline |
|                           | Humidity Compliance (55±5%)     | state-timeline |
| ANALYTICS & SPC           | Calculated Time per Board       | heatmap        |
|                           | Z-Score: temperature            | timeseries     |
| SYSTEM ALARMS             | Recent Alarm Events (Last 50)   | table          |
| RCA FLEET SUMMARY         | Top Correlated Alarms (24h)     | table          |
| CYCLE TIME & TRACEABILITY | Avg Cycle Time (Fleet)          | stat           |
|                           | Board Traceability              | table          |

ปัจจุบัน แดชบอร์ดแสดงผลเฉพาะส่วนบนสุดเท่านั้น (Executive HUD: แถว PRODUCTION / QUALITY / RISK, สถิติ/ตาราง 13 พาเนล, y=0–15) รวมกับพาเนล Pipeline Heartbeat อีก 1 อัน — ทุกอย่างที่อยู่ต่ำกว่า y=16 คือพื้นที่ว่างในแดชบอร์ดที่ใช้งานจริง ทั้งที่มี 9 พาเนลถูกกำหนดไว้ครบถ้วนในไฟล์แต่ไม่ได้ถูกใช้งาน ซึ่งน่าจะหลงเหลือมาจากการแก้ไขยุบ/ขยายแถว (row-collapse/expand) ที่ไม่ได้ปรับโครงสร้างอาร์เรย์พาเนลให้กลับมาเป็นแนวระนาบ (re-flatten) ในเอกสารฉบับนี้ไม่ได้มีการแตะต้องหรือแก้ไข — เพียงเพื่อการตรวจสอบยืนยันเท่านั้น

**ผลสืบเนื่องต่อการออกแบบด้านล่าง**: ส่วนที่ 2 (Production & Compliance), 3 (Analytics & SPC), และบางส่วนของ 4 (System Alarms) และ 9 (Traceability) มีแบบร่างแรกของคิวรี/พาเนล (first-draft) อยู่แล้วในไฟล์นี้ แผนในระยะถัดไปควรตรวจสอบความถูกต้องของ `targets` (SQL) ของพาเนลที่ถูกทิ้งร้างแต่ละตัว และนำกลับมาใช้ใหม่กับสคีมาปัจจุบันก่อนที่จะเขียนใหม่ทั้งหมด

### 1.3 การค้นพบ B — ระบบย่อยของการแจ้งเตือนเป็นของจริง มีหลายชั้น และรองรับประเด็นที่ 8 เกือบทั้งหมดแล้ว

- `public.ldi_alarm_log` / `ldi_alarm_ms_code` (พจนานุกรมหลัก) / `ldi_alarm_lifecycle` (สถานะการรับทราบ/แก้ไข: `status` OPEN→ACK→RESOLVED, `acknowledged_by`/`resolved_by`/`resolution_note`) / `v_ldi_alarm_category` (สรุปหมวดหมู่)
- `public.v_ldi_alarm_context` (`postgres/init/039-rca-alarm-view.sql`) มีการจอย (join) การแจ้งเตือนแต่ละครั้งกับโทรมาตรของเครื่องจักรในช่วง 5 นาทีก่อนหน้า และติดสถานะ (flag) `flag_temp_out_of_spec` / `flag_vac_out_of_spec` / `flag_pe_out_of_spec` แล้ว — นี่คือการจอยข้อมูลจริงและทำงานได้จริงว่า "การแจ้งเตือนนี้เกิดขึ้นพร้อมกับเงื่อนไขกระบวนการที่ไม่ได้มาตรฐานหรือไม่" ซึ่งเกี่ยวข้องโดยตรงกับประเด็นที่ 8 (ผลกระทบของการแจ้งเตือนต่อการผลิต) และแดชบอร์ด Engineering Analytics ก็ใช้พาเนล RCA นี้อยู่แล้ว
- `public.v_ldi_rca_truth_test` (materialized, `database/migrations/064-materialize-spc-fleet-rca-views.sql`) ทำไปได้ไกลกว่านั้น: สำหรับแต่ละหมวดหมู่การแจ้งเตือน ระบบจะคำนวณอัตราความไม่ได้มาตรฐาน (out-of-spec) ที่สังเกตพบ **ในระหว่างช่วงเวลาการแจ้งเตือนเทียบกับอัตรามาตรฐานของทั้งระบบ** และ **อัตราส่วนการเพิ่มขึ้น (lift ratio)** พร้อมกับตั้งค่าสถานะความเชื่อมั่น `LOW SAMPLE (n<30)` นีคือค่าสถิติที่คำนวณไว้แล้วอย่างแท้จริงว่า "การแจ้งเตือนประเภทนี้มีความสัมพันธ์กับปัญหาการผลิต/คุณภาพมากแค่ไหน" — ไม่ใช่สิ่งที่ต้องสร้างขึ้นใหม่สำหรับประเด็นที่ 8 แต่เพียงแค่ต้องนำมาแสดง
- `services/alarm-api/` (Express, การเขียนฐานข้อมูลจริงไปยัง `ldi_alarm_lifecycle`, พร็อกซีที่ `/alarm-api/` ภายใต้การตรวจสอบ `auth_request` แบบเดียวกับที่โมเดลแฝด 3D ใช้ซ้ำ) มีการติดตั้งส่วนสำหรับเขียนไว้แล้ว (`POST /alarms/ack`, `POST /alarms/resolve`) ซึ่ง `ims-ldi-alarm-console.json` ใช้เรียกเข้า
- จังหวะเวลารีเฟรช: `v_machine_spc_fleet`, `v_ldi_rca_recent_window`, `v_ldi_rca_truth_test` เป็น TimescaleDB materialized views ที่รีเฟรชทุกๆ 1 นาทีโดยผ่านงานเบื้องหลัง (`add_job('public.refresh_spc_fleet_rca_mvs', INTERVAL '1 minute')`) — ไม่พึ่งพา `pg_cron`, จัดการด้วยตัวเองทั้งหมด

### 1.4 การค้นพบ C — มีข้อมูล SPC อยู่แล้วในระดับกองเครื่องจักร (fleet scale) แยกต่างหากจากแดชบอร์ด RCA ของแต่ละเครื่อง

`public.v_machine_spc_fleet` (materialized) ให้ข้อมูลตาม `eqp_id` + `location`: `n_pe`/`cp_pe`/`cpk_pe`/`pe_pass_rate`, ค่าลักษณะเดียวกันสำหรับ JE, รวมไปถึง `worst_cpk`/`worst_n` ข้อมูลนี้คือข้อมูลสรุป SPC ของกองเครื่องจักรทั้งหมด ที่ `ims-easy-overview.json` ใช้ดึงสถิติ "Avg Cpk (Fleet)" มาใช้งาน ประเด็นที่ 3 (Analytics & SPC) ที่ระดับ Command Center สามารถนำมาใช้ได้โดยตรงโดยไม่ต้องคำนวณสูตร Cpk ใหม่ แผนภูมิควบคุมพารามิเตอร์แบบเจาะลึก (CUSUM, Nelson Rules, แผนภูมิควบคุมความหนา/สัดส่วน) มีอยู่ใน `ims-ldi-engineering-analytics.json` แล้วและควรอยู่ที่นั่นต่อไป — ประเด็นที่ 3 ใน Command Center คือส่วนสรุป/นำทาง (summary/navigation) เพื่อไปยังแดชบอร์ดนั้น ไม่ใช่การทำซ้ำระดับความลึกของข้อมูลเหล่านั้น

### 1.5 การค้นพบ D — สายใยแห่งการตรวจสอบย้อนกลับ (ประเด็นที่ 9) ปรากฏเป็นเพียงชิ้นส่วนที่ขาดการเชื่อมต่อ ไม่ใช่เส้นทางเดียวกัน

ชิ้นส่วนของจริง ซึ่งแต่ละชิ้นได้รับการยืนยันการมีอยู่และมีข้อมูลอยู่แล้วในเซสชันนี้ หรืองานข้างเคียง:

- **โรงงาน → โซน**: `public.devices.location` — มีค่าสตริงจริงๆ 5 ค่า ไม่มีคอลัมน์พิกัดตัวเลข/x-y นี่คือโมเดลโซนแบบเดียวกับที่โมเดลแฝดทั้ง 2D และ 3D ใช้
- **โซน → เครื่องจักร**: `public.devices.device_id`, `device_type='ldi'`, 10 จาก 23 แถวที่ลงทะเบียนรายงานข้อมูลจริง (`LDI-01`..`LDI-10`)
- **เครื่องจักร → การแจ้งเตือน**: `ldi_alarm_log.equipmentid` → `ldi_alarm_ms_code` → `ldi_alarm_lifecycle` (โดย `logid`+`logdate`) → `v_ldi_alarm_category`
- **การแจ้งเตือน → การผลิต**: `v_ldi_alarm_context` (รวบรวมโทรมาตร 5 นาที + การติดสถานะความมาตรฐาน (spec-flags)) และ `v_ldi_rca_truth_test` (ผลกระทบระดับหมวดหมู่) ทั้งสองส่วนนี้อธิบายไว้ข้างต้นแล้ว
- **เครื่องจักร → การผลิต/บอร์ด**: `public.v_ldi_machine_latest_full` (`board_no`, `total_board`, `mo`, `log_id`), `v_ldi_machine_snapshot`, `v_ldi_event_timeline`, และตารางพาเนล "Board Traceability" ที่ถูกทิ้งร้างในข้อค้นพบ A

ปัจจุบันไม่มีแดชบอร์ดใดที่นำเสนอสิ่งเหล่านี้เป็นเส้นทางการคลิกที่เชื่อมต่อกันเป็นเส้นเดียว (โรงงาน → โซน → เครื่องจักร → การแจ้งเตือน → การผลิต) สิ่งที่มีอยู่ใกล้เคียงที่สุดคือรูปแบบการเจาะลึกข้อมูลของโมเดลแฝด (`var-machine_id`+`var-factory` → Machine Snapshot โดยค่าตั้งต้นอ้างอิงถึง "เหตุการณ์ล่าสุด, MO ทั้งหมด") รวมกับพาเนล "Alarm Context (±5 นาที)" ของ Machine Snapshot เอง — นั่นคือ เครื่องจักร → การแจ้งเตือน และ เครื่องจักร → การผลิต ที่เชื่อมต่อกันที่โหนดปลายทาง (leaf) แล้ว สิ่งที่ขาดหายไปคือจุดเริ่มต้น โรงงาน/โซน และ การแจ้งเตือน → สรุปการผลิต ที่อยู่บนสุดของสายใย ไม่ใช่ที่ระดับข้อมูลดิบ

### 1.6 การค้นพบ E — ข้อตกลงเรื่องการเจาะลึกโดยพนักงานคุมเครื่อง (ประเด็นที่ 7) ได้รับการพิสูจน์แล้ว ถึง 2 ครั้ง

โมเดลแฝดทั้งสองแบบ รูปแบบของ Action Queue / Alarm Console ต่างบรรจบกันที่ข้อตกลง (contract) ของ URL เดียวกัน โดยได้รับการยืนยันจากงาน SDD ทั้งสี่งานในเซสชันนี้:

```
/d/ims-ldi-machine-snapshot/set2-machine-snapshot?var-machine_id=<eqp_id>&var-factory=<factory>&from=...&to=...
```

การละเว้นตัวแปร `var-mo`/`var-event_time_ms` อย่างจงใจ ทำให้ค่าเริ่มต้น (defaults) ของตัวแปร Machine Snapshot กลับไปเป็น "เหตุการณ์ล่าสุด, MO ทั้งหมด" (ตรวจสอบกับตรรกะคิวรีตัวแปรของ `ims-ldi-machine-snapshot.json` ถึงสามครั้ง: 2D POC, การสร้าง 2D เต็มรูปแบบ, 3D POC) นี่คือข้อตกลงที่มีอยู่ — ในระยะต่อไป ควรใช้สิ่งนี้ซ้ำ (reuse verbatim) สำหรับจุดเริ่มต้นใหม่ใดๆ ในการเจาะลึก (ภาพรวมระดับผู้บริหาร → โซน, โซน → เครื่องจักร ฯลฯ) แทนที่จะสร้างรูปแบบที่สองขึ้นมา

### 1.7 การค้นพบ F — โมเดลแฝดทั้ง 2D และ 3D ล้วนเป็นของจริง คงที่ (frozen/stable) และในขณะนี้แยกตัวออกจาก Command Center

ไม่มีการเชื่อมโยงจาก `ims-ldi-factory-digital-twin.json` (2D) หรือ `services/factory-twin-3d/` (3D) กลับไปที่ `ims-ldi-manufacturing.json` หรือในทางกลับกัน ทั้งสองอย่างอยู่แยกเป็นอิสระต่อกัน (freestanding) ทั้งคู่มีข้อมูล สถานะ/บอร์ด/MO/การแจ้งเตือน ต่อเครื่องจักรแบบเดียวกัน รวมทั้งเป้าหมายการเจาะลึกข้อมูลแบบเดียวกัน ประเด็นที่ 5 และ 6 จึงเป็นปัญหาด้าน **การผสานรวม (integration)** (สิ่งเหล่านี้จะไปอยู่ที่ไหนสัมพันธ์กับ Command Center — แบบพาเนลฝัง, ลิงก์นำทางด้านบนสุด, หรือสลับหน้า) ไม่ใช่การสร้างใหม่

### 1.8 สิ่งที่ขาดหายไปจริงๆ (ไม่ใช่แค่ถูกทิ้งร้าง)

- ยังไม่มี "ภาพรวมโรงงานระดับผู้บริหาร (C-Level)" เพียงหน้าเดียวที่ครอบคลุมรายละเอียดรายเครื่องจักร — `ims-easy-overview.json` ใกล้เคียงที่สุด (สรุปข้อมูลกองเครื่องจักรโดยไม่ต้องตั้งค่า) แต่วางตัวเป็นช่องทางด่วนสำหรับฝ่ายปฏิบัติการ/วิศวกรรม ไม่ใช่สรุปสำหรับผู้บริหาร และไม่มีสรุปข้อมูลรายโซน/โรงงาน
- ไม่มีพาเนลใดรวบรวม "การแจ้งเตือนและผลกระทบต่อการผลิตที่วัดได้" มาจัดอันดับรวมกันเพื่อนำเสนอต่อเจ้าของสายการผลิต — มีสูตรคำนวณแล้ว (`v_ldi_rca_truth_test`) แต่ยังไม่มีการแสดงผล
- ยังไม่มีแดชบอร์ดใดเสนอเส้นทางการคลิก (click path) โรงงาน → โซน → เครื่องจักร → การแจ้งเตือน → การผลิต อย่างครบถ้วนในรูปแบบเดียวกัน; มีข้อมูลสำหรับแต่ละช่วง แต่ไม่มีเส้นทางเชื่อมโยง

## 2. ข้อเสนอการออกแบบ

### 2.1 หลักการ: ซ่อมแซมก่อนสร้างใหม่

จากการค้นพบ A งานแรกที่ต้องดำเนินการในแผนระยะต่อไป (ไม่ใช่งานในเอกสารนี้) คือการแบนเรียบแถว (re-flattening) 5 แถวที่พังใน `ims-ldi-manufacturing.json` ก่อนที่จะออกแบบพาเนลใหม่ — ให้ตรวจสอบความถูกต้องของ SQL ของแต่ละพาเนลที่ถูกทิ้งร้างว่าตรงกับสคีมาปัจจุบันหรือไม่ (บางคิวรีอาจเก่ากว่าการเปลี่ยนแปลงสคีมาในภายหลังในเซสชันนี้ เช่น ปัญหา `board_id`/`log_id`) จากนั้นให้เลือกว่าจะเรียกคืน, แก้ไข หรือจะจงใจแทนที่แต่ละส่วน ซึ่งวิธีนี้คาดว่าจะสามารถแก้ไขปัญหาข้อที่ 2, 3, 4, และ 9 ไปได้มากโดยที่ไม่ต้องออกแบบพาเนลใหม่เลย

### 2.2 ทิศทางการออกแบบในแต่ละประเด็น

1. **ภาพรวมโรงงานระดับผู้บริหาร (C-Level)** — เพิ่มส่วนใหม่บนสุด (หรือสร้างแดชบอร์ดใหม่ — คำถามปลายเปิด, ดูส่วนที่ §3) ให้อยู่เหนือระดับของ `ims-easy-overview`: สร้างบทสรุปรายโรงงาน/โซน (5 โซน) ไม่ใช่รายเครื่องจักร ใช้วิธีจัดกลุ่ม `v_ldi_machine_latest_full` + `devices.location` ซึ่งพิสูจน์ผลแล้วในโมเดลแฝดทั้งสองมาใช้ซ้ำ
2. **การผลิตและความสอดคล้อง (Production & Compliance)** — ซ่อมแซมแถวที่ถูกทิ้งร้างก่อน (Production & Process Table, Temp/Humidity Compliance timelines — ซึ่งเป็นประเภทพาเนลเดียวกับที่พิสูจน์แล้วว่าทำงานได้ใน Operator Andon) และตรวจสอบคิวรีของพาเนลที่ถูกทิ้งร้างอีกครั้งว่ายังเข้ากันกับสคีมาล่าสุดก่อนการเรียกคืน
3. **การวิเคราะห์และ SPC (Analytics & SPC)** — ซ่อมแซมแถวที่ถูกทิ้งร้าง (Calculated Time per Board, Z-Score temperature) เพื่อให้เป็นชั้นแสดงผลสรุป (summary layer) สำหรับ Command Center โดยดึงข้อมูลจาก `v_machine_spc_fleet` (ซึ่งตั้งรีเฟรชทุกๆ 1 นาทีแล้ว) เพื่อคำนวณ Cpk รวม (fleet Cpk) พร้อมทำจุดคลิกเพื่อลิงก์ระบุเป็นเอกสารไว้ว่า "ดู Engineering Analytics สำหรับแผนภูมิควบคุม SPC แบบเต็ม" แทนที่จะมาทำซ้ำความลึกของแดชบอร์ดนั้น
4. **การแจ้งเตือนระบบ (System Alarms)** — ซ่อมแซมตาราง "Recent Alarm Events" ที่ถูกทิ้งร้าง; และต้องตัดสินใจว่า Command Center ควรจะรวม (embed) ปุ่มโต้ตอบการ ack/resolve เหมือนกับ Alarm Console เอาไว้ หรือให้เป็นแค่สถานะอ่านได้อย่างเดียวพร้อมปุ่มลิงก์ (คำถามปลายเปิด, ส่วนที่ §3) — รูปแบบ "สถานะอ่านได้อย่างเดียว, ต้องไปที่ Alarm Console ต่างหากสำหรับการโต้ตอบ" ใน Andon Board คือตัวอย่าง (precedent) ที่มีอยู่ให้ปฏิบัติตาม เว้นแต่จะมีเหตุผลให้ต้องทำแบบอื่น
5. **การผสานรวม 2D Factory Digital Twin** — เพิ่มลิงก์สำหรับการนำทางจริง (real navigation link) (ไม่ใช่การฝังพาเนล — พาเนลประเภท Canvas หนักเครื่อง และโมเดลแฝดก็เป็นแดชบอร์ดเต็มรูปแบบอยู่แล้ว) เพื่อเชื่อมจาก Command Center สู่ `ims-ldi-factory-digital-twin` และในทางกลับกันหากมีประโยชน์ ไม่จำเป็นต้องทำงานเกี่ยวกับคิวรีเพิ่มเติม; ข้อมูลของโมเดลแฝดนั้นเทียบเท่ากับข้อมูลในชั้นรายเครื่องจักร (per-machine layer) ของ Command Center อยู่แล้ว
6. **การผสานรวม 3D Factory Digital Twin** — ผสานการนำทางแบบเดียวกับประเด็นที่ 5 โดยอาศัย nginx route เดิมที่มีอยู่คือ `/factory-twin-3d/` (มีระบบรับรองความถูกต้อง `auth_request` ผ่านเซสชัน Grafana อยู่แล้ว ไม่จำเป็นต้องทำเพิ่ม) โมเดลแฝด 3D ถูกแช่แข็งตามคำสั่งของผู้ใช้ในเซสชันนี้ — ไม่มีการแก้โค้ดในระยะนี้ นอกเสียจากจะได้รับอนุญาตเป็นการเฉพาะแยกต่างหาก
7. **การเจาะลึกข้อมูลโดยพนักงานคุมเครื่อง (Operator drill-down)** — นำข้อตกลง `var-machine_id`+`var-factory` → Machine Snapshot (ข้อค้นพบ E) ที่พิสูจน์แล้วมาขยายต่อยอดไปประยุกต์ใช้กับจุดเริ่มต้นใหม่ใดๆ ระดับโซน/โรงงาน ที่สร้างขึ้นสำหรับข้อที่ 1 เพื่อให้มุมมอง C-Level สามารถเจาะลึก (drill) โซน → เครื่องจักร ได้โดยใช้ข้อตกลง (contract) เดียวกับส่วนที่เหลือใช้งานอยู่แล้ว
8. **ผลกระทบของการแจ้งเตือนต่อการผลิต** — ดึงการประมวลผลสัดส่วนเพิ่ม/ความน่าเชื่อถือ (lift/confidence computation) ของ `v_ldi_rca_truth_test` ที่มีอยู่แล้วมาแสดงผลโดยตรง (วิธีนี้ยังช่วยแก้ไขแถว "Top Correlated Alarms" ที่ถูกทิ้งร้างได้ด้วย, ดูข้อค้นพบ A/B) ดีกว่ามาคำนวณหาสหสัมพันธ์ (correlation) ใหม่จากศูนย์ นอกจากนี้ ข้อมูล `v_ldi_alarm_context` ซึ่งมีการตั้งค่าสถานะความมาตรฐาน (spec-flags) แยกรายแจ้งเตือน ก็เป็นแนวคิดรูปแบบเดียวกันในระดับแถว ซึ่งสามารถดึงไปใช้สร้างเป็นตารางรายละเอียดได้เลย
9. **การตรวจสอบย้อนกลับ โรงงาน → โซน → เครื่องจักร → การแจ้งเตือน → การผลิต** — ปัญหานี้เป็นช่องโหว่ด้านการนำทางแบบเชื่อมต่อ (ข้อค้นพบ D/E) ไม่ใช่ช่องโหว่ด้านข้อมูล ในการออกแบบต้องสร้างเป็นเส้นทางการคลิก (click path) แบบนำทาง 1 เส้นทาง โดยใช้รูปแบบเจาะลึกข้อมูลที่พิสูจน์แล้วมาใช้งานในแต่ละระดับ (hop): ภาพรวมระดับ C-Level (แบบสรุปรายโซน) → รายละเอียดรายโซน (รายชื่อเครื่องจักร, ใช้การจัดกลุ่มโซนรูปแบบเดียวกับของโมเดลแฝด) → เครื่องจักร (หน้า Machine Snapshot, ซึ่งมีการแสดงบริบทแจ้งเตือน และบริบทการผลิตคู่กันไว้แล้ว) — การซ่อมแซมพาเนล "Board Traceability" ที่ถูกทิ้งร้างจะช่วยปิดงานช่องว่างเชื่อมโยงระหว่างระดับ เครื่องจักร → การผลิต ลงได้

### 2.3 เลื่อนออกไปอย่างชัดเจน / อยู่นอกเหนือขอบเขตสำหรับแผนการดำเนินงานในระยะต่อไป

- ไม่มีการแก้ไขโมเดลแฝด 3D (ถูกแช่แข็ง, ตามคำแนะนำอย่างชัดเจน)
- ไม่มีการตั้งสมมติฐานเกี่ยวกับการย้ายฐานข้อมูลใหม่ใดๆ ณ ขณะนี้ — ข้อค้นพบข้างต้นล้วนชี้ไปที่ views/functions/tables _ที่มีอยู่แล้ว_; หากพบช่องโหว่ข้อมูลที่แท้จริงระหว่างการทำงาน ควรจัดการตั้งค่าสถานะเป็นการเฉพาะในเวลานั้น ไม่ใช่ตั้งสมมติฐานกันตั้งแต่ตอนนี้
- ไม่มีโมเดล CAD, ไม่มีการเชื่อมต่อกระบวนการระหว่างเครื่องจักรต่อเครื่องจักร, ไม่มีการตั้งพิกัดโรงงาน (เป็นข้อจำกัดที่ตั้งไว้และไม่มีการเปลี่ยนแปลง)
- ยังไม่มีการตัดสินใจเรื่องผัง (topology) ของแดชบอร์ด (ขยาย Manufacturing Command Center ต่อ vs. สร้างแดชบอร์ดใหม่ระดับ C-Level vs. ปรับโครงสร้างแดชบอร์ดที่มีอยู่) — ดูคำถามปลายเปิดด้านล่าง; นี่คือตัวเลือกสำหรับการออกแบบและการวางแผนระยะต่อไป, ยังไม่ต้องรีบตัดสินใจผ่านเอกสารตรวจสอบฉบับนี้

## 3. คำถามปลายเปิด (สำหรับการออกแบบ/การวางแผนระยะต่อไป, ไม่ตอบในที่นี้)

1. **Topology**: ภาพรวมระดับ C-Level (ข้อที่ 1) ควรเป็นแค่ส่วนเพิ่มเติมขึ้นมาใหม่ส่วนบนสุด (top section) ในแดชบอร์ด `ims-ldi-manufacturing.json` เดิม หรือจะดึงแยกออกมาสร้างแดชบอร์ดสแตนด์อโลน (standalone dashboard) ไปอยู่ข้างบนเลยดี? ตอนนี้ Manufacturing Command Center มีการกำหนดพาเนลเอาไว้ 21 อัน (รวมพาเนลที่ถูกทิ้งร้างอีก 9) การพยายามยัดบทสรุปโรงงาน/โซนเอาไว้ชั้นบนสุดอาจจะสู้แยกให้มันเป็นจุดเริ่มต้นดึงเข้าใช้งานของมันเองไม่ได้
2. **การโต้ตอบของ System Alarms**: จะใช้ระบบที่มีสถานะอ่านได้อย่างเดียว (ตัวอย่างจาก Andon) หรือรวมหน้าต่างโต้ตอบ (embed Alarm Console's ack/resolve) (ตัวอย่างใหม่)?
3. **2D vs 3D โมเดลแฝดในฐานะระบบที่เป็น "หลัก (canonical)" เมื่อคลิกเจาะเข้ามาจาก Command Center**: แปะลิงก์ทั้งคู่ แปะแค่อันใดอันนึงพร้อมสลับไปมา หรือจะให้มีระบบเลือกเพื่อสลับ (switcher) ไปมาที่ตัว UI เองดี? เพราะทั้งสองระบบ ล้วนทำงานจริงอยู่ (real) ในปัจจุบัน ยังไม่พบปัญหาทางเทคนิคไหนที่จะต้องบอกว่าอันไหนดีกว่ากัน
4. **Traceability UX**: ใช้แดชบอร์ดเดียวทำลิงก์เจาะลึกลงไปเป็นชั้นๆ ต่อกันไปเรื่อย (แบบดั้งเดิม) เทียบกับ ทำแดชบอร์ดเพื่อ "ตามรอยหา board/alarm โดยเฉพาะ" ที่รวมระดับต่างๆ (hop) ทั้งหมดไว้หน้าเดียว — แบบแรกตรงกับมาตรฐานเดิมทั้งหมดที่มีใน repository นี้ ส่วนแบบหลังจะเป็นการสร้างกระบวนทัศน์ (pattern) ใหม่ขึ้นมา
5. **ขอบเขตการซ่อมแซมพาเนลที่ถูกทิ้งร้าง**: SQL คิวรีของ 9 พาเนลที่ถูกทิ้งร้างยังคงสามารถใช้กับสคีมาปัจจุบันได้หรือไม่? (เพราะบางตัวอาจเก่าเกินไป เช่น ปัญหา `board_id` ไม่มีข้อมูล จนต้องแทนด้วย `log_id`) สิ่งนี้ต้องการการตรวจสอบ (audit) คิวรีอย่างละเอียดก่อนเป็นอันดับแรกสุดในรอบแผนการดำเนินการครั้งหน้า จะถือเอาเองว่ามันใช้งานได้สมบูรณ์เลย ณ ตอนนี้ ไม่ได้

## 4. สิ่งที่เอกสารนี้ไม่ได้ทำ

ไม่มีการดัดแปลงไฟล์ ไม่ได้เข้าไปแตะต้อง กู้คืน (restored) หรือซ่อมแซม JSON ใดๆ ในแดชบอร์ด ไม่มีการเขียนไมเกรชัน ไม่มีการสั่งงานคิวรี นอกจากการอ่าน (read-only) ข้อมูลภายใน (`SELECT`/`\d`/`psql`) และการเข้าตรวจสอบ (read-only) บน `git`/ไฟล์ เอกสารฉบับนี้เป็นเพียง การตรวจสอบยืนยัน (audit) + และการออกแบบ, ตามที่ได้รับมอบหมาย
