# แฝดดิจิทัลโรงงาน 3 มิติ (3D Factory Digital Twin) — ข้อกำหนดสถาปัตยกรรมและการออกแบบ

> สถานะ: สำหรับการออกแบบเท่านั้น ไม่อนุมัติให้ดำเนินการใช้งานจริง ยังไม่มีการสร้างโค้ด แดชบอร์ดใหม่ หรือบริการใหม่สำหรับสิ่งนี้ เอกสารฉบับนี้มีไว้เพื่อตรวจสอบและอนุมัติ แก้ไข หรือปฏิเสธก่อนเริ่มงานใน Task 4.x
>
> เอกสารฉบับนี้แทนที่ Task 13 (Placeholder ของแผนการย้ายไปยัง 3D Digital Twin) ในแผนงาน 2D twin โดยตรง ซึ่งเดิมจงใจปล่อยไว้โดยไม่มีการออกแบบจนกว่าจะมีพิกัดจริง ผู้ใช้ได้ขอให้สร้างการออกแบบล่วงหน้าก่อนมีพิกัดจริง โดยข้อมูลการจัดวางทั้งหมดจะถูกทำเครื่องหมายว่าเป็นการจำลองอย่างชัดเจน จนกว่าจะมีการระบุแผนผังโรงงานจริง เอกสารฉบับนี้เคารพคำขอดังกล่าว และในขณะเดียวกันก็ระบุอย่างชัดเจนว่าสิ่งใดเป็นข้อมูลจริงในปัจจุบันและสิ่งใดไม่ใช่

## 0. ข้อบังคับที่ไม่อาจต่อรองได้จากงาน 2D twin

ข้อบังคับเหล่านี้ใช้ได้กับทุกงานในแผนการสร้าง 2D และยังคงใช้ในที่นี้โดยไม่มีการเปลี่ยนแปลง:

- ไม่นำข้อมูลจำลองมาแสดงเป็นข้อมูลจริง ในกรณีที่การออกแบบนี้ใช้พิกัดทดแทน ทุกพิกัดจะถูกระบุว่า "จำลอง (SIMULATED)" เสมอ จะไม่มีการอ้างว่าเป็นตำแหน่งเครื่องจักรจริง
- ห้ามใช้ปลั๊กอินภายนอกของ Grafana ได้รับการยืนยันในเซสชันนี้แล้วว่า: Grafana 13.1.1 core ไม่มีประเภทพาเนลที่รองรับ 3 มิติ (`canvas` รองรับเพียง 2 มิติเท่านั้น) นี่เป็นเหตุผลที่ §1 ด้านล่างสรุปว่า 3D twin ไม่สามารถอยู่ภายใน Grafana ได้
- ใช้เฉพาะข้อมูลสถานะ/การแจ้งเตือน/การผลิตของเครื่องจักรจริงเท่านั้น ซึ่งดึงข้อมูลจากตาราง/วิวเดียวกันที่ได้รับการพิสูจน์แล้วในเซสชันนี้ (`v_ldi_machine_latest_full`, `ldi_alarm_log`, `ldi_alarm_ms_code`, `ldi_alarm_lifecycle`)
- `board_id` ไม่ถูกใช้งาน (ว่างเปล่า 100% ของแถวข้อมูลจริง) `log_id` คือตัวระบุเหตุการณ์จริงต่อเหตุการณ์
- แดชบอร์ดที่มีอยู่ (`ims-ldi-manufacturing.json`, `ims-ldi-operator-andon.json`, และ `ims-ldi-factory-digital-twin.json` ที่เพิ่งสร้างเสร็จ) จะไม่ถูกแก้ไขโดยสิ่งใดๆ ในเอกสารฉบับนี้

## 1. Grafana 2D Digital Twin เทียบกับเว็บแอปพลิเคชัน 3D ที่แยกต่างหาก

**การตัดสินใจ: ใช้เว็บแอปพลิเคชัน 3D แยกต่างหาก ลิงก์/ฝังจาก Grafana ไม่ใช่การสร้างภายใน Grafana**

ข้อจำกัดจริง ไม่ใช่ความชอบส่วนตัว: พาเนลเชิงพื้นที่เพียงอย่างเดียวของ Grafana คือ `canvas` (ยืนยันแล้วว่าเป็น core/internal ในเซสชันนี้ผ่าน `GET /api/plugins`) และ Canvas เป็นระบบการจัดตำแหน่งแบบ 2D (สัมบูรณ์) — มันไม่มี Scene graph 3 มิติ, ไม่มีกล้อง, ไม่มีความลึก, ไม่มีการจัดแสง ไม่มีประเภทพาเนลหลักของ Grafana ใดที่สามารถเรนเดอร์ 3 มิติได้ วิธีเดียวที่จะนำ 3 มิติเข้าไป *ภายใน* Grafana ได้คือใช้ปลั๊กอินพาเนลจากชุมชนภายนอก ซึ่งข้อบังคับ "ห้ามใช้ปลั๊กอินภายนอก" ห้ามไว้อย่างเด็ดขาด — นี่ไม่ใช่ข้อจำกัดที่หลีกเลี่ยงได้ แต่มันคือการปิดประตูโดยการออกแบบ

**แนวทางปฏิบัติที่มีอยู่แล้วในพื้นที่เก็บข้อมูลนี้สำหรับ "บริการแยก แหล่งที่มาเดียวกัน เซสชันที่ตรวจสอบสิทธิ์แล้ว":** `services/alarm-api` — เป็นบริการ Express + `pg`, เป็นพร็อกซีผ่าน `proxy/nginx.conf` ที่ `/alarm-api/`, ถูกควบคุมโดย `auth_request` กับการตรวจสอบเซสชัน `/api/user` ของ Grafana เอง (`proxy/nginx.conf` บรรทัดที่ ~20-30) ไม่มีระบบการยืนยันตัวตนใหม่ ใช้การเข้าสู่ระบบที่ผู้ปฏิบัติงานใช้ไปแล้ว 3D twin ควรทำตามรูปแบบนี้อย่างแท้จริง: `services/factory-twin-3d/`, เป็นพร็อกซีที่ `/factory-twin-3d/` (หรือเส้นทางที่คล้ายกัน), ประตู `auth_request` เดียวกัน นี่ไม่ใช่แนวคิดสถาปัตยกรรมใหม่ — มันคือรูปแบบเดียวที่พื้นที่เก็บข้อมูลนี้ได้สร้าง, ทดสอบ, และพิสูจน์แล้วหนึ่งครั้ง

2D Canvas twin จะยังคงเป็นกระดานสถานะหลักสำหรับผู้ปฏิบัติงาน/ระดับ C (รวดเร็ว, เปิดตลอดเวลา, โหมดคีออสก์ไม่ต้องเลื่อนจอ) ส่วน 3D twin คือมุมมองเสริมที่เลือกเข้าชมได้และมีรายละเอียดมากขึ้น — เข้าถึงผ่านลิงก์/ปุ่มจาก 2D twin (หรือการนำทางของ Grafana) ไม่ใช่การมาแทนที่

## 2. เทคโนโลยีการเรนเดอร์

**คำแนะนำ: Three.js (WebGL), แบบพื้นฐาน (Vanilla) หรือร่วมกับ bundler ขนาดเล็ก (Vite)**

เหตุผลที่ไม่ได้กล่าวอ้างลอยๆ แต่ตรวจสอบได้: Three.js เป็นมาตรฐานพฤตินัยสำหรับการแสดงภาพ 3 มิติบนเบราว์เซอร์ ไม่จำเป็นต้องใช้ Server-side rendering (เข้ากันได้กับโมเดล "บริการน้ำหนักเบาแยกต่างหาก" ใน §1) และ — สิ่งสำคัญสำหรับ §12 (ประสิทธิภาพที่สเกลขนาดใหญ่) — รองรับ `InstancedMesh` สำหรับการเรนเดอร์รูปร่างของเครื่องจักรที่เหมือนกันหลายร้อยเครื่องในการเรียกวาดภาพครั้งเดียว (draw call) ซึ่งมีความสำคัญโดยตรงเมื่อขยายขนาดเกิน 10 เครื่อง

พื้นที่เก็บข้อมูลนี้ไม่มีประวัติการใช้เฟรมเวิร์กส่วนหน้า (frontend framework) ใดๆ มาก่อน (`package.json` ที่รากของพื้นที่เก็บข้อมูลไม่มี frontend dependencies; ไม่มี `src/`, ไม่มี React/Vue/Svelte ที่ไหนเลย) นี่คือส่วนประกอบใหม่ของเทคโนโลยีสแต็ค (tech stack) อย่างแท้จริง ไม่ใช่รูปแบบอื่นของสิ่งที่มีอยู่แล้ว — ถูกเน้นย้ำอย่างชัดเจน ไม่ได้ถูกมองข้าม `package.json` ของ `services/alarm-api` (มีแค่ Express + `pg`) คือแบบแผนที่ใกล้เคียงที่สุด สำหรับฝั่ง *แบ็กเอนด์ (backend)* เท่านั้น

ทางเลือกที่พิจารณาและปฏิเสธสำหรับเฟสนี้: การส่งออกจาก Game engine เต็มรูปแบบ (Unity WebGL, Unreal Pixel Streaming) — ต้นทุนการดำเนินงานสูงกว่ามาก (ไปป์ไลน์การสร้าง, เซิร์ฟเวอร์สตรีมมิ่งที่ใช้ GPU สำหรับ Pixel Streaming) สำหรับการแสดงสถานะโรงงานที่ไม่ต้องการการเรนเดอร์ระดับ Game engine. Three.js คือขนาดที่เหมาะสมสำหรับปัญหานี้

## 3. ลำดับชั้น: โรงงาน → อาคาร → ชั้น → โซน → เครื่องจักร

**ข้อมูลจริงในปัจจุบัน:** `public.devices.location` เป็นคอลัมน์ข้อความแบนๆ (flat text column) เดียวที่มี 5 ค่าจริง (`Site A - Zone 1`, `Site A - Zone 2`, `Site A - Zone 3`, `Site B - Zone 1`, `Site B - Zone 2`) — ยืนยันแล้วในเซสชันนี้ ไม่มีคอลัมน์ `building`, `floor`, หรือ `zone` อยู่ที่ไหนในสคีมาเลย "Factory 2" / "Factory 3" และคำต่อท้าย (`DF INNER`/`DF OUTER`/`SM`) ถูกเข้ารหัสรวมกันในสตริงเดียว ไม่ได้ถูกแยก

**โมเดลลำดับชั้นที่เสนอ** (ใหม่, ไม่แตะต้อง `devices` หรือตารางข้อมูลโทรมาตร (telemetry) ใดๆ):

```sql
-- NEW TABLE, proposed, not created by this document
CREATE TABLE public.factory_layout_hierarchy (
  hierarchy_id   SERIAL PRIMARY KEY,
  factory_code   TEXT NOT NULL,        -- เช่น '2', '3' -- ตรงกับค่า ldi_data.factory จริง
  building_name  TEXT,                 -- ชื่ออาคารจริง เมื่อทราบแล้ว -- อนุญาตให้เป็นค่าว่าง (nullable) จนกว่าจะถึงตอนนั้น
  floor_name     TEXT,                 -- ตัวระบุชั้นจริง เมื่อทราบแล้ว -- อนุญาตให้เป็นค่าว่างจนกว่าจะถึงตอนนั้น
  zone_name      TEXT NOT NULL,        -- แมปกับสตริง devices.location จริงในตอนนี้
  UNIQUE (factory_code, building_name, floor_name, zone_name)
);
```

จนกว่าจะมีข้อมูลอาคาร/ชั้นจริง `building_name`/`floor_name` จะยังคงเป็น `NULL` และลำดับชั้นจะเป็นแบบ `โรงงาน → โซน → เครื่องจักร` (ตรงกับความจริงในปัจจุบัน) แทนที่จะเป็นโครงสร้างต้นไม้ 4 ระดับแบบเต็มตามที่ผู้ใช้ร้องขอให้รองรับ — สคีมารองรับต้นไม้ที่ลึกกว่าโดยไม่ต้องกำหนดให้มีข้อมูลครบถ้วนก่อนที่จะทราบข้อมูล นี่คือวิธีการเดียวกันของ "โครงสร้างมีอยู่แล้ว ข้อมูลค่อยตามมาทีหลัง" ที่ใช้สำหรับตารางพิกัดใน §4

## 4. โมเดลพิกัดจริง — x/y/z, การหมุน, มาตราส่วน, การวางแนว

**ตารางใหม่ที่เสนอ** (แยกจาก `devices`, แยกจาก `factory_layout_hierarchy`, เชื่อมกัน (joined) โดย `device_id` — การแยกส่วนนี้คือสิ่งที่ทำให้การ "สลับโดยไม่ต้องเขียนตรรกะข้อมูลโทรมาตรใหม่" ใน §5 เป็นไปได้):

```sql
-- NEW TABLE, proposed, not created by this document
CREATE TABLE public.device_3d_placement (
  device_id     TEXT PRIMARY KEY REFERENCES public.devices(device_id) ON DELETE CASCADE,
  hierarchy_id  INTEGER REFERENCES public.factory_layout_hierarchy(hierarchy_id),
  pos_x         DOUBLE PRECISION NOT NULL,
  pos_y         DOUBLE PRECISION NOT NULL,
  pos_z         DOUBLE PRECISION NOT NULL DEFAULT 0,
  rot_x         DOUBLE PRECISION NOT NULL DEFAULT 0,
  rot_y         DOUBLE PRECISION NOT NULL DEFAULT 0,
  rot_z         DOUBLE PRECISION NOT NULL DEFAULT 0,
  scale         DOUBLE PRECISION NOT NULL DEFAULT 1.0,
  is_simulated  BOOLEAN NOT NULL DEFAULT TRUE,   -- TRUE จนกว่าการสำรวจจริง/การนำเข้า CAD จะตั้งเป็น FALSE
  source        TEXT NOT NULL DEFAULT 'simulated_grid',  -- 'simulated_grid' | 'cad_import' | 'manual_survey'
  updated_at    TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

`is_simulated`/`source` ไม่ได้มีไว้สำหรับตกแต่ง — ผู้ใช้งานตารางนี้ทุกราย (ตัวเรนเดอร์ 3 มิติ, รายงานใดๆ ในอนาคต) สามารถและจะต้องแยกสาขาใน `is_simulated` เพื่อแยกแยะด้วยสายตาอย่างชัดเจนระหว่างการวางตำแหน่งจริงและการวางตำแหน่งทดแทน (เช่น ป้าย "SIMULATED LAYOUT" ในมุมมอง 3 มิติเมื่อใดก็ตามที่เครื่องจักรที่มองเห็นได้มีค่า `is_simulated = TRUE`) เป็นการตอบสนองต่อ §18/§19 เชิงโครงสร้างแทนที่จะเป็นเพียงธรรมเนียมปฏิบัติ

**ข้อมูลตั้งต้น (Seed data) จำลองสำหรับ Task 4.1/4.2** (POC และเฟส 10 เครื่องจักร): รูปแบบตารางที่กำหนดได้ล่วงหน้า (deterministic grid layout) — เช่น `pos_x = (zone_index * 10)`, `pos_y = (machine_index_in_zone * 5)`, `pos_z = 0` — การจัดกลุ่มโซนเหมือนกับ 2D twin ที่ได้รับการพิสูจน์แล้ว (5 โซน, โซนละ 2 เครื่อง) เพียงแต่กำหนดพิกัด 3 มิติปลอมแต่เสถียร เป็นแบบกำหนดได้ล่วงหน้า (ไม่สุ่ม) ดังนั้นการรันข้อมูลตั้งต้นใหม่จะไม่สับเปลี่ยนการจัดวางระหว่างเซสชัน

## 5. การอัปเกรดพิกัดจำลอง → พิกัดจริง โดยไม่ต้องเขียนข้อมูลโทรมาตร/ตรรกะแบบสอบถามใหม่

นี่คือเหตุผลทั้งหมดที่ §3/§4 ถูกแยกตารางออกจาก `devices`/`ldi_data`/`v_ldi_machine_latest_full` โฟลว์ข้อมูลของเรนเดอร์เรอร์ 3 มิติคือแบบสอบถามอิสระ 2 แบบ:

1. **การจัดตำแหน่ง** (เปลี่ยนแปลงยาก): `SELECT device_id, pos_x, pos_y, pos_z, rot_x, rot_y, rot_z, scale, is_simulated FROM device_3d_placement` — นี่เป็นเพียงแบบสอบถามเดียวที่จะเปลี่ยนเมื่อพิกัดจริงมาถึง
2. **สถานะ/โทรมาตร** (เปลี่ยนแปลงบ่อย): ใช้แบบสอบถาม `v_ldi_machine_latest_full` + ตารางการแจ้งเตือน แบบเดียวกับที่ได้พิสูจน์แล้วใน 2D twin — ไม่เปลี่ยนแปลง

ตัวเรนเดอร์ทำการรวมชุดผลลัพธ์ทั้งสองนี้ที่ฝั่งไคลเอ็นต์ (หรือผ่าน API endpoint แบบบางๆ (thin API) ที่ทำหน้าที่รวม) ด้วย `device_id` การย้ายจากพิกัดจำลองไปเป็นพิกัดจริงคือสคริปต์นำเข้าข้อมูลรูปแบบ `data_generators` ที่ใช้ `UPDATE` แถวใน `device_3d_placement` (ตั้งค่า `is_simulated = FALSE`, `source = 'cad_import'` หรือ `'manual_survey'`) — มันไม่เคยไปแตะต้อง `devices`, `ldi_data`, หรือแบบสอบถามใดๆ ใน 2D twin, ไปป์ไลน์การแจ้งเตือน, หรือแดชบอร์ดที่มีอยู่ นี่คือกลไกที่เป็นรูปธรรมที่อยู่เบื้องหลังขั้นตอน "รอ Layout โรงงานจริง → เปลี่ยนจากตำแหน่งจำลอง → ตำแหน่งจริง" ในแผนภาพโฟลว์การทำงานของผู้ใช้

## 6. การรองรับหลายโรงงาน / เครื่องจักรหลายร้อยเครื่อง

สคีมา `factory_layout_hierarchy`/`device_3d_placement` ใน §3/§4 ไม่มีข้อผูกมัดตายตัว (hardcoded) สมมติฐานสำหรับ 2 โรงงาน หรือ 10 เครื่องจักร — `factory_code`/`hierarchy_id` เป็นข้อความอิสระ (free text)/FK, และ `device_3d_placement` เป็นหนึ่งแถวต่อหนึ่ง `device_id` ไม่ว่าจำนวนจะเท่าใด การขยายไปสู่โรงงาน/เครื่องจักรเพิ่มเติมคือเรื่องของการเพิ่มข้อมูล (แนวทางการย้ายข้อมูลใน §5) ไม่ใช่การเปลี่ยนแปลงสคีมา

**เพดานขีดจำกัดจริงที่วัดผลแล้วสำหรับการออกแบบ:** `docs/evidence/SCALE_TEST_2026-08-15.md` (จากงานความน่าเชื่อถือที่ผ่านมาของพื้นที่เก็บข้อมูลนี้) พบว่าสำเร็จ 100% จนถึง 250 อุปกรณ์, การหักเหของความหน่วงเวลา (latency inflection) P95 เกิดขึ้นระหว่าง 100-250 อุปกรณ์ และเกิดข้อผิดพลาดจริงเมื่อเกิน 500 อุปกรณ์ — คอขวดอยู่ที่ Node-RED CPU (118-135%) ไม่ใช่ที่ฐานข้อมูล 3D twin นี้เป็นการเพิ่มโหลดของการอ่านข้อมูลทับลงไปบน TimescaleDB ตัวเดียวกัน ดังนั้นรูปแบบการคิวรีข้อมูล (§13) จะต้องอยู่ในรูปแบบ ค่าล่าสุด/`LIMIT 1` ซึ่งได้พิสูจน์แล้วว่าใช้ทรัพยากรน้อย และจะต้องไม่ไปแย่งโควตาการทำงานที่ไปป์ไลน์การนำเข้าข้อมูลใช้อยู่แล้ว — ทั้งสองนี้ใช้โควตา CPU สองส่วนที่แยกกัน (การนำเข้าข้อมูล เทียบกับ การอ่านหน้าแดชบอร์ด)

## 7. สถานะเครื่องจักรแบบเรียลไทม์, การเตือน, ความคืบหน้าการผลิต, board_no/total_board, MO, การปฏิบัติตามมาตรฐาน

ทั้งหมดนี้ **มีอยู่จริงและได้รับการพิสูจน์แล้ว** — ไม่จำเป็นต้องออกแบบแบบสอบถามใหม่, เพียงแค่หาตัวรับส่งข้อมูลแบบใหม่ (§13) เพื่อดึงข้อมูลเดิมไปไว้ใน Three.js scene แทนหน้าต่าง Canvas:

- สถานะ (0/1/2/3 NO_DATA/IDLE/OK/ALARM): ใช้ตรรกะ CASE เดียวกันกับ Andon panel 1000 และ 2D twin, ไม่มีการเปลี่ยนแปลง
- ความคืบหน้าของบอร์ด: `board_no`/`total_board` ดึงจาก `v_ldi_machine_latest_full`, ไม่มีการเปลี่ยนแปลง
- MO: ใช้วิวเดียวกัน, ไม่มีการเปลี่ยนแปลง
- บริบทการแจ้งเตือน (จำนวน/เจ้าของ/เวลาที่ผ่านไป): รูปแบบการคิวรีเดียวกับ CTEs อย่าง `alarm_raw`/`alarm_ctx` ของ 2D twin, ไม่มีการเปลี่ยนแปลง
- การปฏิบัติตามมาตรฐาน: ใช้การคิวรีแบบ Environmental Compliance แบบเดียวกับที่พิสูจน์แล้วบน Andon/2D-twin (อุณหภูมิ 20-24°C และ ความชื้น 50-60%RH), ไม่มีการเปลี่ยนแปลง

## 8. การเลือกเครื่องจักร และการเจาะลึกไปยังแดชบอร์ด IMS ที่มีอยู่

นำกลไกเดิมที่ใช้ใน 2D twin กลับมาใช้ (จาก Task 3, และได้รับการยืนยันอย่างเป็นอิสระแล้ว): การคลิกเครื่องจักรในภาพแบบ 3D scene จะเป็นการเปิด `/d/ims-ldi-machine-snapshot/set2-machine-snapshot?var-machine_id=<real-id>&var-factory=<real-factory>`, ข้าม `var-mo`/`var-event_time_ms` (ในเซสชันนี้ได้ตรวจสอบตัวแปรตั้งต้นของหน้า Machine Snapshot แล้ว ว่าจะใช้ผลเป็น "เหตุการณ์ล่าสุด, และทุกรายการของ MO" ในกรณีที่ไม่ระบุตัวแปรเหล่านั้นลงไป — ซึ่งเป็นการช่วยหลีกเลี่ยงปัญหาความล่าช้าในเชิงโครงสร้าง) การระบุพิกัดใน 3D ของ Three.js (การแคสต์รังสีตัดผ่านวัตถุเป้าหมายในซีน) เป็นความสามารถมาตรฐานที่รองรับอย่างแพร่หลาย — และไม่เหมือนกับ `links[]` ในกราฟานา คานวาส (Grafana Canvas), ฟังก์ชันนี้สามารถนำไปทดสอบการทำงานกับเว็บเบราว์เซอร์ได้จริง ซึ่งช่วยให้หลุดพ้นจากปัญหา “ไม่มีเครื่องมือให้บนเบราว์เซอร์” ที่เคยกีดกันขั้นตอน click-verification ไม่ให้ตรวจสอบความถูกต้องได้ตอนที่พัฒนางานในรูปแบบ 2D twin เนื่องจากตัวแอพรูปแบบ 3D สามารถทำหน้าเหมือนเว็บเพจปกติได้ ไม่ได้เป็นการแคปหน้าจอออกมาแสดงแบบ Grafana-rendered panel.

## 9. ภาพจำลอง VCP / เครื่อง LDI แบบสามมิติ (3D)

**คำแนะนำสำหรับระยะแรก:** ให้ใช้รูปแบบรูปทรงพารามิเตอร์แบบทั่วไปเป็นตำแหน่งทดแทนอย่างง่าย (กล่องสี่เหลี่ยมติดป้าย, หรือรูปทรงที่มีฝาปิดแบ่งตามชนิดเครื่องจักร), ไม่จำเป็นต้องทำแบบจำลองภาพเสมือน "สมจริง" แบบ 3 มิติที่เป็นตัวแทนเครื่องจักร LDI/VCP

ไม่ว่าจะเป็นไฟล์ CAD, ไฟล์ต้นแบบจากรูปภาพ, หรือเอกสารการออกแบบของผู้ขายสำหรับรูปทรงเครื่องจักรจริง ยังไม่มีใครจัดเตรียมให้ และก็ยังไม่มีให้ใช้งานในตอนนี้ในตัวพื้นที่เก็บข้อมูล การสร้างโมเดลแบบสามมิติที่ "ดูสมจริง" โดยที่ไม่มีภาพอ้างอิงของจริง นับว่าเป็นวิธีการสวมรอยแอบอ้างในลักษณะที่ต้องควรหลีกเลี่ยงเป็นอย่างยิ่งมาตลอดการพัฒนานี้ — กล่องที่เป็นการทดแทนชั่วคราวอย่างชัดเจน พร้อมสีสัน/และไอคอนบ่งชี้ที่นำมาจากสถานะจริงของมัน (ระบบที่มีป้ายสีแบบใช้ 4 สีแบบเดียวกันที่ใช้ในระบบตัวแทนโลกคู่ขนาน 2D, โดยการนำอันที่มีอยู่มาใช้ใหม่และไม่คิดค้นประดิษฐ์ซ้ำอีกรอบ), นับว่าเป็นความถูกต้องแม่นยำในการเปิดเผยตัวตนอย่างที่มันเป็น. ถ้า/และเมื่อไหร่ก็ตามที่มีไฟล์ CAD หรือขนาดโมเดลของเครื่องจักรตัวจริงส่งเข้ามาให้ การสลับรูปแบบรูปทรงไปใช้งานของจริง ก็จะเป็นเพียงขั้นตอนของการแสดงผลภาพเท่านั้น — ซึ่งจะไม่มีการเปลี่ยนแปลงโครงร่างระบบบอกพิกัดตาม §4, หรือโครงร่างระบบข้อมูลสืบค้นตาม §7 ไปด้วย

## 10. การเชื่อมโยง เครื่องจักร-สู่-เครื่องจักร / และขั้นตอนกระบวนการ

**ยังไม่มีข้อมูลที่เป็นความจริงเพื่อสนับสนุนสิ่งนี้เลย ในตอนนี้.** ยังไม่มีทั้งในตารางหรือส่วนการแสดงผล (view) ไหนในสคีมานี้ (schema) ที่ให้รายละเอียดขั้นตอนกระบวนการผลิต, หรือลำดับกระบวนการเส้นทางสำหรับเครื่องจักรในสายการผลิต — เนื่องจากว่า `ldi_data`/`ldi_alarm_log`/`devices` ทำได้แค่การอธิบายการแจ้งเตือนและการโทรมาตรเฉพาะของแต่ละเครื่องจักร, ซึ่งไม่ได้กล่าวถึงความสัมพันธ์ในระหว่างพวกมัน. การสร้างรูปแบบแสดงเส้นเชื่อมกระบวนการในหน้าจำลองแบบระบบ 3 มิติจึงจำเป็นจะต้องมี ทั้งการ (a) มีข้อมูลอ้างอิงขั้นตอนที่ถูกต้องและตรงไปตรงมา ที่ในปัจจุบันนี้มันยังไม่มีด้วยซ้ำ, หรือทางเลือกอีกทางก็คือ (b) นั่งสร้างกระบวนการไหลที่ "ดูเหมือนจะใช่" ด้วยการปรุงแต่งขึ้นมา ซึ่งเป็นการกระทำที่เกินขอบเขตข้อตกลงอย่างเด็ดขาดตามกฎเกณฑ์ของความแน่วแน่ที่เขียนอยู่ในข้อ §0.

**คำแนะนำ:** ให้ยกเลิกความเชื่อมโยงระบบการทำงานระหว่างเครื่องจักรไปก่อน ในตอนช่วงที่มีการเริ่มนำรูปแบบโมเดลจำลองตัวโลกคู่ขนาน 3 มิติมาประยุกต์ใช้ในครั้งแรกเลย หาก/เมื่อใดก็ตามที่เรามีสายป่านกระบวนการที่มีการเชื่อมโยงระบบการทำงานแบบมีอยู่จริง (ตัวอย่างเช่น ข้อมูลใหม่ตาราง `process_routing` ในภายหลัง), การเสริมสร้างการเชื่อมโยงกระบวนการดังกล่าวเข้าด้วยกันก็คงทำได้แบบง่ายๆและตรงประเด็น (ด้วยการวาดรูปขีดเส้นทึบ/ขีดท่อ ระหว่างกัน ในจุดของตัว `device_3d_placement` บนหน้าจอทั้งสอง) — แต่การที่เราหลีกเลี่ยงการจัดรูปแบบให้มันเสียตั้งแต่ในจุดนี้ ก็เพื่อว่าเราจะไม่ได้ต้องไปออกแบบโครงร่างตรรกะใหม่เพื่อมาใช้จำลองสถานการณ์ต่างๆด้วยการปรุงแต่งข้อมูลที่ไม่มีตัวตนให้มันเกิดขึ้น, ซึ่งถือว่าเป็นอะไรที่แย่กว่าการที่เราทิ้งช่องโหว่ส่วนนี้ให้ยังไม่ได้มีการจัดการไปซะ

## 11. มุมกล้อง / ประสบการณ์นำทาง UX สำหรับ C-Level, NOC, และผู้ใช้ระบบ

มีเป้าหมายทั้งหมดสำหรับผู้ชม 3 ประเภท, ด้วยความต้องการจริงที่แตกต่างกันถึง 3 กลุ่ม (แบ่งเซกเมนต์เหมือนการออกแบบในตัว 2D แบบ "มองผ่านครั้งแรกของผู้ระดับบริหาร C-Level เทียบกับ ผู้ปฏิบัติการที่สามารถเจาะลึกส่วนย่อย"):

- **C-Level / การแสดงผ่านคีออสก์ / จอมอนิเตอร์ของฝ่ายดูแลและตรวจสอบเน็ตเวิร์ก (NOC wall)**: คือแบบกล้องฟิกซ์อยู่กับที่, แล้วหมุนแพนโดยอัตโนมัติหรือหยุดตั้งกล้องตายตัวสำหรับมุมมองภาพมุมกว้างโดยรวม (ไม่ว่าจะด้วยมุมที่มองเห็นทั้งหมดจากเหนือจรดล่างหรือจะเป็นในแบบเฉียงมุมที่ระดับ 3/4 เพื่อให้ครอบคลุมโรงงานทั่วๆ), การที่ไม่ต้องทำความเข้าใจการสัมผัสอินเตอร์แอคอะไรเลย — ถือว่าเป็นการจำลองระบบลักษณะเดียวกันกับ 2D twin แบบ "ไม่มีความต้องมีปฎิสัมพันธ์การรับส่งเลย", แบบที่ปรากฏอยู่ในโหมดสแตนด์อโลนของโหมด Andon-style คีออสก์ ไม่มีการแสดงระบบการนำร่องในหน้าของโปรแกรม
- **สำหรับวิศวกรผู้ใช้ / พนักงานควบคุมระบบ, หน้าต่างเซสชันการรับส่งตอบโต้**: ก็จะเป็นโมเดลแบบมาตรฐาน (อย่างพวก Three.js แบบมี `OrbitControls` — โดยใช้คำสั่งแบบสากลก็คือ เช่น ดึงและลากหมุนแพนไปรอบๆ, การคลิกเลื่อนด้วยเม้าส์วีลหรือการหยิกหน้าจอเพื่อย่อ/ขยายในหน้าการซูมมิ่ง, ลากเมาส์คลิกขวาแพนลากยาวซ้าย-ขวาเพื่อเลื่อนสไลด์), พร้อมกับการใช้คีย์ลัดเช่น "เริ่มต้นภาพมุมใหม่" (reset view) และทางลัดแบบ "วาร์ปหรือเคลื่อนร่อนจุดโฟกัสไปหา" (fly to) ไปยังโซนโดยเฉพาะต่อหนึ่งโซน (เช่น แตะป้ายโซน แล้วตัวกล้องจำลองการบันทึกภาพหน้าจอจะหันแพนจุดสนใจหลักกลับไปเน้นให้เห็นทั่วบริเวณสำหรับโซนๆนั้นแบบพอดีเด๊ะ, มันเป็นการหลีกเลี่ยงเรื่องน่าปวดหัวสำหรับการเดินสายในตัวโครงสร้างโรงงานอันกว้างใหญ่แบบที่มีความเสี่ยงสูงว่าจะเกิดการสับสนหลงลืมว่าอยู่จุดใดเมื่อจำเป็นต้องรับคำสั่งทิศทางผ่านหน้าจอเท่านั้น).
- ทั้งสองรูปแบบรับคำสั่งฉากและสคีมาการวางข้อมูลด้วยพื้นฐานเบื้องหลังในข้อมูลชุดจริงเดียวเป๊ะๆกัน — โหมดกล้องที่นำมาใช้คือมีสวิทช์เพื่อกลับด้าน UI แต่ไม่ใช่ทางเลือกสำหรับการจัดโครงสร้างโฟลว์กระแสทางข้อมูลที่ต้องมาทำอะไรให้วุ่นวายเปลี่ยนไปจากเดิม.

## 12. กลยุทธ์ในการรองรับประสิทธิภาพความจุ ระดับจำนวนเครื่องจักร 10, 100, ไปจนถึงจำนวนแบบ 500+ เครื่อง

- **สำหรับเครื่องจักรขนาดจำนวนระดับแบบ 10 เครื่อง** (ฟลีตกลุ่มรายงานเครื่องจักรจริงระดับปัจจุบัน): แทบจะไม่ต้องมีระบบคัดกรองช่วยเหลือเลยแม้แต่น้อย — การพิจารณาสร้างรูปทรง 3 มิติที่เป็นไปตามวัตถุต่อเครื่อง (`Mesh`) ธรรมดาก็เพียงพอแก่การรันแสดงผลด้วยอัตราที่สบายๆเกินพอไปได้อย่างง่ายดาย สำหรับอัตราโครงสร้างมิติแค่นี้.
- **สำหรับเครื่องจักรขนาดจำนวนแบบ 100+ เครื่อง**: ควรจะปรับเปลี่ยนมุมรูปเรขาคณิตด้วยการเรนเดอร์ภาพให้กับบรรดาเครื่องจักร ไปเป็นการปรับโครงสร้างระบบให้เปลี่ยนไปใช้ `THREE.InstancedMesh` แบบมีศูนย์กลางการรองรับร่วมที่ใหญ่ขึ้น (เรียกใช้งานเพื่อการแสดงผลรูปทรงการจำลองพารามิเตอร์ของกลุ่มโมเดลชิ้นงานหลักที่มันเหมือนๆกันได้จบภายในการออกดรอว์คอลสิทธิ์วาดเรนเดอร์ลอตเดียวได้เลย (one draw call), เพื่อที่จะแบ่งสีสันตามความแตกต่างที่ตั้งมาจากสิทธิกำหนดแบบลักษณะต่อหนึ่งอินสแตนซ์ที่กำหนดให้การแปลงร่างวัตถุในระบบข้อมูล) — ซึ่งทั้งหมดนี่ก็ยังเป็นจุดแข็งและเป็นเทคนิคแบบ Three.js ในระดับแบบมาตรฐานทั่วไปที่ไว้สำหรับปรับแก้แบบฟอร์ม "ชุดทำซ้ำปริมาณเยอะๆสำหรับทรงรูปเรขาคณิตขั้นต้น", ใช้งานให้เกิดประโยชน์และสร้างความประยุกต์อย่างเหมาะสมตามข้อ §9 ที่ว่าด้วยคำแนะนำข้อเสนอเรื่องการเลือกนำเรขาคณิตของพารามิเตอร์มาใช้นั่นเอง.
- **สำหรับเครื่องจักรขนาดจำนวนแบบ 500+ เครื่อง**: อ้างอิงตามข้อ §6, นี่คือจุดที่มันพ้นจุดที่จะรับน้ำหนักได้จนเป็นเรื่องใหญ่ไปถึง *ไปป์ไลน์นำเข้าข้อมูล (ingestion pipeline)* เสียแล้ว (ไม่เกี่ยวข้องกับโปรแกรมที่ทำไว้จำลองตัวนี้เลย) — ตัวไปป์ไลน์ต่างหากที่จะออกอาการเริ่มมีสภาวะดรอป หรือไม่ก็ขาดห้วงและเริ่มถูกตั้งตัดสัญญาณตัดขาดอันเนื่องมาจากไทม์เอ้าท์ เมื่อเปรียบเทียบในสภาพอัตราสเกลของความสามารถเชิงรับในตรรกะโลกความเป็นจริงที่ได้มีการรวบรวมทำแบบเก็บหลักฐานเป็นที่เรียบร้อยเอาไว้แล้ว — ด้วยสาเหตุที่ราคาค่าเฉลี่ยในการรับน้ำหนักสำหรับการเรนเดอร์ภาพระบบทวินสามมิติในเวลาที่จะจัดอินสแตนซ์เมชถึงระดับกว่า 500 ตัว ไม่เคยนับว่าเป็นสาเหตุทำให้กระบวนการประมวลผลกลายไปเป็นตัวที่ขัดขวางเกิดคอขวดแต่อย่างใดเลยตามสเกลนี้, แต่อุปสรรคหรือต้นสายปลายเหตุของเรื่องราวตัวจริงก็คือช่องโหว่ความสามารถขัดขวางสำหรับช่วงลำเลียงไปป์ไลน์ดึงและกรองต้นน้ำข้อมูลนี่แหละที่เป็นปัญหาที่ต้องตามแก้กันต่อไปต่างหาก. เมื่อเป็นเช่นนั้นในยามนี้ที่มันยังจำเป็นจะต้องอ้างมาใช้งานจึงมีทางลัดของตัวขจัดข้อมูลฟรุสทรัม (Frustum culling) ไปเป็นอันดับแรกก่อน (ตัว Three.js ก็สามารถทำเรื่องนี้ให้เองเป็นปกติตามอัตโนมัติมาให้อยู่แล้ว) และด้วยหนทางต่อมา ถ้ายังจำเป็น, คือหนทางแบบต้องตั้งรูปแบบอ้างมาลดคุณภาพระยะไกล (LOD - level-of-detail) ซึ่งก็คือการลดและทำการสลับโหมดพรรณนารายละเอียดสำหรับโซนหรือระยะภาพที่จะโดนหลุดขอบสกรีนพอยท์/ทิ้งระยะตกหล่นให้อยู่แบบทิ้งห่างจากมุมกล้องเพื่อไปเป็นไพ่ตายสเตปหนทางปรับสมดุลแบบใบต่อไป ในยามที่พบว่ารายงานระดับชั้นของโปรไฟล์ที่ตรวจสอบตรวจจับชี้แจงสถานการณ์อย่างชัดเจนว่าสภาพยังคงล้าหลังตามความเร็วในการไหลผ่านหน้าปัดไปไม่ได้ — ไม่ต้องเสียเวลาเตรียมการล่วงหน้าเพื่อมานั่งเขียนแบบเอาในที่ตรงนี้ด้วยเพราะว่า มันยังไม่มีพยานหรือมีหลักฐานของความจริงในสมมติฐานถึงอัตรา 500-เครื่องใดๆ เกิดขึ้นจริงหรือเคยบันทึกเอาไว้เผื่อรอดูและปรับปรุงประสิทธิภาพอ้างอิงให้เปรียบเทียบได้ (ก็แค่อ้างอิงมาจากเครื่องจักรปัจจุบัน 10 เครื่องที่เป็นตัวตนจริงกันแค่นั้นเอง).
- มุมมองด้านแบบสอบถามฝั่งคิวรี (Query-side): ชุดสถานะ/การแจ้งเตือน/ข้อมูลชุดคำสั่งแบบสอบถามการผลิต จะยังต้องค้างคงคาและปรับคงรูปแบบที่ตรงกับลักษณะ `LIMIT 1`/`DISTINCT ON` ที่แสดงเฉพาะถึงค่าสถานะอันล่าสุดเสมอตามกระบวนทัศน์แบบเดียวกัน ที่ได้รับใบรับรองมาตรฐานว่าต้นทุนถูกดีแล้วจากส่วนสัดทวินรุ่นโลก 2D ตามข้อ (§7) — อันจะเป็นแรงฉุดรักษาและส่งเสริมคงประคองเรื่องทุนและอัตราบาทราคาค่าตัวการใช้การคิวรีคงรูปแบนราบคงที่อยู่ได้เสมอ ไม่ว่าภาพรายละเอียดส่วนซับซ้อนสเกลงานในสถาปัตยกรรม 3D ก็ไม่สามารถสร้างความยากลำบากเพิ่มเติมต่อส่วนคิวรีข้อมูลดึงผลเหล่านี้ได้.

## 13. ข้อมูล / โครงสร้างสถาปัตยกรรมการตั้งคำถามแบบสอบถาม และการเชื่อมระบบร่วมกับกราฟานา (Grafana integration)

**บริการใหม่: `services/factory-twin-3d/`** (การตั้งชื่อจะต้องจับคู่วางกฎระเบียบแบบเดียวกันตามอย่างที่ใช้กันกับ `services/alarm-api`'s), ภายใต้รูปแบบชุดเดียวกับการร่างวางตามโครงสร้างแบบเดียวกันอย่างแท้จริง:

- แบ็กเอนด์ (Backend): ส่วนของ Express (หรือ Node HTTP server ในระดับย่อส่วนต่ำสุดที่มีคุณสมบัติใกล้เคียง) + `pg`, ให้บริการรองรับได้ (a) หน้าฟรอนต์เอนด์เว็บพอร์ทัลที่เป็นสแตติกโหลดจัดบันเดิล (static Three.js frontend bundle) แบบ Three.js และ (b) ตัวอ่านค่าฐานข้อมูลและให้ผลคืนข้อมูลออกมาเป็นแบบ JSON API สเกลอ่านอย่างเดียวไซส์บางเบาขนาดเล็ก: ส่วน `GET /api/placement` (รวมเอาข้อมูล device_3d_placement + กับ hierarchy แบบจับตาราง join เชื่อมร้อยต่อ), กับ `GET /api/state` (แบบสอบถามเรียกคำสั่งสำหรับค่าข้อมูลสถานะแบบชุดที่ตรงกับช่วงล่าใหม่สุดที่เหมือนกันตามรอยข้อ §7, เปลี่ยนผลลัพธ์เป็นโครงร่างแบบ JSON ในตัวแทนที่จะใช้รูปแบบชุด `table` ในมุมของหน้ากระดานกราฟานาแทน)
- บริการนี้ไม่มีจุดปลายทางแบบการเขียน (write endpoints) — ระบบนี้นับได้ว่าต่างชั้นกันกับการอ้างถึงระบบรับทำบริการคิวรีสำหรับโปรแกรม `alarm-api` (เพราะที่ตัวโน่นนั้นรองรับมีจุดเส้นทางที่บันทึกเขียนฐานข้อมูลจริงผ่านกระบวนทัศน์สำหรับยืนยันแอ็กชัน ack/resolve), แต่โลกแฝดแบบคู่วิกฤตทวินที่ว่านี้เป็นสิทธิ์อนุญาตใช้ได้ในหมวดแค่รับสถานะหรือคือแบบระดับการทำงานเพียงชนิด *โหมดรับข้อมูลสำหรับให้อ่านแต่เพียงอย่างเดียว (read-only)*. สำหรับออปชันที่กะว่าจะมีเพิ่มเติมภายภาคหน้า อย่างเรื่องของระบบคำสั่ง "รับรองผลรายงานทราบผ่านโหมด 3 มิติ (acknowledge from the 3D view)", จะต้องผ่านขั้นตอนทำโครงสร้างเส้นทางที่จะถูกประวิงไปใช้กับการดึงคำสั่งที่ *ถูกยัดส่งใส่ลงไปสู่ในทาง (into)* ทางด้านฝั่งตัว API ระบบแจ้งเตือนเก่าที่เคยมีมาก่อนอย่างตัว `alarm-api`, ไม่ได้นับว่าต้องไปเจียดปันพื้นที่สำหรับเขียนเส้นทางเพื่อทำการรวบรวมเขียนผ่านในฝั่งทางด้านตัวของระบบบริการนี้แต่อย่างใด — เรียกสั้นๆคือ, "อุตส่าห์ดึงมาให้ใช้แล้วก็ใช้ไป, ห้ามลอกสร้างมันขึ้นมาใหม่ก็เป็นพอ".
- ทำการพร็อกซีซ่อนการจราจรเครือข่ายของตัวเองส่งต่อผ่านทราฟฟิกไปในด้าน `proxy/nginx.conf` โดยมีตัวใหม่ที่จุดบล็อกในหน้าปัดพื้นที่ `location /factory-twin-3d/ { auth_request /auth-check; proxy_pass http://factory-twin-3d:<port>/; ... }`, ภายใต้กติกาลอกคัดการทำงานมาจากกระบวนการตัวคุมบล็อกของระบบระเบียบการในฝั่งทราฟฟิกที่มีปรากฏขึ้นมาอยู่ก่อนแล้วในตัว `alarm-api` แบบไม่ให้ผิดเพี้ยนไปแม้แต่น้อยในมิติเชิงรูปแบบเค้าโครง.
- การโพลเช็คเป็นระยะ หรือการผลักข้อความแบบเบาๆจากระบบ WebSocket/SSE (SSE push) ในช่วงขณะยามที่มีสถาะอัพเดทขึ้นมา — เมื่อมองไปให้เห็นแล้วพบว่าจังหวะสอดประสานความเร็วด้วยกฎที่ยืนยันความสามารถอย่างอัตรารอบ "เวลาอัตราคืนชีพความสด: ไว้แค่ `refresh: "5s"`" ที่มีผลตามมาจากงานพัฒนาปรับรุ่นจำลองโลกแฝดรุ่น 2 มิติเก่าก่อนๆนั้น ถือได้ว่าพียงพอแบบพร้อมมูลสมบูรณ์ดีเป็นที่สุดกับการรับส่งการป้อนความถี่รับอัปเดตแบบเรียลไทม์จากศูนย์กลางตัวจริงอยู่ก่อนแล้ว (เพราะที่ฝั่งของกระแสเครื่องรันโมดูลจำลองนั้น มันทำการสุ่มรัวส่งข้อความแบบโพลกระชั้นรัวอัปเดตไปอยู่อย่างต่อเนื่องก็จริง แต่มันไม่ได้มีตัวกรองปรับสปีดหรือปรับรีแฟลชรับส่งในห้วงระดับน้อยกว่าเศษเสี้ยวเสี้ยววินาที หรือ sub-second) ดังนั้น, เมื่อมันตั้งโพลรับข้อมูลของระบบเบสิกบ้านๆเช่นตัวเซนส์แบบคำสั่งอ้างอย่างตัว `setInterval` ที่จ่อหน้าแผงประตูเส้นทางไว้ที่ตัวรับสัญญาณของระบบไปป์ไลน์ในตัว `/api/state` ที่หมั่นตรวจจับกระแสมาป้อนที่รอบระยะทุก 5 วินาทีนั้น มันเป็นอะไรที่เข้าข่ายครบถ้วนเพียงพอและถือว่าตรงกับแนวทางโครงสร้างตามมารยาทแดชบอร์ดที่มีกันมาแต่ก่อนเก่าไปได้แบบเหลือๆแล้วล่ะนะ; ไม่มีความเป็นไปได้ที่จะไปงัดหาเหตุผลยกอ้างให้จำเป็นต้องปั้นโครงการงอกระบบรับผลักรับดันอะไรให้มันใหญ่โตและเลิศหรูกว่าที่เป็นอยู่จากรายการของหลักการและความต้องการที่มีแบบชัดเจนอย่างที่ได้รับและรวบรวมมาแล้วเท่าที่ผ่านมาในตอนนี้.

## 14. เรื่องของความปลอดภัยและกลไกสิทธิควบคุมเพื่อดูแลการเข้าถึงข้อมูลระบบ (Security and access control)

ดึงการนำรูปอ้างอิง `auth_request` เพื่อมาใช้ยืนยันสำหรับพฤติกรรมการรองรับเส้นสายที่มีใช้งานมาอยู่ก่อนตามเก่าในรูปแบบอย่างเป๊ะของ `proxy/nginx.conf` มาอ้างพิจารณาใช้ตามตรงดั่งที่ว่าไว้ใน (§1, §13) — ตัวโมเดลทวินหน้ากระดานปัดโหมดทวินรับสถานการณ์ภาพรุ่นที่อัปแบบ 3D ไปนี้นั้นมันจะดักหมอบหลังประตูรักษาการยืนยันเซสชั่นทางฝั่งทางด่านที่มีส่วนในการเก็บประทับตราพาสคุกกี้ซึ่งก็เป็นอะไรที่ระบบจากทางแดชบอร์ดหลักๆของตัว Grafana session ทั่วไปนั้น ทางฝ่ายโมดูลรับแจ้งเหตุในตัว `alarm-api` เขาก็มีการอ้างเอาส่วนนั้นดึงมาใช้งานอยู่แล้ว, ไม่จำเป็นต้องทำการผูกติดใช้ระบบระเบียบลงล็อกรหัสผ่านให้บัญชีใหม่, และยังไม่จำเป็นจะต้องลากหาสถานที่ระบบลงขุมเก็บระบบสิทธิในตัวบัญชีที่จัดสร้างขึ้นมาอะไรๆใหม่เลยด้วยซ้ำ. ทางด้านฟังก์ชั่นเสริมรักษาการที่มีอย่างตัวชุดรหัสระบบ `GF_SECURITY_COOKIE_SECURE`/`GF_SECURITY_STRICT_TRANSPORT_SECURITY` มีความตั้งมั่นเอาไว้กำหนดตั้งสถานะโหมดค่าฟิล์ดพารามิเตอร์ปัจจุบันอยู่ที่ด่าน `"false"` โดยตรงในพิกัดช่องข้อมูล `docker-compose.yaml` (มีระบุเอาไว้อย่างตรวจสอบความถูกต้องเป็นที่แน่ชัดแล้ว, ในมิติของการเป็นโครงร่างแบบท้องถิ่น/หรือด่านระดับผู้พัฒนาพัฒนาโครงร่างระบบเพื่อการศึกษา local/dev posture) — ข้อกำหนดสภาพแวดล้อมดังกล่าวนี้นั้นถือเป็นนโยบายข้อบังคับแบบร่วมครอบจักรวาลที่มันมีส่วนไปผูกมัดครอบคลุมต่อทั่วทั้งสภาพแวดล้อมตามเงื่อนไขสภาพความเป็นอยู่ที่มีการตั้งกฎกติกาตกลงเอาไว้อยู่เป็นมาตรฐานของทุกระบบงานตามแบบส่วนที่มีอยู่เป็นคลังใหญ่ของระบบรวมอยู่แล้ว, นี่จึงนับว่าไม่ได้เป็นคุณสมบัติจำเพาะที่จะต้องมาเกิดการกำหนดผูกพันขึ้นมาในมิตินี้ของกรอบและตารางที่กำลังมีการลงมีดวาดโครงสร้าง หรือแม้กระทั่งควรจะต้องถูกแก้ไขงัดแงะขึ้นมาจากแค่เหตุผลตามข้อเรียกร้องหรือถูกเปลี่ยนอย่างกะทันหันไปตามใจในทางอำเภอใจแบบตามใครแต่เพียงเฉพาะฝ่ายใดฝ่ายหนึ่งก็คงไม่ใช่เรื่อง; ดังนั้นเราจึงทำการแจ้งหมายให้ติดธงแสดงระบุพิกัดเอาไว้แล้วโดยสอดคล้องอย่างแจ่มแจ้งเพื่อพาดพิงสื่อไปให้คนที่เค้ามีหน้าที่หลักสำหรับไปดูแลเอาเองในส่วนการไปกุมบังเหียนสำหรับตั้งค่าลงล็อคป้องกันแบบฮาร์ดเดนนิ่งสำหรับการวางในขั้นโปรดักชั่นแบบภาคการทำงานจริง (production hardening) เป็นไปในฐานะของกรณีแบบอย่างเดียวกันกับในมาตรฐานของสิ่งที่จะเป็นเงื่อนไขให้กับทุกหน่วยทุกระบบสแต็กตัวบริการไหนๆตัวอื่นๆที่มีตัวมีตนอยู่ในพื้นที่แห่งนี้.

## 15. ในมิติของการชั่งน้ำหนักเปรียบเทียบภาระรับผิดชอบระหว่าง ตัวแทนของส่วนระบบประมวลผลแอปหน้าต่างระบบ Windows แบบดั้งเดิม กับ โมเดลสถาปัตยกรรมแบบหน้าแอปพลิเคชันส่วนที่ใช้งานผ่านทางฝั่งหน้าเว็บไซต์

**สำหรับข้อสรุปแนวทางคำแนะนำ: สิทธิในความเห็นชอบให้กับเพียงโมเดลระบบเว็บแอปพลิเคชันแต่เพียงฝ่ายเดียว, เป็นไปตามความตั้งใจในห้วงระยะนี้.** ตัวขับของฝั่งระบบการพัฒนาหน้าเรนเดอร์เรอร์เอนจินกราฟิก Three.js นั้นจะยึดหลักพึ่งพาประมวลหน้าเบราว์เซอร์/รวมพลผ่านแบบแผนตัว WebGL เป็นแบบโดยตามธรรมชาติแบบมีส่วนในการร่วมสายโดยกำเนิดอยู่แล้ว — แต่ถ้าเลือกให้ไปพัฒนายังเส้นทางสำหรับประมวลผลเพื่อฝั่งทางในรูปแบบหน้าตาแพลตฟอร์มแอปหน้าจอตั้งโต๊ะ (desktop app) ของฝั่ง Windows ไปตามหน้าโจทย์ก็จะมีความจำเป็นในทันทีที่จะต้องเลือกว่า (a) จะยอมเอาส่วนของเว็บแอปเวอร์ชันเดียวนี้นี่แหละไปห่อพันรวมแปลงไปเป็นก้อนบรรจุแบบฝังด้วยโครงชุดครอบแบบระบบ Electron ทับไปอีกชั้น (ซึ่งจะมีความซับซ้อนที่ตามมาเพิ่มขึ้นพ่วงเป็นภาระพะรุงพะรังสำหรับเรื่องความจุกจิกของส่วนแพกเกจที่ซับซ้อนขึ้น/ภาระจังหวะการอัปเดตเวอร์ชั่น/และการดูแลเรื่องความยากง่ายเรื่องตัวกระจายส่งแจกแอป โดยแลกมากับการที่ไม่ได้เกิดมีโควต้าขีดความสามารถสมรรถนะล้ำหน้าอะไรใหม่ที่งอกขึ้นมาเพิ่มมาให้อีกเลย, เนื่องจากยังไงซะแกนมันก็คงวนหนีไม่พ้นการจะไปเป็นแค่ส่วนประสมที่เป็นเบราว์เซอร์ Chromium+Three.js ที่ถูกยำรวมกันเอาไว้ไปในท้ายที่สุดอยู่ดี), หรือตัวเลือกอีกหนทาง (b) ย้ายยกร่างปรับแบบไปให้กลายเป็นแอปบนโครงร่างระดับเครื่องยนต์เรนเดอร์เอนจินเพื่อไปสู่ส่วนประมวลกราฟิกประมวลแบบทรีดีแยกตามสายการประมวลออกแบบมาต่างหากตรงจุดแท้ในระนาบแบบสถาปัตยกรรมตัวเครื่องระดับเนทีฟ (native) ของพื้นบ้านเดิมแท้เลยไปจะดีกว่า (สถาปัตยกรรมแบบตามเครื่องยนต์กราฟิกอย่างของค่ายที่มาจาก Unity/Unreal/หรือฝั่งค่ายชุดเครื่องมือของทางสาย DirectX) — ซึ่งการก้าวกระโดดแบบขยับสเกลขึ้นครั้งนี้เป็นการทุ่มเทเปลี่ยนสเกลชนิดที่สเกลโครงสร้างชุดสัญญาต่อเทคโนโลยีที่จะต้องแลกเปลี่ยนยอมใช้แบบแยกไปนั้นจะขยายตัวมีไซส์บวมออกขยายใหญ่ตามไปมากขึ้นไปจากเดิมที่เคยใช้อยู่นี้แบบเป็นอย่างมาก ในขณะที่เรื่องนี้จะไม่มีปูมหลักฐานเพื่อการยอมรับยืนยันที่สามารถยกอ้างร่องรอยการมาเชื่อมสายร่วมที่เคยสร้างเป็นผลงานต้นแบบใดๆที่มีความสอดคล้องนำมาวางให้สืบความได้จากที่หลงเหลือใดๆในตัวตู้คลังที่เก็บระเบียนนี้ได้อีกเลย, และยังรวมไปจนถึงสภาวะเหตุผลที่จะเอามาหักล้างเพื่อยืนกรานถึงความเป็นข้อเรียกร้องที่แสดงอ้างว่าเป็นตัวความต้องการความรับผิดชอบในระดับที่จะแสดงหาและพิสูจน์ให้ประจักษ์แบบหาหลักฐานเห็นผลได้จริงเป็นชิ้นเป็นอันในตอนนี้ยังไม่มีเลยด้วยซ้ำ (อย่างเกณฑ์กฎตัวชี้วัดหรือก็คือข้อเรียกร้องตามรายการตกลงของเกณฑ์ตรวจรับจากฝั่งตัวแทนของส่วนฝ่ายความต้องการจากผู้ใช้งานมันก็ยังไม่มีเลยที่มีการแจ้งบ่งบอกถึงเรื่องราวชื่อเฉพาะหรือกำหนดที่ถูกเรียกขึ้นมาว่าคือรูปแบบลักษณะเฉพาะที่เป็นจุดอ้างแบบว่าสามารถอ้างแสดงความสามารถของการที่เป็นสิ่งเฉพาะหรือข้อบังคับผูกติดได้แต่เพื่อเฉพาะเจาะจงต้องเป็นระดับบน Windows สกุลแพลตฟอร์มอย่างเดียวเท่านั้นให้ได้มาจริงๆ, อย่างเรื่องของการบังคับจำยอมต้องเรียกร้องหาเพื่อการควบคุมแบบเข้าถึงและอ้างเพื่อควบคุมผ่านขุมพลังของกราฟิกตัวบอร์ด GPU ลึกสุดไปในวงแหวนท้องถิ่นแบบเนทีฟเกินกรอบหรือไกลไปกว่าข้อที่ฝั่งที่สามารถมีให้มอบได้ที่มันเป็นในฝั่งเว็บของเบราว์เซอร์นั้นมันพอที่จะอนุโลมมอบส่วนนี้ให้มาได้, หรือจะพูดให้เห็นภาพก็คือส่วนที่พอจะนำไปช่วยสนับสนุนเพื่อแก้ต่างในส่วนทางนี้ให้เป็นที่เข้าใจมีเหตุผลจนยอมรับในท้ายที่สุดได้). แต่ก็ในกรณีสมมติฐานที่ถ้าว่าหากวันใดวันหนึ่งเรื่องมันจะมีกรณีตัวตนโจทย์ของคำสั่งความต้องการข้อเรียกร้องข้อชี้วัดจากฝั่งของการทำงานสายความเป็นจริงมันจะไปโผล่ปรากฏตัวในสถาปัตยกรรมของการที่จะต้องใช้ข้อแม้ให้มันเป็นแบบฝั่งของตัวเครื่องระดับแบบประมวลแอปเนทีฟบน Windows เอาขึ้นมาเองสำหรับในอนาคต (ซึ่งก็สามารถจะอ้างยกตัวอย่างที่อาจเกิดขึ้นก็เช่น จะต้องเอาไปผูกใช้งานกับเครื่องตั้งป้อมเปิดจอมอนิเตอร์ตัวพีซีรูปแบบอย่างเครื่องคีออสก์สำหรับจอตั้งพื้นเปิดแช่จอติดไว้ตลอดกาล แต่ว่าด้วยเหตุผลที่จะมีตัวชี้วัดสเกลว่ารูปแบบที่ถ้าไปเป็นตัวฝั่งแอปโครงเนทีฟล้วนมันจะสามารถพิสูจน์มีพยานยืนยันแล้วว่าประสิทธิภาพคะแนนดีกว่าในฝั่งของประสิทธิภาพที่ได้จากที่ตัวที่ต้องไปอิงประมวลหน้าเว็บอย่างเบราว์เซอร์หลายขุมแน่ๆ), จุดแบบนั้นมันคือเหตุปัจจัยของการเปิดเรื่องหัวข้อตัดสินใจที่จะแยกพอยน์ใหม่ประเด็นต่างหากให้เป็นเหตุการณ์ในรูปแบบที่ต้องมีการตามแกะรอยประเมินพิจารณาทำกระบวนการการตั้งทิศในลำดับถัดไปที่จะเอามาพิจารณาติดตามต่างหากโดยเจาะจงลงไปมากกว่า, แต่จะต้องไม่ให้มาเป็นมาตรฐานที่เป็นจุดยืนในการผูกมัดหรือมาชี้นำเป็นกรอบตัวแม่บทหลักของเรื่องให้มาใช้สำหรับครอบประเด็นในตอนนี้ที่ว่าเรากำลังที่จะมีส่วนออกแบบในจังหวะเวลานี้.

## 16. ว่าด้วยเรื่องความพร้อมถึงสิทธิการเข้าถึงของโครงสร้างระดับเรื่องความสามารถ (Accessibility) ร่วมกันกับข้อเสนอเรื่องของส่วนกลยุทธ์ตามแบบฉบับความยืดหยุ่นที่ช่วยเรื่องประสิทธิภาพสำหรับการรองรับเพื่อให้ตอบสนองในด้านการแสดงผลตามแบบปรับลดขนาดสเกลสกรีนอัจฉริยะแบบแสดงผลกว้างได้

ในข้อจำกัดในแบบที่สอดคล้องกับเรื่องราวข้อเท็จจริงแบบสัตย์ซื่อ, และไม่ได้พยายามทำเป็นตีเนียนพยายามข้ามไม่พูดกล่าวถึงหรือเพิกเฉยแบบไม่มีใครสนใจแต่อย่างใด: ในตัวส่วนของการจำลองเพื่อรับหน้าแสดงผลมิติรุ่นแบบที่เรนเดอร์ความจัดเรียงในฉากที่เป็นสเกลรูปแบบเป็นเว็บสามมิติแบบทรีดีฉาก 3D WebGL มันถือเป็นสิ่งที่มีรูปแบบและมีความพร้อมด้วยโครงสร้างข้อจำกัดที่จะสามารถรับเข้าคู่พร้อมกับเรื่องราวที่จะไปใช้สิทธิของรูปแบบช่วยซัพพอร์ตกติกาในเรื่องเครื่องมือของการรับอ่านอ่านป้อนข้อมูลแบบ (screen-reader-accessible) คือเรื่องของระบบคนพิการให้ดียากได้มากกว่าของแบบในความจงใจจากตัวส่วนแผงกราฟานารุ่นดั้งเดิม (ที่ก็คือรูปแบบของการวาดจำลองระดับสองมิติแผงคู่ 2D twin (ซึ่งอย่างน้อยที่สุดมันก็คือจะยังมีฐานข้อระบบชุดที่ได้เปรียบด้วยพื้นฐานชุดที่อยู่ในโครงสร้างพื้นหลักแบบ DOM ที่เป็นพาร์ทข้อมูลตัวอักษรเชื่อมโยงตรงขนานแบบ DOM-adjacent text elements ที่ทางค่าย Grafana เขายังจะมีความพร้อมที่จะเอาไปผูกให้ความช่วยเหลือแสดงออกมาได้อยู่)). สำหรับมาตรการแบบรูปธรรมสำหรับการเข้าไปร่วมสนับสนุนจัดการช่วยประนีประนอมในโครงร่างนี้, แทนที่จะเป็นการอ้างมาแค่การบอกปัดเรื่องว่าคือตัวชูโรงที่เป็นแค่ในสิทธิ์เรียกร้องสมบูรณ์เทียบระดับความเป็นระบบของการเข้าถึงที่ทำไว้เต็มสมบูรณ์ที่พร้อมสำหรับคนกลุ่มคนทุกประเภทเท่านั้น:

- ในข้อมูลทุกๆส่วนที่เป็นระบบแจ้งแบบแจ้งค่าส่วนเครื่องแต่ละเครื่องแต่ละตัวตามสิทธิ์อย่างของส่วนรายละเอียดพวก ค่าของสถานะป้ายชื่อจริง/ส่วนเลเบล/สัญญาณกระตุ้นการแจ้งเตือนต่างๆนั้นจะสามารถเข้าถึงได้เพื่อเป็นส่วนข้อมูล "นอกจากนี้ (ALSO available)" ไปด้วยในรูปแบบการโชว์ให้เปิดไปตามแนวทางลิสต์ด้านแถบเมนูในด้านตัวระบบแสดงแถบด้านข้างที่เป็นแผง HTML ง่ายๆ/และแบบมุมมองภาพการดูที่ลิสต์อ่านแบบหน้าเรียงแถว (มันเป็นรายการคิวรีข้อมูลดึงชนิดเดียวกัน, เพียงแค่เปลี่ยนสลับเพื่อนำแบบการเรนเดอร์ในมุมที่ไม่ใช่ทรีดีภาพลึกแทน) ที่ถูกปรับให้สลับมาขึ้นโชว์หน้าข้างหน้ามุมข้างซ้อนแสดงขนานไปประชันอยู่ข้างตัวคู่พร้อมด้วยในตัวการจำลองหน้าเรนเดอร์ในมุมเรนเดอร์ฉาก 3D ได้ด้วย — สิ่งๆนี้นี่คือส่วนที่เป็นข้อเท็จจริงที่ปรากฏว่านี่คือรูปแบบสำหรับการเอาไปใช้งานในส่วนที่จะนำไปใช้รับหน้าโหมดที่ถดถอยและกลับไปเป็นแบบลดระดับมาใช้หน้าตาการรองรับที่สามารถแสดงฟอลแบ็กสำรองในเรื่องโครงสร้างช่วยรับหน้าเรื่องสิทธิของการเข้าถึงจริง (accessibility fallback) ซึ่งมันเป็นแนวคิดจริงที่ไม่ใช่ว่าจู่ๆจะไปงัดอ้างแค่ว่าคือตัวเอาไปปรับปะและผูกเอาไว้แปะป้ายที่ถูกงัดนำมาสวมไปใส่ดื้อๆในส่วนของการที่ถูกนำมาพะติดที่แบบขอไปทีเพียงแค่แบบภายหลังจากที่มานำมาใช้ในหน้าส่วนเพื่อของตัวฟังก์ชันดูภาพในลักษณะบน 3D เอาดื้อๆตามเท่านั้น.
- การเอาชุดสี (Color) มาใช้นั้นจะไม่ได้เป็นแค่วิธีการที่จะให้เป็นในมุมของตัวแสดงผลการบ่งบอกตัวส่งสัญญาณที่สิทธิเด็ดขาดตัวแรกตัวเดียวเลยเด็ดขาด (ถือเป็นกฎพื้นมาตรฐานลักษณะแบบฉบับแนวทางความผูกพันของเดียวกันตามรอยตามสิ่งที่หน้าแฝดคู่ 2D twin นั้นเขามีการยึดถือเอาไว้อยู่เป็นทุนเดิมกันอยู่แล้ว: เอาตัวสเตปของสัญญาณสี + มาทำงานจับมาให้สอดรับด้วยร่วมคู่ไปในทิศทางของรูปแบบตัวไอคอนที่จะมีรูปทรงของสิทธิร่วม (color + icon shape together), แทนที่จะต้องมาคอยต้องเพ่งเอาที่ตัวของผลตามสีที่ออกมาแต่ลำพังอย่างเดียวตามเท่านั้น) — ซึ่งจะลากส่งถ่ายทอดส่งทอดต่อมาได้เอาไปปรับผูกใช้ประยุกต์ไปยังในรูปแบบโครงสร้างฝั่งสิทธิมุมของตัวหน้าโหมดแบบหน้าสามมิติ หรือว่า 3D view ด้วยการคงตัวรูปแบบดั้งเดิมให้มาเป็นในโครงสร้าง สีสัญญาณ (color) + เสริมทับข้อความติดป้ายของส่วนที่เป็นฉลากชื่อป้ายบอกเลเบลแสดง (label text) + และออปชั่นฟังก์ชันเสริมที่มีความคู่สิทธิ์เป็นตัวเลือกตาม (optionally) ด้วยการใช้เป็นแบบภาพสไปรต์ตัวไอคอน (icon sprite).
- เรื่องของคุณสมบัติในด้านที่จะมีความหยืดหยุ่นเรื่องหน้าการแสดงการออกแบบที่ตอบรับได้ (Responsive): พอเมื่อความยาวพิกัดที่ต่ำลากลงเกินกว่าหรือก็คือกว้างที่ขีดขั้นของตัวฐานพิกัดขีดจำกัดความกว้างของหน้าจอต่ำกว่าความกว้าง (width) ต่ำสุดขั้นของการใช้งานระดับที่มีใช้งานเป็นหลักจริง (เช่นบน หน้าจอฝั่งโมบายตัวโทรศัพท์ถือ), โครงร่างของระบบสิทธิก็จะทำฟอลแบ็กลดระดับลดตัวเองยอมอ่อนข้อเพื่อทำการผลักเปลี่ยนให้ตัวมันปรับหันเพื่อโชว์ออกมาอย่างรวบรัดจำนนลดรูปให้เหลือแบบแค่เพื่อไปเหลือโชว์หน้าในรูปแบบที่มีมุมการมองเป็นแค่หน้าดูธรรมดาสุดแบบเรียงทื่อๆที่ตัวการดูลิสต์มุมการมองในแถบลำตัวแท่งด้านข้างแต่เพียงแค่นั้น (plain list/sidebar view) โดยตัวเลือกที่จะยอมไม่เอาความทู่ซี้พยายามรบเร้าหรืองัดดันทุรังไปเพื่อการดิ้นรนจัดฉากที่แสดงหน้าจำลองการตั้งภาพสำหรับหน้ามุมโรงงานแบบสามมิติแต่อย่างใดกับการที่จะไปบีบรัดแบบจอสัมผัสสกรีนไซต์กระจิริดที่ทั้งเล็กและไม่มีช่องไฟให้มองเห็นอะไรได้ถนัดตาเลย — โหมด 3 มิติที่เป็นภาพบรรยากาศตัวโรงงานจำลองนั้นโดยข้อเท็จจริงในพฤติการณ์ไม่ใช่รูปแบบการตั้งมุมภาพพิกัดสำหรับจะไปเป็นตัวเป้าที่ต้องรองรับที่จะเอาไปย่อจัดยัดสำหรับให้ไปอิงตามส่วนหน้าจอติดต่อเป้าของโทรศัพท์แบบปกติ, จงอย่าเสแสร้งเลยว่าจะพยายามไปเสกจัดฉากแสร้งทำให้มันเป็นแบบที่สามารถทำแบบนั้นได้.

## 17. วิธีที่แผนผังโรงงานจริงในอนาคตจะถูกนำเข้า/และบำรุงรักษา

มีเส้นทางตามที่สิทธิที่สามารถได้มีโอกาสในเส้นทางการอิงและจัดได้เป็นรูปแบบข้อมูลแห่งความเป็นจริงถึง 3 ช่องทาง, จัดเรียงลำดับไปตามหลักเกณฑ์ตัวชี้วัดที่มีน้ำหนักสิทธิ์ความเป็นไปได้มากสุดถึงความสมจริง โดยพิจารณาในขณะจากที่ว่าปัจจุบันนี้นั้นอะไรๆมันก็ยังคงเป็นในสภาพที่เรียกว่ายังไม่มีแม้แต่อะไรเกิดมีตัวมีตนกันขึ้นมาเลย:

1. **การสำรวจโดยการจดลงด้วยคนแบบสำรวจมือล้วนๆ (Manual survey entry)**: วิธีการแสนดั้งเดิมคลาสสิกที่อาศัยช่องกรอกใส่แบบบันทึกด้วยตารางสเปรดชีตง่ายๆของคนคุมฐานแล้วอัปเดทโยนก้อนดึงค่าข้อมูลแบนราบ/หน้าตารางการทำงานของสเปรดชีตสำหรับดึงเพื่อเป็นช่องทางบันทึกเขียนค่านำเข้าในค่าทราฟฟิกตรงยิงเข้าในสิทธิ์ไปทางช่องตารางส่วน `device_3d_placement` (§4) ได้โดยตรง — แบบแผนนับเป็นระดับใช้แรงใช้ค่าเหนื่อยได้ระดับแสนต่ำสุด, และก็เป็นโอกาสสูงที่สูตรนี้จะสิทธิที่จะรับโอกาสความน่าจะเป็นการเป็นเส้นทางแรกๆสำหรับโหมดข้อมูลตัวจริงแรกที่สุดเลย, เป็นแบบแผนที่ไม่ได้ที่จะต้องไปเรียกร้องระบบช่วยทูลของเครื่องมือในกระบวนการระบบของ CAD แต่อย่างใดเลยด้วย.
2. **ระบบดึงข้อมูลส่งออกแบบจากกระบวนทัศน์การดึงอิมพอร์ตข้อมูลที่วาดจาก CAD/รูปแบบไฟล์จากหน้าแปลนแปลนอาคาร (CAD/floor-plan import)**: ในเหตุการณ์ที่ถ้าหากมีไฟล์ CAD ทางสถาปัตยกรรมตัวจริง (พวกมาตรฐานในไฟล์แบบ DWG/DXF/IFC) มันปรากฏตัวเป็นไฟล์ให้มาได้ให้ได้ใช้งานพร้อมกันเมื่อใดก็ตามละก็, เมื่อถึงเวลานั้นมันจะใช้ตัวช่วยที่เป็นส่วนดึงตัวแกะข้อมูลครั้งเดียวที่เป็นสคริปต์ตัวสกัดแบบวันไทม์จะถูกงัดออกมาทำงานแยกชำแหละเพื่อถอดรูปร่างพิกัดที่แกะได้ข้อมูลค่าเป็นตัวแทนของแนวอิงจริงตามพิกัดแนวแกนแนวค่า x/y แบบเป็นข้อมูลรายตามเป้าตัวเครื่องจักรต่อตัวได้ (ที่มีความเชื่อมผูกพิกัดไว้รับกันตามข้อมูลในรหัสของแท็กระบุป้ายข้อมูลจริง/ของอุปกรณ์ใน `device_id` อันเป็นจุดตัดอ้างอิงรอยร้อยไขว้ข้ามจับคู่ (cross-reference) ตรงจุดพิกัดนี่แหละที่ทีมผู้ดูแลแผนกอาคารจะต้องเอามาประเคนเตรียมแจกจ่ายระบุชี้มาให้) เข้ามายัดดึงเพื่อนำไปใส่ลงยังสเกลเดียวกันตามตัวพิกัดฐานในรูปแบบเดิมในโครงสร้างในรูปลักษณ์สคีมาของในตัวที่เป็นพิกัดตัวฐานที่อ้างข้อมูลสิทธิเดียวกับตัว `device_3d_placement` ตารางเดียวกันนั้น — ถือว่าเป็นในโครงร่างเดียวที่ตรงใช้ตัวสคีมาเดียวกันเป๊ะ, ที่จะแตกต่างกันก็คงแค่ดึงสับค่ามาจากในคอลัมน์จากด่านหน้าจุดกำเนิดส่วนพิกัดค่าอย่างที่ตัวแปรฝั่งในช่องที่รับจุดต้นทางในจุดรับต้นขั้วอย่างตรงที่ตัว `source` เพียงแค่เท่านั้นเอง.
3. **การเข้าโหมดเพื่อเข้าไปทำหน้าที่บำรุงรักษาอย่างต่อเนื่อง (Ongoing maintenance)**: ที่จุดคอลัมน์ของข้อมูล `updated_at` + ตามด้วยของฝั่งชุดอิงตำแหน่งคอลัมน์ของทาง `source` (§4) สิ่งเหล่านี้นั้นมีความหมายก็คือ การเข้ามาสำรวจปรับปรุงหรือการสำรวจหน้างานแกะรอยแก้ซ้ำตรวจสอบปรับรอบพิกัดซ้ำ/หรือมีจุดที่ต้องการรันทำการแก้เปลี่ยนใหม่ มันเป็นเพียงก็แค่การสับเปลี่ยนด้วยการทำหน้าที่การ `UPDATE` แค่นั้นเอง, ด้วยรูปแบบการแก้ไขที่จะไม่จำยอมที่จะรักษาลู่รอยบันทึกหน้าแถบประวัติบันทึกการแก้การลบ (history) หรือประวัติในหน้าทับหน้าที่มีอยู่ในของแถวแบบตัวที่มันมีอยู่นี้แต่เดิมให้เก็บมาอีกต่อไปเลย เว้นเสียแต่เพียงว่าจะมีเรื่องที่โผล่ว่ามีเคสตัวความต้องการอันเกิดเป็นข้อเรียกร้องมาจากทางคำสั่งหน้าความต้องการตัวไหนๆในอนาคตที่เจาะจงเรียกร้องเอาว่าจะมีอยากขอดูเรื่องของข้อมูลประวัติในระเบียนของการเปลี่ยนแปลงการแก้ไขพิกัดข้อมูลจัดวางนี่แหละ (ที่ตอนนี้ยังไม่ได้มีการออกแบบมาเตรียมรอรับไว้ที่ตรงที่นี้นะ, ด้วยเพราะยังไร้เหตุผลจำเป็นตัวรับของแบบกรณีเคสที่จะต้องใช้จริงที่ว่านั้นในเวลานี้ — ไม่ต้องมาทำเกินแบบที่ YAGNI อ้างหลักไว้).

จะเห็นว่าไม่มีโครงร่างเส้นทางในที่นี้นั้น ได้ถูกมาออกแบบวางไว้ว่าจะเป็นกลไกในระดับที่ต้องไปเป็นหน้างานของการประมวลผลดึงอัตโนมัติ/ที่มีคุณสมบัติติดตั้งเครื่องค้นหาที่บอกและค้นหาสถานที่ระบบที่สามารถตามแกะรอยค้นหาที่ตั้งพิกัดได้ด้วยตัวของมันเอง (ตัวอย่างเช่น อย่างไม่มีระบบพิกัดจำแนกชี้จับตามความสามารถจุดของพวก BLE/UWB แบบหาพิกัดตำแหน่งชี้จุดได้เรียลไทม์) — ไม่มีจุดใดหรือส่วนใดๆในเรื่องนี้สำหรับหน้าสถาปัตยกรรมตัวจริงที่เป็นโครงการระบบพื้นฐานแบบฉบับความจริงแท้ของที่ตัวรวบรวมตัวที่รวบรวมเรปโป (repo) นี้ ที่จะชี้เป็นเชิงแนะนำได้ว่าของพวกพรรค์ที่มีในเชิงนี้นั้นมันมีติดตั้งมาให้พร้อมใช้แล้วหรือมันถูกบรรจุเตรียมแพลนเอาไว้, แล้วการมานั่งนึกเสกสร้างประดิษฐ์เอาปั้นฝันความสามารถพวกนี้นั้น มันก็คือตัวแทนตรงเป๊ะของตัวอย่างของคำว่าระบบคุณสมบัติในพิกัดพวกระดับจำพวกเพื่อเก็งกำไรคาดการณ์ฟีเจอร์ในอากาศที่ว่า ซึ่งเรื่องเอกสารนี้นั้นตามกรอบกฎการพิจารณาสิทธิข้อที่ว่าคือข้อที่ไม่สามารถประนีประนอมใดๆได้เลยในตัวของมันเองของบทนี้ (§0) ก็ถือว่าเป็นตัวที่ออกมาตั้งกฎปิดประตูกีดกันชี้ชัดเตะสกัดห้ามเอาไว้เองหมดแล้ว.

## 19. ไม่มีข้อที่ว่าด้วยการใช้เพื่อเอาในเรื่องของระบบพิกัดอิงทางกายภาพที่ใช้เอามาจากของข้อมูลที่ประดิษฐ์ปรุงแต่งแบบหลอกๆ (fabricated physical coordinates) แต่อย่างใดทั้งสิ้น — มันนับคือข้อตกลงและเงื่อนไขบทระเบียบของข้อบังคับอย่างเด็ดขาดที่เอามายึดถือไว้ในการใช้ช่วงเฟสนี้เลย

เป็นการประกาศย้ำแสดงที่ระบุถึงแบบซ้ำแบบเพื่อให้ตรงตัวตรงไปตรงมาเนื่องจากสาเหตุเพราะว่ามันรับน้ำหนักถึงเสาหลักสำคัญของการพยุงส่วนโครงนี้เอาไว้ทั้งหมดเลยทีเดียว: ไม่มีสิทธิในส่วนสิ่งก่อสร้างสถาปัตยกรรมหรืออะไรก็ช่างที่ถูกจัดทำชูสร้างประดิษฐ์กันขึ้นมาใหม่ภายใต้พิกัดหรือกรอบของข้อบังคับตัวกฎสถาปัตยกรรมการออกแบบนี้จะได้รับอนุมัติว่ายอมปล่อยผีให้มันสามารถแสดงให้เห็นหรือโชว์รูปลักษณ์ข้อมูลของรูปแบบระบบในตัวพิกัดจัดวางที่มีลักษณะเป็นการจัดทำแบบเพื่อสิทธิเป็นการแค่ของระดับอ้างที่ทำมาเพื่อการจำลองเพียงเท่านั้นว่าเหมือนดั่งว่าเป็นสิทธิ์ที่ทำมาใช้ว่าเป็นเสมือนประหนึ่งว่าพวกมันมีลักษณะเป็นเช่นดั่งของจริงไปเสียแบบนั้น. ในชิ้นส่วนระดับมุมมองภาพหน้าเรนเดอร์เรอร์พื้นผิวในการจัดแสดงผลใดๆก็ตามที่มีส่วนไปนำผลการโชว์มาด้วยการเรียกดูส่วนที่ชี้ระบุในส่วนค่าข้อมูลตารางชุดตัว `device_3d_placement` ก็จะต้องมีระบบในหน้าที่ตรวจสอบที่ตรงกับ `is_simulated` ด้วยในตัวด้วยเสมอและยังจะต้องเป็นจุดชี้ที่ต้องคอยต้องโชว์เพื่อช่วยให้ความสว่างแสดงให้มีข้อสังเกตจุดชี้ในแบบปรากฏขึ้นเตะตาส่งบอกถึงชี้ว่าตำแหน่งจุดบอกหรือจุดสเกลพวกจุดอ้างของการแสดงการจัดวางในพิกัดการจำลองตัวนี้ให้เห็นชัด (ตัวอย่างคือแบบ แถบแบนเนอร์, โชว์ด้วยการติดป้ายเลเบล, โชว์แสดงผ่านป้ายชี้ความแตกต่างตัวรูปแบบการเรนเดอร์ในมุมสไตล์ที่ชี้เป้าถึงความชัดเจนตรงนี้ด้วยความกระจ่างชัดเจน) แบบต้องโผล่ไปโชว์เมื่อไหร่ตอนใดเวลาไหนก็ได้ที่มันดันไปพบว่าตรงนี้เกิดว่ากลายเป็นสิทธิที่เป็นค่าที่จริงแล้วขึ้นมา (true). นี่แหละสิทธิที่ว่าเรื่องถึงการดึงเอาสิ่งพวกนี้ในฐานะสิทธิเพื่อเอามาทำหน้าที่ในการเป็นหน้าเป็นตาเอามาเป็นของพวกตัวระบบเกณฑ์ตกลงที่ใช้เป็นเป้าหมายในด้านสำหรับเพื่อพิจารณาเป็นระบบทดสอบตรวจรับการใช้งาน (§20), มันไม่ใช่รูปแบบอ้างพิกัดที่เอามาบอกว่าจะเป็นแค่สิทธิตามระดับเจตนาดีที่แค่กล่าวมาเฉยๆแต่กลับไม่ใช้พิกัดทดสอบดักไว้จริงๆจังๆ.

## 20. กรอบพิจารณาเรื่องกฎเกณฑ์การยอมรับข้อตกลงตามมาตรฐานและระบบกระบวนทัศน์สำหรับในตัวแผนย้ายรับถ่ายโอนระบบการประเมิน

**พิกัดเกณฑ์เป้าหมายการตอบรับสำหรับอ้างพิจารณาสำหรับแผนโครงการพัฒนาหน้า Task 4.1 (ในมิติรุ่นสำหรับ 1-เครื่องตามแผนรุ่นรับเป้าเป็นจุดการรันทดสอบ POC รุ่นสามมิติ):**

- [ ] มีตัวตนจริงของอุปกรณ์ 1 ชิ้นในรูปแบบที่เป็นความเป็นจริง (ด้วยชุดรูปแบบสถานะข้อมูล/หรือหน้าข้อมูลชุดของอ้างพิกัดจากตัว board_no/แล้วก็ชุดจากตัวที่เป็นของ mo/และการเตือนข้อมูลจริงทั้งหมด, คิวรีมาดูโชว์ถ่ายมาเป็นดึงสดล้วน) มีภาพแสดงแบบรับค่าพิกัดมาแบบมีเรนเดอร์บนโครงร่างหน้าจอสามมิติจากในตัวฉากเรนเดอร์เอนจิน Three.js ที่จุดพิกัดในจุดบอกที่เป็นแบบจุดของเป้าการจำลอง, แต่ต้องเป็นระบบพิกัดที่โชว์ติดป้ายมาแบบอย่างชัดว่านี่สิทธิพิกัดที่มาเพื่อแสดงในฐานะว่าเป้าเพื่อจำลองมา (simulated).
- [ ] เมื่อกดไปแตะที่อิงกับจุดตามพิกัดของเครื่องเครื่องนั้นก็จะนำตัวไปปรากฏสู่เปิดขึ้นไปยังหน้าแผงระบบกระดานของตัวหน้าตัวจับเพื่อแสดงหน้าจอของฟังก์ชันเป้าของการเจาะสิทธิที่เป็นของระบบ Snapshot เครื่องจักรระดับเจาะจงลึกในหน้าแบบตัวจริงที่มีรายละเอียดครบตรงสอดรับพิกัดถูกต้องทุกประการกับ `var-machine_id`/`var-factory` (ครั้งนี้จะสามารถใช้สิทธิตรวจสอบความถูกต้องที่ทำจากตัวเบราว์เซอร์ได้เลย, แทนที่จะต้องเป็นแบบอย่างรุ่นในพิกัดกราฟิกตัว 2D ของรุ่นก่อนใน Canvas — ซึ่งก็ให้ไปหาที่อ้างอิงรอยอธิบายอ่านเพิ่มพิกัดตามเนื้อความตามที่ว่ามาใน (§8)).
- [ ] มีสิทธิยืนยันให้ `services/factory-twin-3d/` พิกัดโผล่เปิดมีอยู่จริงได้ด้วยในที่แห่งนี้, โดยจะเป็นแบบต้องลอดช่องพร็อกซีโผล่ผ่านออกมาโดยด่านจุดจากตัวของ nginx โดยที่จะยังถือระเบียบที่คงระบบที่มีสิทธิอยู่ในฐานะด่านที่มีหน้าประตูของการมีช่องรักษาประตูป้อนตรวจด้วยระเบียบประตูรั้วที่เป็นด่านพาสที่มีกฎด่านของ `auth_request` ที่เป็นรั้วด่านเกณฑ์ด้วยกฎเหมือนกันชุดแบบเป๊ะๆอย่างระบบของที่มีหน้าในอย่างตัวของแผงฟังก์ชันของประตูที่ชื่อรุ่นคือ `alarm-api`.
- [ ] ห้ามเด็ดขาดและต้องตรวจสอบจนแน่ใจว่าจะไม่มีระบบและพิกัดตัวโครงแดชบอร์ด/บริการเก่าอันไหนที่มีแต่ดั้งแต่เดิมถูกแก้ไขโดยพละการ.

**พิกัดเกณฑ์เป้าหมายการตอบรับสำหรับอ้างพิจารณาสำหรับแผนโครงการพัฒนาหน้า Task 4.2 (รุ่นพัฒนาชุดขนาดแบบสเกลชุดฟลีตแฝด 3 มิติ ขนาด 10-เครื่องจักร):**

- [ ] ทุกเครื่องรวมทั้งหมด 10 เครื่องล้วนเป็นต้องเป็นข้อมูลรับเครื่องจักรที่มีอยู่ตัวเป็นๆในตัวเครื่องจักรแบบสเกลตัวจริงแท้, ในหน้าสเกลหน้าจัดหน้าพิกัดจริงที่ต้องเรียงมาใน 5 โซนพื้นที่ที่อยู่ในหน้าสเกลอิงอ้างของที่พื้นที่นั้นมี (ในตัวอิงพิกัดอิงของ `factory_layout_hierarchy` ที่เกิดมามีเมล็ดพันธุ์ฐานมาจากรากแก้วเมล็ดต้นแบบของพิกัดพยานของที่เกิดดึงมาจากสิทธิพื้นที่ `devices.location` โดยแท้ของจริงเพียวๆ), แต่ว่าจะมีสถานะจุดอ้างสำหรับการตั้งวางจัดอยู่แต่ในพิกัดการจัดวางเป็นฉากหน้าการจัดวางจำลองที่ต้องจำลองไว้โชว์อยู่ในภายในแต่ละในโหนดของเขตโซนพื้นที่แต่ละอันเองไป.
- [ ] พิกัดหน้ากระดานตัวข้อมูลของสภาวะอ้างหน้าแบบตัวรับจุดชุดของด้านตัวชุดพิกัดสถานะ/ตัวอ้างการประมวลแจ้งเตือน/ด้านตัวของการรับหน้าฟิกเกอร์สเกลการคิวรีข้อมูลที่ใช้ไปกับการอิงผลด้านการผลิต จะเป็นความพิกัดอ้างที่ตรงความรับตามตรงกันในมิติสิทธิของสเกลรูปแบบมาตรฐานคิวรีสดในฉากแบบสเกลเดียวกันเป๊ะตามชุดของที่มีในด้านโครงของรูปแบบ 2D twin แบบเป๊ะเป๊ะ (คือความรันในแบบมีสิทธิยืนได้บนฐานที่เป็นตรงดิ่งอิงของความถูกต้องระดับแบบค่าในขณะที่เรียลไทม์ (real-time correctness), ที่สามารถเรียกเป็นข้อเท็จจริงมาตรวจสอบได้ยืนยันซ้ำแบบเป็นหน้าเป็นอิสระ).
- [ ] ตัวกรอบดึงภาพแบนเนอร์ที่บอกความหมายที่เป็นเครื่องหมายป้ายของการเตือนการบอกเตือนที่ทำเรื่องระบุเค้าโครงตัวเค้าโครงฉากจุดสถานการณ์ของฉากการจำลองจะต้องปะโชว์เพื่อให้สามารถมีพยานภาพพิกัดเพื่อให้ประจักษ์มองเห็นชัดมีพิกัดตามหน้าข้อแจ้งระบุย้ำกติกาตามกฎรับสิทธิตาม §19.

**พิกัดเกณฑ์เป้าหมายการตอบรับสำหรับอ้างพิจารณาสำหรับแผนโครงการพัฒนาหน้า Task 4.3 (พิกัดทดสอบโหมดรันรอบเช็คสิทธิ์แบบวัดเพื่อทดสอบในเรื่องสิทธิทดสอบประสิทธิภาพ):**

- [ ] มีผลประเมินด้วยคะแนนของพิกัดอัตราแบบประมวลการวัดสิทธิด้านที่รับตัวประมวลอิงตามประสิทธิภาพประมวลแบบของภาพเรนเดอร์ในสเกลรอบของรอบภาพอัตราของภาพเฟรม/ตามหน้าสิทธิผลพิกัดเวลาของเฟรมในสภาพเวลาที่จริง (real render/frame-time measurement) ที่รับเครื่องจำลองด้วยเครื่องจักรจริง 10 เครื่อง (ที่เป็นขุมฟลีตทัพข้อมูลการจัดตั้งเครื่องมีอยู่แล้วจริงๆนี้แหละ) เป็นไปตามจุดควบคู่กับการที่จะต้องรับหน้าที่ของสิทธิจัดบวกคะแนนเพิ่มให้กับผลรอบเทสอ้างสำหรับการทำหน้าเป็นชุดบทเทสที่จัดฉากเพื่อเอามาใช้ทดสอบคะแนนเป้าตามคะแนนรับวัดสิทธิขยายอัตราการทวีสเกล (synthetic scale test) ในสเกลทดสอบเป้าเครื่องจักรแบบพิกัดที่ระดับจำลองระดับที่ระดับถึง 100/กับคะแนนระดับทวีถึงพิกัดขยายไป 500 เครื่องไปเลย (โดยอาศัยจุดความสอดคล้องตามหน้าหลักแฝงยุทธศาสตร์กลยุทธ์เทคนิคที่ถูกแฝงซ่อนเอาไว้ให้รองรับใน (§12) อันเป็นการดึงสเกลวิชาตามตระกูลพวกระบบ `InstancedMesh`) — มีการรองรับจากการบันทึกพิสูจน์การทดสอบแบบตัววัดมีหลักฐานที่มีการวัดคะแนนออกมาที่จับต้องได้จริง (measured), ไม่ได้มาจากการใช้การลอยลมกล่าวอ้างคะแนนเอาตามมโนหรือสมมติฐานเดา (not assumed).
- [ ] ระยะช่องไฟความดีเลย์หน่วงความล่าช้าในผลรวมคะแนนรับรอบสิทธิคิวรีสำหรับตัวช่องทางการยิงของผลสำหรับในด่านรับรองผลตัวของไปป์ไลน์แบบ `/api/state` ต้องได้รับผลประเมินว่าค่าที่วัดดึงคะแนนเวลามานั้น มีพิกัดความต่างเวลาดึงรั้งมาอ้างโดยเทียบดึงจุดที่ผลเปรียบของส่วนกับคะแนนในกรอบฐานคุมตั้งรับเกณฑ์งบประมาณด่านอ้างเวลาที่ใช้คุมจำกัดอยู่ที่งบประมาณเพดานพิกัดขอบเขตเดิมคือ 300ms ที่เป็นฐานสเกลกำหนดเวลาตามด่านของพิกัดกรอบระเบียบค่ารับอ้างที่ใช้อยู่พิกัดเดียวกันเพื่ออ้างเป้ามาใช้พิกัดนี้ตลอดของมาตามที่มีใช้มาตลอดในกรอบระเบียบตัวโครงงานหลักๆของทั่วทั้งกรอบโครงนี้ด้วย.

**พิกัดเกณฑ์เป้าหมายการตอบรับสำหรับอ้างพิจารณาสำหรับแผนโครงการพัฒนาหน้า Task 4.4 (เรื่องระบบอ้างงานของจุดรวมงานประสมแบบจุดรวมมิติงานโครงด้านระบบอินทิเกรชันเป้าหมายเป้าของการขุดช่องงานที่เป็นช่องที่ระดมสิทธิเรื่องของการทำจุดขุดเจาะลงรายละเอียดของการดึงเพื่อขุดเจาะหน้าเพื่อลิงก์ไปยังแดชบอร์ดลึก):**

- [ ] ระบบกลไกรองรับสิทธิที่จะสามารถรับอ้างป้อนสั่งทำการคลิกเพื่อเปิดดึงข้ามด่านโยกส่งไปยังปุ่มจุดที่หน้าการพิกัดเปิด Snapshot เครื่องจักร จะต้องได้รับการทดสอบตรวจสอบสิทธิเป้าหมายถึงผลยืนยันแล้วด้วยการทดลองปฏิบัติจริงบนระบบช่องทางการทำงานของเซสชันระดับของในหน้าเปิดเบราว์เซอร์ที่เป็นในส่วนของการปฏิบัติแบบด้วยใช้คนหรือกระแสจากหน้าการใช้ตามจริง สำหรับเป้าสิทธิในการรองรับรับได้กับแบบคลุมรวบทดสอบรวดเครื่องจักรจริงแบบทุกจุดเป้าแบบสำหรับทั้งหมดเลยทั้งจำนวนที่ 10 เครื่องนี้เลย (ด่านพิกัดนี้นับเป็นอะไรที่มันบรรลุได้แล้วและก็ทำมาให้สำเร็จเพื่อเป็นโครงที่ได้จากที่นี้นะในแนวทางลักษณะที่เป็นสิทธิของการรับมาในโครงอ้างที่จะไม่ใช่ได้มาในวิธีของที่สิทธิแบบที่มีแบบเดียวกันที่เคยถูกปัดตกไม่อาจทำสิทธิที่ว่ามานี้แบบของในด่านหน้าแผงคานวาส Grafana Canvas รุ่นหน้าอดีตโน้นได้เลย — ให้ใช้หมุดติดธงพิกัดการแจ้งแบบเห็นโผล่หน้าให้เด่นชัดกันไปเลยว่า ถ้าระบบอ้างพิกัดที่พบมีว่ายังไร้ซึ่งแววของพิกัดที่จะมีการดึงด่านสำหรับที่จะใช้ในการอ้างที่ในตัวจากโครงเครื่องมือเครื่องเคียงช่วยเบราว์เซอร์สำหรับที่มีอ้างยังอ้างไม่ได้ที่จะไม่มีเตรียมไว้รับมือในจังหวะด่านช่วงพิกัดช่วงนี้แล้วละก็, ก็ให้ตัวพิกัดนั้นปรับย้อนกลับตกลงทำยอมฟอลแบ็กปรับลู่เพื่อตั้งเพื่อเปลี่ยนสับหน้าไปใช้เกณฑ์กติกาสำหรับการเป็นอ้างหน้าตามพิกัดสิทธิวิธีในการอ้างสิทธิรันสเกลทดสอบแค่ที่ในพิกัดโครงสร้างอย่างเดียวลอยๆแบบเดียวไป (structural-only verification) ดั่งเป๊ะแบบเดียวกับดั่งที่การที่ตัวรุ่น 2D twin นั้นมันก็เคยถูกใช้โหมดวิธีการแบบนี้).

**มิติระบบหน้าแผงรูปแบบของสิทธิแบบสำหรับระเบียบแนวทางของการย้ายแผนโอนระบบอ้างโอนกระบวนการรับถ่ายโอนระบบการประเมินย้ายปรับ (ลำดับก้าวตามหน้าในส่วนในพิกัดหน้าขั้นของที่มาตรงกันกับการเกิดจังหวะที่สั่งเพื่อโหมดรับหน้าหยุดรันเบรกหยุดของขั้นตอนที่ (STOP) → ด่านขั้นบันไดเข้าพิกัดของ "สเตปจังหวะหยุดเพื่อรอรันให้ดึงได้เค้าโครงระบบแบบรับผังแผงพิกัดสำหรับของโครงสร้างความจริงที่ของแท้จริง (waiting for real layout)" ในโฟลว์หน้าจอของผู้ใช้งาน):**

1. ภาระพิกัดระบบลำดับหน้างานตามส่วนโครงด่าน Tasks 4.1-4.4 ถูกโอนจัดรันแพ็กเกจส่งออกมาสู่ตัวงานด้วยหน้าสิทธิพิกัดเงื่อนไขการส่งด่านของค่า `device_3d_placement.is_simulated = TRUE` สำหรับด่านพิกัดค่าที่กะเกณฑ์รองรับใช้บังคับแถวการอ้างพิกัดรองรับข้อมูลด้วยกันทั้งหมดนั่นเลย, แบบตามกฎที่มีรับพิกัดความสามารถเพื่อรันอ้างระบบบนพื้นพิกัดแบบหน้ากริดรับอิงแบบตัวตามที่ระบบในหน้าของตามกฎหมายกำหนดแบบตัวที่วางกฎไว้ตาม (§4).
2. การปฏิบัติหน้าด่านหน้างานจะถูกปิดสับรันหยุดลงชั่วคราว. จะยังคงค้างหน้าโครงให้ปิดล็อครับจะยังไม่มีการพิกัดสั่งรันอนุมัติหน้าด่านลำดับการปฏิบัติพิกัดทำงานหน้าไหนๆของสิทธิรุ่นอิงแบบในฝั่งของระบบหน้า 3D ใดๆที่จะมีการโอนถ่ายส่งเพื่อสั่งผลักดันผลักส่งก้าวหน้าทำงานไปเรื่อยเปื่อยหรืองานอื่นจะขยับต่อเป็นอันขาด จนรอกว่าจะจนกว่าจะมาพบอ้างว่ามีจุดสำหรับสิทธิที่มาของต้นทางการดึงพิกัดรับตัวของแหล่งที่มาจากฝั่งหน้าการจัดวางโรงงานในฉบับที่เป็นของตัวผังของที่เป็นแหล่งมาจากสถานที่อันจัดวางที่ของเป็นเรื่องจริง (§17) มีการนำส่งมาจากจุดที่เป็นในรูปแบบที่จะถูกอนุมัติรับอ้างมาจัดหาเพื่อยื่นจ่ายให้ส่งมาให้อย่างตัวให้เห็นกันจริงๆได้ซะก่อน.
3. เมื่อเวลามาถึงและพบว่าจุดรอยค่ารับระบบการเชื่อมด้วยรอยอ้างของด่านความรับค่าตามระบบเพื่ออ้างตามในตัวโครงร่างพิกัดจุดเป็นความจริงส่งมาถึง: รันเดินหน้าแบบด้วยรันหน้าสายหน้าทางผ่านจุดทางสายกระบวนทัศน์สำหรับการสิทธิพิกัดด่านหน้าที่ของรับนำเข้าข้อมูลแบบฉบับตามในด่านรอยต่อระบบของพิกัดรับตามของ (§17), รันแบบการจัดตัวสั่งด้วยหน้าคำสั่งรูปแบบจุดระบบตามคำสั่งด่านพิกัดคิวรีอย่างจุดการเข้าสู่โหมด `UPDATE device_3d_placement SET is_simulated = FALSE, source = '<real source>'` ทำในแบบเจาะรันเฉพาะให้รายต่อของในโครงเฉพาะแต่ละของรายแถวแต่ละรายการไป. คะแนนเป็นหน้าอ้างด้วยศูนย์เป็นพิกัดการเป็นจุดแบบให้ความว่างหน้าเป็นศูนย์ความไม่มีสิทธิให้แก้ไขสำหรับที่ว่าการดึงหน้าด้วยความเกี่ยวพันถึงรอยร่องหน้าการคิวรีเปลี่ยนแปลงระบบอะไรกับจุดใดๆของการยุ่งย่ามกับการพิกัดคิวรีข้อมูลดึงหน้าของในพวกด่านรับของตัวข้อมูลอ้างระบบคิวรีตามในด่านการโทรมาตรใดๆในด่านของ (§5), จะอ้างคะแนนเป็นหน้าศูนย์หน้าความสำหรับจะเป็นเป้าบอกว่างที่เป็นค่าพิกัดไม่มีความเปลี่ยนแปลงในจุดระเบียบแบบในเรื่องพิกัดระเบียบระบบคิวรีต่อพวกของในหน้ากระดานด้านรอยในกระดานด้านฝั่งประมวลภาพบนหน้าสำหรับฝั่งโหมดมุมที่เรนเดอร์/และด่านอ้างฝั่งของความดึงที่เกี่ยวกับการดึงระบบเรื่องที่พิกัดโค้ดรับโหมดแบบการรองรับรูปแบบรับปฏิสัมพันธ์กับคนทำงานหรือผู้ใช้งานอินเตอร์แอคแบบไหนๆที่มันผ่านการถูกจัดทำประกอบดึงสร้างให้ขึ้นตัวก่อร่างแบบมีรูปแบบเอามาแล้วในช่วงพิกัดในจุดที่ระเบียบของหน้า 4.1-4.4 — ที่เป็นจุดชี้อ้างเพื่อการจะเปลี่ยนได้มันจะอ้างสิทธิสำหรับจะเปลี่ยนแบบให้เปลี่ยนผ่านสิทธิไปได้เปลี่ยนไปก็จะอ้างชี้จุดพิกัดเปลี่ยนให้เปลี่ยนเอาได้ก็แต่เพียงแค่ที่เป็นส่วนเนื้อหาในจุดที่จะมาเป็นแค่สำหรับเฉพาะที่แค่พิกัดของส่วนในเนื้อข้อมูลของตัวก้อนข้อมูลกันเองแต่เพียงอย่างเดียวนั้นแค่นั้น, แล้วแบนเนอร์แจ้งป้ายรับตัวแบบพิกัดของเรื่องของพวกระบบที่จะเป็นการทำป้ายพิกัดที่จะชี้ว่าคือของในโหมดพิกัดระดับป้ายบอกแบนเนอร์ที่เป็นป้ายปะหลอกในโหมดด่านการพิกัดอิงตัวโหมดภาพพิกัดฉากหน้าหลอกที่มีตัวระบุการอ้างฉากของการจำลองแบบตามในจุดระบุจากในด่านข้อรับเงื่อนไขพิกัดที่ (§19) ก็อันจะดึงสิทธิของการมีตัวมีตนเพื่อให้มันดึงสิทธิในการเป็นพิกัดที่ต้องอันตรธานลบสิทธิการหายโชว์มันให้ต้องพิกัดจางลบหายสาบสูญไปได้แบบสิทธิของความแบบไปตลอดกาลได้ทันทีเมื่อมันดันเช็คตรวจสอบจุดระเบียบแล้วมันเจอว่ามันสิทธิของคิวรีทุกส่วนใดของเป้าที่แถวข้อมูลที่ตรวจสอบใดๆในจุดตัวที่สามารถเรียกแสดงให้มองเห็นในหน้าทัศนียภาพเห็นได้ทุกอย่างแล้วของจุดข้อมูลทุกอันนั้นมันล้วนจะพิกัดมันเป็นข้อมูลสิทธิที่เป็นระดับรันค่าแบบคือสิทธิของการอิงพิกัดว่าเป็นแบบความจริง (real) จนครบเรียบร้อยได้ทั้งหมดแล้วทุกอันทุกแถวข้อมูล.

## ยกเว้นออกนอกกรอบโครงร่างจากความสนใจพิกัดสิทธิขอบเขตของการออกแบบระบบฉบับระเบียบออกแบบด่านฉบับการพิกัดนี้อย่างชัดเจนไปเลย

- ระบบด่านอ้างของการจะมีการจัดขั้นตอนที่จะนำเอามารันทำไปพิกัดนำปฏิบัติไปอ้างมาประยุกต์ทำลงหน้าโครงงานอ้างการใช้ระบบใดๆ — ด้วยสิ่งนี้นับว่าเป็นเพียงพิกัดเป้าแบบของความเรื่องที่จะทำรับแบบหน้าที่แค่โครงในเรื่องจะออกแบบเพียงเพื่อการจัดร่างเอกสารเพื่อรับอิงใช้พิกัดระดับมาเพื่อมาเป็นงานในเรื่องเอกสารว่าด้วยเรื่องโครงเพื่อเอาไว้ในการออกแบบเพื่อออกแบบเพียงอย่างเดียว, โดยที่มีสาเหตุอิงมาจากพิกัดความสิทธิอันได้รับคำดึงจากที่มีส่วนในการให้หน้าของหน้าเป้าอิงจากผลตัวพิกัดความที่เป็นในส่วนความดึงพิกัดที่อ้างรับจุดในการต้องการรับตรงจุดของเจตนาที่มีสิทธิชี้เพื่อรับการของตัวแบบของความแบบต้องการอ้างมาจากคำสั่งพิกัดที่มาจากตรงคำสั่งข้อที่มีการขอจากด้านหน้าของผู้มีส่วนของผู้ใช้เอาไว้ให้ในระดับเฉพาะเจาะจงมาตามนั้นแล้วด้วย.
- ระบบจุดดึงพิกัดอิงการโชว์ดึงจุดสิทธิบอกลากพิกัดจุดสิทธิลากโยงแสดงการเชื่อมจุดรอยต่อที่แสดงข้ามจุดเป็นความสัมพันระหว่างจุดอ้างบอกเรื่องสายรอยต่อระหว่างพิกัดบอกเพื่อการแสดงสายเชื่อมของในระบบหน้าของเครื่องจักร-ที่จะแสดงไปหา-เครื่องจักรในหน้าของการเรียงตามกระบวนการ (§10) — ไร้ซึ่งพิกัดอิงที่จะเป็นความมีข้อมูลอยู่ตามความหมายระดับว่าความเป็นแบบที่มีอยู่ข้อมูลที่มีแบบความจริง.
- การดึงพิกัดดึงหน้าของการโชว์อ้างสิทธิเพื่อรับสิทธิการดึงแบบที่เป็นพิกัดพยานของการที่หาด้วยระบบสิทธิที่พิกัดทำงานรันระดับคิวรีโชว์ระบุสิทธิที่อ้างพิกัดระบบอ้างระบบโชว์อัตโนมัติ/สิทธิพิกัดการหาเพื่อด้วยตนเองการประมวลหน้าสิทธิการเสาะพบระบบที่จะคิวรีเรื่องของค้นหาและชี้ระบุเปิดเผยสถานที่ชี้ตำแหน่งด้วยพิกัดพึ่งพาตนเองเอง (§17) — ยังไร้ซึ่งหน้าตาของด่านโครงหน้าข่ายของพื้นระบบพิกัดระบบข่ายส่วนพื้นฐานอิงความเป็นจริงที่จะเอื้อความเพื่อช่วยให้รับกับระบบนี้ได้เลย.
- การดึงเพื่อแบบของแอปรุ่นรุ่นที่มีสายมาจากในสเกลโหมดเครื่องแบบประมวลการสร้างเพื่อรันโหมดโครงในประมวลจุดของโหมดแอปสำหรับแอปในแอปพลิเคชันสำหรับรูปแบบความแบบดั้งเดิมของ Windows แอปหน้าฝั่งเนทีฟ (Native Windows app) (§15) — เพราะว่ามันยังอ้างพิกัดดึงความที่พิกัดว่าไร้ซึ่งตัวโครงอ้างเรื่องระบุหน้าอ้างที่มีถึงเรื่องว่าพบจะความระบุความหน้าสำหรับอิงเหตุผลจากตัวระบุเรื่องความเป็นหน้าที่มีเงื่อนไขจากความเรื่องข้อต้องการในความแบบที่มีตัวประจักษ์ใดที่เป็นระดับที่มีเพื่ออ้างรับความรับตัวสเกลการอ้างของจริงมารองรับแบบให้พบได้ดึงขึ้นได้ในตอนนี้เลย.
- ด่านระบบที่มีโหมดที่ความสิทธิด้านที่ความสามารถการมีพิกัดคุณสมบัติเรื่องความครบความเรื่องของคุณภาพสิทธิพิกัดระดับโครงความเรื่องรองรับด่านความแบบเพื่อที่จะรับความให้โอกาสสิทธิในโครงหน้าเรื่องสำหรับการเพื่อให้สามารถพร้อมระบบเพื่อให้สิทธิ์พิกัดความหน้าให้ได้กับโหมดเรื่องผู้พิการเข้าถึงใช้งานระบบด่านในด่านพิกัดที่เอาเพื่อดึงระดับในพิกัดจุดของการไปทาบเพื่อให้ออกมาจนเต็มเปี่ยมดึงสมบูรณ์จนเป็นในสิทธิพิกัดว่าเพื่อความระดับความทาบให้เทียบสเกลทัดเทียมในแบบของแฝดพี่อย่างด่านตัวโครง 2D twin (§16) — เนื่องจากระบบความแบบรับการมุมจำลองของที่ระบบรันโหมดสเกลในพิกัดรูปแบบของในตัวสามมิติ (3D scenes) ล้วนมีข้อจำกัดจุดที่จุดบกพร่องข้อในจุดบกพร่องรันด่านอิงพิกัดข้อความอ่อนด้อยจุดข้อความอิงในตัวมันเองที่มีความติดรันตัวติดขัดแฝงสิทธิติดอิงฝังรากในจุดข้อพิกัดจำกัดจุดข้อที่มันเป็นด่านอิงจุดหน้าในสิทธิความเป็นเนื้อแบบกำเนิดในตัวโดยธรรมชาติของมันอยู่แล้ว, แค่อิงเพื่อสามารถแค่ที่จะดึงระบบสิทธิดึงรันระบบแบบเพื่อแบบคอยเพื่อบรรเทาอ้างพิกัดรับชดเชยผ่อนผันด่านจุดรันความปัญหาที่ความให้ลดเรื่องแบบทอนผ่อนด่านพิกัดปัญหามันผ่อนคลายลงเฉยๆแต่ก็ไม่ได้จะพิกัดสิทธิถึงว่าระดับดึงคิวรีจะหาอ้างลบด่านข้อจำกัดลบมันทิ้งโละขจัดจุดบกพร่องพิกัดทิ้งหายไปได้หมดหรอกนะ.
- พิกัดที่จะหาดึงสิทธิเพื่ออ้างรับความมีการเข้าหาโหมดไปแก้ไขหน้าพิกัดเรื่องโครงรับสิทธิอ้างเรื่องเปลี่ยนแปลงข้อมูลโครงงานรับโครงด่านของไฟล์หน้า `ims-ldi-manufacturing.json`, หรือแบบตัวของไฟล์อย่าง `ims-ldi-operator-andon.json`, หรือแบบหน้าของระบบแบบด่านโครงรันของที่ไฟล์พิกัดของที่ตัวไฟล์อย่างตัว `ims-ldi-factory-digital-twin.json`.
